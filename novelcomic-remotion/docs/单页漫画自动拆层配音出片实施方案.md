## 1. 目标

把当前“调用方提供 HTTPS 图片和图层包，编辑器负责组装与渲染”的能力，补成以下无人值守闭环：

```text
用户上传一页漫画
→ 自动分格并确定阅读顺序
→ OCR、对白归属和角色识别
→ 按镜头选择 L0/L1/L2/L3 动画等级
→ 生成整图、透明图层、补图和眼嘴状态图
→ TTS 配音并确定对白时间
→ 通过 Compose API 构建可继续编辑的 v2 工程
→ 生成眨眼、口型、镜头及图层运动
→ 联系表和低清视频自动审片
→ 修正或降级
→ 按 5～18 秒批次渲染 H.264
→ 生成可下载材料包
```

总愿景不是“模型能返回几张图片”，而是：

1. 用户只提供一页普通漫画和少量生产参数。
2. 系统最终返回有序 MP4 列表、可恢复工程和生产材料包。
3. 任一镜头的拆层、补图或状态图失败时仍能降级成整图镜头并出片。
4. 重试不会重复建轨、覆盖新草稿或重复扣费。
5. 阶段 E 完成后提供可校验 checksum 的 ZIP 材料包。

分阶段完成定义不能混用：

- 阶段 A：只封口编辑器。通过施工单第 10 节中除“上游草稿服务 CAS”外的 10 项；CAS 在阶段 B 验证。
- 阶段 B：L0 无人值守闭环，返回有序 MP4、可重新打开的工程和交付 manifest；ZIP、自动审片和 L1/L2 不作为门禁。
- 阶段 C/D：分别增加 L1、L2，失败仍回到阶段 B 的 L0 可交付结果。
- 阶段 E：加入自动审片、完整成本与取消、多租户和 ZIP，达到上述总愿景。

## 2. 当前基线和真实缺口

### 2.1 已具备

`novelcomic-remotion` 已具备：

- v2 工程、Shot、LayerPackage、ImageMotion 和 OutputBatch 类型。
- `evaluateImagePose` 统一运动求值。
- 整图序列、图层导入、对白、运动、批次规划和分批渲染 API。
- Player、选框和 Remotion 使用同一套图片姿态求值。
- 联系表帧位规划和交付 manifest。
- 阶段 0～5 的单元测试基线。

### 2.2 先修复，不能带入自动生产

1. `buildBlinkSpriteStates` 和 `buildMouthFlapSpriteStates` 没有接入 Compose 命令。
2. `import-layers.ts` 把备用状态放在 Shot 结束帧之后，实际播放不会切换。
3. 现有 `/api/compose/audio/add` 使用随机 asset/item/track ID，不支持稳定 upsert、`clientRequestId`、revision 边界和统一错误协议，不能直接作为自动配音入口。
4. 联系表异步模式只回显 taskId，没有真正创建任务和图片。
5. `export-package` 只生成 manifest，不打包 ZIP。
6. `docs/COMPOSITION.md`、`docs/api_docs.md`、Lambda site 和真实 H.264 端到端尚未封口。
7. `image/sequence` 当前是居中 `contain`，没有阶段 B 要求的 `blurred-background-contain`。
8. `padProjectToMinimumDuration` 已有领域函数，但没有 Compose HTTP 命令。

### 2.3 上游能力为空

当前工作区中没有可定位的 `novelcomic-agent` 目录。以下方案把它视为需要新增或从其他仓库接入的上游生产服务；如果该服务实际位于独立仓库，目录名可以调整，但职责边界不变。

缺少的上游能力包括：

- 分格和阅读顺序。
- OCR、气泡检测、对白归属和说话人识别。
- L0/L1/L2/L3 分层策略。
- 人景分割、遮挡补图、眼睛和嘴巴状态图。
- TTS、音频时长和可选音素/viseme。
- 草稿 revision、产品请求/Compose 命令分层幂等和 compare-and-set。
- 长任务队列、成本账本、自动审片、重试和降级。
- `comic_*` Agent 工具。

## 3. 架构

本节规定组件、真相来源、唯一写路径和任务寿命。后文的数据契约、执行顺序、工具和文件落点都从这里推导。实施时不能另开一条写工程、扣费或出片的路径。

不要把模型调用、任务队列或草稿数据库塞进 `novelcomic-remotion`。建议拆成四层：

```text
┌─────────────────────────────────────────────┐
│ Product API / Agent Skill                   │
│ 接收用户任务、返回进度和交付结果              │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│ novelcomic-agent                            │
│ 状态机、队列、Draft CAS、幂等、成本、降级     │
└──────────────┬─────────────────┬────────────┘
               │                 │
┌──────────────▼────────────┐ ┌──▼──────────────────────┐
│ Comic Vision / Audio      │ │ novelcomic-remotion     │
│ 分格、OCR、分层、补图、TTS │ │ 确定性工程变换和渲染      │
└──────────────┬────────────┘ └──┬──────────────────────┘
               │                 │
               └────────┬────────┘
                        ▼
              对象存储、PostgreSQL、Redis
```

职责约束：

- `novelcomic-remotion`：完整工程进、完整新工程出；不保存 revision，不执行概率模型。
- `novelcomic-agent`：只通过 Compose API 修改工程，不让大模型直接编写 `UndoableState`。
- Vision/Audio worker：只生产带稳定 ID、远程 URL 和诊断信息的中间产物。
- 对象存储：保存原图、分格、图层、状态图、音频、预览、视频和 ZIP；工程 JSON 不存图片二进制。
- PostgreSQL：保存生产任务、草稿 revision、幂等记录、阶段产物和成本。
- Redis/队列：只负责调度、锁和短期进度，不作为工程最终真相来源。

### 3.1 一条生产任务的寿命

一次生产的主键是幂等事务中生成的 `productionId`，并规定 `projectId = productionId`。全文不再创建第二个工程身份。Agent 工具若因兼容需要接收 `draftId`，其值必须等于 `projectId`，新接口统一只暴露 `projectId`。

Remotion 的 `UndoableState` 没有自身 ID；`LayerPackage.projectId`、对象存储前缀、草稿、产物和批次都引用上述 `projectId`。受理事务先调用 `project/create` 得到空 v2 工程，再将它保存为 revision=0；后续禁止再次调用 `project/create` 覆盖该草稿。

任务寿命从源文件进入自有对象存储、并且作用域内的 `tenantId + prodClientRequestId + payloadHash` 幂等记录提交成功开始，到 `DELIVERED`、`PERMANENT_FAILED` 或 `CANCELLED` 结束。

重试、降级、更换 worker、重放 Compose 都发生在同一次寿命里。同一次产品意图的重试继续使用原来的 `prodClientRequestId`；每条 Compose 命令使用自己的 `commandId`。

```text
受理并固化输入
→ 分析（分格 / OCR / PanelSpec）
→ 语音（TTS / 时长 / 帧时间线）
→ 素材（每个 Shot 先有 L0；L1/L2 可降级）
→ 逐条 Compose，再 CAS 提交草稿
→ 校验
→ 预览与审片
→ 批次规划
→ 分批渲染
→ 打包
→ DELIVERED
```

阶段名以第 8 节状态机为准。这里规定每一跳由谁提交事实。单个 Shot 降级或预算停止增强后，任务继续走向 `DELIVERED`。只有无法产出任何可播放结果时进入 `PERMANENT_FAILED`；只有用户或管理员取消时进入 `CANCELLED`。

### 3.2 八把键各管一件事

| 键 | 管什么 | 相同意味着 |
| --- | --- | --- |
| `tenantId + prodClientRequestId + payloadHash` | 一次用户意图 | 回放同一个生产任务 |
| `pageId = sha256(源字节)` | 一页原稿 | 同一张图 |
| `shotId` / `lineId` / `layerId` | 定稿镜头、原始对白、图层 | 同一逻辑对象的 upsert |
| `projectId + shotId + stage + inputHash` | 一个付费或耗时阶段 | 复用已成功的 `AssetArtifact` |
| `providerRequestId` | 一次已发出的供应商调用 | 超时后先对账，再决定是否重打 |
| `expectedRevision` | 草稿的一代 | CAS 成功后这一代才可读 |
| `projectContentHash + frameRange + renderConfig` | 一批成片 | 复用该批 MP4 |
| manifest 内容 hash | 一份交付包 | 复用该 ZIP |

产品请求 ID 与命令 ID 使用不同字段和命名空间：

```text
prodClientRequestId = prod:{caller-supplied-id}
commandId           = compose:{projectId}:{ordinal}:{commandName}:{inputHash}
toolRequestId       = tool:{toolName}:{caller-supplied-id}
```

`payloadHash` 在源文件固化后计算，只包含契约版本、`pageId[]`、页序、阅读方向、output、style、budget、voices 和 defaultVoiceId 的 canonical JSON；不含临时 URL、签名参数、创建时间或数据库 ID。相同租户和请求 ID、不同 hash 返回 409；同 ID、同 hash 返回原任务。

这些键彼此独立：意图键负责回放任务，命令键负责恢复 Compose 游标，产物键负责省下供应商调用，revision 负责保护新草稿，渲染键负责复用视频。

### 3.3 谁持有哪一份真相

| 事实 | 持有者 | 丢失后的恢复 |
| --- | --- | --- |
| 任务阶段、预算、降级记录、成本 | PostgreSQL | 从已提交阶段继续 |
| 草稿 `project JSON` 和 `revision` | PostgreSQL，仅 CAS 成功后 | 读最后一次成功的 revision |
| 幂等回执 | PostgreSQL | 同一意图返回原任务 |
| 原图、分格、图层、音频、预览、MP4、ZIP | 对象存储 | 按 `AssetArtifact.url` 或批次 URL 取回 |
| 阶段产物、`inputHash`、供应商请求号 | PostgreSQL 的 `AssetArtifact` | 命中则直接复用 |
| 队列、锁、短期进度 | Redis | 可丢；进度改读 PostgreSQL 的阶段 |
| 工程变换结果 | `novelcomic-remotion` 的当次响应 | 响应未 CAS 前不算草稿，按同一命令重放 |

进度接口以 PostgreSQL 的阶段和产物状态为准。Redis 里的百分比只作为在跑提示。编辑器打开的是最近一次 CAS 成功的工程。

### 3.4 控制面和数据面

状态机是唯一驱动。它推进阶段、检查预算、记录降级，并调用草稿适配器。

数据面只生产字节和诊断：分析得到 `PanelSpec`，语音得到 `LineAudio`，定时编排得到 `TimedShotSpec`，图层得到 `LayerPackage`。这些产物先落对象存储和 `AssetArtifact`，再由状态机引用它们去调 Compose。

大模型处在控制面的决策点上，不在数据面上：

- 动画等级、审片修正只返回第 5、9 节已经枚举的动作。
- 决定写入任务记录后，仍由状态机执行。
- 写工程的 `comic_*` 工具是同一组命令的另一种调用方，与状态机一起进入第 6.1 节的草稿适配器；只生产 Artifact 的工具不经过草稿适配器。

阶段 B 由状态机驱动，等级固定 L0。不规则分格和说话人识别可以调用视觉模型；失败时分别落到整页 L0 和 `speaker:unknown`。这一阶段不依赖大模型写工程。

预算闸门在状态机发出付费调用之前。项目预算到达第 5.5 节的阈值后，不再发起 L2/L3。任务进入 `CANCELLED` 之后，worker 在下一次付费调用和 CAS 之前重新读取任务状态。已经返回的供应商结果可以补记 `AssetArtifact`，随后不再写入草稿。

### 3.5 写草稿的唯一路径

Worker 不持有工程，Compose 进程不保存 revision。

```text
读 PostgreSQL：draft(projectId) → project + revision
→ 带 expectedRevision 调用一次 Compose
→ Remotion 校验并返回完整新工程（不落库）
→ UPDATE … WHERE revision = expectedRevision
→ 成功：保存 newProject，revision + 1，这一代成为唯一可读草稿
→ 冲突：重读；付费产物按 inputHash 复用，不重新打供应商
```

`novelcomic-remotion` 内部保持「完整工程进、完整新工程出」：

```text
route → Zod → normalize → 领域命令 → reorder → validate → 响应
```

运动求值、Shot 和批次的细节以 [动态漫画编辑器架构设计.md](./动态漫画编辑器架构设计.md) 为准。自动生产额外遵守两条：写入命令使用稳定业务 ID upsert；`spriteStates` 只有 `applySpriteMotion` 一个写入者。

### 3.5.1 Compose 命令账本

`COMPOSING` 不是不可分割的大步骤。上游为每个 Compose 命令保存：

```ts
type ComposeCommandRecord = {
  commandId: string;
  projectId: string;
  ordinal: number;
  name: string;
  inputHash: string;
  expectedRevision: number;
  resultingRevision?: number;
  status: 'pending' | 'running' | 'committed' | 'failed';
  attempt: number;
  lastErrorCode?: string;
};
```

`UNIQUE(projectId, ordinal)` 和 `UNIQUE(commandId)` 防止同一游标生成两条命令。只有 CAS 成功后才把命令标为 `committed` 并记录 `resultingRevision`，两者在同一 PostgreSQL 事务中完成。进程恢复时只执行最小 ordinal 的未提交命令；Compose 已返回但 CAS 未提交时，用同一 `commandId` 重放确定性命令，不重新调用供应商。

### 3.6 同步口和异步口

| 口 | 方式 | 成功时已经成立的事实 |
| --- | --- | --- |
| 创建生产任务 | 同步受理 | 幂等记录、空草稿 revision=0、任务行已提交 |
| 单次 Compose | 同步 | 输入工程已变换为响应中的新工程 |
| 草稿 CAS | 同步 | 该 revision 已成为唯一可读草稿 |
| 分格、OCR、TTS、分割、补图 | 异步 worker | 受理只表示已入队；完成看 `AssetArtifact.status` 和 URL |
| 联系表、低清视频、H.264、ZIP | 异步 worker | 受理只表示任务已登记；完成看产物 URL 和 checksum |

联系表和 ZIP 的排队不放进 Next route 进程。route 只返回帧计划，或向上游提交任务。

第 11.2 节的 worker 文件是进程打包方式。阶段边界以状态机为准：语音阶段即使和素材 worker 放在同一进程，图层失败也不重跑 TTS；分析 worker 不写 `LayerPackage`；渲染 worker 不调用分割和 TTS；打包 worker 不重新分格、不重新渲染。

默认实施时单独提供 `voice-worker`。如果部署上与 `asset-worker` 合并，队列名、job type、产物键和重试计数仍必须独立，禁止因图层任务重试而重跑 TTS。确定性 OpenCV 分格首版只在 Agent 的 Python analyzer 中实现；只有确定性质量门禁失败时才调用独立视觉服务，不能在主服务和独立视觉服务各维护一套常规分格算法。

### 3.7 降级沿同一条写路径返回

```text
image/sequence 先为每个 Shot 写下 L0 整图轨
→ L1/L2 门禁通过后，才用图层轨盖住原人物
→ 任一增强失败：保留 L0，在 Shot 诊断中记录降级
→ 任务继续校验、规划和渲染
```

分格最终失败时，整页就是这一个 L0 Shot。增强失败的镜头仍然带着对白、配音和基础镜头运动进入成片。

### 3.8 进程和恢复窗口

```text
novelcomic-agent
├── Product API          受理、查询、取消
├── 状态机               阶段、预算、降级
├── Draft repository     CAS
└── workers              分析 / 素材 / 渲染 / 打包
        │
        ├── comic-vision-worker     可选；只收发版本化 JSON
        └── novelcomic-remotion     无状态 Compose
                └── Lambda          静帧与 H.264

PostgreSQL      任务、revision、幂等、产物、成本
Redis           队列、锁、短期进度
对象存储        全部字节
```

`comic-vision-worker` 不持有草稿库写入凭证，也不直接写 Remotion 工程。

进程可以在两份已提交事实之间死掉。恢复时只补当前窗口，不从头再买一遍：

| 已提交 | 尚未提交 | 恢复 |
| --- | --- | --- |
| 幂等记录和 revision=0 | 分析入队 | 把仍处于 `CREATED` 的任务重新入队 |
| 供应商已受理 | `AssetArtifact` 完成行 | 用 `providerRequestId` 对账后补写；对不上才按第 8.3 节重试 |
| `AssetArtifact` 已完成 | 对应 Compose | 从该阶段继续，复用 URL |
| Compose 已返回新工程 | CAS | 用同一 `commandId` 作为 Compose envelope 的 `clientRequestId` 重放该命令 |
| CAS 已成功 | 下一条命令或渲染 | 从新 revision 继续，已成功命令不重放 |
| 某批渲染已受理 | 该批视频 URL | 只查询或重试该批 |
| 各批视频已在对象存储 | ZIP | 只重跑打包 |

所有长任务都使用数据库租约字段 `leaseOwner/leaseExpiresAt/heartbeatAt`。worker 领取任务时原子更新租约，运行中续租；租约过期后其他 worker 可以接管。同一 job 的业务唯一键不变，因此接管只会对账或复用产物，不会再次付费。Redis 锁只能减少并发，不能替代数据库唯一约束和租约。

### 3.9 实施阶段只决定谁上场

阶段定义仍以第 12 节为准。上场顺序不改变本节的边界：

| 阶段 | 上场 | 此时仍不建设 |
| --- | --- | --- |
| A | Remotion 的 sprite、稳定 voice、真实 H.264 | 状态机、视觉模型、草稿库 |
| B | 鉴权受理、CAS、分析、TTS、基本成本/取消、L0 Compose、批次和成片 | 人景分割、审片模型、ZIP |
| C | L1 素材 worker 和质量门禁 | 眼嘴状态图 |
| D | L2 状态图，并由 `applySpriteMotion` 写入 | L3 |
| E | 审片、有限修正、成本对账与告警、多租户管理、ZIP、完整 `comic_*` | L3 仍单独立项 |

阶段 A 可以没有上游。从阶段 B 起，草稿 CAS 和 `inputHash` 复用必须已经在场，否则后面的重试无法保住「不覆盖新草稿、不重复扣费」。

### 3.10 这些回执都还在寿命中间

| 看到的事实 | 已经成立的事 |
| --- | --- |
| 用户上传 URL 仍可访问 | 文件还在调用方；任务尚未出生 |
| 幂等记录提交成功 | 任务已出生，同一意图可以回放 |
| 分格完成 | 已有 `PanelSpec`，还没有定稿 Shot |
| TTS 完成 | 已有按 `stableLineKey` 保存的 `LineAudio`，尚未入轨 |
| `AssetArtifact` 为 completed | 该阶段的供应商调用可以复用 |
| Compose HTTP 200 | 响应里有一份新工程；草稿 revision 未变 |
| CAS 成功 | 这一代草稿成为唯一可读工程 |
| contact-sheet 返回 taskId | 帧计划或任务已登记；联系表图片未必存在 |
| 低清预览 URL | 审片输入已就绪 |
| Lambda `renderId` | 该批已提交；MP4 未必可下载 |
| `export-package` 的 manifest | 清单可以生成；ZIP 由打包 worker 另交 |
| `DELIVERED` | 这次生产结束；阶段 B 要求 MP4/工程/manifest，阶段 E 还要求 ZIP checksum 通过 |

终态提交之前，材料包引用的源文件和中间材料都保留在对象存储。

## 4. 核心数据契约

### 4.1 ProductionRequest

```ts
type ProductionRequest = {
  prodClientRequestId: string;
  contractVersion: 1;
  sourcePages: Array<{
    clientSourceId?: string;
    imageUrl: string;
    pageNumber: number;
  }>;
  readingDirection: 'rtl' | 'ltr';
  output: {
    width: 1080;
    height: 1920;
    fps: 30;
    language: string;
    panelFitPolicy: 'blurred-background-contain';
  };
  style: {
    motionStrength: 'subtle' | 'normal';
    subtitleMode: 'clean-bubble-and-caption' | 'preserve-bubble';
  };
  budget: {
    projectLimitRmb: number;
    shotLimitRmb: number;
    maxPaidCallsPerShot: number;
  };
  voices?: Record<string, string>;
  defaultVoiceId: string;
};
```

首版固定竖屏 1080×1920、30fps。不要在第一版同时支持任意画幅和帧率。

`tenantId`、调用者身份和权限从鉴权上下文取得，禁止相信请求体自报。服务内部的幂等唯一键为 `(tenantId, prodClientRequestId)`。

首版固定使用 `blurred-background-contain` 落幅：原 panel 等比完整显示，空白区域使用同一 panel 放大、模糊并压暗后填充。禁止仅用黑边 `contain`，也禁止无安全区分析的居中 `cover`，否则横构图 panel 在竖屏中会出现大块黑边或被裁掉对白和人物。后续如增加其他落幅策略，必须进入请求契约和 `inputHash`。

### 4.2 分阶段分析、语音和定稿契约

```ts
type RawLine = {
  stableLineKey: string;
  bubbleReadingOrder: number;
  text: string;
  speakerId?: string;
  bubblePolygon?: Array<{x: number; y: number}>;

};

type PanelSpec = {
  pageId: string;
  panelIndex: number;

  panelUrl: string;

  readingOrder: number;

  diagnostics: {
    panelConfidence: number;

    warnings: string[];
  };
};

type LineAudio = {
  stableLineKey: string;
  audioUrl?: string;
  durationMs?: number;
  providerRequestId?: string;
  visemes?: Array<{timeMs: number; value: 'closed' | 'half' | 'open'}>;
  missingReason?: string;
};

type TimedDialogueSpec = {
  lineId: string;
  stableLineKey: string;
  text: string;
  speakerId?: string;
  bubblePolygon?: Array<{x: number; y: number}>;
  fromFrame: number;
  durationInFrames: number;
  voiceUrl?: string;
  visemes?: Array<{frame: number; value: 'closed' | 'half' | 'open'}>;
};

type TimedShotSpec = {
  shotId: string;
  pageId: string;
  panelIndex: number;
  panelPartIndex: number;
  panelUrl: string;
  animationLevel: 'L0' | 'L1' | 'L2' | 'L3';

  seed: number;
  dialogues: TimedDialogueSpec[];

```

稳定 ID 规则：

```text
pageId  = sha256(source bytes)
stableLineKey = line:{pageId}:{panelReadingOrder}:{bubbleReadingOrder}:{clauseIndex}
shotId  = shot:{pageId}:{readingOrder}:part:{panelPartIndex}
lineId  = stableLineKey
layerId = 语义名；同语义多实例时追加稳定序号
speakerId = speaker:{pageId}:{canonicalCharacterIndex}
```

不要使用模型随机返回的名称或数据库自增 ID 作为业务幂等键。

分析阶段只生成 `PanelSpec`；TTS 以不含可变 `shotId` 的 `stableLineKey` 生成 `LineAudio`；根据真实音频时长拆句、拆 Shot 后，才冻结 `TimedShotSpec`、`shotId` 和帧时间线。这样拆镜不会使已完成的 TTS 产物失去复用键。

`panelPartIndex` 从 0 开始。普通 panel 只有 `part:0`；同一 panel 因对白过长拆成多个 Shot 时递增，后续 part 复用同一 `panelUrl` 和 `LineAudio`，不重新分格或重复调用付费模型。旁白可以没有 `bubblePolygon`。无法稳定识别角色时使用 `speaker:unknown`，TTS 使用 `defaultVoiceId`。

### 4.3 AssetArtifact

每个付费或耗时步骤都保存独立产物记录：

```ts
type AssetArtifact = {
  artifactId: string;
  projectId: string;
  shotId?: string;
  stage:
    | 'ingest'
    | 'analyze'
    | 'tts'
    | 'clean-panel'
    | 'layer-l1'
    | 'layer-l2'
    | 'inpaint'
    | 'preview'
    | 'render-batch'
    | 'package';
  inputHash: string;
  provider: string;
  providerRequestId?: string;
  status: 'pending' | 'running' | 'completed' | 'failed' | 'cancelled';
  urls: string[];
  checksums: string[];
  diagnostics: Record<string, unknown>;
  costRmb: number;
  createdAt: string;
};
```

`inputHash` 至少包含源素材 hash、阶段版本、模型版本和参数。相同 hash 已成功时直接复用，避免 Agent 重试导致再次调用付费供应商。

页级产物的 `shotId` 为空。数据库使用表达式唯一索引：

```sql
UNIQUE (project_id, stage, input_hash, COALESCE(shot_id, ''))
```

URL 是可刷新定位信息，不是内容身份；对象 key、checksum 和 size 才用于交付校验。

### 4.4 Product API

首版 Product API 固定为：

```text
POST   /v1/comic-productions
GET    /v1/comic-productions/{productionId}
POST   /v1/comic-productions/{productionId}/cancel
GET    /v1/comic-productions/{productionId}/deliveries
```

`POST` 接收 `ProductionRequest`。推荐先通过受控上传接口取得自有对象存储 key；若允许传入 `imageUrl`，服务端必须下载并固化后才能创建生产任务。成功新建返回 202，同幂等键回放返回原 production 和当前状态，同键不同 `payloadHash` 返回 409。

状态响应至少包含 `productionId/projectId`、当前阶段、已完成阶段、Shot 降级摘要、预算使用、可重试错误和交付摘要，不返回整份工程 JSON或签名 URL 日志。取消接口是幂等操作：已终态时返回当前终态；运行中写入 `cancelRequestedAt`，worker 在下一次付费调用、Compose CAS 和渲染提交前检查。

鉴权上下文决定 `tenantId` 和 caller。查询、取消、草稿及对象 URL 都必须校验租户归属。对象 key 使用：

```text
{tenantId}/{productionId}/source/{pageId}
{tenantId}/{productionId}/artifacts/{stage}/{artifactId}
{tenantId}/{productionId}/renders/{batchId}/{contentHash}.mp4
{tenantId}/{productionId}/delivery/{manifestHash}.zip
```

下载 URL 使用短期签名且可刷新；日志、错误和模型提示不得记录签名查询参数、原始鉴权头或完整工程。源文件和中间产物的保留期由租户策略决定，删除任务必须先撤销交付 URL，再异步删除对象和数据库中的敏感内容。

## 5. 从一页漫画到工程的执行顺序

### 5.1 接收和固化输入

1. 校验鉴权、租户配额、声明 MIME、嗅探 MIME、尺寸、文件大小和内容安全。
2. 把用户文件复制到自有对象存储，不能长期依赖临时上传 URL。服务端拉取 URL 时禁止私网、环回、链路本地地址，限制重定向、响应大小和下载时长，并对最终域名执行 allowlist。
3. 计算 SHA-256，创建 `pageId`。
4. 用固化后的 `pageId[]` 和 canonical 请求字段计算 `payloadHash`。
5. 以 `tenantId + prodClientRequestId` 建立幂等记录：
   - 同 ID、同 hash：返回原任务。
   - 同 ID、不同 hash：返回 409。
6. 在同一事务中创建生产任务、保存 `project/create` 返回的 revision=0 草稿、写入第一条 outbox 事件。
7. 事务提交后由 outbox dispatcher 投递分析任务；不得在数据库提交前直接向 Redis 发 job。

### 5.2 自动分格

标准漫画先走确定性算法：

1. 灰度化和自适应阈值。
2. 检测长直线、留白沟槽和封闭轮廓。
3. 过滤过小框，合并被文字气泡切碎的相邻区域。
4. 根据 `rtl/ltr` 和纵向位置构建阅读顺序。
5. 输出 panel crop、bounds、置信度和诊断图。

以下情况才调用视觉模型兜底：

- 无边框或跨格。
- 轮廓重叠。
- 标准算法存在明显阅读顺序歧义。
- 面板覆盖率、重叠率或数量门禁不通过。

分格质量门禁：

```text
0 < panel 数 <= 30
所有 panel 位于页面内
常规网格的非设计性重叠率 <= 8%
常规网格的有效 panel 覆盖率 >= 55%
阅读顺序唯一
```

以上是首版初始阈值，只用于决定“确定性结果是否可直接采用”，不是通用漫画质量标准。阈值、算法版本和阅读方向必须进入分析阶段 `inputHash`；修改阈值后不能复用旧分析产物。跨格、无边框或设计性重叠直接进入视觉模型兜底，不用常规网格阈值强行裁切。

兜底仍失败时，把整页作为一个 L0 Shot，保证任务可以继续。

### 5.3 OCR 和对白归属

1. 检测文字行和气泡 polygon。
2. OCR 返回文本、方向、语言和置信度。
3. 用气泡中心点或最大相交面积归属 panel。
4. panel 内按阅读方向排序生成稳定 `lineId`。
5. 视觉模型只负责说话人和旁白语义判断，不负责重新生成 OCR 原文。
6. 低置信文字保留原图，并把 `requiresManualReview` 写入诊断。

字幕策略：

- `clean-bubble-and-caption`：对白气泡清除成功后，在编辑器中添加字幕。
- `preserve-bubble`：保留原气泡；仍可配音，但默认不重复显示同文字幕。
- 清除失败不能阻断生产，应回退 `preserve-bubble`。

阶段 B 只承诺 `preserve-bubble`。启用 `clean-bubble-and-caption` 前，必须新增“气泡 mask → 文字清除/补图 → clean panel 质量门禁”的独立产物阶段，明确由 Vision worker 生成 `cleanPanelUrl`。不能把 OCR 结果或原始 panel 直接标成 clean panel。该能力未启用或门禁失败时，系统自动回退 `preserve-bubble`，并在诊断中记录原因。

### 5.4 先做 TTS，再确定镜头时长

镜头时长不能只由固定模板决定，必须以实际 TTS 时长为准：

```text
lineDuration = 实际音频时长
dialogueStart = 上一句结束 + 150ms 停顿
shotDuration = max(视觉最小时长, 最后一句结束 + 450ms 尾停顿)
```

规则：

- 无对白 Shot 首版固定 3 秒。
- 单 Shot 不得超过 18 秒；超过时拆成多个 Shot 或缩短停顿，不能在渲染阶段硬截音频。
- 优先在对白边界拆 Shot；单句仍超限时按标点拆成稳定子句，再生成子 `lineId`。拆出的 Shot 使用递增 `panelPartIndex`，复用同一 panel 和分析产物。
- 全项目不足 5 秒时，在批次规划前调用 `padProjectToMinimumDuration` 补足到 5 秒；不能把短项目直接交给 `plan-batches`。
- TTS 音频上传对象存储后再写工程。
- 有 provider 音素/viseme 时保存；没有时第一版按对白区间做确定性三态口型。
- TTS 失败时降级为“可见字幕 + 无配音”，并在交付清单标记缺失原因。即使请求是 `preserve-bubble`，该行也必须临时 `visible=true`，避免得到原气泡存在但无声、无可访问字幕的不可审结果。

所有毫秒值按工程 fps 转成整数帧，舍入规则固定为 `Math.round`。停顿、尾停顿、默认无对白时长、拆句算法版本和 TTS 语速都必须进入 `inputHash`，保证重放得到相同时间线。

### 5.5 选择 L0/L1/L2/L3

先规则判断，再让视觉模型处理语义：

```text
环境、多人复杂遮挡、低置信度             → L0
主体清晰且可做人景分割                   → L1
对话近景、眼嘴区域足够大                 → L2
重点镜头且预算充足、部件边界清晰          → L3
```

第一版生产配额建议：

- 至少 70% 使用 L0/L1。
- L2 只用于对话近景。
- L3 默认关闭，只对测试集中的重点镜头开放。
- 单 Shot 连续两次质量失败后强制降一级。
- 项目预算使用到 80% 后停止 L2/L3 增强。

### 5.6 图层准备

#### L0

- 直接使用 panel 或 clean panel。
- 只应用 camera push/pull/pan。
- 不生成 LayerPackage。

#### L1

1. 分割人物 RGBA。
2. 判断运动是否会暴露人物后方区域。
3. 不暴露时限制人物位移，只做呼吸和微视差。
4. 会暴露时生成背景 mask，先 OpenCV 小洞补图，再按需调用 inpaint API。
5. 输出 background、body/character、foreground。

#### L2

在 L1 基础上生成：

- `eye-open`、`eye-closed`。
- `mouth-closed`、`mouth-half`、`mouth-open`。

状态补丁必须：

- 使用相同 bounds。
- 覆盖完整眼周或嘴周，不能只输出瞳孔/嘴缝。
- 具有相同画布和 alpha 边界。
- 重组后与原图的差异只集中在目标区域。

#### L3

只在后续阶段增加 head、arm、hair 和 foreground 等多部件。L0～L2 跑通前不实施。

### 5.7 图层质量门禁

每个 LayerPackage 生成后执行：

1. 按 zIndex 重组静帧。
2. 与源 panel 计算重组差异。
3. 检查 alpha 空洞、透明边缘、越界和状态图漂移。
4. 检查人物轻微运动是否暴露未补区域。
5. 产出 `recompositionScore`、`alphaHoleRatio`、`edgeArtifactScore`。

失败处理：

```text
状态图失败 → L2 降 L1
多部件失败 → L3 降 L2/L1
补图失败   → 限制运动；仍失败降 L0
人景分割失败 → L0
```

## 6. 构建 Remotion 工程

### 6.1 草稿适配器

Agent 工具不能接收或返回完整工程 JSON。工具后端统一执行：

```text
读取 draft(project, revision)
→ 调用一个 Compose API
→ 校验返回工程
→ transaction compare-and-set(expectedRevision)
→ 保存 newProject 和 revision + 1
→ 返回摘要
```

CAS 冲突时：

- 确定性 Compose 操作重新读取并重放。
- 付费模型步骤不重新调用，复用 `AssetArtifact`。
- 连续冲突达到上限后返回 `DRAFT_REVISION_CONFLICT`。

注意：现有 Compose 路由虽然解析 `expectedRevision`，但没有存储，因此不可能自己完成跨请求 CAS。CAS 必须在上游草稿服务落地。

### 6.2 正常调用序列

`project/create` 已在受理事务前完成并保存为 revision=0，不属于可重放的常规 Compose 序列。后续顺序为：

```text
1. image/sequence（带 panelFitPolicy）
2. dialogue/add
3. 写每句 voice audio
4. 对 L1/L2/L3 Shot 调 layers/import
5. 写 camera 和普通 item motion
6. 写 blink 和 mouth-flap
7. project/pad（仅总时长不足 5 秒）
8. project/validate
9. 阶段 E 才执行 contact-sheet / preview / 修正或降级
10. plan-batches
11. render-batches
12. export-package 生成 manifest
13. 阶段 E 由独立 Packager worker 生成 ZIP
```

`image/sequence` 先为所有 Shot 建立稳定 ID 的 L0 panel 轨。`layers/import` 必须是原子命令：质量门禁通过并成功导入全部必需图层后，把 panel 轨设为 `hidden=true`，但保留其 item 和 asset；导入失败不改变 L0。显式降级到 L0 时恢复 `hidden=false` 并隐藏或删除该 Shot 的增强轨。

L1/L2 包必须提供能遮住原人物的 clean background；不能让含原人物的 L0 panel 在增强轨下同时可见，否则前景人物移动时会露出双影。任何阶段都不要删除 panel asset，保证降级可以恢复。

### 6.2.1 Motion 脚本模块和作用程度

Motion 不直接写入渲染层，也不由工作流脚本拼接关键帧。职责拆分如下：

| 模块 | 职责 |
| --- | --- |
| `src/editor/motion/intensity.ts` | 定义 `light`、`medium`、`heavy` 三档作用程度及默认值 |
| `src/editor/motion/presets.ts` | 根据预设、时长、种子和作用程度展开确定性的关键帧 |
| `src/editor/comic/apply-motion.ts` | 校验目标并把展开结果写入 item/shot |
| `src/editor/comic/apply-sprite-motion.ts` | 处理眨眼、口型等离散 Sprite 状态 |
| `app/api/compose/item/motion/route.ts` | 校验请求参数并调用 Compose command |
| `scripts/comic/run-production.mjs` | 编排可恢复生产步骤，通过 `--motion-profile` 为不同部位选择运动和强度 |

强度只影响幅度，不改变预设的运动类型、周期或关键帧结构。默认使用 `medium`，兼容未传强度的旧命令：

| 预设 | `light` | `medium` | `heavy` |
| --- | ---: | ---: | ---: |
| `hair-sway` 旋转 | `1°` | `2°` | `3°` |
| `breathing` 缩放 | `1.01` | `1.02` | `1.03` |
| `float` 位移 | `6 px` | `12 px` | `24 px` |
| `camera-push/pull` 缩放 | `1.04` | `1.08` | `1.12` |
| `pan-left/right` 位移 | `40 px` | `80 px` | `120 px` |

请求示例：

```json
{
  "target": {
    "type": "item",
```

### 6.6 Shot 时长和音频

1. 调 `shot/edit` 原子调整 Shot。
2. 平移后续 Shot、图层、对白和归属音频。
3. 重新生成该 Shot 的 mouth-flap。
4. 重新规划批次。
5. 已渲染批次内容 hash 变化时只使受影响批次失效。

若替换声音后单个 Shot 超过 18 秒，必须先按第 5.4 节重新拆分 Shot，再执行平移和批次规划；不能让超长 Shot 进入 `plan-batches`。

### 6.7 竖屏落幅和短项目垫长

## 8. 任务状态机、幂等和恢复

### 8.1 状态机

```text
CREATED
→ INGESTING
→ ANALYZING
→ SYNTHESIZING_VOICE
→ PREPARING_ASSETS
→ COMPOSING
→ VALIDATING
├─ 阶段 B ──────────────────────────────┐
└─ 阶段 E → PREVIEWING → REVIEWING     │
                         ├─ 通过 ──────┤
                         └─ FIXING ────┘
→ PLANNING_BATCHES
→ RENDERING_BATCHES
├─ 阶段 B → DELIVERED
└─ 阶段 E → PACKAGING
→ DELIVERED
```

终态：

```text
DELIVERED | PERMANENT_FAILED | CANCELLED
```

状态转换只能由状态机服务按允许边提交：

- 阶段 B 在 `VALIDATING` 成功后直接进入 `PLANNING_BATCHES`，渲染和 manifest 完成后进入 `DELIVERED`。
- 阶段 E 才进入 `PREVIEWING/REVIEWING/FIXING/PACKAGING`；`FIXING` 最多回到 `VALIDATING` 一次，不能无限循环。
- 单 Shot 不进入任务状态。它通过 `animationLevel`、`degradedFrom` 和 diagnostics 记录降级，任务继续。
- 预算不足以做增强时停止 L2/L3 并继续交付；只有预算或策略导致任何可播放结果都不能产生时才 `PERMANENT_FAILED`。
- 只有用户或管理员取消才进入 `CANCELLED`。已经完成的供应商结果可以记账和入库，但取消后禁止新的付费调用、CAS 和渲染提交。
- 每一阶段必须先提交产物/命令事实，再推进状态；状态推进和下一条 outbox 事件在同一事务中完成。

阶段完成条件：

| 阶段 | 提交后必须成立 |
| --- | --- |
| `INGESTING` | 源对象、pageId、checksum 已保存 |
| `ANALYZING` | 所有页有 `PanelSpec`，失败页有整页 fallback |
| `SYNTHESIZING_VOICE` | 每个 `stableLineKey` 有 `LineAudio` 或明确 `missingReason` |
| `PREPARING_ASSETS` | 每个定稿 Shot 至少有 L0 素材 |
| `COMPOSING` | 本轮所有 Compose 命令账本均 `committed` |
| `VALIDATING` | 工程没有 error 级 issue |
| `RENDERING_BATCHES` | 所有批次有 checksum 通过的 MP4 |
| `PACKAGING` | manifest hash 与 ZIP checksum 均已保存 |

### 8.2 幂等层次

1. 产品请求：`tenantId + prodClientRequestId + payloadHash`。
2. 阶段任务：`projectId + shotId + stage + inputHash`。
3. Compose 命令：稳定 shot/layer/line ID。
4. 草稿写入：`expectedRevision` CAS。
5. 渲染：`projectContentHash + frameRange + renderConfig`。
6. 打包：manifest 内容 hash。

只有网络超时、5xx 和明确 `retryable=true` 的错误可以自动重试。同一产品意图重试使用相同 `prodClientRequestId`；同一 Compose 命令重试使用相同 `commandId`。

### 8.3 重试上限

- 确定性本地步骤：最多 3 次。
- 供应商超时：同 provider 最多 2 次。
- 图像质量失败：最多修正 1 次，随后降级。
- TTS：主 provider 1 次重试，再 fallback provider。
- Lambda 渲染：只重试失败批次。
- 达到预算或取消后禁止再创建付费调用。

### 8.4 PostgreSQL 最小模型

阶段 B 开工前至少落下这些表和约束：

| 表 | 关键字段与唯一约束 |
| --- | --- |
| `idempotency_keys` | `tenant_id, request_id, payload_hash, production_id`；`UNIQUE(tenant_id, request_id)` |
| `productions` | `production_id, tenant_id, state, cancel_requested_at, budget_limit, reserved_cost, actual_cost` |
| `drafts` | `project_id, revision, project_json, content_hash`；`PRIMARY KEY(project_id)` |
| `compose_commands` | 第 3.5.1 节字段；`UNIQUE(project_id, ordinal)`、`UNIQUE(command_id)` |
| `asset_artifacts` | 第 4.3 节字段；`UNIQUE(project_id, stage, input_hash, COALESCE(shot_id,''))` |
| `cost_entries` | `provider_request_id, reservation, actual, status`；供应商请求号非空时唯一 |
| `output_batch_renders` | `project_id, batch_id, content_hash, render_id, status, url, checksum`；三元组唯一 |
| `outbox_events` | `event_id, aggregate_id, type, payload, available_at, published_at` |
| `worker_jobs` | `job_key, type, status, attempt, lease_owner, lease_expires_at, heartbeat_at`；`job_key` 唯一 |

草稿 CAS 使用：

```sql
UPDATE drafts
SET project_json = :newProject,
    content_hash = :newContentHash,
    revision = revision + 1
WHERE project_id = :projectId
  AND revision = :expectedRevision;
```

影响行数不是 1 即为 `DRAFT_REVISION_CONFLICT`。命令 committed、成本变化、状态推进和 outbox 写入必须分别在其业务事务中原子提交。

### 8.5 Outbox、成本和供应商对账

- 任何“数据库状态已变更后需要入队”的动作都先写 `outbox_events`，dispatcher 至少一次投递；consumer 按 `job_key` 幂等领取。
- 付费调用前在数据库中原子预留最坏成本；预留后再次检查取消与预算。供应商完成后按真实费用结算并释放差额，失败则按供应商计费规则结算或释放。
- `AssetArtifact.costRmb` 是产物快照，`cost_entries` 是财务账本真相，禁止两边独立累加。
- 供应商超时时先使用 `providerRequestId` 查询。只有明确不存在或 provider 声明可安全重放时才发第二次请求。
- provider 不支持查询时，将任务标为人工可对账错误；不能用新请求号静默再买一次。
- Lambda 已提交后即使用户取消也可能继续计费；系统停止后续批次，并对已提交 renderId 继续查询直至终态，以便记录实际成本。

- 失败自动回 L0。

门禁：测试集中适合 L1 的镜头，80% 无明显透明洞或人物残影。

### 阶段 D：L2 眼嘴状态

- 眼嘴定位。
- 状态补丁生成和缓存。
- blink/mouth-flap 写入。
- 音频、字幕和口型同步检查。
- 失败自动回 L1。

门禁：近景测试集的状态图无明显漂移，切换不超频，口型只在对白期间发生。

### 阶段 E：Agent QA 和生产化

- `comic_*` 工具。
- 联系表和低清审片。
- 自动修正/降级。
- 成本、取消、告警、恢复和多租户。
- ZIP 交付。

L3 多部件仅在 A～E 稳定后作为独立阶段评估。

## 13. 测试计划

### 13.1 单元测试

- 分格排序和稳定 ID。
- OCR 气泡到 panel 归属。
- TTS 时长到 Shot/对白帧换算。
- 横格、竖格和整页降级的竖屏落幅。
- 短于 5 秒项目的确定性垫长。
- 超过 18 秒 panel 的稳定 `panelPartIndex` 和子句拆分。
- 动画等级和预算决策。
- 输入 hash 和幂等键。
- revision CAS 冲突。
- blink seed 确定性。
- mouth-flap 对白边界和最大切换频率。
- 降级矩阵。

### 13.2 契约测试

- `PanelSpec`、`LineAudio`、`TimedShotSpec`、LayerPackage、Compose route 和 Agent tool JSON Schema。
- 错误码、HTTP 状态和 `retryable`。
- dialogue voice 稳定 upsert。
- 所有远程素材必须是允许域名 HTTPS。

### 13.3 集成测试

- 一页标准漫画完整出片。
- 横构图 panel 不出现纯黑边，人物和对白不被裁掉。
- 单 Shot 短项目垫长后可以正常规划批次。
- 同一 panel 的超长对白能拆成多个稳定 Shot，重放不新增 part。
- 不规则分格触发视觉模型。
- OCR 低置信保留诊断。
- 分割失败降 L0。
- 状态图失败降 L1。
- TTS 失败降字幕。
- 同一 `prodClientRequestId` 重放不重复扣费；同一 `commandId` 重放不增加轨道。
- revision 冲突后重读和重放。
- worker 在供应商完成、Compose 返回、CAS 成功和批次提交后的各恢复窗口崩溃，均只从最近已提交事实继续。
- provider 超时先按 `providerRequestId` 对账，无法确认时不得静默二次付费。
- 两个 worker 竞争同一 job 时只有租约持有者提交结果。
- 单批 Lambda 失败只重渲目标批。
- ZIP checksum 和播放顺序。

### 13.4 固定视觉回归集

至少覆盖：

- 黑白和彩色漫画。
- 单人近景、多人对话、环境和动作镜头。
- 无边框、跨格和常规网格。
- 复杂头发、手臂遮挡、强光效和速度线。
- 横排、竖排和拟声词。
- 嘴被手或物体遮挡。

每次保存原图、重组图、代表帧和差异图，不只记录一个“通过/失败”布尔值。

## 14. 分阶段验收

### 14.1 阶段 A

1. 旧工程和三张整图工程均可真实渲染 H.264。
2. blink、mouth-flap 和 dialogue voice 重放不增加 item/track，状态帧不越界。
3. Player、still 和 Lambda 的首/中/尾关键帧一致。
4. 施工单第 10 节除上游 CAS 外的 10 项通过。

### 14.2 阶段 B

1. 上传一页标准漫画，无需 PSD、图层或音频即可得到有序 MP4、可编辑工程和 manifest。
2. 固定 10 页夹具覆盖常规网格、无边框、跨格、横构图、竖排文字、无对白、超长对白、低置信 OCR、TTS 失败和分格失败；每类至少一页。
3. 分格失败页以整页 L0 出片；TTS 失败行有可见字幕。
4. 横构图无纯黑边且不裁掉主要人物和对白；短项目自动垫长，超 18 秒 panel 按稳定 part 拆镜。
5. 所有批次 5～18 秒、顺序连续，单批失败可以单独恢复。
6. 产品请求和 Compose 命令分别幂等，CAS 冲突不覆盖新草稿，供应商调用不重复计费。
7. 阶段 B 跳过自动审片和 ZIP 仍可进入 `DELIVERED`。

### 14.3 阶段 C/D

1. 阶段 C 的 L1 适配镜头 80% 无明显透明洞或人物残影，失败自动回 L0。
2. 阶段 D 的近景眼嘴状态无明显漂移，口型只在对白期间发生，失败自动回 L1。
3. 测试集最终同时包含 L0、L1、L2，但该要求不阻塞阶段 B。

### 14.4 阶段 E

1. 联系表和低清预览是真实渲染产物，QA 只能选择有限修正动作。
2. 下载 ZIP 包含允许分发的源图、panel、图层、音频、字幕、工程、诊断、视频、manifest、播放顺序和 checksum。
3. 多租户鉴权、取消、预算、租约接管、告警和保留/删除策略通过集成测试。
4. 最终工程可以重新打开、编辑并渲染，ZIP checksum 与 manifest 一致。

## 15. 不应在第一版做的事

- 不要求所有 Shot 都拆成多部件。
- 不部署本地大型分层模型。
- 不做 PSD 往返。
- 不做骨骼、网格、粒子和完整曲线编辑器。
- 不让 Agent 直接写工程 JSON。
- 不把联系表 taskId 回显当成异步任务完成。
- 不把 manifest 当成已生成 ZIP。
- 不在没有真实 H.264、Lambda 对比和降级测试时宣称生产闭环完成。

## 16. 建议的第一条开发主线

最短可验证路径是：

```text
修 sprite 和稳定 voice API
→ 一页漫画 OpenCV 分格
→ OCR
→ TTS
→ 全部先走 L0
→ Compose 工程
→ 真实 H.264
→ 再逐步把合适镜头升级为 L1/L2
```

这样先证明“只给一页漫画一定能出片”，再提高画面质量。若一开始同时建设 L3 拆层、复杂补图、Agent 自动审片和生产队列，出现失败时无法判断问题位于视觉模型、工程变换、草稿并发还是渲染部署。

## 17. 脚手架准入边界

本文补强后，下一轮可以按以下边界创建文件：

1. 立即实施 `novelcomic-remotion` 阶段 A，只改第 11.1 节第一批文件并跑现有测试基线。
2. 阶段 A 领域测试通过后，在已有 Python 3.11 / FastAPI `novelcomic-agent` 服务内增加 `src/novelcomic_agent/comic/`，不另建服务或运行时；首批只建 Pydantic contracts、PostgreSQL migrations、Draft CAS、Compose 命令账本、状态迁移、outbox 和 job lease。
