# 动态漫画编辑器文件编写顺序

> 配套架构：[动态漫画编辑器架构设计.md](./动态漫画编辑器架构设计.md)  
> 用途：按依赖顺序实施，避免并行修改同一核心类型造成返工  
> 更新时间：2026-10-02

## 1. 使用规则

本施工单中的顺序是“依赖顺序”，不是文件名排序。

执行约束：

1. 严格按阶段推进，前一阶段门禁未通过不得开始后一阶段。
2. 每个纯函数源文件完成后立即编写同名测试，不把测试集中拖到阶段末。
3. 先写领域函数，再写 route；route 内不复制业务逻辑。
4. 修改核心类型后立即执行 `pnpm typecheck`，尽早暴露影响面。
5. 每个阶段只提交该阶段内容，方便回滚和评审。
6. 标记为“新增”的文件当前不存在；标记为“修改”的文件已在仓库中。

推荐分支：

```text
feature/comic-editor-motion
feature/comic-editor-compose
feature/comic-editor-batches
feature/comic-editor-delivery
```

```json

    "test": "vitest run",
    "test:watch": "vitest"
```

```text
lint    = eslint .
format  = prettier --write .
```

## 9. 推荐提交切分

每次提交都应独立通过 typecheck 和 test：

```text
test: add vitest foundation
feat(comic): add v2 project and motion types
feat(comic): add state normalization and errors
feat(motion): add deterministic pose evaluator
feat(editor): render evaluated image poses
feat(render): pass shots through composition props
feat(compose): add atomic command wrapper
feat(compose): add image sequence and dialogue
feat(comic): add shot lifecycle
feat(comic): import layer packages atomically
feat(comic): add motion commands
feat(render): plan and render frame-range batches
feat(comic): add preview and delivery manifests
docs(comic): publish v2 schema and APIs
```

不要把阶段 1～4 压成一个提交；运动公式、状态迁移、HTTP 和 Lambda 同时变化时几乎无法定位回归。

## 10. 全部完成后的验收脚本

自动门禁：

```bash
pnpm test
pnpm typecheck
pnpm lint
pnpm build
```

业务验收：

1. 加载一个未迁移的旧视频工程并成功导出。
2. 用三张整图创建 v2 工程并导出。
3. 导入含状态图的 LayerPackage。
4. 添加 camera、breathing、blink 和 mouth-flap。
5. 修改 Shot 时长并检查后续内容平移。
6. 对同一 shotId/layerId/lineId 重放工程变换，不增加轨道或 item。
7. 由上游草稿服务验证 clientRequestId 重放和 expectedRevision 冲突。
8. 规划 20 Shot 工程，所有批次均在 5～18 秒。
9. 只重试一个失败批次。
10. 生成联系表和交付 manifest。
11. 比较 Player、still 和 Lambda 的首/中/尾关键帧。

以上 11 项全部通过后，动态漫画编辑器才达到生产闭环，不以“路由存在”或“本地能播放一次”作为完成标准。
