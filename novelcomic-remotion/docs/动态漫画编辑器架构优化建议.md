# 动态漫画编辑器架构优化建议

> 审查基线：2026-10-06  
> 适用工程：novelcomic-remotion  
> 关联文档：动态漫画_PS_AE功能边界与补全规格.md

## 1. 审查结论

当前工程不需要推倒重做。

现有架构已经具备素材、时间线、动态漫画领域逻辑、拆层、蒙版、Clean Plate、关键帧、高级合成、质量检查和渲染交付。当前最大的风险不是功能太少，而是同一个画面正在被多套数据模型和多条求值链路共同控制。

建议优先收敛五个边界：

1. 一个统一的工程文档模型。
2. 一条确定性的逐帧求值管线。
3. 一套命令、事务和撤销系统。
4. UI、领域逻辑、像素计算和渲染器严格分层。
5. 可恢复、可取消、可重试的异步任务协议。

优化方式应采用“新增门面和适配器，再逐步迁移”，不能同时重写编辑器、渲染器和工程格式。

## 2. 当前架构值得保留的部分

- src/editor/comic 已形成动态漫画领域层，shot、拆层、口型、批次和交付没有全部塞进 React 组件。
- motion、composition、masks 中已有较多纯函数，适合作为后续求值内核。
- L0、Clean Plate、Cutout、语义图层和质量预览已经有明确概念。
- AdvancedProjectState 已具备父子级、预合成、Mask、Track Matte 和受限表达式基础。
- 本地渲染、远程渲染、批次规划、manifest 和 checksum 已形成完整交付方向。
- 自动测试基线良好：本次审查运行 100 个测试文件、329 个测试，全部通过。
- 表达式使用安全解析器，而不是直接执行任意 JavaScript，这个安全边界应继续保持。

## 3. 当前主要架构问题

### 3.1 同一个图层有多套变换模型

当前画面姿态可能同时来自：

- 普通 item 的 left、top、width、height、rotation、opacity。
- ImageItem.motion.transform 的关键帧、锚点和循环。
- AdvancedProjectState 图层的 transform、父子级、预合成和表达式。
- shot.cameraMotion 的二维镜头运动。
- boneRig 和 meshGrid 的局部变形。
- quality preview 对可见层集合的临时改写。

这会导致以下问题：

- UI 修改了一套属性，渲染器读取另一套属性。
- 普通图层加入高级合成后出现两份位置、尺寸或透明度。
- 很难解释最终覆盖顺序。
- 导入、导出和迁移需要同时理解多种结构。
- 新增运动模糊或多层视差时容易再次复制变换逻辑。

### 3.2 普通图层和高级图层是两条渲染路径

MainComposition 目前先渲染普通 Layers，再渲染 AdvancedLayers，并通过 excludedItemIds 避免重复。

这种方式短期可用，但长期存在风险：

- 图层从普通模式切换到高级模式时，身份和属性所有权不清晰。
- 普通 item 和 advanced layer 的裁切、淡入淡出、Mask、缓存行为可能不同。
- 质量预览、选择框和最终渲染需要同时理解两条路径。
- 每增加一种图层能力，都可能需要在两套渲染器中各实现一次。

### 3.3 帧求值入口分散

当前至少存在：

- evaluateImagePose。
- evaluateAdvancedFrame。
- sprite asset 求值。
- shot camera 求值。
- bone rig 求值。
- mesh warp 求值。
- quality preview 可见性规划。

这些模块本身并非错误，但缺少一个公开且稳定的“最终帧求值总入口”。

风险是编辑器 Player、预览帧、本地渲染和远程渲染可能在未来产生不同结果。

### 3.4 React 组件承担跨资源业务事务

钢笔、像素选区、拆层面板和高级合成面板中仍包含较多业务流程：

- 读取资产和像素。
- 生成 Mask、Cutout 或 Clean Plate。
- 创建上传任务。
- 直接拼装多个领域对象。
- 写编辑器状态。
- 决定是否进入 Undo。
- 处理错误和 toast。

结果是：

- 同一个完整操作很难在 API、脚本和 UI 中复用。
- 异步步骤中途失败可能留下孤儿资产或半成品引用。
- 组件体积快速增大。
- 测试只能覆盖局部函数，难以覆盖完整事务。

### 3.5 大型组件已经成为维护瓶颈

本次扫描中较大的业务组件包括：

- comic-layer-panel.tsx：约 1141 行。
- motion-controls.tsx：约 1035 行。
- inspector-dock.tsx：约 911 行。
- layer-panel.tsx：约 865 行。
- advanced-composition-panel.tsx：约 855 行。
- editor-sidebar.tsx：约 652 行。
- timeline-item-film-strip.tsx：约 634 行。

文件行数本身不是错误，但这些组件同时承担状态、领域变更、异步任务和视图时，会显著增加回归风险。

### 3.6 像素计算仍与 UI 生命周期耦合

工程已开始使用 WebGL2、MaskDocument 和 tile snapshot，这是正确方向；但选区、Cutout、Clean Plate、Difference 和部分 mask 操作仍存在在主线程读取或复制全尺寸像素的路径。

对于 8K 漫画页，主要风险包括：

- getImageData 阻塞主线程。
- 重复创建 Uint8ClampedArray。
- React state 或闭包长期持有整张像素数组。
- 画笔每次移动都触发过大范围重算。
- 历史记录若保存全图会迅速耗尽内存。

### 3.7 Context 数量较多但缺少细粒度 selector

context-provider 已拆分多个 Context，这是比单一巨大 Context 更好的做法；但 use-context 仍然主要按整块对象订阅。

随着 10,000 item 上限和复杂面板增加，可能出现：

- 只修改一个 item，却使订阅全部 items 的组件重新渲染。
- 每个面板重复执行 find、Object.values 和派生排序。
- 当前 useShotById 每次都在线性数组中查找。

当前不必立刻更换状态库，应该先建立索引和 selector 边界。

### 3.8 工程版本迁移缺少单一入口

工程已有 schemaVersion、normalize 和多处 Zod schema，但 item、advanced、comicEditLayers、shots、voice profiles 和外部交换包仍有各自的演进路径。

风险包括：

- 老工程只能局部兼容。
- 保存文件和外部交换包使用不同版本策略。
- 无法快速判断工程能否无损升级。
- 子模型新增必填字段时容易遗漏迁移。

### 3.9 异步任务协议不统一

分层、补底、上传、配音、渲染均具有任务生命周期，但目前状态类型、轮询、AbortController 和错误展示由不同模块分别实现。

例如 AI 分层面板直接在组件中轮询，渲染又维护另一套 RenderingTask。

结果是：

- 页面刷新后任务不一定能恢复。
- 重试和取消语义不同。
- 同一输入可能重复提交。
- 很难建立统一任务中心。

### 3.10 诊断信息分散

目前错误可能存在于：

- toast。
- ProjectIssue。
- layer diagnostics。
- expression diagnostics。
- track matte validation。
- AI 任务错误。
- render task 状态。

这些信息没有统一实体定位和修复建议，导致质检面板很难成为真正的生产入口。

## 4. 推荐的目标分层

建议最终形成以下单向依赖：

    UI / Workspaces
      - 拆层工作区
      - 动画工作区
      - 对白音频工作区
      - 质检交付工作区
            ↓
    Application
      - Commands
      - Transactions
      - Undo / Redo
      - Async Job Coordinator
            ↓
    Domain
      - ProjectDocument
      - Timeline / Shots
      - Scene Graph
      - Comic Layers / Dialogue
      - Validation / Migrations
            ↓
    Evaluation Kernel
      - Frame Evaluation
      - Curves / Expressions
      - Parenting / Precompose
      - Camera / Sprite / Rig / Mesh
      - Render Plan / Diagnostics
            ↓
    Infrastructure
      - Asset Store / Upload
      - Pixel Worker
      - AI Provider Adapters
      - Local / Remote Renderer
      - Import / Export Adapters

约束：

- Domain 和 Evaluation Kernel 不得依赖 React。
- Domain 不得直接调用 fetch、Next.js route 或 toast。
- UI 不得直接拼装跨多个领域对象的事务。
- 供应商 API 只能通过 Infrastructure adapter 接入。

## 5. 具体优化方案

### 5.1 建立统一 ProjectDocument 门面

建议顶层文档包含：

- schemaVersion。
- metadata。
- composition settings。
- assets。
- timeline。
- shots。
- scene graph。
- comic document。
- dialogue document。
- async job references。

第一步不是立即替换 UndoableState，而是先建立四个门面函数：

- legacyStateToProjectDocument。
- projectDocumentToLegacyState。
- normalizeProjectDocument。
- migrateProjectDocument。

迁移期间现有 UI 可以继续读取旧模型，但新功能必须通过新的 Application command 写入，禁止继续增加新的平行状态。

### 5.2 用 Scene Graph 收敛普通和高级图层

统一 SceneNode 至少包含：

- id 和 source。
- parentId。
- transform。
- animation。
- masks。
- matte。
- blendMode。
- rig。
- mesh。
- visibility。

过渡规则：

1. item 保留素材来源、时间范围和基础媒体属性。
2. SceneNode 成为最终合成变换和层级关系的唯一 owner。
3. 旧 item.motion 通过 adapter 映射为 SceneNode animation。
4. AdvancedProjectState 逐步迁移为 SceneGraph 的合成和嵌套部分。
5. 同一属性在任意时刻只能有一个可写 owner。

### 5.3 建立统一帧求值门面

新增 evaluateSceneFrame(project, frame, options)，统一输出 EvaluatedFrame。

固定求值顺序：

1. 解析时间范围和当前 shot。
2. 解析 sprite asset。
3. 采样图层本地关键帧。
4. 采样骨骼和网格。
5. 求父子世界变换。
6. 求预合成局部时间和嵌套节点。
7. 应用 shot 二维镜头。
8. 解析 Mask、Matte 和 Blend Mode。
9. 应用质量预览可见性计划。
10. 输出确定性的 RenderNode 列表和 diagnostics。

编辑器 Player、预览帧、本地渲染和远程渲染必须共同调用该门面。

第一阶段可以只包装现有 evaluateImagePose 和 evaluateAdvancedFrame，不改变画面结果。

### 5.4 建立 Command 和 Transaction 层

建议将业务动作表达为命令，例如：

- CompleteLayerSeparation。
- ApplyCleanPlate。
- AddKeyframe。
- SetLayerParent。
- PrecomposeLayers。
- AttachDialogueVoice。

命令返回：

- 新的工程状态。
- 需要创建、上传或删除的资产 effect。
- 需要启动的异步 job effect。
- diagnostics。

对于“生成 Mask → Cutout → 上传 → Clean Plate → 新建图层”的长事务：

1. 先生成 effect plan。
2. 必要资产全部成功后一次提交工程状态。
3. 失败时不写无效 assetId。
4. 整个业务动作只占一个 Undo 记录。
5. 临时资产由事务清理或后续垃圾回收处理。

### 5.5 建立 ProjectIndex

按工程 revision 缓存以下索引：

- itemById。
- trackByItemId。
- nodesByItemId。
- childrenByParentId。
- itemsByShotId。
- comicLayerByItemId。
- assetReferenceCount。
- matteDependentsByNodeId。

收益：

- 避免每帧和每个面板重复 Object.values、find 和排序。
- 加速删除校验、层级查询、Shot 跳转和孤儿资产检查。
- 为资产垃圾回收和影响分析提供基础。

### 5.6 Pixel Worker 与 Tile Mask

应迁移到 Worker 的任务：

- 魔棒 flood fill。
- 色彩范围。
- 羽化、扩张、收缩和反相。
- Cutout 像素生成。
- Difference、透明洞和边缘指标。
- 本地 inpaint。

建议蒙版内部采用 tile：

- 例如 256×256 tile。
- 画笔只提交 dirty tile。
- 历史记录保存 stroke 或 tile diff，不保存全图副本。
- 使用 OffscreenCanvas、ImageBitmap 和 transferable buffer。
- React 只保存 session id、版本号、工具参数和缩略诊断。

现有 MaskDocument、TileSnapshot 和 WebGL2Renderer 可以作为迁移基础，不应废弃。

### 5.7 统一 AsyncJob 协议

所有上传、分层、补底、配音和渲染任务应统一包含：

- id。
- kind。
- inputHash。
- queued、running、succeeded、failed、cancelled 状态。
- progress。
- attempt 和最大重试次数。
- result reference。
- structured error。
- createdAt、updatedAt。

要求：

- 相同 inputHash 支持幂等复用。
- 页面刷新后可恢复任务。
- 支持取消和明确重试。
- AI 服务未配置时返回 capability error，不创建伪任务。
- Next.js route 只处理协议，供应商差异放在 adapter 中。

### 5.8 统一 Diagnostics

统一诊断对象至少包含：

- code。
- severity。
- message。
- entity reference。
- frame。
- suggested fix。

同一结构用于：

- 图层错误徽标。
- 保存前检查。
- 渲染前阻断。
- 批量质检。
- AI 和异步任务错误。
- 最终交付报告。

toast 只负责提示，不作为唯一错误记录。

### 5.9 Capability Registry 消除假入口

菜单、工作区和工具栏不应硬编码为静态按钮。

每个 capability 应描述：

- id。
- ready、beta 或 unavailable。
- commandId。
- 所属工作区。
- 当前选择要求。
- 浏览器能力要求。
- 外部服务要求。
- 不可用原因。

UI 只能展示 ready 或明确标识的 beta 能力。没有 command 的入口不得出现在生产界面。

### 5.10 拆分大型组件

优先拆分顺序：

1. layer-panel.tsx：拆为工具控制器、视口、Mask history、提交命令和属性面板。
2. advanced-composition-panel.tsx：拆为图层树、变换、父子、预合成、Matte 和表达式面板。
3. motion-controls.tsx：拆为关键帧、曲线、预设、骨骼和网格 section。
4. inspector-dock.tsx：改为 item type 和 feature section 注册机制。
5. comic-layer-panel.tsx：拆为数据 selector、树视图、操作 command 和 diagnostics。
6. timeline-item-film-strip.tsx：拆分帧提取、可见槽位、缓存和视图。

组件的目标是编排 hook 和 view，不直接实现领域算法或跨资源事务。

### 5.11 工程迁移和兼容策略

顶层 schemaVersion 必须控制整个工程，而不是只控制动态漫画局部字段。

迁移要求：

- 每次只支持 N → N+1 的纯函数迁移。
- migrateProjectDocument 顺序执行全部迁移。
- 迁移前保留原始快照。
- 迁移后执行 normalize 和 validate。
- 无法无损迁移时给出明确诊断，不静默删除字段。
- 外部交换包版本与工程版本分开，但必须有显式转换器。

## 6. 推荐的状态更新顺序

统一最终覆盖顺序：

1. 媒体 item 提供 source、时间范围和固有尺寸。
2. SceneNode 提供基础二维变换。
3. 动画曲线修改 SceneNode 本地变换。
4. 骨骼和网格修改节点内部几何。
5. 父子级求世界变换。
6. 预合成求局部时间和合成空间。
7. Shot 二维镜头修改最终合成视图。
8. Mask 和 Track Matte 计算可见区域。
9. Blend Mode 计算合成方式。
10. Quality Preview 只改变诊断显示计划，不反向修改工程数据。

该顺序必须写成自动测试，不能只存在于文档。

## 7. 不建议做的事情

- 不要现在更换 React、Next.js 或 Remotion。
- 不要为了减少 Context 数量立刻引入另一套全局状态库。
- 不要把当前模块化单体拆成大量微服务。
- 不要用事件总线替代有返回值的 Command。
- 不要让编辑器预览和最终渲染维护两套 Scene Graph。
- 不要同时维护两套可写工程模型；旧模型在过渡期只能通过 adapter 写回。
- 不要在架构优化期间继续扩展完整 PS 或 AE 功能范围。
- 不要为性能提前缓存所有帧；先缓存索引、曲线和可复用 Render Plan。

## 8. 实施优先级

### P0：阻止复杂度继续增长

1. 明确并测试统一的变换覆盖顺序。
2. 新建 evaluateSceneFrame 门面，先包装现有求值器。
3. 新建 Command 和 Transaction 接口，先迁移“完成拆层”。
4. 建立 Capability Registry，隐藏所有无 Command 的入口。
5. 建立顶层 ProjectDocument 版本与迁移入口。
6. 新功能禁止直接从 React 组件拼装跨模块状态。

### P1：解决性能与重复模型

1. 建立 ProjectIndex。
2. 像素操作迁入 Worker。
3. 蒙版历史统一为 tile 或 dirty-rect。
4. 普通 item motion 和 advanced transform 迁入统一 SceneNode。
5. 编辑预览、预览帧和最终渲染统一使用 evaluateSceneFrame。
6. 拆分 layer-panel、motion-controls 和 advanced-composition-panel。

### P2：提高生产可靠性

1. 统一 AsyncJob。
2. 统一 Diagnostics。
3. 建立资产引用计数和垃圾回收。
4. 工程快照、崩溃恢复和任务恢复。
5. 增加逐帧 Render Plan 调试面板。
6. 增加性能指标：求值耗时、绘制耗时、像素任务耗时和缓存命中率。

## 9. 第一批建议代码改动

第一批只做不改变视觉结果的门面重构：

1. 新建 src/editor/domain/project-document.ts。
2. 新建 src/editor/domain/project-index.ts。
3. 新建 src/editor/evaluation/evaluate-scene-frame.ts。
4. 新建 src/editor/application/commands/types.ts。
5. 新建 src/editor/application/commands/complete-layer-separation.ts。
6. 新建 src/editor/capabilities/registry.ts。
7. 用 golden fixture 对比重构前后的关键帧、图层顺序和 Render Plan。

完成这批后，再迁移 Pixel Worker 和统一 Scene Graph。这样对现有工作区风险最低，也能立即阻止新功能继续直接写入多套状态。

## 10. 可量化验收标准

- 同一帧通过编辑器 Player、预览帧、本地渲染和远程渲染得到相同 Render Plan。
- 任意视觉属性只有一个可写 owner。
- 完成拆层是一次 Undo；任一步失败都不产生可见半成品和无效资产引用。
- 8K 图像画笔过程中不把整张 RGBA 数组写入 React state。
- 10,000 item 工程按 id 和关系查询不依赖每次全量扫描。
- 修改一个 item 不应导致所有无关图层检查器重新计算。
- AI、上传和渲染任务刷新页面后能够恢复状态。
- 老工程必须通过顺序 migration 打开。
- 无法无损迁移时必须给出明确错误和原始工程备份。
- 所有生产界面入口都能映射到 capability 和 command。
- Project validation、render validation 和 delivery verification 使用统一 Diagnostic 结构。
- 现有 329 个测试继续全部通过，并新增求值一致性和事务回滚测试。

## 11. 最终判断

现架构可以继续演进，但不应继续在 React 面板中直接增加 PS/AE 功能。

最先要做的是建立 ProjectDocument、Scene Graph、evaluateSceneFrame 和 Command/Transaction 四个核心门面。它们完成后，现有拆层、关键帧、父子级、预合成、口型和渲染能力都可以保留，同时显著降低功能互相覆盖、预览与渲染不一致、异步操作留下半成品和大图性能失控的风险。
