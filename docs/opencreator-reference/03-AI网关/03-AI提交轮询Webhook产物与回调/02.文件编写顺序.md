# AI 提交、轮询、Webhook、产物与回调：文件编写顺序

这篇只回答一个问题：NovelComic 如果要照 OpenCreator 接上 AI Provider 提交、轮询、Webhook、产物处理和 Consumer 回调，应该先写哪些文件、每一步完成到什么程度。

运行时原理见 [01-AI提交轮询Webhook产物与回调.md](./01-AI提交轮询Webhook产物与回调.md)，机制拆解见 [00-AI提交轮询Webhook产物与回调技术点.md](./00-AI提交轮询Webhook产物与回调技术点.md)。本文按依赖排序，不按厂商回调到达的时间排序。

命名约定：

- AI 服务路径默认按 OpenCreator 的 `opencreator-ai/` 写。
- Consumer 路径默认按 OpenCreator 的 `opencreator-consumer/` 写。
- Provider client 和模型 registry 已在前一组完成，本篇从 `queued ai_task` 继续。

本组目标不是“某个厂商能返回结果就行”，而是完整结果闭环：

```text
Provider submit
  → queued 任务真正提交给厂商

Result convergence
  → immediate / polling / webhook 都归一成 ProviderResult

Artifact processing
  → 成功和失败都进入 callback_pending

Consumer callback
  → 签名投递、重试、DLQ、Consumer 对单
```

---

## 总体顺序

```text
packages/contracts/src/provider-result.schema.ts
  → packages/db/src/task-repository.ts
  → packages/db/src/attempt-repository.ts
  → packages/runtime/src/provider-worker.ts
  → apps/api/src/routes/provider-webhooks.ts
  → packages/db/src/provider-event-repository.ts
  → packages/runtime/src/provider-webhook-service.ts
  → packages/storage/* artifact store
  → packages/runtime/src/artifact-worker.ts
  → packages/contracts/src/webhook.schema.ts
  → packages/db/src/callback-delivery-repository.ts
  → packages/runtime/src/consumer-callback.ts
  → packages/runtime/src/callback-worker.ts
  → opencreator-consumer/main.py
  → opencreator-consumer/services/invocation/model_invocation_service.py
```

`task-repository.ts` 在建单组已经能读写 `ai_task`。这一组在对应 worker 动手前，先补提交、结果和 skip 用到的方法。

可以按五段推进：

```text
结果契约
  → provider-result schema
  → task-repository 补 markProviderSubmitted / applyProviderResult / addRobinSkipProvider
  → attempt-repository

Provider 执行
  → provider-worker：提交、immediate、polling、fallback

Webhook 收敛
  → webhook route
  → provider-event-repository
  → provider-webhook-service

产物出口
  → artifact store / artifact-worker

Consumer 回调
  → 对 Consumer 的 webhook schema
  → callback-delivery-repository
  → callback service / retry / DLQ
  → Consumer 验签和对单
```

---

## 写之前必须已有

这些能力不在本文新写范围内，但缺少任何一项，后续链路都会对不上：

1. AI task 能建单并进入 `queued`。
2. provider-execution 队列能拿到 submit job。
3. AI registry 能按 `model_id` 选出 Provider call。
4. 至少一个 Provider call 已实现 `submit()` 和 `normalizeResult()`。
5. Task repository 能读取和更新任务。
6. Consumer 已经有 model invocation 或等价记录。
7. Consumer 的回调 URL 可从 AI 侧访问。

完成基线：队列里存在 `provider-execution` 的 submit job，worker 能按 `ai_task_id` 读回任务。

## 1. 先写统一 ProviderResult 契约

OpenCreator 对照：

[provider-result.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/provider-result.schema.ts)

先定义所有结果入口都要收敛到的形状：

```text
ProviderResult
ParsedProviderResult
NormalizedTaskResult
NormalizedError
```

至少要表达：

- 等待、成功、失败状态。
- Provider 和厂商模型 ID。
- Provider request id。
- 统一结果。
- usage。
- error。
- raw summary。

完成标准：同一个 Provider 的 submit、polling 和 webhook 结果都能转成统一结构。

## 2. 写 provider worker 提交流程

OpenCreator 对照：

[provider-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-worker.ts)

先实现主干：

```text
process(submit job)
  → taskRepository.requireByAiTaskId()
  → submitCoreTask()
  → markProviderSubmitted()
  → updateProviderTelemetry()
  → upsertAttempt()
  → status=waiting_provider
```

写回落在已有的 `task-repository.ts`：补 `markProviderSubmitted()`。本次提交记录落在新建的 `attempt-repository.ts`：补 `upsertAttempt()`。

第一轮先不写完整 fallback。先让一个任务能提交给一个 Provider，并写回 `provider_request_id`。

完成标准：`queued` 任务能推进到 `waiting_provider`，attempt 表能看到本次 Provider 提交。

---

## 3. 接 immediate result

仍在 [provider-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-worker.ts)。

如果 `submitCoreTask()` 返回：

```text
immediateResult
```

worker 要立刻：

```text
call.normalizeResult()
  → taskRepository.applyProviderResult()
  → enqueue artifact-processing
```

完成标准：同步出结果的 Provider 不需要 Webhook 或 polling，也能进入 artifact-processing。

---

## 4. 接 polling

仍在 [provider-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-worker.ts)。

polling 模式调用：

```text
getCoreProviderResult()
  → call.getResult()
  → call.normalizeResult()
```

需要处理：

- 仍在等待 Provider。
- 成功。
- 失败。
- 超时或异常。

完成标准：polling Provider 最终能写入 `ProviderResult`，成功进入 artifact-processing，失败进入 fallback 或最终失败。

---

## 5. 写 Robin fallback 入队

Provider 失败后，worker 要判断：

```text
getRemainingRobinProviders()
```

如果还有剩余 Provider，skip 写在 `task-repository.addRobinSkipProvider()`：

```text
addRobinSkipProvider(provider:model_id)
  → enqueue provider-execution submit job
  → payload 带 skip_providers
```

如果没有剩余 Provider：

```text
applyProviderResult(failed)
  → enqueue artifact-processing
```

完成标准：第一家失败后第二家会被尝试；请求钉死 Provider 时不会 fallback。

## 6. 写 Provider Webhook 路由

OpenCreator 对照：

`apps/api/src/routes/provider-webhooks.ts`

Webhook 路由负责：

```text
读取 provider path
读取 raw/body/headers
调用 ProviderWebhookService.handleWebhook()
返回 2xx 或明确错误
```

这层只做 HTTP 入口，不直接写任务状态。

完成标准：厂商 Webhook 能进入 AI API，并把 provider 名、payload、headers 交给 service。

## 7. 写 ProviderWebhookService

OpenCreator 对照：

[provider-webhook-service.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-webhook-service.ts)

核心顺序：

```text
coerceJsonWebhookBody()
  → parseCoreProviderWebhook()
  → resolveTask()
  → isSameProviderAttempt()
  → normalizeCoreProviderResult()
  → record provider event
  → applyProviderResult()
  → enqueue artifact-processing 或 fallback
```

必须处理：

- payload 是字符串 JSON。
- `data` 字段是 JSON 字符串。
- 找不到任务。
- 旧 attempt 迟到。
- 任务已被轮询处理。
- 同一 Webhook 重放。

完成标准：Webhook 和 polling 同时到达时，只会有一条路径推进任务。

## 8. 写 provider event 记录

OpenCreator 对照：

- [provider-event-repository.ts](../../../../../opencreate/opencreator-ai/packages/db/src/provider-event-repository.ts)
- [provider-webhook-service.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-webhook-service.ts)

事件落库在 repository。service 用 `event.inserted` 决定要不要继续推进任务。

每个 Webhook event 要记录：

```text
ai_task_id
provider
provider_request_id
event_id
event_type
provider_status
normalized_status
raw_summary
signature_verified
received_at
```

`event.inserted` 用来判断是否是新事件。重复事件不应该重复推进 artifact 队列。

完成标准：同一个 event id 重放，不会导致重复回调 Consumer。

## 9. 写 artifact store

OpenCreator 对照：

`packages/storage/*`

artifact store 提供：

```text
processResult(task.result)
```

第一轮可以是 pass-through，但接口要先留好，因为不同 Provider 的 `normalizeResult()` 可能已经上传了媒体，也可能只是返回了临时 URL。

完成标准：成功结果经过 artifact store 后，仍能得到稳定的 result 结构。

## 10. 写 artifact worker

OpenCreator 对照：

[artifact-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/artifact-worker.ts)

成功任务：

```text
updateStatus(processing_artifacts)
  → artifactStore.processResult()
  → updateResult()
  → updateStatus(callback_pending)
  → enqueue consumer-callback
```

失败任务：

```text
status=failed
  → skip artifact processing
  → updateStatus(callback_pending)
  → enqueue consumer-callback
```

完成标准：成功和最终失败都会进入 consumer-callback 队列。

## 11. 写 Webhook payload 契约

OpenCreator 对照：

[webhook.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/webhook.schema.ts)

定义两层：

```text
AiTaskWebhookPayload
  → 内部完整 payload

AiTaskPublicWebhookPayload
  → 对 Consumer 的精简 payload
```

对外状态：

```text
success | failed | timed_out | cancelled
```

内部状态：

```text
succeeded | failed | timed_out | cancelled
```

完成标准：对外 payload 不泄漏不必要的内部字段，但保留 Consumer 对单和写结果需要的字段。

## 12. 写 ConsumerCallbackService

OpenCreator 对照：

[consumer-callback.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/consumer-callback.ts)

实现：

```text
deliver(ai_task_id)
  → load task
  → build internal payload
  → build public payload
  → rawBody = JSON.stringify(publicPayload)
  → timestamp
  → signature = HMAC(secret, timestamp + "." + rawBody)
  → POST webhook_url
```

请求头：

```text
content-type: application/json
x-oc-timestamp
x-oc-signature
x-oc-idempotency-key
```

完成标准：Consumer 能用原始 body 验签；2xx 后 AI 侧按 `task.error ? failed : succeeded` 写最终任务状态。

## 13. 写 callback delivery 记录

OpenCreator 对照：

- [callback-delivery-repository.ts](../../../../../opencreate/opencreator-ai/packages/db/src/callback-delivery-repository.ts)
- [consumer-callback.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/consumer-callback.ts)

投递记录落在 repository。`ConsumerCallbackService` 每次请求后写入这条记录。

每次投递都要记录：

```text
ai_task_id
webhook_url
attempt
idempotency_key
rawBody
status
response status / response summary
```

这样 callback 失败后可以排查到底是网络、签名、Consumer 4xx/5xx，还是超时。

完成标准：每次回调成功或失败都有 delivery 记录。

## 14. 写 callback worker 和 DLQ

OpenCreator 对照：

[callback-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/callback-worker.ts)

callback worker 负责：

```text
ConsumerCallbackService.deliver()
  → 成功：job succeeded
  → 失败：BullMQ retry
  → attempts 或 retry window 耗尽
  → markFailed(callback_failed)
  → callback-dlq
  → alert
```

完成标准：Consumer 一直非 2xx 时，任务最终进入 `callback_failed`，并能在 DLQ 查到失败原因。

## 完整验收顺序

按这个顺序验完整链路：

1. provider worker 能从 submit job 读取 `ai_task_id` 并加载任务。
2. Provider submit 成功后，任务写入 `provider_request_id` 和 `waiting_provider`。
3. immediate result 能直接进入 artifact-processing。
4. polling result 能归一化成功或失败。
5. Provider Webhook 能解析、定位 task，并忽略旧 attempt。
6. 同一个 Webhook 重放不会重复推进 artifact 队列。
7. Provider 失败时，有 Robin 就 fallback，没有 Robin 就最终失败。
8. 成功结果进入 `processing_artifacts → callback_pending`。
9. 失败结果跳过产物处理，但也进入 `callback_pending`。
10. Consumer callback payload 的 `success`、`result.output`、`error` 形状正确。
11. HMAC 签名能被 Consumer 用原始 body 验证。
12. Consumer 返回 2xx 后，AI 侧按任务是否有 `error` 进入最终 `succeeded` 或 `failed`。
13. Consumer 非 2xx 或超时会重试。
14. 重试耗尽后任务进入 `callback_failed`，并产生 DLQ 记录。
15. Consumer 能按 `ai_task_id` / `client_context` 对回 invocation。
16. Frontend 只通过 Consumer/Publisher 的 workflow event 看到节点变化，不直接消费 AI task。
