# AI 提交、轮询、Webhook、产物与回调全链路笔记

这份不是接口清单，是给面试和迁移用的链路笔记。要讲清楚的不是“厂商返回了 JSON”，而是 `queued` 的 `ai_task` 如何提交给 Provider，三条结果入口如何收成同一份 `ProviderResult`，产物和失败如何都进入 `callback_pending`，以及精简 payload 如何签名投递给 Consumer。

先把一句话背下来：

provider worker 把任务送到厂商；polling 和厂商 Webhook 把结果收成 `ProviderResult`；artifact worker 把结果整理到 `callback_pending`；callback worker 把精简 payload 签名投递给 Consumer。AI 网关到此为止，画布节点由 Consumer 往后推。

## 0. 先分清五件事

`Provider submit`：把 AI 任务交给一家厂商，写下 `provider_request_id`，状态进入 `waiting_provider`。

`Provider result`：`immediateResult`、轮询、厂商 Webhook 三条入口收成的统一结果。厂商原始 JSON 不能直接穿透到 Consumer。

`Artifact processing`：成功任务整理产物；失败任务跳过整理。两边都进入 `callback_pending`，再投入 consumer-callback 队列。

`Consumer callback`：对建单时保存的 `webhook_url` 做 HMAC 投递。`2xx` 只表示 Consumer 收下了 HTTP。

`Workflow event`：Consumer 把回调挂回 invocation 并推进 DAG 之后，Publisher / Frontend 才看见节点变化。它们不接厂商 Webhook，也不轮询 `ai_task`。

## 1. submit job 只带任务 ID

`provider-execution` 的 submit job 只有：

```text
ai_task_id
skip_providers?
```

worker 先 `requireByAiTaskId()` 回库读完整任务，再拿 `model_id`、`options`、`webhook_url` 去 `submitCoreTask()`。重试和 fallback 都以任务文档为准。

提交成功后写下：

```text
provider
provider_model_id
provider_request_id
provider_status
result_mode
attempt
```

状态变成 `waiting_provider`。这表示已经交给某一家厂商，后面等同步结果、轮询或厂商回调。

## 2. 三条入口收成同一份 ProviderResult

```text
immediateResult
  → submit() 当场带了最终结果，worker 立刻 normalize

polling
  → worker 调 getResult()，再 normalizeResult()

provider webhook
  → POST /v1/provider-webhooks/:provider
  → ProviderWebhookService.handleWebhook()
```

三条路都走 `applyProviderResult()`。成功通常把结果写入任务并进入 artifact-processing。仍在处理中则保持 `waiting_provider`，不入产物队列。

厂商 Webhook 还要过两道闸：

```text
parseCoreProviderWebhook()
  → 按 ai_task_id 或 provider_request_id 找到任务
  → provider event 去重，重复 event 不再推进
  → isSameProviderAttempt()
  → 任务已经离开 waiting_provider 就忽略
```

`isSameProviderAttempt()` 对的是当前 provider、厂商模型 ID、`provider_request_id` 和 attempt。Robin 换家之后，旧厂商迟到的 Webhook 不能覆盖新 attempt。轮询已经把任务推走时，重复 Webhook 只回接受，不再次入队。

## 3. Webhook 模式也可能被轮询兜底

参考实现里，`result_mode=webhook` 不代表 worker 提交完就一定退出。后面还有 Robin，而且当前 call 实现了 `getResult()` 时，worker 会轮询兜底：厂商把 Webhook 弄丢了，任务不能永远停在 `waiting_provider`，否则下一家永远轮不到。

最后一家、没有 `getResult()` 的纯 Webhook，job 可以返回。任务停在 `waiting_provider`，等厂商回调或外部补偿。厂商永不回调、又没有补偿时，任务会一直停在这里。

## 4. Provider 失败要先看还有没有下一家

```text
当前 call 失败
  → 记下 attempt
  → addRobinSkipProvider(provider:model_id)
  → 还有剩余 call：再入一条带 skip_providers 的 submit job
  → 没有剩余 call：写成最终 failed，进入 artifact-processing
```

所以内部的 `failed` 之后，fallback 还可能回到 `waiting_provider`。`TASK_STATUS_ORDER` 没有接进这些写路径，排障要连 attempt、skip 和 callback 一起看。

最终失败也会通知 Consumer。失败在 artifact worker 里跳过产物处理，直接改成 `callback_pending`。

## 5. artifact worker 把两边都送到可回调

成功：

```text
processing_artifacts
  → artifactStore.processResult()
  → updateResult()
  → callback_pending
  → enqueue consumer-callback
```

失败：

```text
failed
  → 跳过 processResult()
  → callback_pending
  → enqueue consumer-callback
```

媒体上传可能已经发生在 Provider `normalizeResult()` 使用的 uploader 里。参考实现的 artifact worker 使用 `PassThroughArtifactStore`，负责整理并持久化结果，不默认再上传一遍。

## 6. 给 Consumer 的是精简 payload

内部是 `AiTaskWebhookPayload`，对外是 `AiTaskPublicWebhookPayload`。

```text
内部成功状态 succeeded
  → 对外 success

内部 failed | timed_out | cancelled
  → 对外同名
```

参考口径里，对外结果收成 `result.output: string[]`：媒体优先用处理后的 artifact URL，文本包成单元素数组。内部 telemetry、raw summary 不整包外传。拿到回调不能反推出完整 `ai_task`。

投递头：

```text
content-type: application/json
x-oc-timestamp
x-oc-signature
x-oc-idempotency-key
```

签名是 HMAC-SHA256，内容是 `timestamp + "." + rawBody`，密钥是 `consumerWebhookSecret`。Consumer 必须用收到的原始 body 验签。重新 `JSON.stringify` 之后的字符串对不上。

## 7. 2xx 之后才写最终状态，耗尽才进 DLQ

callback worker 调 `deliver(ai_task_id)`。网络错误、超时、Consumer 非 2xx 都按 attempts 和 retry window 重试。

次数或窗口耗尽：

```text
markFailed()
  → status=callback_failed
  → callback-dlq
  → alert
```

`callback_failed` 是通知没送到，模型结果仍留在 AI 文档里。现码不会自动再挂回 Consumer，要运维补偿。

Consumer 返回 2xx 之后，最终状态看任务上有没有 `error`：

```text
有 error → failed
没有 error → succeeded
```

失败任务也可以被成功投递。投递成功和模型成功是两件事。

## 8. Consumer 对单是另一层

AI 侧只知道 HTTP 是否 2xx。Consumer 入口是：

```text
POST /callbacks/models/{vendor}
```

入口验签、检查 timestamp、用 `x-oc-idempotency-key` 去重，再按这些字段找 invocation：

```text
ai_task_id / external_task_id
trace_id
client_context.result_id
node_id
run_id
```

对上之后写 invocation 结果和终态，再由 DAG 事件推到 Publisher 和前端。对不上就写入 pending callback。pending 表示 Consumer 还没挂上业务单，不表示 AI 投递失败，也不表示 Provider 失败。

## 9. 文件编写顺序

按依赖写，仓储方法放在第一次被调用之前：

```text
结果契约
  → ProviderResult schema
  → task-repository 补提交 / 结果 / skip
  → attempt-repository

Provider 执行
  → provider-worker：提交、immediate、polling、fallback

Webhook 收敛
  → /v1/provider-webhooks/:provider
  → provider-event-repository
  → ProviderWebhookService

产物出口
  → artifact store / artifact-worker

Consumer 回调
  → 对外 webhook schema
  → callback-delivery-repository
  → ConsumerCallbackService / callback worker / DLQ
  → Consumer 验签和对单
```

建单组已经能读写 `ai_task`。这一组补的是提交、结果和 skip，不是再造一张任务表。

## 10. 面试 1 分钟口述

`queued` 任务进 provider worker 后，只按 `ai_task_id` 回库，再按 Robin 提交一家，写下 `provider_request_id`，状态变成 `waiting_provider`。结果有三条入口：submit 上的 `immediateResult`、worker 轮询、厂商 Webhook。它们都先收成 `ProviderResult`。Webhook 要去重，还要确认是当前 attempt；旧厂商迟到的回调不能覆盖已经 fallback 的新尝试。后面还有 Robin 且实现了 `getResult()` 时，参考实现会用轮询兜底，避免 Webhook 丢失后永远等不到下一家。成功走产物整理，失败跳过产物，两边都到 `callback_pending`。callback worker 用 `timestamp.rawBody` 做 HMAC，POST 建单时的 `webhook_url`。对外成功状态是 `success`。Consumer 回 2xx 后，有 `error` 就写 `failed`，否则写 `succeeded`。投递耗尽写 `callback_failed` 并进 DLQ，那是通知失败。画布不接这条回调，Consumer 对上 invocation 之后才推 workflow event。

## 11. 面试官追问怎么答

如果问为什么 job 里只有 `ai_task_id`：

重试、fallback 和排障都要读数据库里的最新任务。job 里复制一份 options，会出现两份事实。

如果问轮询和 Webhook 同时到了怎么办：

谁先把任务推进离开 `waiting_provider`，另一边看到已经处理过就退出。Webhook 还有 event id，同一事件重放不会再次进入 artifact 队列。

如果问 Webhook 模式为什么还要轮询：

参考实现里，后面还有下一家、而且这条 call 有 `getResult()` 时，轮询是兜底。它防止厂商回调丢失后，Robin 永远没有机会。最后一家纯 Webhook 可以停在 `waiting_provider` 等回调。

如果问失败了为什么还要回调 Consumer：

DAG 需要知道这个节点失败了。artifact worker 对最终失败跳过产物处理，但仍然投递。Consumer 回 2xx 后，AI 侧因为任务上有 `error`，最终状态仍是 `failed`。

如果问 `callback_failed` 和 `failed` 的区别：

`failed` 是模型或 Provider 链路的结果。`callback_failed` 是这份结果没有送到 Consumer。文档里的结果还在，要补偿重投，不是再打一次厂商。

如果问前端能不能直接看 `ai_task.status`：

不能。前端看的是 Consumer 发布、Publisher 推送的 workflow event。厂商 Webhook 只进 AI API。

如果问验签为什么必须用原始 body：

签名覆盖的是发出去的那一串字节。Consumer 解析后再序列化，键顺序和空格都会变，HMAC 会对不上。

## 12. NovelComic 当前实现自查

类和测试已经把提交、轮询、Webhook 收敛、产物、签名投递和 DLQ 串起来。运行进程只接上了其中一段。

- `apps/worker` 在跑 `ProviderWorkerProcessor` 和 `ArtifactWorkerProcessor`。submit 成功会 `markProviderSubmitted()`，状态进入 `waiting_provider`。`immediateResult` 和 `result_mode=polling` 会归一化并投入 artifact 队列。产物库用的是 `PassThroughArtifactStore`，不在这一步把媒体再上传一遍。
- 这个 worker 没有注入 attempt repository，`upsertAttempt()` 在进程里不会写。`consumer-callback` 队列创建了，进程里没有对应的 callback worker。`CallbackWorkerProcessor`、HMAC 和 DLQ 在代码和验收测试里，没有挂到 `apps/worker` 的启动路径。
- API 注册了 `POST /v1/provider-webhooks/:provider`，但 `apps/api` 构造的是没有 repository 的 `ProviderWebhookService`。这条路由解析后直接 `202`，不会 `applyProviderResult()`，也不会入 artifact 队列。把 repository 和 event repository 注入之后，服务才会做同 attempt 校验、event 去重，并忽略已经离开 `waiting_provider` 的任务。
- worker 只在 `result_mode === 'polling'` 时调用 `getResult()`。参考笔记里的 “webhook 且后面还有 Robin 就轮询兜底” 还没写进 `resolveProviderResult()`。当前 KIE 图像 call 是 `webhook`，提交后任务停在 `waiting_provider`，等厂商回调。回调入口又还没接上仓储。
- 还有下一家时，`markProviderFailedAttempt({ has_fallback: true })` 把状态写成 `queued`，并把 `provider:model_id` 放进 skip 后重新入队。没有 `addRobinSkipProvider()`。没有下一家才写成 `failed`。这和参考路径里的 `failed → waiting_provider` 不是同一套状态字。
- 对外状态会把内部 `succeeded` 收成 `success`。`result.output` 在当前 schema 里是可选字符串，旁边可以有 `artifacts`。参考笔记里的 `result.output: string[]` 还没按那个形状收口。签名是 `timestamp.rawBody` 的 HMAC-SHA256。
- Consumer 有 `POST /callbacks/models/{vendor}`。验签用原始 body，并检查 timestamp。对不上 invocation 时写入 `pending_model_callbacks`。对上之后用 idempotency key 和 invocation 终态避免重复写。`consumer_webhook_secret` 为空时，验签函数直接通过，配了密钥才真正校验。

验收要分成三层：类和测试是否覆盖三条入口、去重、签名、DLQ；worker 进程是否真的提交并整理产物；API 和 callback worker 是否把 Webhook 和 Consumer 投递接上。只看到 `waiting_provider` 和一条 202，不能算结果闭环已经在跑。
