# AI 模型注册、Provider 与 Robin 全链路笔记

这份不是模型清单，是给面试和迁移用的链路笔记。要讲清楚的不是“下拉里有一个模型名”，而是一个 `model_id` 如何收成 registry ID，`CORE_MODELS` 为什么才是可执行权威，一条 Provider call 必须带上什么，以及 Robin 为什么只是按数组顺序换下一家。

先把一句话背下来：

Publisher / Frontend 的模型目录决定用户看见什么；Consumer 决定业务节点传什么 `model_id`；`opencreator-ai` 的 `CORE_MODELS` 决定这个 ID 到底能不能执行、找哪家 Provider 执行。

## 0. 先分清四个东西

`产品模型目录`：Publisher / Frontend 用来展示、分组、定价、排序和控制可见性。

`Consumer 模型映射`：把业务节点上的模型名或 `config_name` 转成 AI registry ID，再把节点参数收成 `options`。

`AI registry`：`CORE_MODELS` 里真正可执行的 `CoreModelEntity`。没放进这个数组，就不算已注册。

`Provider call`：某个模型到某个厂商模型的一条执行配置。它不是一次任务 attempt。attempt 是 worker 真正提交之后写下的记录。

面试时一定要把这四个东西讲开。Robin 是 `robin_calls` 的有序 fallback，不是随机、加权、并发竞速或负载均衡。

## 1. `CORE_MODELS` 是执行权威源

AI 网关能执行哪些模型，最终看静态数组 `CORE_MODELS`。每一项是 `CoreModelEntity`：

```text
id
aliases
displayName
robin_calls
```

`displayName` 只是 registry 里的展示名，不等于产品目录里的价格、排序、分组和可见性。模型文件写了、前端目录有了、Consumer 映射有了，只要没 import 进 `CORE_MODELS`，AI 网关就不认识。registry 编译进进程，新增模型要发布 AI 服务，不是后台改配置立刻生效。

参考文档里的“180 个模型、23 个 Provider”只描述当时代码快照，不要当成长期常量。

## 2. `CoreProviderCall` 才是一条可执行路径

`CoreProvider` 是 AI core 认可的厂商名，例如 `fal`、`openai`、`kling`。它是执行适配层，不是产品展示分类。一个产品模型可以挂多条 Provider fallback；同一个 Provider 也可以承载多个厂商模型 ID。

每个 `robin_calls` 元素至少要有：

```text
provider
model_id
options_schema
result_mode
submit()
getResult?()
normalizeResult()
```

- `provider`：AI core 内部 Provider 名。
- `model_id`：厂商侧模型 ID，不是 registry 的规范 ID。
- `options_schema`：这一条 call 接受的参数形状。
- `result_mode`：结果从 webhook 来，还是要轮询。
- `submit()`：真正提交给厂商。
- `getResult()`：轮询或兜底时读结果。
- `normalizeResult()`：把厂商原始结果收成统一 `ProviderResult`。

所以“注册一个模型”不是只加一个名字。没有 `submit` 和 `normalizeResult`，后面的任务仓储、artifact worker 和 Consumer 回调无法判断成功、失败、媒体 URL 和错误码。

## 3. 别名只解决入口兼容

Consumer 可以传规范 ID，也可以传别名。`resolveCoreModelId()` 查找：

```text
entry.id === model_id
  或 entry.aliases 包含 model_id
```

命中就返回规范 `entry.id`。不命中时当前实现原样返回，真正失败推迟到 `requireCoreModel()`。OpenCreator 未注册时的口径是 `Model is not registered`，错误码 `3008`。

别名只打通旧模型名、产品层命名和 registry 命名。它不是另一个独立模型。

建单可以先收别名。Provider worker 打厂商前还要再 `requireCoreModel()`。前端目录、Publisher 配置、Consumer 映射都不能代替这一步。

## 4. 参数 schema 跟选中的 Provider call 绑定

`validateCoreModelOptions()` 定义在 `model-runtime.ts`。默认用 `robin_calls` 第一条 call 的 `options_schema`。

如果请求用 `options.provider` 钉死 Provider，先确认这家在当前模型的 `robin_calls` 里，再用那一条 call 的 schema。钉死后不能继续用第一家的 schema。

`model-constraints.ts` 和 `model_constraints.json` 是另一层输入限制：尺寸、时长、格式、文本长度、Provider retry。它们给提交前预校验用，不替代 call 自己的 `options_schema`。JSON 里即使有历史 `pricing` 字段，也不能当成产品售价的权威源。价格、权益、排序仍在 Publisher / Frontend。

参数校验失败时，不应该落成可执行任务。

## 5. `options.provider` 是显式钉死，不是透传字段

```text
extractRequestedProviderFromOptions()
  → trim + lower
  → 确认 Provider 在 robin_calls 内
  → 只选这一家
```

真正进厂商 API 前，`stripProviderFromOptions()` 把 `provider` 从 options 拿掉。上游只收业务参数，不收 OpenCreator 的内部路由字段。

钉死之后失败不会换到别的 Provider。`getRemainingRobinProviders()` 直接返回空数组。

## 6. Robin 按数组顺序换下一家

顺序就是 `robin_calls` 数组顺序：

```text
robin_calls[0]
  → robin_calls[1]
  → robin_calls[2]
```

`submitCoreTask()` 会：

```text
requireCoreModel(model_id)
  → 读取 options.provider
  → 按顺序滤掉 skip_providers
  → 调第一条剩余 call.submit()
```

失败后，worker 把精确 call 写进跳过集合：

```text
provider:model_id
```

再创建带新 `skip_providers` 的 fallback job。跳过粒度是 Provider 加厂商模型 ID，不只是 Provider 名。同一个 Provider 的另一个 `model_id` 仍然可以是下一条 fallback。

没有剩余 call，或者请求已经钉死 Provider，就走最终失败，不再换厂商。

## 7. `result_mode` 只有 webhook 和 polling

`CoreProviderResultMode` 在参考实现里只有：

```text
webhook
polling
```

同步拿到最终结果的 Provider 不另开第三种模式，而是在 `submit()` 返回里带 `immediateResult`。轮询兜底预先拿到的首次结果用 `firstPollResult`。它们是 submit 返回上的附加结果，不是 Provider call 的模式。

## 8. Provider worker 只负责按任务提交

worker 从队列拿到：

```text
ai_task_id
skip_providers?
```

然后回库读任务，调用 `submitCoreTask()`。成功后写下：

```text
provider
provider_model_id
provider_request_id
provider_status
result_mode
attempt
```

并把任务推进到 `waiting_provider`。Provider client 只讲厂商协议，不知道产品目录，也不知道 Consumer 的 node invocation。轮询、Webhook 收敛、产物和回调不在本篇展开。

## 9. Consumer 映射是桥，不是权威

提交前 Consumer 做：

```text
业务节点模型名 / config_name
  → OpenCreatorAIModelMapper.to_opencreator_model_id()
  → OpenCreatorAIOptionsBuilder.build()
  → POST /v1/tasks
```

映射解决业务层名字和 registry ID 的差异。options builder 要和选中 call 的 `options_schema` 对齐：字段名、类型、必填项，以及可选的 `provider` 钉死字段。映射错了，或 options 对不上，最终仍会被 AI 侧 `requireCoreModel()` / `validateCoreModelOptions()` 拦住。

`client_context` 把 run、节点、result 等业务上下文交给网关保存，回调时带回来。网关不拿它做模型路由。

## 10. 产品目录不能反推可执行

产品目录回答：用户能看到什么、节点里显示什么名字、价格和权益是什么、哪些模型对当前用户可见。

AI registry 回答：这个 `model_id` 是否注册、参数能不能过 schema、能走哪些 Provider、失败后能不能换下一家、结果怎么归一化。

两边可以对齐，不能合成一张表，也不能互相反推。产品目录有模型，不代表 registry 可执行；registry 有模型，也不代表目录必须展示。Agent 自己的聊天模型集合也不要和画布目录、AI registry 合并统计。

如果把产品目录当成执行 registry，会出现三件事：前端能选但网关不认识；网关能执行但没有价格和展示配置；Consumer 映射和 registry ID 不一致，运行时才失败。

## 11. 文件编写顺序

按五段迁移，不要从大前端模型表开始：

```text
AI core 类型
  → CoreProvider / CoreModelEntity / CoreProviderCall

Provider 适配
  → client / result normalizer

模型注册
  → 单个模型文件 / CORE_MODELS

运行时选择
  → model-runtime / constraints / Robin / provider-worker

跨仓目录和映射
  → Consumer mapper / options builder / Publisher catalog / Frontend catalog
```

第一轮只接一家 Provider、一条 `robin_calls`。单条跑通 submit 和 normalize 之后，再加第二条做 fallback，最后才让产品目录和这条 registry ID 对齐。删掉任一边，验收要能指出失败在目录、映射还是 registry。

## 12. 面试 1 分钟口述

OpenCreator 的模型能不能打厂商，不看前端下拉，看 `CORE_MODELS`。每个模型是一个 `CoreModelEntity`，里面按顺序挂 `robin_calls`。每条 call 带厂商名、厂商模型 ID、参数 schema、`webhook` 或 `polling`，以及 `submit`、可选的 `getResult` 和 `normalizeResult`。Consumer 先把业务模型名映射成 registry ID，再把节点参数收成 options。建单时 `resolveCoreModelId()` 收别名，`validateCoreModelOptions()` 用选中那条 call 的 schema 验参。worker 打厂商前 `requireCoreModel()`，未注册就是 `Model is not registered`。`submitCoreTask()` 从第一条没被 `skip_providers` 跳过的 call 开始提交，跳过键是 `provider:model_id`。`options.provider` 会把路线钉死，失败后不再换厂商，并且这个字段不会透传给上游。Robin 只是数组顺序 fallback。产品目录管展示和价格，不管能不能执行。

## 13. 面试官追问怎么答

如果问模型文件写了为什么还是未注册：

registry 的权威是 `CORE_MODELS` 这个数组，不是目录扫描。没 import、没放进数组，`requireCoreModel()` 找不到。

如果问 Robin 是不是选最快的那家：

不是。它按 `robin_calls` 从前往后试。失败才跳过精确的 `provider:model_id`，再试下一条。没有权重，也没有并发。

如果问钉死 Provider 之后第一家挂了会不会自动换：

不会。`getRemainingRobinProviders()` 在请求带了 `options.provider` 时返回空。这是显式指定，不是建议。

如果问为什么跳过键要带厂商模型 ID：

同一个 Provider 下面可以有多个 `model_id`。只跳过 Provider 名，会把同一家还能用的另一条 call 一起禁掉。

如果问 `model_constraints.json` 里的价格能不能当售价：

不能。那份数据服务输入限制和 Provider 能力。售价、权益、排序以 Publisher / Frontend 产品目录为准。

如果问同步模型为什么没有 `sync` 这个 result mode：

参考实现把同步结果放在 `submit()` 的 `immediateResult` 上。`result_mode` 只区分后面要等 webhook，还是要自己轮询。

如果问 Consumer 映射成功是不是就一定能执行：

不是。映射只是跨仓桥。最终注册和参数校验仍在 AI registry。

## 14. NovelComic 当前实现自查

本章运行时已经有一条最小可执行模型，Robin 和钉死 Provider 的代码路径也在。它还不是 OpenCreator 那张大 registry。

- `CORE_MODELS` 目前只有 `kie-image-v1`。别名是 `kie-image`、`z-image`。唯一一条 call 是 `kie:z-image`，`result_mode` 为 `webhook`，带 `submit`、`getResult` 和 `normalizeKieResult`。没放进数组的模型不会被 `requireCoreModel()` 找到。
- 未注册抛 `CoreModelNotRegisteredError`，code 是 `MODEL_NOT_REGISTERED`，文案是 `Model is not registered`。当前实现没有数字错误码 `3008`。
- `validateCoreModelOptions()` 用选中 call 的 `options_schema`。没钉 Provider 时用第一条；钉了就用那一家，校验前拿掉 `provider`，校验通过后再把这个控制字段放回任务 options。真正 `submit()` 前会再次 `stripProviderFromOptions()`。
- `submitCoreTask()` 按 `provider:model_id` 跳过 `skip_providers`。`getRemainingRobinProviders()` 在 options 里有 `provider` 时返回空。worker 失败后把 `provider:model_id` 写入 skip，再投入带 `skip_providers` 的 submit job。
- 当前这张注册表只有一条 call，所以线上的 KIE 图像没有第二家可换。fallback 机制在 worker 里，第二条 call 还没注册。
- 类型里的 `CoreProviderResultMode` 写成了 `sync | polling | webhook`。worker 仍把 submit 返回上的 `immediateResult` 当成当场结果。参考笔记里的模式只有 `webhook` 和 `polling`，同步结果不另开 mode。
- Consumer `OpenCreatorAIModelMapper` 只认识 `kie-image-v1`、`kie-image`、`z-image`，以及若干 config 下的 `default`。表里没有的名字直接抛 `MissingOpenCreatorAIModelMapping`，到不了 AI。`OpenCreatorAIOptionsBuilder` 把节点参数收成 options，prompt 和若干别名字段对齐 KIE schema。
- Publisher 内置目录有 `text_to_image_config` / `kie-image-v1`。前端 `LOCAL_CLOUD_MODEL_DATA` 用同一个 ID。这是展示配置，不是 `CORE_MODELS`。`model_constraints.json` 记的是 prompt 长度、输入模态和 KIE retry，不决定售价。

验收要分开看：类型和 normalizer、模型是否进了 `CORE_MODELS`、别名和未注册错误、钉死 Provider 不 fallback、worker 能写下 `provider_request_id` 并把任务推进到 `waiting_provider`、Consumer 映射和 options 能过 AI 校验、产品目录 ID 和 registry ID 对得上。只在下拉里看到 “KIE Image”，不能算 Provider call 已接通。
