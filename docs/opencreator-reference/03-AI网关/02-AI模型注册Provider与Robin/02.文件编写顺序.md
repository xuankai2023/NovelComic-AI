# AI 模型注册、Provider 与 Robin：文件编写顺序

这篇只回答一个问题：NovelComic 如果要照 OpenCreator 接上 AI 模型注册、Provider call 和 Robin fallback，应该先写哪些文件、每一步完成到什么程度。

运行时原理见 [01-AI模型注册Provider与Robin.md](./01-AI模型注册Provider与Robin.md)，机制拆解见 [00-AI模型注册Provider与Robin技术点.md](./00-AI模型注册Provider与Robin技术点.md)。本文按依赖排序，不按用户在前端选择模型的顺序排序。

命名约定：

- AI 服务路径默认按 OpenCreator 的 `opencreator-ai/` 写。
- Consumer 路径默认按 OpenCreator 的 `opencreator-consumer/` 写。
- Publisher/Frontend 的模型目录只在后面接入，不作为 AI registry 的第一步。

本组目标不是“前端下拉里出现模型”，而是 AI core 里真正有可执行模型：

```text
CoreProvider / CoreProviderCall
  → 定义 Provider 和一条可执行调用

CoreModelEntity / CORE_MODELS
  → 把模型注册进 AI 执行表

model-runtime
  → 收别名、验注册、选 Provider、跑 Robin

Consumer mapper / options builder
  → 把业务节点模型接到 AI registry
```

---

## 总体顺序

```text
packages/core/src/types.ts
  → packages/core/src/provider/{provider}_client.ts
  → packages/core/src/provider/{provider}_result.ts
  → packages/core/src/models/{model}.ts
  → packages/core/src/models/index.ts
  → packages/core/src/model-runtime.ts
  → packages/core/data/model_constraints.json
  → packages/core/src/model-constraints.ts
  → packages/runtime/src/provider-worker.ts
  → opencreator-consumer/services/opencreator_ai/model_mapper.py
  → opencreator-consumer/services/opencreator_ai/options_builder.py
  → opencreator-consumer/model_gateway/providers/opencreator_ai.py
  → opencreator-publisher/controller/v1/models.py
  → opencreator-frontend/src/constants/availableModelInstances.tsx
```

可以按五段推进：

```text
AI core 类型
  → types.ts

Provider 适配
  → provider client / result normalizer

模型注册
  → model file / CORE_MODELS

运行时选择
  → model-runtime / constraints / provider-worker

跨仓目录和映射
  → Consumer mapper / Publisher catalog / Frontend catalog
```

---

## 写之前必须已有

这些能力不在本文新写范围内，但缺少任何一项，后续链路都会对不上：

1. AI 任务契约已经能创建 `ai_task`，并把 submit job 写入队列。
2. AI 服务能读取配置和 Provider 凭据。
3. 至少选定一个真实 Provider 作为第一条接入对象。
4. 已经知道这个 Provider 的提交接口、结果接口或 Webhook 格式。
5. 已经约定 AI 统一结果 `ProviderResult` 的成功、失败和媒体字段。
6. Consumer 已经能构造 `model_id` 和 `options`。

完成基线：队列里的 provider worker 能按 `ai_task_id` 读回任务，但还可以没有任何真实 Provider call。

## 1. 先写 AI core 类型

OpenCreator 对照：

[types.ts](../../../../../opencreate/opencreator-ai/packages/core/src/types.ts)

先定义所有后续文件都要依赖的类型：

```text
CoreProvider
CoreModelEntity
CoreProviderCall
CoreProviderResultMode
CoreSubmitResult
CoreRunContext
```

最核心的形状：

```text
CoreModelEntity
  → id
  → aliases
  → displayName
  → robin_calls

CoreProviderCall
  → provider
  → model_id
  → options_schema
  → result_mode
  → submit()
  → getResult?()
  → normalizeResult()
```

完成标准：可以写出一个内存里的 fake model 和 fake provider call，并通过 TypeScript 类型检查。

---

## 2. 写第一个 Provider client

OpenCreator 对照：

`packages/core/src/provider/*_client.ts`

先选一个 Provider，不要一开始铺开 20 多家。Provider client 只负责和上游 API 通信：

```text
submit()
poll 或 getResult()
cancel?()
parse webhook?()
```

它不应该知道 Publisher 产品目录，也不应该知道 Consumer node invocation。它只处理厂商协议。

完成标准：给定配置和参数，能向 Provider 发出一次请求，并拿到厂商 request id 或同步结果。

---

## 3. 写 Provider result normalizer

OpenCreator 对照：

`packages/core/src/provider/*_result.ts`

每个 Provider 都要把厂商结果归一成 AI 网关统一结果：

```text
ParsedProviderResult
  → ProviderResult
```

至少要统一：

- 成功还是失败。
- 错误码和错误消息。
- 输出媒体 URL 或文本。
- 原始结果摘要。
- 是否仍在等待 Provider。

完成标准：Provider 返回成功、失败、处理中三类响应时，都能得到稳定的统一结果。

---

## 4. 写第一个模型文件

OpenCreator 对照：

[models 目录](../../../../../opencreate/opencreator-ai/packages/core/src/models)

先写一个最小模型：

```text
export const XxxModel: CoreModelEntity = {
  id: "...",
  aliases: [...],
  displayName: "...",
  robin_calls: [
    {
      provider: "...",
      model_id: "...",
      options_schema: ...,
      result_mode: "webhook" | "polling",
      submit,
      getResult?,
      normalizeResult
    }
  ]
}
```

第一轮只需要一条 `robin_calls`。等单 Provider 跑通后，再加第二条做 fallback。

完成标准：模型文件能被单测直接 import，`options_schema` 能校验合法/非法 options。

---

## 5. 把模型放进 `CORE_MODELS`

OpenCreator 对照：

[models/index.ts](../../../../../opencreate/opencreator-ai/packages/core/src/models/index.ts)

把模型 import 并加入：

```text
export const CORE_MODELS = [
  XxxModel
]
```

不要只创建模型文件却忘了加入数组。AI registry 的权威是 `CORE_MODELS`，不是目录扫描。

完成标准：`CORE_MODELS` 能列出新模型；没加入数组的模型不会被 `requireCoreModel()` 找到。

---

## 6. 写模型约束数据

OpenCreator 对照：

[model_constraints.json](../../../../../opencreate/opencreator-ai/packages/core/data/model_constraints.json)

这份数据用于模型能力和输入限制。OpenCreator 当前文件里也有 `pricing` 等历史字段，但写 NovelComic 的执行链路时，不要把它当成产品模型目录的权威源。

可以记录：

- 输入类型。
- 尺寸、时长、数量、文本长度。
- 枚举选项。
- Provider 特殊限制。

产品侧信息仍应以 Publisher/Frontend 目录为准：

- 售价。
- 前端排序。
- 用户权益。
- 产品分组。

完成标准：约束数据能被运行时读取，和模型 `options_schema` 不冲突；产品目录字段即使存在，也不作为 AI registry 是否可执行的判断依据。

---

## 7. 写模型约束读取

OpenCreator 对照：

[model-constraints.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-constraints.ts)

实现或补齐约束读取：

```text
getModelConstraints()
getProviderEntry()
updateModelConstraintsConfig()
```

这层只负责约束配置，不负责选择 Provider call。Provider call 的参数 schema 校验在下一步 `model-runtime.ts` 里完成。

完成标准：运行时可以按模型 ID 或展示名查到约束；Provider retry 配置也能通过 Provider ID 查到。

---

## 8. 写模型运行时

OpenCreator 对照：

[model-runtime.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-runtime.ts)

这一层先写这些函数：

```text
listCoreModels()
resolveCoreModelId()
requireCoreModel()
validateCoreModelOptions()
extractRequestedProviderFromOptions()
stripProviderFromOptions()
getRemainingRobinProviders()
submitCoreTask()
```

其中 `validateCoreModelOptions()` 的规则是：

```text
没有 options.provider
  → 用默认第一条 Provider call 的 options_schema

有 options.provider
  → 确认 Provider 在 robin_calls 内
  → 用该 Provider call 的 options_schema
  → 校验后保留 provider 控制字段
```

其他核心行为：

```text
resolveCoreModelId()
  → id 或 aliases 命中就返回规范 id

requireCoreModel()
  → 查 CORE_MODELS，不存在就抛未注册错误

submitCoreTask()
  → 选择 ordered calls
  → 跳过 skip_providers
  → 调 call.submit()
```

完成标准：传别名能找到模型；传不存在模型会报 `Model is not registered`；不同 Provider call 可以使用不同 schema；指定 Provider 时只尝试这一家。

---

## 9. 写 Robin fallback

Robin 逻辑仍在模型运行时和 provider worker 之间配合完成。

运行时要支持：

```text
skip_providers: ["provider:model_id"]
```

worker 失败后要能：

```text
记录失败 attempt
  → 判断 getRemainingRobinProviders()
  → 有剩余 Provider 时重新 enqueue submit job
  → 带上新的 skip_providers
```

注意跳过粒度是 `provider:model_id`，不是只跳过 Provider 名。

完成标准：第一家 Provider 失败后，第二家 Provider 会被尝试；如果请求钉死 Provider，则失败后不 fallback。

---

## 10. 接 provider worker

OpenCreator 对照：

[provider-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-worker.ts)

worker 读取任务后调用：

```text
submitCoreTask({
  ai_task_id,
  model_id,
  options,
  webhook_url,
  skip_providers
})
```

提交成功后写：

```text
provider
provider_model_id
provider_request_id
provider_status
result_mode
attempt
```

完成标准：worker 能把一个 `queued` 任务推进到 `waiting_provider`，并写入 Provider request id 和 attempt。

OpenCreator 对照：

[model_mapper.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/model_mapper.py)


这层用于兼容业务旧模型名、配置名和 AI registry ID。

完成标准：每个要走 `opencreator-ai` 的节点模型，都能映射到一个 AI core 认识的模型 ID。

## 12. 写 Consumer options builder

OpenCreator 对照：

[options_builder.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/options_builder.py)

把业务节点参数转成 AI `options`：

```text
ModelProviderRequest
  → options
```

这里要和模型 `options_schema` 对齐：

- 字段名一致。
- 类型一致。
- 必填字段齐全。
- 可选 Provider 钉死字段写成 `provider`。

完成标准：Consumer 组出的 options 可以通过 AI 侧 `validateCoreModelOptions()`。

## 13. 接 Consumer 的 opencreator-ai Provider

OpenCreator 对照：

[opencreator_ai.py](../../../../../opencreate/opencreator-consumer/model_gateway/providers/opencreator_ai.py)

这个 Provider 做完整提交：

```text
OpenCreatorAIModelMapper.to_opencreator_model_id()
OpenCreatorAIOptionsBuilder.build()
OpenCreatorAITaskRequest(...)
OpenCreatorAITaskClient.submit()
```

完成标准：Consumer 的模型节点能创建 AI task，返回的 `external_task_id` 是 `ai_task_id`。

## 14. 最后接 Publisher/Frontend 产品目录

OpenCreator 对照：

- [models.py](../../../../../opencreate/opencreator-publisher/controller/v1/models.py)
- [availableModelInstances.tsx](../../../../../opencreate/opencreator-frontend/src/constants/availableModelInstances.tsx)

等 AI registry 和 Consumer 映射都跑通后，再补产品目录：

```text
Publisher models API
  → Frontend availableModelInstances
  → 节点下拉展示
```

这一步不能反过来作为执行权威。

完成标准：前端可选模型、Consumer 映射和 AI `CORE_MODELS` 三者能对上；删掉其中任一边，验收能明确失败在哪里。

## 完整验收顺序

按这个顺序验完整链路：

1. `CoreProvider` 包含要接入的 Provider。
2. Provider client 能提交一次请求并拿到 request id 或同步结果。
3. Provider normalizer 能归一成功、失败、处理中结果。
4. 单个模型文件包含合法 `CoreModelEntity` 和至少一条 `robin_calls`。
5. 模型被加入 `CORE_MODELS`。
6. `resolveCoreModelId()` 能处理 ID 和 alias。
7. `requireCoreModel()` 对未注册模型返回稳定错误。
8. `validateCoreModelOptions()` 能按默认 Provider 和钉死 Provider 分别校验参数。
9. `submitCoreTask()` 能提交默认第一家 Provider。
10. 第一家失败时，Robin 能跳到下一家；钉死 Provider 时不会 fallback。
11. provider worker 能把任务写到 `waiting_provider`，并记录 Provider request id。
12. Consumer 映射后的 model ID 能被 AI registry 识别。
13. Consumer 构造的 options 能通过 AI 参数校验。
14. Publisher/Frontend 目录展示的模型能和 Consumer 映射、AI registry 对齐。

做完这组后，再继续写 [AI提交轮询Webhook产物与回调](../03-AI提交轮询Webhook产物与回调/14-AI提交轮询Webhook产物与回调.md)。
