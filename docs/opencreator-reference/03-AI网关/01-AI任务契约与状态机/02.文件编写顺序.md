# AI 任务契约与状态机：文件编写顺序

这篇只回答一个问题：NovelComic 如果要照 OpenCreator 接上 AI 任务契约、幂等建单和状态边界，应该先写哪些文件、每一步完成到什么程度。

运行时原理见 [01-AI任务契约与状态机.md](./01-AI任务契约与状态机.md)，机制拆解见 [00-AI任务契约与状态机技术点.md](./00-AI任务契约与状态机技术点.md)。本文按依赖排序，不按用户在画布上看到的顺序排序。

命名约定：

- AI 服务路径默认按 OpenCreator 的 `opencreator-ai/` 写。
- Consumer 路径默认按 OpenCreator 的 `opencreator-consumer/` 写。
- NovelComic 如果后续服务名不同，模块边界保持一致，路径前缀替换即可。

本组目标不是“能调到某个模型”，而是先有一张可靠的 AI 任务单：

```text
Create task contract
  → 严格定义 Consumer 能提交什么

Task state contract
  → 定义 AI 网关内部任务状态

Task repository
  → 幂等创建 ai_task

Task service and route
  → 校验模型、落库、入队、返回 ai_task_id
```

---

## 总体顺序

```text
packages/contracts/src/task-state.ts
  → packages/contracts/src/create-task.schema.ts
  → packages/contracts/src/db.schema.ts
  → packages/core/src/model-runtime.ts
  → packages/core/src/model-constraints.ts
  → packages/db/src/task-repository.ts
  → packages/runtime/src/task-service.ts
  → apps/api/src/routes/tasks.ts
  → packages/runtime/src/state-machine.ts
  → opencreator-consumer/services/opencreator_ai/schemas.py
  → opencreator-consumer/services/opencreator_ai/task_client.py
  → Consumer node invocation 保存 ai_task_id
```

可以按四段推进：

```text
契约
  → task-state / create-task schema / db schema

模型校验
  → model runtime / model constraints

建单服务
  → repository / task service / route

Consumer 接入
  → schemas / task client / invocation 关联
```

Provider 提交、Robin fallback、产物处理、Consumer callback 暂时不要塞进本篇实现顺序。它们依赖这里产出的 `ai_task_id` 和任务文档。

---

## 写之前必须已有

这些能力不在本文新写范围内，但缺少任何一项，后续链路都会对不上：

1. AI 服务能启动，并有 HTTP API 框架。
2. AI 服务能连接 Mongo 或项目当前数据库。
3. AI 服务有队列基础设施，或至少有可替换的 enqueue 抽象；本篇只要求能写入 `provider-execution` 的 submit job，不要求 Provider worker 已完整执行。
4. 已经有模型 registry 的最小数据结构，能判断模型是否存在。
5. Consumer 已经有 node invocation 或等价业务记录。
6. Consumer 能拿到 AI 服务 base URL 和调用凭据。
7. 已经约定 AI 回调 Consumer 的公开 URL 形状。

完成基线：手动发一个最小合法请求，AI API 可以返回结构化 4xx 或 `202 Accepted`，而不是进程报错；即使 Provider worker 还没接完，任务也能稳定落到 `queued`。

## 1. 先写任务状态枚举

OpenCreator 对照：

[task-state.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/task-state.ts)

先定义 AI 网关内部状态：

```text
received
queued
submitted_to_provider
waiting_provider
processing_artifacts
callback_pending
callback_failed
callback_succeeded
succeeded
failed
timed_out
cancelled
ignored
```

同时可以定义：

```text
TERMINAL_TASK_STATUSES
TASK_STATUS_ORDER
```

注意：如果 NovelComic 第一轮只是照 OpenCreator 行为迁移，不要把 `TASK_STATUS_ORDER` 立即做成所有 repository 写入的强制门禁。OpenCreator 当前主链存在 fallback 后离开 `failed` 的事实。

完成标准：其他 contract 和 repository 可以复用同一份状态类型；不能在各文件里散落字符串状态。

---

## 2. 写建任务请求契约

OpenCreator 对照：

[create-task.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/create-task.schema.ts)

定义：

```text
CreateAiTaskRequestSchema
CreateAiTaskRequest
CreateAiTaskResponse
```

请求字段至少包含：

```text
model_id
options
webhook_url
trace_id
idempotency_key
locale
client_context
```

规则：

- `model_id` 必填。
- `options` 必填，且必须是 object。
- `webhook_url` 必填，必须是可回调 URL。
- `trace_id` 可选，但建议 Consumer 总是传。
- `idempotency_key` 可选，但 Consumer 执行节点时应尽量传。
- `client_context` 可选 object，由 Consumer 回调时解释。
- schema 默认严格，不接受未知字段。

完成标准：非法 body 在进入 service 前就被拒绝；合法 body 能得到类型安全的 request 对象。

---

## 3. 写任务数据库形状

OpenCreator 对照：

[db.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/db.schema.ts)

先把建单阶段需要的字段定住：

```text
ai_task_id
status
model_id
core_model_id
options
webhook_url
trace_id
idempotency_key
locale
client_context
created_at
updated_at
```

再预留后续 worker 会写的字段：

```text
provider
provider_request_id
attempts
skip_providers
result
error
callback
```

不要把 workflow run、node status 或前端节点样式塞进 `ai_task`。AI 任务文档只保存 AI 网关事实。

完成标准：repository 能用同一份类型写入和读取任务；后续 worker 不需要猜字段名。

---

## 4. 写模型 ID 归一和 registry 校验

OpenCreator 对照：

[model-runtime.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-runtime.ts)

先实现两个能力：

```text
resolveCoreModelId(model_id)
requireCoreModel(core_model_id)
```

`resolveCoreModelId()` 做别名收敛：

```text
alias
  → core model id
```

`requireCoreModel()` 做最终校验：

```text
core model id
  → registered model entity
  → or throw unknown model
```

完成标准：传入规范 ID 能找到模型；传入别名能收敛；传入不存在的模型会得到稳定错误码或错误对象。

---

## 5. 写模型参数校验

OpenCreator 对照：

[model-constraints.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-constraints.ts)

建单请求里的 `options` 不能只按 object 放过。要按模型二次校验：

```text
validateCoreModelOptions(core_model_id, options)
```

第一轮可以支持最小规则：

- required 字段。
- 字段类型。
- enum。
- number 范围。
- string 长度。
- array item 类型。

完成标准：同一个 `/v1/tasks`，不同 `model_id` 会使用不同 options schema；参数不合法时不落库、不入队。

---

## 6. 写任务仓储和幂等索引

OpenCreator 对照：

[task-repository.ts](../../../../../opencreate/opencreator-ai/packages/db/src/task-repository.ts)

先实现：

```text
createOrGet(input)
getById(ai_task_id)
updateStatus(ai_task_id, status)
```

`createOrGet()` 是核心。行为固定：

```text
有 idempotency_key
  → 按 key 建唯一索引
  → 并发重复请求只能成功创建一条
  → 其他请求返回已有任务

没有 idempotency_key
  → 每次创建新任务
```

索引建议：

```text
ai_task_id unique
idempotency_key unique sparse
trace_id
status
created_at
```

完成标准：并发发送同一个 `idempotency_key`，数据库里只有一条任务；返回值能区分 `created` 和 `existing`。

---

## 7. 写建单服务

OpenCreator 对照：

[task-service.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/task-service.ts)

服务层负责串起前面的能力：

```text
createTask(request)
  → resolveCoreModelId(request.model_id)
  → validateCoreModelOptions(core_model_id, request.options)
  → repository.createOrGet()
  → if created enqueue submit job(ai_task_id)
  → return response
```

入队 payload 保持小：

```text
{
  "ai_task_id": "..."
}
```

不要把 `options`、`webhook_url`、`client_context` 复制进 job。Worker 要按 `ai_task_id` 回库读最新任务事实。

完成标准：合法请求能创建 `queued` 任务；重复幂等请求不重复入队；模型或参数非法时不创建任务。

---

## 8. 写 HTTP 路由

OpenCreator 对照：

[tasks.ts](../../../../../opencreate/opencreator-ai/apps/api/src/routes/tasks.ts)

路由只做四件事：

```text
POST /v1/tasks
  → parse body
  → CreateAiTaskRequestSchema 校验
  → taskService.createTask()
  → 返回 202 或 200
```

响应规则：

```text
新建任务
  → 202 Accepted
  → ai_task_id / status=queued

幂等命中
  → 200 OK
  → ai_task_id / existing=true
```

完成标准：HTTP 不等待 Provider；Provider worker 只有空实现或尚未启动时，建单接口仍能稳定创建 `queued` 任务并写入 submit job。

---

## 9. 写状态检查辅助

OpenCreator 对照：

[state-machine.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/state-machine.ts)

可以先写：

```text
assertTaskStatusCanAdvance(from, to)
isTerminalStatus(status)
```

但是否接入每个写路径要谨慎。照 OpenCreator 当前行为迁移时，先把它作为辅助函数保留，不要贸然强制所有状态单向前进。

原因是后续会有：

```text
waiting_provider
  → failed
  → waiting_provider
```

这是 Provider fallback 的现码事实。

完成标准：测试覆盖允许路径和拒绝路径；文档明确它不是当前所有运行写路径的强制约束。

---

## 10. 写 Consumer 请求 schema

OpenCreator 对照：

[schemas.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/schemas.py)

Consumer 侧定义和 AI 网关对应的请求/响应类型：

```text
CreateTaskRequest
CreateTaskResponse
```

字段和 AI 网关契约保持一致，但职责不同：

- Consumer schema 方便业务组包和类型检查。
- AI contract 负责最终校验和拒绝非法请求。

完成标准：Consumer 能从 node invocation 生成完整请求对象，包含 `webhook_url`、`idempotency_key` 和 `client_context`。

---

## 11. 写 Consumer AI 客户端

OpenCreator 对照：

[task_client.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/task_client.py)

实现：

```text
create_task(request)
  → POST {AI_BASE_URL}/v1/tasks
  → timeout
  → parse response
  → return ai_task_id / status / existing
```

客户端要处理：

- 4xx 参数错误。
- 5xx 服务错误。
- 网络超时。
- 幂等命中的 200。
- 新建任务的 202。

完成标准：本地或测试环境可以从 Consumer 发起一次 AI task 创建，并拿回 `ai_task_id`。

---

## 12. 把 `ai_task_id` 挂回 Consumer invocation

建单成功后，Consumer 不应该只把 `ai_task_id` 打日志。它要写回当前节点调用记录：

```text
node invocation
  → ai_task_id
  → trace_id
  → idempotency_key
  → provider gateway status
  → client_context
```

后续 AI 回调回来时，Consumer 才能通过这些字段对账并推进 DAG。

完成标准：给定一个 `ai_task_id`，能从 Consumer 侧查到它属于哪个 workflow、哪个节点、哪次 invocation。

---

## 13. 最后再接 Provider worker 的读取入口

OpenCreator 对照：

[provider-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-worker.ts)

本篇只需要保证 worker 能从队列拿到：

```text
ai_task_id
```

然后可以：

```text
repository.getById(ai_task_id)
```

真正的 Provider 选择、Robin fallback、轮询、Webhook 和产物处理放到后续专题。

完成标准：队列里能看到 submit job；worker 即使只打印任务，也能按 ID 读回完整 `ai_task`。这一步只验读取边界，不验 Provider 提交成功。

## 完整验收顺序

按这个顺序验完整链路：

1. 非法请求体被 `CreateAiTaskRequestSchema` 拦住，不落库。
2. 未注册模型或非法 `options` 被拦住，不落库。
3. 合法请求返回 `202 Accepted` 和 `ai_task_id`。
4. 数据库出现一条 `status=queued` 的 `ai_task`。
5. 队列出现一个只包含 `ai_task_id` 的 submit job。
6. 同一个 `idempotency_key` 重复请求返回已有 `ai_task_id`，不重复入队。
7. Consumer 能把 `ai_task_id` 写回 node invocation。
8. 通过 `trace_id` 可以从 Consumer invocation 查到 AI task，再从 AI task 查回请求上下文。
9. 状态枚举没有和 workflow run/node status 混用。
10. Provider worker 能按 `ai_task_id` 读回任务，但 Provider 选择、提交、轮询、Webhook 和产物处理不在本篇验收范围内。完整验收顺序
