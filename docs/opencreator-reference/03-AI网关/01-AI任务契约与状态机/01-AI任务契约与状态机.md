# OpenCreator 是怎么做 AI 任务契约与状态机的

如果要看机制拆解，读 [00-AI任务契约与状态机技术点.md](./00-AI任务契约与状态机技术点.md)。如果要按 NovelComic 的实现顺序落文件，读 [02.文件编写顺序.md](./02.文件编写顺序.md)。

## 一、先说结论

OpenCreator 的 AI 网关不是“前端点 Run 后直接调厂商模型”。画布执行链路里，Consumer 在某个节点需要模型能力时，才向 `opencreator-ai` 创建一张 AI 任务单。

```text
Consumer 执行模型节点
  → 组装 model_id / options / webhook_url
  → POST /v1/tasks
  → AI API 校验请求形状
  → 收敛模型别名
  → 按 registry 校验 options
  → 幂等写 ai_task(status=queued)
  → 新任务入 provider-execution 队列
  → 返回 ai_task_id
```

必须区分四件事：

- `workflow run`：Publisher/Consumer 层的一次画布执行。
- `node invocation`：Consumer 层某个节点的一次执行记录。
- `ai_task`：AI 网关层的一次模型调用任务。
- `provider attempt`：AI 网关向某个厂商模型的一次提交尝试。

`ai_task.status` 只覆盖 AI 网关内部，不是画布节点状态的权威源。

---

## 二、必须有的文件

按一次 AI 任务创建的顺序背。前 10 步完成“收单、校验、落库、入队”；第 11 步只是状态辅助；第 12 步才把 `queued` 任务交给 Provider worker 读取。真正的提交、轮询、Webhook 和产物处理不在本篇展开。

1. `opencreator-consumer/services/opencreator_ai/schemas.py`：Consumer 侧声明创建 AI 任务的请求和响应形状。
2. `opencreator-consumer/services/opencreator_ai/task_client.py`：Consumer 调 `POST /v1/tasks`，拿回 `ai_task_id`。
3. `opencreator-ai/packages/contracts/src/create-task.schema.ts`：AI 网关建任务请求契约。
4. `opencreator-ai/packages/contracts/src/task-state.ts`：AI 任务状态枚举和状态顺序辅助表。
5. `opencreator-ai/packages/contracts/src/db.schema.ts`：AI 任务数据库文档形状。
6. `opencreator-ai/packages/core/src/model-runtime.ts`：模型 ID 别名收敛和 registry 校验入口。
7. `opencreator-ai/packages/core/src/model-constraints.ts`：按模型校验 `options`。
8. `opencreator-ai/packages/db/src/task-repository.ts`：幂等创建或读取已有任务。
9. `opencreator-ai/packages/runtime/src/task-service.ts`：建任务服务，串起模型校验、落库和入队。
10. `opencreator-ai/apps/api/src/routes/tasks.ts`：HTTP 路由，返回 `202` 或幂等命中的 `200`。
11. `opencreator-ai/packages/runtime/src/state-machine.ts`：状态前进检查辅助，当前不是所有写路径的强制门禁。
12. `opencreator-ai/packages/runtime/src/provider-worker.ts`：从队列取 `ai_task_id`，按 ID 回库读取任务，后续才进入 Provider 提交链路。

### `opencreator-consumer/services/opencreator_ai/schemas.py`

OpenCreator 源码：[schemas.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/schemas.py)

Consumer 侧先定义它要发给 AI 网关的请求对象。关键字段是：

```text
model_id
options
webhook_url
trace_id
idempotency_key
locale
client_context
```

这份 schema 是 Consumer 的本地类型约束，不是 AI 网关最终权威。AI 网关仍要用自己的 TypeScript/Zod 契约重新校验。

### `opencreator-consumer/services/opencreator_ai/task_client.py`

OpenCreator 源码：[task_client.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/task_client.py)

负责真正发起：

```text
POST /v1/tasks
```

调用完成后，Consumer 需要保存：

```text
ai_task_id
trace_id
idempotency_key
client_context
```

这样 AI 回调回来时，Consumer 才能把结果对回原来的 node invocation。

### `opencreator-ai/packages/contracts/src/create-task.schema.ts`

OpenCreator 源码：[create-task.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/create-task.schema.ts)

这是 AI 网关建任务的入口契约。它负责回答：

- 哪些字段必填。
- 哪些字段可选。
- `options` 是否必须是对象。
- 请求体是否允许未知字段。

这层只校验“任务单形状”。某个模型具体支持哪些参数，由模型 registry 和 constraints 再校验。

### `opencreator-ai/packages/contracts/src/task-state.ts`

OpenCreator 源码：[task-state.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/task-state.ts)

定义 AI 任务状态：

```text
received
queued
submitted_to_provider
waiting_provider
processing_artifacts
callback_pending
callback_failed
callback_succeeded
succeeded
failed
timed_out
cancelled
ignored
```

这份文件还包含 `TASK_STATUS_ORDER`，但它只是辅助表。当前运行主链不能按它理解成严格单向状态机。

### `opencreator-ai/packages/contracts/src/db.schema.ts`

OpenCreator 源码：[db.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/db.schema.ts)

定义 AI 任务落库形状。建单阶段最关键的是：

- 任务 ID。
- 规范模型 ID。
- 原始请求参数。
- 回调地址。
- 幂等键。
- 追踪上下文。
- 当前状态。
- 时间字段。

Provider、attempt、result 和 callback 相关字段会在后续 worker 中逐步补齐。

### `opencreator-ai/packages/core/src/model-runtime.ts`

OpenCreator 源码：[model-runtime.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-runtime.ts)

这层负责把请求中的模型名对到 registry：

```text
resolveCoreModelId(model_id)
requireCoreModel(core_model_id)
```

`resolveCoreModelId()` 收别名，`requireCoreModel()` 确认模型真的注册。找不到模型时，不应该继续建一张可执行任务。

### `opencreator-ai/packages/core/src/model-constraints.ts`

OpenCreator 源码：[model-constraints.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-constraints.ts)

负责校验模型参数：

```text
validateCoreModelOptions(core_model_id, options)
```

同一个 AI 网关接口可以接收不同模型，但每个模型的 `options` 不一样。因此 `options` 不能只按一个宽泛 object 放过，要在识别模型后再验一次。

### `opencreator-ai/packages/db/src/task-repository.ts`

OpenCreator 源码：[task-repository.ts](../../../../../opencreate/opencreator-ai/packages/db/src/task-repository.ts)

负责任务持久化和幂等：

```text
createOrGet()
```

行为是：

```text
同一个 idempotency_key 第一次进入
  → 创建新 ai_task

同一个 idempotency_key 再次进入
  → 返回已有 ai_task
```

这里要靠数据库唯一约束兜住并发，不能只靠应用层先查再插。

### `opencreator-ai/packages/runtime/src/task-service.ts`

OpenCreator 源码：[task-service.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/task-service.ts)

这是建单服务。它串起：

```text
请求校验后的 body
  → resolveCoreModelId()
  → validateCoreModelOptions()
  → taskRepository.createOrGet()
  → 新建任务才 enqueue submit job
```

队列 job 只需要带 `ai_task_id`，不要把完整请求复制进 job。后续 worker 应该按 ID 回库读取最新任务事实。

### `opencreator-ai/apps/api/src/routes/tasks.ts`

OpenCreator 源码：[tasks.ts](../../../../../opencreate/opencreator-ai/apps/api/src/routes/tasks.ts)

HTTP 入口负责：

- 接收 `POST /v1/tasks`。
- 调建单 schema 校验。
- 调 `TaskService`。
- 根据是否新建返回 `202` 或 `200`。

这里不等待 Provider 结果，也不直接给 Consumer 返回产物。

### `opencreator-ai/packages/runtime/src/state-machine.ts`

OpenCreator 源码：[state-machine.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/state-machine.ts)

提供状态前进检查函数：

```text
assertTaskStatusCanAdvance()
```

但当前主运行写路径没有全面接入它。NovelComic 如果要把它变成强制状态机，必须同步检查 Provider fallback、callback pending、callback failed 等现有码路径，否则会和 OpenCreator 行为不一致。

### `opencreator-ai/packages/runtime/src/provider-worker.ts`

OpenCreator 源码：[provider-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-worker.ts)

建单完成后，任务会进入 provider worker。对本篇来说，只要求 worker 能按 `ai_task_id` 读回任务；再往后才开始：

```text
读取 ai_task
  → requireCoreModel()
  → 选择 robin call
  → submit provider
  → 写 provider_request_id / attempt
  → status=waiting_provider
```

这已经超出“任务契约与状态机”的建单主链，详细放到后续 AI 提交专题。本篇只把边界交代清楚，避免把 Provider 执行逻辑提前塞进建单 API。

## 三、运行时链路

### 1. Consumer 准备 AI 请求

Consumer 在执行模型节点时，把节点配置转成 AI 网关请求：

```text
node invocation
  → model_id
  → options
  → webhook_url
  → trace_id
  → idempotency_key
  → client_context
```

`client_context` 里应该能帮助 Consumer 回调时定位 workflow、节点和 invocation，但 AI 网关不解析它的业务含义。

### 2. AI API 接收建单请求

```text
POST /v1/tasks
  → CreateAiTaskRequestSchema
```

请求形状不合法时直接返回 4xx，不入库、不排队。

合法请求继续进入 `TaskService`。

### 3. 收敛模型 ID 并校验参数

```text
TaskService
  → resolveCoreModelId(model_id)
  → validateCoreModelOptions(core_model_id, options)
```

这一步保证任务进入队列前，模型和参数已经能被 AI registry 理解。

### 4. 幂等写入 `ai_task`

```text
TaskRepository.createOrGet()
  → insert ai_task(status=queued)
  → 或返回已有 task
```

命中已有任务时，不重复创建 submit job。

新任务入库后，状态是 `queued`。这表示任务等待 Provider worker 处理。

### 5. 新任务才入队

```text
if created:
  enqueue provider-execution submit job(ai_task_id)
```

job 只带 ID。Worker 负责回库读取任务、模型、参数、回调地址和上下文。

### 6. HTTP 返回给 Consumer

新建任务：

```text
202 Accepted
{
  ai_task_id,
  status: "queued"
}
```

幂等命中：

```text
200 OK
{
  ai_task_id,
  existing: true
}
```

Consumer 拿到 `ai_task_id` 后，应该把它挂回当前 node invocation，等待 AI 回调推动后续状态。

## 四、状态怎么看

建单链路最稳定的是：

```text
queued
```

Provider 主链常见是：

```text
queued
  → waiting_provider
  → processing_artifacts
  → callback_pending
  → succeeded
```

失败和 fallback 会出现：

```text
waiting_provider
  → failed
  → waiting_provider
```

最终失败也会回调 Consumer：

```text
failed
  → callback_pending
  → failed
```

回调投递失败：

```text
callback_pending
  → callback_failed
```

因此排障时要同时看：

- `ai_task.status`
- attempts
- provider/provider_request_id
- skip providers
- callback delivery 记录
- Consumer 是否已对上 invocation

## 五、和 NovelComic 对照

NovelComic 迁移这条链时，顺序不要从 Provider 开始。应该先把 AI 任务契约做稳：

1. Consumer 能发规范的 `POST /v1/tasks` 请求。
2. AI 网关能严格校验请求体。
3. 模型 ID 能收敛到 registry ID。
4. `options` 能按模型 schema 校验。
5. `ai_task` 能幂等落库。
6. 新建任务才入队。
7. Consumer 能保存 `ai_task_id` 和 `client_context`。

如果 `ai_task` 还没能稳定创建，就不要先写厂商提交、Webhook 或画布节点状态更新。否则后面会缺少幂等、追踪和补偿的权威对象。
