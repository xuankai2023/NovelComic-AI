# AI 任务契约与状态机：技术点

这组只讲 `opencreator-ai` 如何把 Consumer 的一次模型调用收成稳定任务：请求契约、模型 ID 归一、参数校验、幂等建单、队列提交、任务状态和跨仓边界。

先背一句话：

```text
Consumer 负责发起一次业务模型调用；
opencreator-ai 负责把它变成 ai_task；
Provider worker 后面才负责真正打厂商。
```

它不讲 Provider 怎么提交、怎么轮询、怎么接厂商 Webhook，也不讲产物处理和回调重试。那些放到后面的 AI 提交、轮询、Webhook、产物与回调专题里。

最短链路是：

```text
Consumer 组装 model_id / options / webhook_url
  → POST /v1/tasks
  → CreateAiTaskRequestSchema 严格验形
  → resolveCoreModelId 收别名
  → validateCoreModelOptions 按模型校验 options
  → TaskRepository.createOrGet() 幂等写 ai_task
  → 新任务入 provider-execution submit job
  → HTTP 返回 ai_task_id 和 queued
```

所以 `ai_task` 不是画布节点状态，也不是 workflow run 状态。它只表示一次 AI gateway 调用。

这篇的边界固定：

- `workflow run` 的启动、暂停、继续和 WebSocket 事件不归 `opencreator-ai` 管。
- `ai_task` 的模型、参数、Provider attempt、结果和回调投递归 `opencreator-ai` 管。
- Consumer 用 `ai_task_id` 把 AI 结果挂回 node invocation，再由工作流链路推进画布状态。

---

## 1. Consumer 是任务创建方

OpenCreator 对照：

- [Consumer 请求对象](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/schemas.py)
- [Consumer AI 客户端](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/task_client.py)

Consumer 在执行某个模型节点时，组出 AI 网关请求：

```text
model_id
options
webhook_url
trace_id
idempotency_key
locale
client_context
```

其中三项是任务创建的核心：

- `model_id`：Consumer 选中的 AI 模型或别名。
- `options`：模型参数，后面会按 registry 中对应模型的 schema 再验一次。
- `webhook_url`：AI 完成后回调 Consumer 的地址。

`trace_id` 和 `client_context` 用于跨系统追踪和回挂业务上下文，不应该被 AI 网关解释成画布状态。

---

## 2. `/v1/tasks` 只负责收单

OpenCreator 对照：

- [tasks.ts](../../../../../opencreate/opencreator-ai/apps/api/src/routes/tasks.ts)
- [create-task.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/create-task.schema.ts)

入口是：

```text
POST /v1/tasks
```

这层先做严格 schema 校验。请求体里不能随便塞字段，新增上下文必须同步改 Consumer 和 AI 两侧契约。

成功创建新任务时返回：

```text
202 Accepted
ai_task_id
status=queued
```

如果命中同一个 `idempotency_key`，返回已有任务：

```text
200 OK
existing=true
ai_task_id
```

`202` 只表示 AI 网关收下任务并排队，不表示 Provider 已经提交，也不表示模型结果已经出来。

---

## 3. 请求要先过两层校验

第一层是建任务请求形状：

```text
CreateAiTaskRequestSchema
  → 必填字段存在
  → 字段类型正确
  → 不接受未知字段
```

第二层是模型参数：

```text
resolveCoreModelId(model_id)
  → validateCoreModelOptions(core_model_id, options)
```

OpenCreator 对照：

- [model-runtime.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-runtime.ts)
- [model-constraints.ts](../../../../../opencreate/opencreator-ai/packages/core/src/model-constraints.ts)

第一层保证“这是一张 AI 任务单”，第二层保证“这张单的参数能给对应模型执行”。不要把模型参数校验写在 Consumer 里当最终权威，AI 网关仍然必须自己校验。

---

## 4. 模型 ID 会先收成 registry ID

Consumer 传入的 `model_id` 可以是 registry 里的规范 ID，也可以是别名。AI 网关用：

```text
resolveCoreModelId()
```

把别名收成核心模型 ID。找不到别名时，当前实现会原样返回，再由后续 registry 校验决定是否失败。

因此 NovelComic 迁移时要保留这个边界：

- Consumer 可以做前置映射，提升产品层兼容性。
- AI 网关必须拥有最终 registry 校验。
- 不能只靠前端模型目录证明某个模型可执行。

---

## 5. `ai_task` 是 AI 网关的数据库事实

OpenCreator 对照：

- [db.schema.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/db.schema.ts)
- [task-repository.ts](../../../../../opencreate/opencreator-ai/packages/db/src/task-repository.ts)

任务文档至少承载：

```text
ai_task_id
model_id / core_model_id
options
webhook_url
status
trace_id
idempotency_key
client_context
provider / provider_request_id
attempts
result / error
timestamps
```

队列 job 只带 `ai_task_id`。Worker 后续要从 Mongo 重新读取任务文档，而不是信任创建任务时塞进 job 的大对象。这样重试、恢复和排障都以数据库任务为准。

---

## 6. 幂等键决定是否复用任务

`idempotency_key` 用于把同一业务意图合成同一张 AI 任务单。

典型行为：

```text
第一次请求
  → insert ai_task
  → enqueue submit job
  → 202 queued

同 key 重复请求
  → 命中唯一索引
  → 返回 existing task
  → 不重复 enqueue
  → 200 existing
```

没有 `idempotency_key` 时，每次请求都可能创建新任务。调用方要自己承担重复提交风险。

幂等范围应该绑定当前业务意图，例如一次 workflow node invocation，而不是只用模型名或用户 ID 这种过宽字段。

---

## 7. 创建任务和提交 Provider 是两步

`TaskService.createTask()` 创建任务后，只把新任务投入 provider 执行队列：

```text
create ai_task(status=queued)
  → enqueue provider-execution submit job
```

真正调用厂商发生在后续 provider worker 中。建单阶段不应该直接调用 Provider，也不应该等待模型结果后再返回 HTTP。

这条边界很重要：

- API 层稳定快速返回。
- Provider 故障交给 worker 重试和 fallback。
- Consumer 用回调接结果，不阻塞在建单请求上。

---

## 8. 状态枚举不是严格运行时状态机

OpenCreator 对照：

- [task-state.ts](../../../../../opencreate/opencreator-ai/packages/contracts/src/task-state.ts)
- [state-machine.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/state-machine.ts)

契约里的状态包括：

```text
received
queued
submitted_to_provider
waiting_provider
processing_artifacts
callback_pending
callback_failed
callback_succeeded
succeeded
failed
timed_out
cancelled
ignored
```

当前主链常见写法是：

```text
queued
  → waiting_provider
  → processing_artifacts
  → callback_pending
  → succeeded | failed
```

注意：`TASK_STATUS_ORDER` 和 `assertTaskStatusCanAdvance()` 是校验辅助，不是当前所有写路径都会调用的强制运行时约束。排障时不能只按顺序表推断历史。

---

## 9. 失败任务可能重新进入等待 Provider

Robin fallback 会让状态看起来“不单调”：

```text
waiting_provider
  → failed
  → waiting_provider
```

这表示某个 Provider attempt 失败后，系统还有下一家 Provider 可以尝试。最终没有 fallback 时，失败结果仍会进入回调链：

```text
failed
  → callback_pending
  → failed
```

因此 `failed` 在 AI 网关内部既可能是一次 attempt 的失败，也可能是最终失败。判断时要结合 attempt、provider、skip_providers 和 callback 状态。

---

## 10. 回调状态和模型状态不能混为一谈

`callback_failed` 表示 AI 网关向 Consumer 投递结果失败，不表示模型执行又失败了一次。

常见区别：

| 状态 | 含义 |
| --- | --- |
| `failed` | 模型或 Provider 链路最终失败 |
| `callback_pending` | 结果已准备好，等待通知 Consumer |
| `callback_failed` | 通知 Consumer 的投递重试耗尽 |
| `succeeded` | 成功结果已经投递给 Consumer |

如果 `callback_failed` 后 Consumer 没收到结果，AI 文档里仍可能已有结果或错误信息，但需要运维补偿重新投递或手动对账。

---

## 11. 对外任务状态不等于画布节点状态

跨仓边界是：

```text
Frontend
  → 看 workflow run events

Publisher
  → 管 flow project / workflow run / WebSocket events

Consumer
  → 管 DAG node invocation，并调用 AI gateway

opencreator-ai
  → 管 ai_task / Provider / artifact / callback
```

AI 网关不会直接更新画布节点，也不会直接推前端 WebSocket。它只把统一结果回调给 Consumer。Consumer 再把结果挂回 invocation，后续由 workflow 事件链路推到 Publisher 和前端。

---

## 12. 动手前要有的东西

### Consumer

- workflow node invocation 或等价业务调用记录。
- 模型 ID 映射规则。
- `OpenCreatorAI` 客户端。
- `webhook_url` 对外可达。
- `idempotency_key` 生成规则。
- `client_context` 能保存回挂节点所需上下文。

### opencreator-ai

- 建任务请求 schema。
- 任务状态枚举。
- 数据库任务 schema。
- 模型 registry 和参数约束。
- 任务仓储和幂等索引。
- `/v1/tasks` 路由。
- provider-execution 队列。

### 运维和排障

- `trace_id` 全链路透传。
- `ai_task_id` 可从 Consumer invocation 查回。
- attempt/provider 记录可查。
- 回调投递日志可查。

后续 Provider 提交、轮询、Webhook、产物处理和 Consumer 回调，放到 [03-AI提交轮询Webhook产物与回调](../03-AI提交轮询Webhook产物与回调/14-AI提交轮询Webhook产物与回调.md)。
