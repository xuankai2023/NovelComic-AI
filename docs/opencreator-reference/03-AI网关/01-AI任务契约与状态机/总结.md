# AI 任务契约与状态机全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“能调到某个模型”，而是 Consumer 如何把一次业务模型调用收成稳定的 `ai_task`，请求如何过两层校验，幂等键如何挡住重复建单，队列为什么只带任务 ID，以及状态枚举为什么不能当成严格单向状态机。

先把一句话背下来：

OpenCreator 里，Consumer 负责发起一次业务模型调用，`opencreator-ai` 负责把它变成 `ai_task`，Provider worker 后面才负责真正打厂商。`ai_task` 只表示一次 AI 网关调用，不是画布节点状态，也不是 workflow run 状态。

## 0. 先分清四个对象

`workflow run`：Publisher / Consumer 层的一次画布执行。

`node invocation`：Consumer 层某个节点的一次执行记录。

`ai_task`：AI 网关层的一次模型调用任务。事实源是 AI 服务自己的任务文档。

`provider attempt`：AI 网关向某个厂商模型的一次提交尝试。它挂在 `ai_task` 下面，不是另一张业务单。

面试时一定要把这四个东西讲开。很多问题都来自把画布节点亮灯、DAG 节点状态和 AI 任务状态当成同一个字段。

## 1. Consumer 是任务创建方

画布点 Run 之后，前端和 Publisher 先建立一次 flow run。真正需要模型能力时，才由 Consumer 组出 AI 网关请求：

```text
model_id
options
webhook_url
trace_id
idempotency_key
locale
client_context
```

三项是建单核心：

- `model_id`：Consumer 选中的模型或别名。
- `options`：模型参数，后面还要按 registry 里对应模型的 schema 再验一次。
- `webhook_url`：AI 完成后回调 Consumer 的地址。

`trace_id` 和 `client_context` 用来跨系统追踪、回挂业务上下文。AI 网关不把它们解释成画布状态。`client_context` 里应该能帮助回调时定位 workflow、节点和 invocation。

## 2. `/v1/tasks` 只负责收单

入口是：

```text
POST /v1/tasks
```

成功创建新任务：

```text
202 Accepted
ai_task_id
status=queued
```

命中同一个 `idempotency_key`：

```text
200 OK
existing=true
ai_task_id
```

`202` 只表示 AI 网关收下任务并排队。它不表示 Provider 已经提交，也不表示模型结果已经出来。HTTP 不等待厂商，也不把产物直接返回给 Consumer。

请求体不能随便塞字段。新增上下文字段必须同时改 Consumer 和 AI 两侧契约。

## 3. 请求要先过两层校验

第一层是任务单形状：

```text
CreateAiTaskRequestSchema
  → 必填字段存在
  → 字段类型正确
  → 不接受未知字段
```

第二层是模型参数：

```text
resolveCoreModelId(model_id)
  → validateCoreModelOptions(core_model_id, options)
```

第一层保证“这是一张 AI 任务单”。第二层保证“这张单的参数能给对应模型执行”。同一个 `/v1/tasks` 可以收不同模型，但每个模型的 `options` 不一样，不能只按一个宽泛 object 放过。

Consumer 自己的 schema 只是组包和类型检查。AI 网关必须用自己的契约再验一次，不能把 Consumer 或前端模型目录当成最终权威。

形状不合法、模型未注册、参数不合法时，直接 4xx，不入库、不入队。

## 4. 模型 ID 会先收成 registry ID

Consumer 传入的 `model_id` 可以是规范 ID，也可以是别名。AI 网关用 `resolveCoreModelId()` 收成核心模型 ID。找不到别名时，当前实现会原样返回，再由 `requireCoreModel()` 决定是否失败。找不到模型时，不应该继续建一张可执行任务。

因此迁移时要保留两层：

- Consumer 可以做前置映射，方便产品层兼容。
- AI 网关必须拥有最终 registry 校验。

## 5. `ai_task` 是 AI 网关的数据库事实

任务文档至少承载：

```text
ai_task_id
model_id / core_model_id
options
webhook_url
status
trace_id
idempotency_key
client_context
provider / provider_request_id
attempts
result / error
timestamps
```

建单阶段先定住身份、模型、参数、回调、幂等、追踪和 `queued`。Provider、attempt、result、callback 由后续 worker 补齐。

队列 job 只带 `ai_task_id`。Worker 要从数据库重新读取任务文档，不能信任创建时塞进 job 的大对象。重试、恢复和排障都以任务文档为准。

不要把 workflow run、node status 或前端节点样式写进 `ai_task`。

## 6. 幂等键决定是否复用任务

`idempotency_key` 把同一业务意图合成同一张 AI 任务单。范围应该绑到一次 workflow node invocation 这类具体意图，不能只用模型名或用户 ID 这种过宽字段。

```text
第一次请求
  → insert ai_task
  → enqueue submit job
  → 202 queued

同 key 重复请求
  → 命中唯一索引
  → 返回 existing task
  → 不重复 enqueue
  → 200 existing
```

并发要靠数据库唯一索引兜住，不能只靠应用层先查再插。`idempotency_key` 用 sparse unique：有 key 时只能成功插入一条，没有 key 时每次都建新任务。没有 key 的调用方要自己承担重复提交风险。

## 7. 创建任务和提交 Provider 是两步

`TaskService.createTask()` 创建任务后，只把新任务投入 provider 执行队列：

```text
create ai_task(status=queued)
  → enqueue provider-execution submit job(ai_task_id)
```

命中已有任务时不重复入队。真正调用厂商发生在后续 provider worker。建单 API 不应该直接打 Provider，也不应该等模型结果再返回 HTTP。

这条边界让 API 稳定快速返回，Provider 故障交给 worker 重试和 fallback，Consumer 用回调接结果。

Worker 对本篇的要求只到：从队列拿到 `ai_task_id`，再 `getById()` 读回完整任务。Provider 选择、Robin、轮询、Webhook 和产物处理放到后面的专题。

## 8. 状态枚举不是严格运行时状态机

契约里的状态包括：

```text
received
queued
submitted_to_provider
waiting_provider
processing_artifacts
callback_pending
callback_failed
callback_succeeded
succeeded
failed
timed_out
cancelled
ignored
```

`TASK_STATUS_ORDER` 和 `assertTaskStatusCanAdvance()` 是校验辅助，不是当前所有写路径都会调用的强制门禁。排障时不能只按顺序表推断历史。

当前主链常见写法是：

```text
queued
  → waiting_provider
  → processing_artifacts
  → callback_pending
  → succeeded | failed
```

`received`、`submitted_to_provider`、`callback_succeeded` 留在枚举里，当前主链没有写入。阅读时不能假定每个任务都会经过它们。

正式终态是 `succeeded`、`failed`、`timed_out`、`cancelled`。`callback_failed` 和 `ignored` 要单独识别，不能当成这四个终态的同义词。

## 9. 失败任务可能重新进入等待 Provider

Robin fallback 会让状态看起来不单调：

```text
waiting_provider
  → failed
  → waiting_provider
```

这表示某个 Provider attempt 失败后，系统还有下一家 Provider 可以尝试。最终没有 fallback 时，失败结果仍会进入回调链：

```text
failed
  → callback_pending
  → failed
```

因此 `failed` 在 AI 网关内部既可能是一次 attempt 的失败，也可能是最终失败。判断时要结合 attempt、provider、`skip_providers` 和 callback 状态。

如果以后要把 `assertTaskStatusCanAdvance()` 做成强制门禁，必须同时检查 fallback 离开 `failed`、callback pending、callback failed 这些现码路径。否则会和 OpenCreator 行为不一致。

## 10. 回调状态和模型状态不能混为一谈

`callback_failed` 表示 AI 网关向 Consumer 投递结果失败，不表示模型执行又失败了一次。

| 状态 | 含义 |
| --- | --- |
| `failed` | 模型或 Provider 链路最终失败 |
| `callback_pending` | 结果已准备好，等待通知 Consumer |
| `callback_failed` | 通知 Consumer 的投递重试耗尽 |
| `succeeded` | 成功结果已经投递给 Consumer |

`callback_failed` 之后，AI 文档里仍可能已有结果或错误信息，但 Consumer 没收到。这时要运维补偿重新投递或手动对账，不能把任务再理解成“模型又跑失败了”。

## 11. 对外任务状态不等于画布节点状态

跨仓边界是：

```text
Frontend
  → 看 workflow run events

Publisher
  → 管 flow project / workflow run / WebSocket events

Consumer
  → 管 DAG node invocation，并调用 AI gateway

opencreator-ai
  → 管 ai_task / Provider / artifact / callback
```

AI 网关不会直接更新画布节点，也不会直接推前端 WebSocket。它只把统一结果回调给 Consumer。Consumer 再把结果挂回 invocation，后续由 workflow 事件链路推到 Publisher 和前端。

Consumer 拿到 `ai_task_id` 后必须写回当前 node invocation，同时留下 `trace_id`、`idempotency_key` 和 `client_context`。给定一个 `ai_task_id`，要能从 Consumer 查到它属于哪个 workflow、哪个节点、哪次 invocation。

Provider 原始状态必须先归一化，不能直接泄漏成画布状态。

## 12. 文件编写顺序

按四段迁移，不要从厂商提交开始：

```text
契约
  → task-state / create-task schema / db schema

模型校验
  → model runtime / model constraints

建单服务
  → repository / task service / route / state-machine 辅助

Consumer 接入
  → schemas / task client / invocation 保存 ai_task_id
```

完成基线是：非法请求被拦住；合法请求返回 `202` 和 `ai_task_id`；库里有一条 `status=queued` 的任务；队列里有一个只含 `ai_task_id` 的 submit job；同一个幂等键不重复入队；Consumer 能把 `ai_task_id` 挂回 invocation。Provider worker 能按 ID 读回任务即可，提交成功不在本篇验收里。

如果 `ai_task` 还不能稳定创建，就不要先写厂商提交、Webhook 或画布节点状态更新。后面会缺少幂等、追踪和补偿的权威对象。

## 13. 面试 1 分钟口述

OpenCreator 的 AI 网关不是前端点 Run 后直接调厂商。Consumer 在某个模型节点执行时，组出 `model_id`、`options` 和 `webhook_url`，再 `POST /v1/tasks`。AI API 先用严格 schema 验任务单形状，再用 `resolveCoreModelId()` 收别名，按模型 schema 验 `options`。通过后 `TaskRepository.createOrGet()` 幂等写入 `ai_task(status=queued)`，只有新建任务才把 `ai_task_id` 丢进 provider-execution 队列。新建返回 `202 queued`，命中幂等键返回 `200 existing`，并且不重复入队。`202` 只表示收下并排队，厂商还没被调用。队列 job 不复制整份请求，worker 按 ID 回库读。状态枚举很长，但 `TASK_STATUS_ORDER` 只是辅助表，主链没有把 `assertTaskStatusCanAdvance()` 接成强制门禁；Robin fallback 还会让任务从 `failed` 回到 `waiting_provider`。`callback_failed` 是投递失败，不是模型又失败了一次。AI 网关不改画布，Consumer 用 `ai_task_id` 把结果挂回 node invocation。

## 14. 面试官追问怎么答

如果问 `202` 是不是模型已经跑完：

不是。`202` 只表示任务已落成 `queued` 并写入 submit job。Provider 提交、轮询和回调都在 worker 后面。

如果问为什么队列里不放完整 options：

因为重试和恢复要以数据库里的任务文档为准。job 里塞一份创建时的快照，后面改状态、补 attempt、排障都会出现两份事实。

如果问为什么不能只在 Consumer 验模型参数：

Consumer schema 方便组包。可执行模型和参数约束的权威在 AI registry。网关不自己验，非法单会进队列。

如果问状态是不是只能向前：

契约有顺序表，但当前写路径没有全面调用 `assertTaskStatusCanAdvance()`。fallback 会离开 `failed`。排障要看 attempt、provider 和 callback，不能只看顺序数字。

如果问 `failed` 和 `callback_failed` 有什么区别：

`failed` 是模型或 Provider 链路的失败。`callback_failed` 是结果已经有了，但通知 Consumer 的投递重试耗尽。

如果问 AI 任务状态能不能直接驱动画布节点：

不能。`ai_task.status` 和 DAG 节点状态各自持久化。网关回调 Consumer，Consumer 再通过 workflow 事件把节点状态推到 Publisher 和前端。

如果问没有 `idempotency_key` 会怎样：

每次请求都会插入新任务。调用方要自己承担重复提交。有 key 时必须用数据库唯一索引，不能先查再插。

## 15. NovelComic 当前实现自查

本章建单主链已经按契约落地，文档口径和收单代码一致。状态机辅助函数已写，但没有接进写路径。

- `novelcomic-ai` 有 `CreateAiTaskRequestSchema`、`AiTaskDocument`、`TaskRepository.createOrGet()`、`TaskService.createTask()` 和 `POST /v1/tasks`。非法 body 在进 service 前返回 400，不落库。
- 模型先 `resolveCoreModelId()`，再 `validateCoreModelOptions()`。未注册模型或非法 options 变成 `TaskServiceValidationError`，同样 400，不入队。
- 新建任务状态是 `queued`，HTTP `202`，body 里是 `ai_task_id` 和 `status=queued`。命中幂等键返回 HTTP `200`，body 带 `existing: true`。
- `idempotency_key` 是 sparse unique。重复键靠 Mongo `11000` 找回已有任务，不重复 `add('submit', { ai_task_id })`。没有 key 时每次 `insertOne`。
- Consumer 的 `CreateTaskRequest` 字段和网关对齐，`extra=forbid`。`ModelInvocationService` 用 `plan.result_id` 当幂等键，把 `flow_id`、`run_id`、`node_id`、`result_id` 放进 `client_context`，并把 `ai_task_id` 写入 `model_invocations`。
- `assertTaskStatusCanAdvance()` 只在 `state-machine` 自己的测试里被调用。repository 和 worker 写状态时没有走它。
- NovelComic 的 Robin fallback 当前写法，是 `markProviderFailedAttempt({ has_fallback: true })` 把状态写成 `queued` 再重新入队，不是参考文档里的 `failed → waiting_provider`。没有下一家时写成 `failed`。读 OpenCreator 笔记和读 NovelComic 排障日志时，要把这两套 fallback 写法分开。
- `callback_failed` 由回调投递耗尽时的 `markFailed()` 写入。成功投递后，按任务上是否已有 `error` 写成 `failed` 或 `succeeded`。

验收不能只看接口返回了 `ai_task_id`。形状校验、模型参数、幂等不重复入队、invocation 回挂、状态枚举不和 workflow run 混用，要分开过。Provider 选择、轮询、Webhook 和产物处理不在本章验收里。
