# NovelComic 登录、JWT、验证码、邮件全链路笔记

这份不是文件列表，是给面试用的全链路笔记。你要讲清楚的不是“项目里有 auth.py、jwt.py”，而是用户点登录以后，请求怎么从前端走到后端，验证码怎么存，邮件怎么发，ticket 怎么换 Session，JWT 怎么进入业务接口，最后怎么变成当前用户。

先把一句话背下来：

NovelComic 的身份系统交给 Clerk，Publisher 后端不自己保存密码，也不自己给浏览器用户签 JWT。前端先用 Google OAuth，或者按 OpenCreator 参考链路用邮箱验证码/密码拿到 Clerk Sign-in Token，再让 Clerk 激活 Session；之后前端从 Clerk Session 取 `__opencreator_jwt`，业务请求带 `Authorization: Bearer <jwt>`，Publisher 用 Clerk PEM 公钥验签，取 JWT 里的 `sub` 当业务 `user_id`。

## 0. 这条链里先分清四个凭证

`code` 是邮箱验证码，只能短期存在 Redis，验证成功就删掉，不能当登录态。

`ticket` 或 `sign_in_token` 是 Clerk Sign-in Token，只用来换 Clerk Session。登录接口返回 `ticket`，注册接口返回 `sign_in_token`，本质上都是给前端调用 `signIn.create({ strategy: "ticket", ticket })` 用的票，不是业务 JWT。

Clerk Session 是浏览器登录态，由 Clerk SDK 管。Session 激活之后，前端才算登录成功。

`__opencreator_jwt` 是真正打 Publisher 业务接口用的 JWT。它来自 `getToken({ template: "__opencreator_jwt" })`，后端只认这个 Bearer Token。

面试时一定要把这四个东西讲开。很多人会把 ticket 和 JWT 混在一起，这会显得没理解认证链路。

## 1. 应用启动时，认证能力是怎么挂上的

后端入口在 `novelcomic-publisher/app/main.py`。

`create_app()` 创建 FastAPI 应用，先挂 CORS，再调用 `register_middleware(app)` 和 `register_router(app)`。Mongo、Redis、RabbitMQ 这类连接在 `lifespan()` 里初始化到 `app.state.connections`，所以后面的 `/api/v2/user/info` 才能从 `request.app.state.connections.mongo` 拿数据库。

路由和中间件注册在 `novelcomic-publisher/app/core/register.py`。

`register_middleware()` 把两个中间件挂上去：

- `AuthenticationMiddleware` 使用 `ClerkAuthenticationBackend`，负责每个请求进来时检查 JWT。
- `AuthErrorMiddleware` 负责把认证失败包装成统一响应，比如 `{ code: 1002, msg, data: null }`。

`register_router()` 把 `novelcomic-publisher/app/controller/routers.py` 里的 v1、v2 路由挂到应用上。v2 下有 `/api/v2/auth/*` 和 `/api/v2/user/info`，v1 下有 `/api/v1/user/create` 这个 Clerk webhook。

这一步的作用是：项目启动时就把“哪些接口要验 JWT、哪些接口公开”这件事变成全局规则，而不是每个接口自己手写一遍。

## 2. 发验证码链路：从用户填邮箱到邮件发出去

完整链路应该是：

```text
前端输入邮箱
  -> 前端调用 send-code
  -> controller/v2/auth.py 收请求
  -> AuthService.send_verification_code 编排
  -> RedisService 查冷却
  -> ClerkService 查邮箱是否已有用户
  -> 生成 6 位验证码
  -> RedisService 存验证码、code_type、设备指纹、时区
  -> EmailService 发验证码邮件
  -> RedisService 写 60 秒发送冷却
  -> 返回 code_type: login 或 register
```

NovelComic 当前仓库里，HTTP 入口已经在 `novelcomic-publisher/app/controller/v2/auth.py`。

`send_verification_code()` 对应 `POST /api/v2/auth/send-code`。它接收 `email`、`fp_hash`、`fp_time`，然后调用 `AuthService.send_verification_code(email, fp_hash, fp_time)`。这个 controller 不应该自己生成验证码，也不应该自己发邮件，它只负责收参、记录日志、把业务异常转成 HTTP 响应。

这里的异常映射也能讲：

- `RateLimitError` 返回 429，说明同一个邮箱还在 60 秒冷却里。
- `EmailSendError` 返回 500，说明发信通道失败。
- 其他异常返回系统错误。

真正跟 Redis 打交道的是 `novelcomic-publisher/app/services/redis_service.py`。

`RedisService.check_rate_limit(email)` 会看 `novelcomic:auth:rate_limit:<email>` 是否存在。存在就说明一分钟内发过，不能继续发。

`RedisService.store_code_data(email, data)` 存的是一整包 JSON，不只是验证码。里面有：

- `code`：6 位验证码。
- `code_type`：`login` 或 `register`，决定后面走登录还是注册。
- `fp_hash`：设备指纹，注册时可做风控。
- `fp_time`：时区，注册时可做风控。
- `created_at`：验证码生成时间。

它的 Redis key 是 `novelcomic:auth:code_data:<email>`，有效期 `CODE_TTL = 300` 秒。

`RedisService.set_rate_limit(email)` 在邮件真正发出后写入 `novelcomic:auth:rate_limit:<email>`，有效期 `RATE_LIMIT_TTL = 60` 秒。这里顺序很关键：先存验证码、先发邮件，发成功后才写冷却。如果邮件没发出去就写冷却，用户会被白白卡一分钟。

NovelComic 当前仓库有 RedisService，也有 `ClerkService`，但没有看到 `novelcomic-publisher/app/services/email_service.py` 和 `novelcomic-publisher/app/services/auth_service.py`。所以“发邮件编排”在当前 NovelComic 分支里还没落地完整；完整做法可以参考 OpenCreator：

- `opencreator-publisher/services/auth_service.py` 的 `send_verification_code()` 负责串 Redis、Clerk、Email。
- `opencreator-publisher/services/email_service.py` 的 `EmailService.send_verification_code()` 负责选择邮件渠道并发送。

发邮件本身应该放在 EmailService，不应该塞进 controller。OpenCreator 的实现是按邮箱域名分流：国内常见邮箱走阿里云邮件推送，其他邮箱走 AWS SES。NovelComic 的 `config.py` 里已经有阿里云邮件配置字段，比如 `aliyun_dm_access_key_id`、`aliyun_dm_account_name`、`aliyun_dm_from_alias`，说明 NovelComic 至少已经给阿里云发信预留了配置入口。

面试讲法：

发验证码不是“生成一个码发出去”这么简单。这个链路里 Redis 负责两个状态：一个是验证码正文，一个是发送冷却。Clerk 负责判断邮箱是否已有身份用户，从而决定这次验证码是登录用还是注册用。EmailService 只负责发信，AuthService 才负责把这些外部服务串成一个业务动作。

## 3. 验证码登录链路：已有用户怎么登录

完整链路是：

```text
用户输入邮箱验证码
  -> 前端调用 login-with-code
  -> controller/v2/auth.py
  -> AuthService.verify_code_and_login
  -> RedisService.get_code_data
  -> 检查 code_type 必须是 login
  -> 检查验证码是否匹配
  -> ClerkService.get_user_by_email
  -> ClerkService.create_sign_in_token
  -> RedisService.delete_code_data
  -> 返回 ticket 和 user_id
  -> 前端用 ticket 换 Clerk Session
```

NovelComic 的后端入口是 `novelcomic-publisher/app/controller/v2/auth.py` 的 `login_with_code()`。

它调用 `AuthService.verify_code_and_login(body.email, body.code)`。成功后返回 `LoginResponse`，里面应该有 `ticket` 和 `user_id`。失败时分两类：验证码错返回 400；用户不存在返回 404。

为什么要检查 `code_type == "login"`？因为同一个邮箱验证码接口同时服务登录和注册。发码时已经通过 Clerk 判断这个邮箱有没有用户：已有用户发的是 `login` 码，新用户发的是 `register` 码。登录接口不能拿注册验证码来登录，否则链路语义乱掉。

为什么验证成功后要删 Redis？因为验证码只能一次性使用。`RedisService.delete_code_data(email)` 是防止同一验证码重复登录的关键。

前端拿到 `ticket` 后不能直接当 Bearer。正确动作是调用 Clerk SDK：

```ts
const result = await signIn.create({
  strategy: 'ticket',
  ticket: response.ticket,
})

await setActive({ session: result.createdSessionId })
```

这个逻辑 NovelComic 当前前端没有邮箱验证码页面；OpenCreator 的参考实现放在 `opencreator-frontend/src/features/auth/components/VerifyCodeForm.tsx`。NovelComic 现在的 `AuthForm.tsx` 主要保留 Google OAuth。

面试讲法：

验证码登录的本质不是后端返回 JWT，而是后端让 Clerk 给这个用户开一张 Sign-in Token。浏览器拿这张票去 Clerk 换 Session，Session 激活后，再从 Clerk Session 取业务 JWT。

## 4. 验证码注册链路：新用户怎么注册

完整链路是：

```text
用户输入注册验证码
  -> 前端调用 register-with-code
  -> controller/v2/auth.py 提取 X-Forwarded-For
  -> AuthService.register_with_code
  -> RedisService.get_code_data
  -> 检查 code_type 必须是 register
  -> 检查验证码
  -> 再查 Clerk，防重复注册
  -> 读取 fp_hash、fp_time、client_ip 做风控
  -> ClerkService.create_user_with_email
  -> ClerkService.create_sign_in_token
  -> RedisService.delete_code_data
  -> 返回 sign_in_token、expires_in、user_id
  -> 前端用 sign_in_token 换 Clerk Session
  -> Clerk user.created webhook 写本地 users
```

NovelComic 的入口在 `novelcomic-publisher/app/controller/v2/auth.py` 的 `register_with_code()`。

这个函数比登录多一步：它会通过 `_client_ip(request)` 优先取 `X-Forwarded-For` 的第一段，拿不到再用连接地址。这个 IP 不是为了显示，而是给注册风控用。

AuthService 这层在 NovelComic 当前缺失，但从已有 RedisService 和 OpenCreator 参考实现看，注册链路应该做几件事：

先从 Redis 取验证码数据，要求 `code_type == "register"`。如果拿登录码来注册，要拒绝。

然后校验验证码值，错了直接返回 `InvalidCodeError`。

再查 Clerk，防止用户发码之后到注册之间，这个邮箱已经被创建。存在就删验证码并返回“已注册”。

然后做注册风控。OpenCreator 参考实现里会用 `fp_hash` 检查设备指纹注册数量，用 `client_ip` 判断国家，用邮箱域名和 `fp_time` 时区判断异常。NovelComic 当前仓库还没有这些风控工具函数，但 Redis 已经把 `fp_hash` 和 `fp_time` 存起来了，说明数据入口已经准备好。

最后调用 `ClerkService.create_user_with_email()` 在 Clerk 创建身份用户。NovelComic 的 `ClerkService.create_user_with_email()` 会设置邮箱地址，默认 `skip_password_requirement=True`，并可写 `unsafe_metadata`。创建成功后调用 `ClerkService.create_sign_in_token(user_id)`，返回 `sign_in_token` 给前端。

注册成功后，本地 Mongo 用户不是在注册接口里直接 insert，而是走 Clerk webhook。这个设计要讲清楚：身份用户在 Clerk 创建，本地业务用户通过 `user.created` 事件补齐。

面试讲法：

注册链路比登录多了风控和本地用户同步。后端不能只看验证码对不对，还要确认这张验证码本来就是注册码，确认 Clerk 里还没有这个邮箱，再创建身份用户。业务库的 users 表通过 Clerk webhook 落库，避免登录接口和身份系统的创建流程绑死。

## 5. 密码登录链路：为什么不经过 Redis

完整链路是：

```text
用户输入邮箱和密码
  -> 前端调用 login-with-password
  -> controller/v2/auth.py
  -> AuthService.login_with_password
  -> ClerkService.get_user_by_email
  -> ClerkService.verify_user_password
  -> ClerkService.create_sign_in_token
  -> 返回 ticket 和 user_id
  -> 前端用 ticket 换 Clerk Session
```

NovelComic 的入口是 `novelcomic-publisher/app/controller/v2/auth.py` 的 `login_with_password()`。

它失败时把 `InvalidPasswordError` 和 `UserNotFoundError` 都统一成 401，并且统一提示“邮箱或密码错误”。这个细节很重要：不能告诉攻击者到底是邮箱不存在还是密码错，否则会泄露账号枚举信息。

密码登录不需要 Redis，因为没有验证码临时状态。真正的密码校验在 `novelcomic-publisher/app/services/clerk.py` 的 `ClerkService.verify_user_password(user_id, password)`。这个函数调用 Clerk 后端 SDK，密码对返回 True，密码错返回 False。

密码对之后还是不直接返回 JWT，而是 `ClerkService.create_sign_in_token(user.id)`，让前端继续用 Clerk SDK 换 Session。

面试讲法：

密码登录和验证码登录最后殊途同归，都是拿 Sign-in Token 换 Clerk Session。区别只是前半段的认证方式不同：验证码登录靠 Redis 里的 code，密码登录靠 Clerk 校验密码。

## 6. Google OAuth 链路：NovelComic 当前真实前端主链路

NovelComic 当前前端真实存在、能看见的主链路是 Google OAuth。

入口在 `novelcomic-frontend/src/features/auth/components/AuthForm.tsx`。

用户点击“使用 Google 继续”后，`handleGoogleAuth()` 做这些事：

先生成一个 `flowId`。这个 ID 用来把主窗口和弹窗的一次登录流程绑定起来，避免多个弹窗或旧消息串流。

然后把 returnUrl 和 startedAt 写进 localStorage，key 前缀是 `novelcomic:oauth-popup:`。

接着打开 `/oauth-popup-start?flow_id=<flowId>` 这个弹窗。这个路由在 `novelcomic-frontend/src/routes/oauth-popup-start.tsx` 注册，实际组件在 `novelcomic-frontend/src/features/auth/components/OAuthPopupStart.tsx`。

`OAuthPopupStart` 里用 `useSignUp()` 拿到 Clerk 的 signUp 对象，然后调用：

```ts
signUp.authenticateWithRedirect({
  strategy: 'oauth_google',
  redirectUrl: callbackUrl.toString(),
  redirectUrlComplete: completeUrl.toString(),
})
```

Google 和 Clerk 跳转回来后，先进入 `novelcomic-frontend/src/routes/sso-callback.tsx`。这里用 `AuthenticateWithRedirectCallback` 处理 Clerk 回调，然后强制跳到 `/oauth-popup-complete`。

`OAuthPopupComplete` 在 `novelcomic-frontend/src/features/auth/components/OAuthPopupComplete.tsx`。它读取 `flowId` 和当前 `sessionId`，构造消息：

```ts
{
  type: 'novelcomic:oauth-popup-complete',
  flowId,
  sessionId,
  status,
}
```

如果当前窗口是弹窗，它会同时用 `BroadcastChannel` 和 `window.opener.postMessage` 通知主窗口，然后关闭弹窗。主窗口的 `AuthForm` 收到消息后，会检查 origin 和 flowId，确认是自己发起的流程，再执行：

```ts
await clerk.client?.reload?.()
await clerk.setActive({ session: sessionId })
```

到这一步，Clerk Session 才真正激活。后面业务请求才能取 JWT。

面试讲法：

Google OAuth 这段难点不是“调 Google”，而是弹窗登录的状态回传。NovelComic 用 `flowId` 防止串流，用同源校验防止跨站消息，用关闭检测和两分钟超时处理用户中断，用 BroadcastChannel 和 postMessage 做兼容。

## 7. Session 激活以后，JWT 是怎么进业务请求的

Session 激活以后，还没有自动等于后端认证通过。前端还要拿业务 JWT。

全局 Provider 在 `novelcomic-frontend/src/components/providers/providers-router.tsx`。

`ProvidersRouter` 挂了 `ClerkProvider`，里面包了 `ClientProviders`，还挂了 `GlobalAuthModal`。这保证所有需要 Clerk 的组件都在 Provider 下面。

`novelcomic-frontend/src/components/ClientProviders.tsx` 里有 `ApiTokenProvider()`。

它从 Clerk 的 `useAuth()` 里拿 `getToken`，然后注册给 API client：

```ts
setTokenProvider(() => getToken({ template: JWT_TEMPLATE }))
```

这里 `JWT_TEMPLATE = "__opencreator_jwt"`。这个名字必须和 Clerk 后台 JWT Template 一致。

`novelcomic-frontend/src/api/client.ts` 里有三件事：

`setTokenProvider(provider)` 保存这个取 token 的函数。

`getApiToken()` 真正执行 provider，拿当前用户的 JWT。

`request()` 封装 fetch，解析 Publisher 的 `{ code, msg, data }` 响应。

注意：NovelComic 当前的 `request()` 不会自动加 Authorization。受保护接口调用方应该先 `getApiToken()`，拿到 token 后自己写：

```ts
headers: {
  Authorization: `Bearer ${token}`,
}
```

这也是为什么 `novelcomic-frontend/src/api/client.test.ts` 里专门测了两件事：没有 token provider 时不应该发受保护请求；注册 token provider 后，请求头里应该出现 `Authorization: Bearer jwt-token`。

面试讲法：

Clerk Session 是浏览器状态，Publisher 不能直接读取。Publisher 只认 HTTP 请求头里的 Bearer JWT。所以前端必须从 Clerk Session 取 `__opencreator_jwt`，再把它带给业务 API。

## 8. 后端 JWT 验签链路：Bearer 怎么变成 request.user

完整链路是：

```text
业务请求带 Authorization: Bearer <jwt>
  -> AuthenticationMiddleware
  -> ClerkAuthenticationBackend.authenticate
  -> 判断 WHITE_LIST
  -> 非白名单读取 Authorization
  -> 剥掉 Bearer 前缀
  -> JwtService.get_user_id_with_backoff
  -> jwt.decode(token, CLERK_PEM_PUBLIC_KEY, algorithms=["RS256"])
  -> 取 payload.sub
  -> 返回 AuthUser(user_id=sub)
  -> 业务接口 Depends(get_authenticated_user)
```

白名单在 `novelcomic-publisher/app/middleware/auth_middleware.py` 的 `WHITE_LIST`。

白名单里有健康检查、文档、发验证码、验证码登录、验证码注册、密码登录、Clerk webhook。也就是说这些接口不需要浏览器已经登录。

`POST /api/v2/auth/change-password` 和 `GET /api/v2/user/info` 不在白名单里，所以必须带 JWT。

`ClerkAuthenticationBackend.authenticate()` 是核心。它会判断路径是否命中白名单。如果是白名单，就返回一个空的 `PUBLIC_USER`，让请求继续走。如果是 WebSocket，也跳过这条 HTTP JWT 链。

非白名单 HTTP 请求必须有 `Authorization`。没有就抛 `AuthenticationError("Authorization field is required")`。有的话，如果以 `Bearer ` 开头就去掉前缀，否则直接把整个值当 token。

然后它调用 `novelcomic-publisher/app/services/jwt.py` 的 `JwtService.get_user_id_with_backoff(token)`。

`JwtService` 用 `get_settings().clerk_pem_public_key` 和 `RS256` 解码 JWT。payload 必须是 dict，里面必须有 `sub`。过期会抛 `JwtExpiredTokenError`，签名错、格式错、缺 `sub` 会抛 `JwtInvalidTokenError`。

验签成功后，`authenticate()` 返回：

```python
AuthCredentials(["authenticated"]), AuthUser(user_id=user_id)
```

后面的接口就可以通过 `request.user` 拿当前用户。

`novelcomic-publisher/app/dependencies/authenticated_user.py` 的 `get_authenticated_user(request)` 只是从 `request.user` 取出 `AuthUser`。它不验签，因为验签已经在中间件做完了。

面试讲法：

后端不信前端传来的 user_id，也不信请求体里的用户字段，只信 JWT 验签后的 `sub`。这就是防越权的关键。用户想查谁、改谁，不是看他传了什么 user_id，而是看 Bearer Token 里的 subject 是谁。

## 9. 本地用户落库链路：Clerk 用户怎么变成业务用户

JWT 验签通过只说明“这个 Clerk 用户是真的”。业务库里有没有这个用户，还要看本地 `users` 集合。

NovelComic 的本地用户服务在 `novelcomic-publisher/app/services/user.py`。

`UserService.create_user(database, user_id, user_email)` 往 `users` 集合插入：

```python
{
  "user_id": user_id,
  "user_email": user_email,
}
```

`UserService.get_user_by_id(database, user_id)` 按 `user_id` 查，返回 `user_id` 和 `user_email`。

谁来创建本地用户？不是登录接口，而是 `novelcomic-publisher/app/controller/v1/user.py` 的 `clerk_webhook_handler()`。

这个接口路径是 `POST /api/v1/user/create`，在 JWT 白名单里，因为它不是浏览器用户请求，而是 Clerk 服务端回调。它的安全性来自 Svix 签名。

`clerk_webhook_handler()` 先读取原始 body，然后调用 `_verify_payload(request, body)`。这个函数检查 `svix-id`、`svix-timestamp`、`svix-signature` 三个 header，并用 `CLERK_WEBHOOK_SECRET` 验证。签名不对直接 400。

签名通过后，如果 `payload.type` 不是 `user.created`，就返回 ignored。只有 `user.created` 才继续处理。

它从 `payload.data.id` 取 Clerk 用户 id，当成本地 `user_id`；再从 `email_addresses[0].email_address` 取邮箱。插入前先查本地有没有，已有就跳过，没有就调用 `UserService.create_user()`。

面试讲法：

本地 users 表不是身份表，而是业务资料表。身份创建在 Clerk，本地资料通过 Clerk 的 `user.created` webhook 同步。webhook 虽然不带业务 JWT，但它必须过 Svix 签名，所以不是裸接口。

## 10. 查当前用户链路：登录后怎么验证链路通了

最适合验证整条链的是 `GET /api/v2/user/info`。

这个接口在 `novelcomic-publisher/app/controller/v2/user.py` 的 `user_info_v2()`。

它的执行顺序是：

```text
前端带 Authorization: Bearer <jwt>
  -> auth_middleware 验签
  -> request.user.user_id = jwt.sub
  -> user_info_v2 Depends(get_authenticated_user)
  -> UserService.get_user_by_id(database, user.user_id)
  -> 找到返回 200
  -> 找不到返回 404 User not found
```

如果 JWT 过了，但 `/user/info` 返回 User not found，问题不在 JWT，问题在本地用户没落库。要回头查 `clerk_webhook_handler()` 是否收到 `user.created`，Svix 签名是否配置，Mongo 的 `users` 集合是否写入。

这个点面试很好讲，因为它能体现你知道“认证成功”和“业务用户存在”是两件事。

## 11. 改密码链路：为什么它必须带 JWT

改密码入口在 `novelcomic-publisher/app/controller/v2/auth.py` 的 `change_password()`。

它不在白名单里，所以必须先通过 JWT。函数签名里有：

```python
user: Annotated[AuthUser, Depends(get_authenticated_user)]
```

这意味着 user_id 不是从请求体拿的，而是从已经验过的 JWT 里拿的。

然后它调用 `AuthService.change_password(user.user_id, old_password, new_password)`。完整编排参考 OpenCreator：先用 Clerk 验旧密码，再用 `ClerkService.update_user_password()` 写新密码。

面试讲法：

改密码这种接口不能让前端传 user_id，否则用户可以改别人的密码。它必须从 JWT 的 `sub` 得到当前用户，只能改当前登录人的密码。

## 13. 面试 1 分钟口述

NovelComic 的登录链路核心是 Clerk + Publisher JWT 验签。用户登录先拿 Clerk Session，不是后端直接发业务 JWT。Google 登录走前端弹窗 OAuth：`AuthForm` 打开 `/oauth-popup-start`，Clerk 回调到 `/sso-callback`，最后 `/oauth-popup-complete` 用 BroadcastChannel 和 postMessage 通知主窗口，主窗口 `setActive` 激活 Session。邮箱验证码链路设计上是前端调 `/api/v2/auth/send-code`，后端 AuthService 先查 Redis 冷却，再查 Clerk 判断是登录还是注册，生成验证码，存 Redis，发邮件，最后写 60 秒冷却。验证码登录或密码登录成功后，后端返回 Clerk Sign-in Token，前端用 `signIn.create({ strategy: "ticket" })` 换 Session。Session 有了之后，前端通过 `getToken({ template: "__opencreator_jwt" })` 取 JWT，业务请求带 `Authorization: Bearer`。后端中间件用 Clerk PEM 公钥验 RS256，取 `sub` 写成 `request.user.user_id`。本地用户资料不放在 JWT 里，而是 Clerk `user.created` webhook 过 Svix 签名后写入 Mongo 的 `users` 集合。

## 14. 面试官追问怎么答

如果问为什么验证码存 Redis：

验证码是短期状态，天然需要 TTL，还要做发送频率限制。Redis 可以用 key 过期解决 5 分钟验证码有效期和 60 秒发送冷却，也能在验证成功后立即删除，防止重复使用。放数据库也能做，但要自己清理过期数据，读写路径更重。

如果问为什么不自己签 JWT：

因为身份系统已经交给 Clerk。自己签 JWT 会多一套密钥、过期、撤销和用户同步机制。当前后端只验证 Clerk JWT，把 `sub` 映射成业务 user_id，边界更简单。只有将来要支持内部服务 token、多身份源或离线授权时，才需要考虑自签 token。

如果问为什么 webhook 不需要 JWT：

webhook 是 Clerk 服务端调用 Publisher，不是浏览器用户请求，所以它不会带用户 JWT。它的安全边界是 Svix 签名。NovelComic 的 `clerk_webhook_handler()` 会校验 `svix-id`、`svix-timestamp`、`svix-signature` 和 `CLERK_WEBHOOK_SECRET`。

如果问怎么防止越权：

业务接口不从请求体拿 user_id，而是从 Bearer JWT 验签后的 `sub` 拿当前用户。比如 `/api/v2/user/info` 和改密码都走 `get_authenticated_user()`，拿的是中间件写进 `request.user` 的用户。

如果问当前代码风险：

JWT 验签和 Google OAuth 主链路已经比较清楚，但邮箱验证码/密码登录还缺 AuthService、Schema、EmailService。现在 controller 和测试表达了接口预期，Redis 和 Clerk 适配层也在，但全链路还没闭合。要补齐的话，优先写 `schemas/auth.py`，再写 `email_service.py`，再写 `auth_service.py` 串 Redis/Clerk/Email，最后补前端验证码页面和 API 模块。
