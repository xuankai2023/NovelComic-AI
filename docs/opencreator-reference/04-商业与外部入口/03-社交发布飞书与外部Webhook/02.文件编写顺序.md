# 社交发布、飞书与外部 Webhook：文件按什么顺序写

对照 [00-社交发布飞书与外部Webhook技术点.md](./00-社交发布飞书与外部Webhook技术点.md) 和 [01-社交发布飞书与外部Webhook.md](./01-社交发布飞书与外部Webhook.md)。01 讲运行时谁调谁，这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖，不按飞书或平台回调到达的时间排序。

文件名、函数名、目录都用 OpenCreator 的。下面每条链接就是要照着看的源码。

本组要交付的是三条能分开验收的链路，外加把已经属于别的模块的 Webhook 接在正确入口上：

```text
社交授权与发帖
  → state、换票、Redis token、三个 Poster

飞书入站命令
  → 解密、challenge、3 秒内 200、去重、改等级、加积分、回执

飞书出站通知
  → AI、Consumer、B2B、Lark 订单各用自己的 URL

外部 Webhook 边界
  → Clerk 验签留在登录入口
  → Stripe 留在支付入口
  → 厂商和 Consumer 回调留在 AI 网关入口
```

先背这份小目录。后面每节是同一批文件的展开。

链路顺序：

`redis_keys.py` → `base_provider.py` → 三个 provider → `social_post_request.py` → `social_auth.py` → 三个 poster → `routers.py` / 白名单 → `schemas/feishu.py` → `feishu_decrypt.py` → `feishu.py` → `feishu_message_parser.py` → `feishu_bot_service.py` → `feishu_event_service.py` → `feishu-webhook-client.ts` → Consumer `utils/feishu.py` → B2B `feishu_client.py` → `lark_notify.py` → 核对 Clerk / Stripe / AI 回调仍留在原入口

1. `social/provider/__base/redis_keys.py`：三套 Redis 前缀。
2. `social/provider/base_provider.py`：OAuth 抽象。
3. `tiktok_provider.py` / `youtube_provider.py` / `x_provider.py`：换票。
4. `social_post_request.py`：发帖 body。
5. `controller/v1/social_auth.py`：授权、换票、发帖。
6. 三个 Poster：按平台把视频发出去。
7. `routers.py` 与 `auth_middleware.py`：挂路由，只放开平台 webhook 空入口。
8. `schemas/feishu.py`：入站形状。
9. `feishu_decrypt.py` 与 `controller/v1/feishu.py`：先应答。
10. `feishu_message_parser.py`、`feishu_bot_service.py`、`feishu_event_service.py`：命令和回执。
11. AI `feishu-webhook-client.ts` 与 worker 装配。
12. Consumer `utils/feishu.py`。
13. B2B 卡片客户端。
14. `lark_notify.py`。
15. 核对 Clerk、Stripe、厂商 Webhook、Consumer 回调没有挂进 `social_auth` 或 `feishu`。本组不新写这四条。

## 3. 写授权和换票路由

OpenCreator 对照：[social_auth.py](../../../../../opencreate/opencreator-publisher/controller/v1/social_auth.py)

先写这两个入口，先不写发帖：

```text
GET /generate_auth_url/{integration}
GET /callback/{integration}
```

都依赖 `get_authenticated_user`。

授权：

```text
state = os.urandom(16).hex()
SETEX 300  social_auth 前缀 + user_id
返回 auth_url
```

换票：

```text
Redis state == query state
  → DELETE state
  → get_token(code, redirect_uri)
  → SETEX access 23 小时
  → SETEX refresh 364 天
```

state 不一致时不要删 key，也不要拿 code 去换票。

同时在 [routers.py](../../../../../opencreate/opencreator-publisher/controller/routers.py) 把路由挂到 `/social_auth`。`generate_auth_url` 和 `callback` 不要放进白名单。

做完：同一登录用户能拿到授权 URL；用错误 state 调 callback 失败且 Redis state 还在；用正确 state 换票后，access 和 refresh 两把 key 都在，state key 已删除。

## 8. 写命令解析、回执和事件处理

OpenCreator 对照：

- [feishu_message_parser.py](../../../../../opencreate/opencreator-publisher/services/feishu/feishu_message_parser.py)
- [feishu_bot_service.py](../../../../../opencreate/opencreator-publisher/services/feishu/feishu_bot_service.py)
- [feishu_event_service.py](../../../../../opencreate/opencreator-publisher/services/feishu/feishu_event_service.py)

解析先做，不碰数据库：

```text
email=... plan=pro|creator|starter
email=... credits=正整数 remake=非空备注
```

`plan` 映射：

```text
starter → 1
creator → 2
pro → 3
```

回执先打到 `FEISHU_BOT_WEBHOOK`。HTTP 200 且 `code == 0` 才返回 true。这一份回执不加签名。

事件服务接上第 7 步的后台任务：

```text
验 FEISHU_VERIFICATION_TOKEN
  → 未配置则跳过并记警告
SET NX feishu:event:dedup:{event_id}  EX 8 小时
  → 已存在则返回 already processed
只处理 im.message.receive_v1
丢掉 app 发送者、非文本、没有 mentions
先改等级，再加积分
对不上命令则只记日志
```

加积分：

```text
UnifiedCreditsService.add_topup_credits(
  source=feishu_bot,
  idempotency_key=feishu_{message_id}
)
```

`add_topup_credits()` 成功时自己写 `credits_inout_record`，`event_type=feishu_topup`。然后再写 `CreditsTopupRecord(topup_source=feishu)`。验收时两笔都要在。后一笔失败不能回滚已经加上的积分，因为 `event_id` 已经占坑。

单次积分超过 `FEISHU_MAX_CREDITS_PER_OPERATION`（默认 1,000,000）时只发错误回执，不加账。

做完：同一 `event_id` 重放不会加第二次积分；不同 `event_id`、相同 `message_id` 时，积分幂等键仍能挡住重复入账；改等级成功后群里能看到回执。收支记录和 admin 充值记录都能按这次 `message_id` 对上。

## 完整验收顺序

按这个顺序验完整链路：

1. 未登录调用 `generate_auth_url`、`callback`、`post_video` 被拒绝。
2. 登录用户能拿到 TikTok、YouTube、X 之一的授权 URL，Redis 里有 5 分钟 state。
3. state 不一致时不换票，Redis state 仍在。
4. state 一致时写入 access token（约 23 小时）和 refresh token（约 364 天），state 被删除。
5. 没有 access token 时发帖失败。
6. TikTok 走 URL 拉取且可见性为 `SELF_ONLY`；YouTube 默认 private；X 能带上 media id。
7. 一次请求里多个平台并发发帖，任一失败则整次失败。
8. `GET /social_auth/webhooks/{integration}` 未登录返回 ok，且不改 token。
9. 飞书 URL 校验能回 challenge；加密 body 解密失败返回 `code: 1`。
10. 普通飞书事件 HTTP 立即成功，命令在后台执行。
11. 未 @、非文本、机器人自己的消息不会改用户。
12. `plan=pro|creator|starter` 能改对 `system_level`。
13. 加积分超过单次上限被拒绝；合法命令以 `feishu_{message_id}` 入账，收支记录是 `feishu_topup`，admin 充值记录是 `topup_source=feishu`，群里有回执。
14. 同一 `event_id` 重放不会再次改等级或加积分。token 校验失败时去重 key 还不存在，飞书可以重试。
15. AI 模型调用通知对同一 `ai_task_id` 只发一次；飞书 `code != 0` 当失败。
16. Consumer 不发送余额不足告警。
17. 同一 B2B 信号在 `sent` 后不再发送；`failed` 允许下一次评估重发。
18. 定制订单完成后的 Lark 通知失败，不改变订单已完成状态。
19. 飞书 body 打到 Clerk 或 Stripe 入口会被原验签拒绝。Clerk 头打到 `/feishu/event` 不会改积分。
20. 画布节点状态仍只来自 workflow 事件。社交发帖成功和飞书回执都不推进节点。

完整验收要覆盖授权、发帖、飞书入站，以及至少一条出站通知。Clerk、Stripe、厂商回调用它们自己那组的验收，这里只验入口没有串。
