# 社交发布、飞书与外部 Webhook 全链路笔记

这份不是接口清单，是给面试和迁移用的链路笔记。要讲清楚的不是“画布跑完就发出去”，而是社交授权、飞书入站命令、飞书出站通知为什么是三件事，以及别的 Webhook 为什么不能借这三套验签。

先把一句话背下来：

社交授权和发帖留在 Publisher，token 只进 Redis；飞书入站先回 200，再在本进程后台改等级或加积分；出站通知各自打自己的机器人 URL，HTTP 200 之后还要看 JSON `code == 0`。

## 0. 先分清五件事

`社交 OAuth`：Clerk 用户和平台 token 的对应关系，存在 Publisher Redis。浏览器只在换票那一次请求里带 JWT，不保存 access token。

`社交发帖`：拿已有 access token 调 TikTok、YouTube、X。现码没有发布任务表，也没有 outbox。

`飞书入站`：运营在群里 @ 机器人，改等级或加充值积分。HTTP 200 先于业务完成。

`飞书出站`：命令回执、B2B 卡片、Lark 订单、AI 告警、Consumer 异常。每条用自己的 URL。`sent` 不再发，`failed` 还可以再认领。

`其它外部 Webhook`：Clerk、Stripe、厂商、AI→Consumer 留在原入口。本组只核对验签没有串。

画布节点不经过这三条。模型结果回到画布，走的是 AI 网关和 workflow 事件。Frontend 现码没有社交授权页，也没有发帖页。导航里的飞书链接是文档站，不走 OAuth。管理后台自己的飞书登录不进 Publisher 的 `/feishu/event`。

## 1. 授权 URL 绑的是当前登录用户

平台只有三个：`tiktok`、`youtube`、`x`。`generate_auth_url`、`callback`、`post_video` 都要登录用户。路由上的 `get_api_key` 只读取 `Authorization`，并且 `auto_error=False`，不会单独挡人。真正挡未登录请求的是认证中间件。

服务端自己生成 `state = os.urandom(16).hex()`。调用方只传 `redirect_uri`。state 写在：

```text
opencreator:social_auth:{integration}:{user_id}
```

TTL 是 5 分钟。同一个用户、同一个平台，后一次授权会盖掉前一次 state。换票时必须再带同一个 `redirect_uri`，否则平台对不上这次 code。

## 2. 平台跳转和 Publisher 换票不是同一次请求

TikTok、Google、X 把 `code` 和 `state` 送到 `redirect_uri`。Publisher 的 `/callback/{integration}` 不在认证白名单里，仍然要 Clerk JWT。

```text
平台浏览器跳转
  → 前端页面拿到 code、state
  → 前端用当前用户的 JWT 调 Publisher callback
  → 用 JWT.sub 拼 Redis key，比对 state
```

对不上就返回失败，不换 token，也不删 Redis。对上之后先删 state，再向平台换 token。换票若在删除之后失败，这次 state 已经没了，用户要重新走授权。

换票成功后写入：

```text
opencreator:access_token:{integration}:{user_id}     约 23 小时
opencreator:refresh_token:{integration}:{user_id}    约 364 天
```

这是缓存寿命。平台那边的授权被用户取消、或 refresh token 已失效时，Redis 里仍可能有值。三个 Provider 都实现了 `refresh_token()`，发帖路径没有调用它。access token 过期后，现码不会自动刷新，要用户重新授权。

X 的 PKCE 现码是固定值：`code_challenge`、`code_verifier` 都是 `challenge`，方法是 `plain`。这是占位，不能当成已经按用户生成的 PKCE。

## 3. 三个平台的发帖方式不一样

`POST /post_video` 的 body 是 `post_items`。每一项有 `integration`、`text`、`description`、`video_url`，schema 里还有可选 `result_id`。路由处理时没有用 `result_id` 做权限或订阅校验。

| 平台 | 视频怎么上去 | 现码默认可见性 |
| --- | --- | --- |
| TikTok | 平台按 URL 拉取，`PULL_FROM_URL` | `SELF_ONLY` |
| YouTube | Publisher 先下载到临时文件，再 resumable upload | `private` |
| X | Publisher 下载后按 2MB 分段上传，再发带 `media_ids` 的帖 | 发出即公开帖 |

Poster 只读 access token，读不到就直接失败。一次请求里的多个 `post_items` 用 `asyncio.gather` 在本进程并发发完，全部成功才返回成功。没有社交发布 outbox，也没有按视频或平台生成的幂等键。超时后客户端重试，可能在平台侧重复发帖。

`GET /api/v1/social_auth/webhooks/{integration}` 在认证白名单里。处理函数只打日志并返回 `ok`，不验平台签名，也不更新 token 或发帖状态。白名单只放开了 `webhooks/*`。

## 4. 飞书入站先在约 3 秒内应答

路由是 `POST /api/v1/feishu/event`。整段 `/v1/feishu/*` 都在认证白名单里，不验 Clerk JWT。

请求体如果带 `encrypt`，先解密：

```text
key = SHA256(FEISHU_ENCRYPT_KEY)
AES-256-CBC
前 16 字节是 IV
PKCS7
```

解密失败返回 `code: 1`，不进后台任务。`type == url_verification` 时立刻返回 `{"challenge": challenge}`。

其余事件放进 FastAPI `BackgroundTasks`，HTTP 层马上返回 `{"code": 0, "msg": "success"}`。这个 200 只表示 Publisher 收下了请求。后台加积分、改等级还没做完。任务在当前进程里跑，进程退出时，还没执行的后台任务会丢。这里没有队列，也没有 outbox。

## 5. 飞书事件靠 token 和 event_id

后台先看 `header.token` 是否等于 `FEISHU_VERIFICATION_TOKEN`。这个配置为空时，现码会跳过校验并打警告。加密和 token 是两道不同的检查，不能互相代替。

去重 key：

```text
feishu:event:dedup:{event_id}
```

用 Redis `SET NX`，TTL 8 小时，覆盖飞书大约 7.1 小时的重试窗口。key 在业务成功之前就占上。同一 `event_id` 再来会直接跳过。占坑之后处理失败，飞书重试也不会再跑一遍。未识别的 `event_type` 同样会先占坑，再只记日志。token 校验失败发生在占坑之前，同一次事件仍可重试。

现码只处理 `im.message.receive_v1`。过滤掉这些消息：

- `sender_type == app`：机器人自己的消息，避免回环。
- 非 `text`。
- 没有 `mentions`。
- 文本对不上命令。只记日志，不回格式说明。`send_format_error_message()` 写了，这条路径没有调用它。

## 6. 入站只有两条运营命令

先匹配改等级：

```text
email=用户邮箱 plan=pro|creator|starter
```

```text
starter → system_level 1
creator → system_level 2
pro     → system_level 3
```

对上之后按邮箱找用户，调用 `UserService.update_user_system_level()`。这条命令没有单独的业务幂等键，重复执行靠前面的 `event_id` 去重。邮箱若是飞书点出来的 Markdown 链接，只用方括号里看得见的地址。

没对上再匹配加积分。命令文本里的备注字段是 `remake`：

```text
email=用户邮箱 credits=数量 remake=备注
```

积分必须大于 0，备注不能空。单次上限是 `FEISHU_MAX_CREDITS_PER_OPERATION`，没配时按 1,000,000。入账走 `UnifiedCreditsService.add_topup_credits()`，`source=feishu_bot`，幂等键是 `feishu_{message_id}`。这一步自己会写收支记录，`event_type=feishu_topup`。成功后再写一条 admin 用的 `credits_topup_record`，`topup_source=feishu`。

两笔记账都在统一积分入账之后。后一条写失败时，积分已经加上，`event_id` 也已经占坑。不同 `event_id`、相同 `message_id` 时，积分幂等键仍能挡住重复入账。付款入账仍走支付那一篇，只是三池和幂等锁是同一套。

成功或失败都由 `FEISHU_BOT_WEBHOOK` 回群。这个回执不带签名字段。HTTP 200 之后还要看 JSON `code == 0`。

## 7. 出站飞书是多条机器人，互不相通

| 谁发 | 什么时候 | 成功标准 |
| --- | --- | --- |
| Publisher `FeishuBotService` | 入站命令做完 | HTTP 200 且 `code == 0`，回执不签名 |
| Publisher / Consumer `B2B` | 升单信号命中 | 同上，并写下 notification 状态 |
| Publisher `lark_notify` | 定制工作流订单付完 | 发送失败只记日志，订单仍是 completed |
| AI `FeishuWebhookClient` | 模型调用通知、告警、未知 reason | HTTP 200 且 `code == 0`，配了 secret 才签名 |
| Consumer `feishu_notify` | 运行时异常 | 先卡片，失败再退回文本；余额不足类文案直接不发 |

AI 侧签名：

```text
HMAC-SHA256
key = timestamp + "\n" + secret
签名内容为空字符串
结果 Base64
```

模型调用通知先 `claimModelCallNotification(ai_task_id)`，认领不到就不发。未知 reason 和告警是另外的 webhook URL。

B2B 卡片按 `user_id:signal.key` 认领。`sent` 和还在 `sending` 的记录不会再发。状态是 `failed` 时，下次评估可以重新认领再发。`feishu_immediate` 当时就发。`feishu_conditional` 先落一条到期动作，到期且用户还没自己升级，才发一次。Publisher 和 Consumer 各有一份同构客户端，打的是同一个机器人 URL。

定制订单通知打的是 `open.larksuite.com` 的 Lark 机器人。订单已经写成 `completed` 之后才发，通知失败不把订单改回未完成。

Consumer 告警会挡住包含 `Insufficient credits`、`error_code 3003`、`notify_code 3003` 的消息。

## 8. 其它外部 Webhook 只核对入口

这些请求不读社交 token，也不用飞书 `event_id`。验签材料不能互换。

| 入口 | 凭什么收下 | 200 表示什么 |
| --- | --- | --- |
| `POST /api/v3/webhooks/clerk` | Svix 头 + `CLERK_WEBHOOK_SECRET` 验原始 body | 签过的 `session.created` 已记录。现码不再踢掉其它 session |
| `POST /api/v1/user/create` | 登录白名单里的 `user.created` | 开始建用户、绑邀请、发欢迎积分 |
| `POST /api/v1/payments/webhook` | Stripe 签名 | 事件已验签。积分是否到账看处理器 |
| `AI /v1/provider-webhooks/*` | 厂商自己的回调校验 | 厂商事件已进入归一化 |
| AI → Consumer `webhook_url` | `x-oc-timestamp`、`x-oc-signature`、`x-oc-idempotency-key` | Consumer 收下了这一跳 HTTP。画布节点还要等 workflow 事件 |

飞书机器人的 `sign` 验不了 Consumer 那一跳，也验不了 Clerk 或 Stripe。RabbitMQ ACK、Redis Stream ACK 同样不是这几次 HTTP 应答。

## 9. 文件编写顺序

不要从群机器人回执或告警文案开始。Clerk JWT 和 Redis 先就位，再落社交，再落飞书入站，出站按 URL 分开接。

```text
社交 Redis key 和 Provider 抽象
  → 三个平台换票
  → 授权、callback、路由
  → 三个 Poster
  → 社交 webhook 空入口
  → 飞书事件形状和解密
  → HTTP 先应答
  → 命令解析、去重、改等级、加积分、回执
  → AI 出站客户端
  → Consumer 运行时告警
  → B2B 卡片
  → 定制订单 Lark
  → 核对 Clerk、Stripe、厂商回调仍留在原入口
```

如果只有飞书回执，用户还不能发视频。如果 `post_video` 返回成功，也还没有发布任务表或失败补偿。

## 10. 面试 1 分钟口述

社交发帖、飞书命令、飞书通知是三条链。已登录用户向 Publisher 要授权 URL，服务端把 5 分钟 state 按 `user_id` 写进 Redis。平台把 code 带回 `redirect_uri` 之后，前端还要带 Clerk JWT 调 callback。state 对上才删掉并换 token，access 大约 23 小时，refresh 大约 364 天。发帖只读 access token，不自动 refresh。TikTok 让平台按 URL 拉取，默认仅自己可见；YouTube 先下载再上传，默认 private；X 分段上传后发公开帖。多个平台在一次请求里并发，没有 outbox。飞书 `POST /feishu/event` 先解密，challenge 立即返回，其它事件先 200 再进 BackgroundTasks。后台验 token，再用 `event_id` 占 8 小时的坑，然后只处理被 @ 的文本。命令要么改 `system_level`，要么按 `feishu_{message_id}` 加充值积分。出站每条机器人看自己的 URL，HTTP 200 还要 `code == 0`。Clerk、Stripe、厂商回调和 AI 打给 Consumer 的 HMAC 都不进这套验签。

## 11. 面试官追问怎么答

如果问平台 callback 为什么还要 Clerk JWT：

平台跳转只把 code 送到前端页面。Publisher 的 `/callback` 不在白名单里。它用当前用户的 `sub` 拼 Redis key，才能把 token 绑到对的人。不带 JWT 的浏览器跳转对不上 state。

如果问为什么先删 state 再换票：

state 是一次性的。对上之后先删，避免同一个 code 被重放换两次票。代价是换票失败后这次授权作废，用户要重新点授权。对不上则保留 Redis，方便重试比对。

如果问 access token 过期为什么不调 refresh：

`refresh_token()` 在 Provider 上，发帖路径没有调用它。Poster 读不到 access token 就失败。Redis 里的 refresh 只是缓存，不代表平台授权仍有效，也不代表现码会自动续期。

如果问飞书 200 为什么不等于加分成功：

飞书要求大约 3 秒内应答。业务放在 `BackgroundTasks` 里。进程退出时，还没跑的任务会丢。真正改等级或加积分发生在占住 `event_id` 之后。

如果问占坑失败了为什么不能靠飞书重试补：

`SET NX` 在业务成功之前。处理中途失败，重试会看到 key 已存在而跳过。token 校验失败是例外，它发生在占坑之前，飞书还能再投。

如果问飞书 `sign` 能不能验 Consumer 回调：

不能。飞书签名的 key 是 `timestamp + "\n" + secret`，内容是空字符串。Consumer 那一跳是 `timestamp + "." + rawBody`，密钥是 `consumerWebhookSecret`。Stripe 和 Clerk 又各用自己的头。

## 12. NovelComic 当前实现自查

参考笔记里写“还没有社交发帖页，也没有飞书入站命令”。前端仍然没有调用 `generate_auth_url`、`callback` 或 `post_video`。Publisher 里这几条路由、三个 Poster 和飞书入站已经在。

- 授权、换票、发帖都要求登录用户。state、access、refresh 分开三把 Redis key。未登录可以打 `GET /social_auth/webhooks/{integration}`，它只回 ok。
- 换票顺序和参考笔记不同。现码先 `get_token()`，access 和 refresh 都有才删 state 并写入两把 token key。缺 token 时 state 还在，返回 502。参考笔记是对上 state 后先删，再换票。
- X 的 PKCE 仍是固定字符串 `challenge`。Poster 只读 access token，不调用 `refresh_token()`。TikTok 仍是 `PULL_FROM_URL` 加 `SELF_ONLY`。发帖用 `asyncio.gather`，没有 outbox。
- 飞书 `POST /api/v1/feishu/event` 会解密、回 challenge，再把业务放进 `BackgroundTasks`。token 未配置时跳过校验。去重 key 是 `feishu:event:dedup:{event_id}`，8 小时。加积分走 `add_topup_credits()`，幂等键 `feishu_{message_id}`。改等级现码直接写 `users.system_level`，不是单独的 `UserService.update_user_system_level()`。
- 出站已经拆开。AI 的 `FeishuWebhookClient` 在配了 secret 时用 `timestamp\nsecret` 做 HMAC，空消息再 Base64。模型通知先 `claimModelCallNotification(ai_task_id)`。Consumer 会挡住 `Insufficient credits` 和 3003。B2B 认领键现码是 `user_id:action_id`，`sent` 和 `sending` 不再发。定制订单走 `lark_notify.py` 的另一条 webhook，发送失败只记日志并返回 false。
- Clerk、Stripe、厂商 Webhook 仍在各自入口。社交发帖成功和飞书回执都不推进画布节点。
