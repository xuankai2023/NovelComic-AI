# 支付、订阅、积分与用量账本全链路笔记

这份不是接口清单，是给面试和迁移用的链路笔记。要讲清楚的不是“点了升级按钮积分就到账”，而是结账 URL、验签入账、三池余额、Redis 预扣和 `usage_v2` 为什么是五件不同的事。

先把一句话背下来：

用户点击只负责同步打开支付窗，并换到 Stripe 的 `url`。积分要等 `POST /api/v1/payments/webhook` 验签之后，才按订单或发票写入充值池或订阅池。模型花钱发生在 Consumer：先在 Redis 三池里预扣，执行成功后才写 `usage_v2` 并落到 Mongo。

## 0. 先分清五件事

`结账`：Publisher 创建 Stripe Checkout Session，响应里只有 `url`、`id`、`mode`、`status`。浏览器还没付款，本地积分还没变。

`入账`：验签后的 Webhook 改订单、订阅和积分，并写 `credits_inout_record`。回站完成页不参与这一步。

`余额`：`GET /api/v2/user/info` 读三池快照。Webhook 比回站页慢时，完成页已经出现，数字仍是旧的。

`预扣`：Consumer 在调用模型前用一次 Lua 扣 Redis，并写下 `pending_deduction`。这一步不写 `usage_v2`。

`用量`：模型成功后，`tasks/usage.py` 的 `handle_consume()` 写 `usage_v2`、扣 Mongo 三池、写收支、删 pending。失败走 `rollback_deduct()`，把 Redis 加回去，不写 usage。

## 1. 前端只负责把用户送到 Stripe

Safari 会拦掉异步回调里的 `window.open`。点击必须停在同步栈里：

```text
点击
  → openPaymentWindow()
  → 立刻打开 /payment-redirect?request_id=...
  → 支付参数写入 sessionStorage
  → 新页面再请求 checkout
  → 拿到 url 后跳 Stripe
```

支付类型有四种：`subscription_checkout`、`subscription_plan`、`billing_portal`、`credits_checkout`。

`/payment-redirect` 外包 `Protected`。商业化开关关掉、Clerk 未登录、或 `sessionStorage` 里没有这次 `request_id`，页面停住，不创建 Checkout Session。

年付，或月付金额超过 210 美元，会先选支付方式。微信和支付宝年费走一次性支付，入账路径和 Stripe 周期订阅不同。

## 2. 买积分和开订阅不是同一条结账

买积分：

```text
POST /api/v1/payments/checkout
```

请求里是金额、成功回跳、取消回跳。Stripe mode 是一次性 `payment`。本地此时只多一张未完成订单。

新订阅：

```text
POST /api/v2/payments/subscription/checkout
```

请求里是 `subscription_key`、`interval`、`price_id`、`payment_method`。新页面会先读 `GET /api/v2/user/info`，`subscription_billing_state.checkout_eligible` 为假时不创建第二条结账。

已有订阅改套餐：

```text
PUT /api/v2/payments/subscription/plan
```

这条可能返回新的 checkout URL，也可能返回 `requires_action` 和 `client_secret`，让前端做 3DS。本地可以先写成 `3ds_processing`、`payment_failed` 或 `processing`。这些状态只说明发票还没结清，订阅积分要等后面的付清事件。

V1 仍保留同名结账和改套餐接口。前端 A/B 和旧弹窗还会打到 V1。不能凭 URL 上的 `v1` / `v2` 判断积分存在哪张表。

## 3. 回站页只做展示

Stripe 付完后回到 `/credits/result?session_id=...`。`PaymentResult` 用 `BroadcastChannel` 把 `session_id` 告诉原窗口，然后关页。这里没有余额写入。

旁边两口也只读：

```text
GET /api/v1/payments/checkout/{session_id}/status
GET /api/v1/payments/invoice
```

`status` 读 Stripe Checkout Session。`invoice` 给支付记录里的发票链接。两口都不发放积分。

原窗口收到完成广播、升级弹窗关闭、工作流运行前后，都会 `reloadBalance()`，再打 `GET /api/v2/user/info`。拉到的是服务端当前快照。

## 4. Webhook 先验签，再按事件分发

入账入口只有：

```text
POST /api/v1/payments/webhook
```

这条在登录白名单里，不走用户 JWT。安全边界是 `Stripe-Signature`。`STRIPE_WEBHOOK_SECRET` 为空或签名不对，直接 400，积分不变。

验签通过后，事件按 `provider + event_id` 落库。已经成功处理过的同一事件直接跳过。

| 事件 | 做什么 |
| --- | --- |
| `checkout.session.completed` / `checkout.session.async_payment_succeeded` | 一次性买积分入充值池 |
| `invoice.paid` / `invoice.payment_succeeded` | 订阅发票付清，发订阅积分 |
| `customer.subscription.deleted` | 停用订阅积分 |
| `invoice.payment_failed` / `invoice.payment_action_required` | 记下失败或待操作，不发可花积分 |
| `charge.refunded` | 退款 |

延迟支付会先收到 `checkout.session.completed`，当时钱可能还没结算。处理器看到未结算就返回，等后面的 `async_payment_succeeded` 再读 Stripe 当前状态。定制工作流订单在完成处理器里提前返回，走自己的订单表，不进充值积分。

## 5. 可花积分是三池相加

```text
total = topup + active subscription + unexpired gift
```

| 池 | Mongo | Redis | 什么时候能花 |
| --- | --- | --- | --- |
| 充值积分 | `user.credits` | `opencreator:credit_balance_check:{user_id}` | 一直算进总额 |
| 订阅积分 | `subscription_user_credits` | `opencreator:subscription_user_credits:{user_id}` | `status=active` 且未过期 |
| 赠送积分 | `gift_credits` | `opencreator:gift_credits:{user_id}` | `expire_timestamp` 还没到 |

查询快照以 Mongo 为准。消费端扣费以 Redis 为准。写入用 cache aside：先写 Mongo，再删对应 Redis key。key 被删掉后，下一次扣费才从 Mongo 回填。删除失败时，Mongo 已是新余额，Redis 仍可能是旧值，幂等锁继续留着，避免再加一次。

这个缝隙被记成后续工作：扣积分端以 Redis 为准，快照端仍以 Mongo 为准。

## 6. 充值按订单幂等，订阅等发票付清

一次性支付结算后：

```text
CheckoutSessionCompletedProcessor
  → add_topup_credits_from_payment(order_id)
  → user.credits 增加
  → 删除充值 Redis key
  → 写 recharge 收支
```

换算写在服务里：用户等级 `3` 每美元 500 积分，其他用户每美元 400。金额单位是美分：`credits = cents * credits_per_dollar / 100`。

幂等键是 `order_id`。Redis `SET NX` 占住 `opencreator:credits:idempotency:{order_id}`。Mongo 写入成功前失败会放开锁；写入成功后，即使删缓存失败也不放开锁。收支记录是 `source=stripe_payment`，`event_type=recharge`，`credit_type=topup`。

周期订阅的积分不在 checkout 接口里发：

```text
invoice.paid / invoice.payment_succeeded
  → SubscriptionSucceedProcessor
  → a_reward_subscription_credits()
  → save_subscription_credits()
  → 删除订阅 Redis key
```

`billing_reason` 分成创建、续费、套餐变更。订阅状态必须是 `active` 才发积分。月付直接发这一期；年付启动按月续发，每一期仍走 `save_subscription_credits()`。订阅删除走 `a_deactivate_subscription_credits()`。

微信或支付宝年费走 `process_one_time_subscription_order()`。它发的是订阅积分，仍用订单幂等，不走充值换算。

`PUT /subscription/plan` 返回成功、3DS `client_secret` 或支付失败，都不等于新套餐积分已经可花。

## 7. 用量、入账、支付是三张历史

| 接口 | 事实 | 数据来源 |
| --- | --- | --- |
| `GET /api/v2/usage/history` | 模型消费 | `usage_v2` |
| `GET /api/v2/usage/income` | 积分入账 | `credits_inout_record`，方向 `in` |
| `GET /api/v2/payments/history` | 订单和支付 | 支付记录 |

一笔充值同时出现在入账和支付历史里，不出现在用量历史里。用量历史要等模型扣费确认之后才有这条。

记账很多地方走 `safe_create_record()`。记账失败会打错误日志，已完成的余额变更不回滚。余额和账本短时间可能对不上，需要补录，不能靠失败记账把积分扣回去。

## 8. 模型扣费在 Consumer，预扣先于 usage

Publisher 不在执行路径里扣模型费用。

```text
reserve_deduction_for_route()
  → 按原价算，再按订阅折扣重算
  → 两次结果有一次不大于 0 就返回，不占坑
  → check_for_pre_deduction()
```

Redis key 缺失时从 Mongo 回填。Lua 在同一次脚本里：

1. 先扣订阅积分。
2. 再扣充值积分。
3. 最后扣未过期赠送积分。
4. 总额够，才写下 `opencreator:pending_deduction:{deduction_id}`，保留 24 小时。

不够就返回失败，调用方抛余额不足，不写 usage。

模型成功后 `queue_usage_once()` 把消费推进 `handle_consume()`：

```text
写 usage_v2
  → 扣 Mongo 三池
  → 写 usage_deduct 收支
  → 删除 pending
  → deduction_status = deducted
```

同一 `deduction_id` 已经是 `deducted` 时不再扣第二次。模型失败走 `rollback_deduct()`，按当初三池扣减量把 Redis 加回，并删 pending。

`do_deduct()` 还在文件里。现网预扣已经在 Lua 里完成，成功入账不再靠它减 Redis。

## 9. 文件编写顺序

按依赖写，不按用户付款成功的时间顺序。结账 URL 只是前半段，同一轮不能停在跳转页。

```text
三池和收支形状
  → 只返回 URL 的 checkout
  → 前端支付窗
  → Webhook 验签和 event_id 去重
  → 一次性买积分入账
  → 订阅发票付清和停用
  → 用户信息返回三池快照
  → 用量、入账、支付三张历史
  → Redis 预扣
  → usage_v2 确认和失败回滚
  → 赠送积分过期、年付按月续发
```

checkout 已经返回 URL 时，不要在接口里加积分。回站页显示完成时，也不要把它当成到账。

## 10. 面试 1 分钟口述

用户点支付时，浏览器在同一次点击里打开 `/payment-redirect`，新页面再创建 Stripe Checkout Session，拿到 `url` 就跳走。这时本地只有一张未完成订单。买积分打 V1 `payment` 模式，新订阅打 V2 `subscription` 模式。改套餐即使返回 3DS `client_secret`，也不发可花积分。Stripe 打 `POST /api/v1/payments/webhook`，先验 `Stripe-Signature`，再按 `event_id` 去重。已结算的一次性支付按 `order_id` 加充值积分，等级 3 是每美元 500，其余 400。订阅要等 `invoice.paid`，状态是 `active` 才发订阅积分。回站页只广播 `session_id`，余额以之后的 `GET /api/v2/user/info` 为准。模型执行前，Consumer 用 Lua 按订阅、充值、赠送的顺序扣 Redis，并写 pending。成功才写 `usage_v2` 和 Mongo；失败把 Redis 加回。用量、入账、支付是三张历史，不能合成一张状态。

## 11. 面试官追问怎么答

如果问 checkout 返回 200 为什么不加积分：

200 只表示 Stripe 托管页创建成功。钱还没结算，订单还可能被取消。加分必须发生在验签后的 Webhook 里，并且用订单或发票做幂等。

如果问完成页已经显示支付完成，余额为什么还是旧的：

完成页不写账。它把 `session_id` 广播回原窗口，原窗口再读用户信息。Webhook 慢一步时，快照仍是入账前的三池。

如果问为什么查询看 Mongo、扣费看 Redis：

扣费要在一次 Lua 里判断总额并占坑，不能先读 Mongo 再扣。入账则先写 Mongo 再删缓存，下一次扣费回填。删缓存失败时锁不放开，避免同一笔订单再加一次。

如果问订阅结账成功为什么还不能花新套餐的积分：

周期订阅的积分绑在发票付清上。`checkout.session.completed`、改套餐接口和 3DS 都可能发生在发票结清之前。`status` 不是 `active` 就不发。

如果问预扣成功算不算已经入账：

不算。预扣只改 Redis，并留下 `pending_deduction`。`usage_v2` 要等模型成功后的 `handle_consume()`。失败回滚不写用量历史。

如果问记账失败为什么不把积分扣回去：

`safe_create_record()` 失败只记日志。余额变更已经提交。回滚会把一笔真实入账抹掉，补录账本比回滚余额安全。

## 12. NovelComic 当前实现自查

参考笔记里写“NovelComic 现在还没有这条支付账本”。现码已经接上结账、验签入账、三池快照、三张历史、Redis 预扣和 usage 确认。

- 前端有 `openPaymentWindow()`、`/payment-redirect` 和 `/credits/result`。买积分打 `POST /api/v1/payments/checkout`，订阅打 `POST /api/v2/payments/subscription/checkout`。改套餐响应里如果带 `requires_action` 和 `client_secret`，支付窗会留下这个 secret。
- Publisher 的 `POST /api/v1/payments/webhook` 在登录白名单里，用 `Stripe-Signature` 验签。密钥为空或签名错误返回 400。事件按 `provider + event_id` 去重。买积分走 `CheckoutSessionCompletedProcessor`，订阅发票走 `SubscriptionSucceedProcessor.process_event()`。
- `SubscriptionSucceedProcessor.process()` 仍只做邀请奖励和支付成功信号。Webhook 分发不走这个方法。排障时要把 `process()` 和 `process_event()` 分开。
- 充值换算已经是等级 3 每美元 500、其余 400，幂等键走订单。用户信息会带回三池快照和 `checkout_eligible`。用量、入账、支付历史分别在 `/api/v2/usage/history`、`/income`、`/api/v2/payments/history`。
- Consumer 的预扣 Lua 按订阅、充值、赠送扣减，pending 前缀是 `opencreator:pending_deduction`。成功由 `UsageTask.handle_consume()` 写 `usage_v2`，同一 `deduction_id` 已经 `deducted` 就不再扣。失败走 `rollback_deduct()`。`emit_credits_deducted()` 还在，它在确认入账之后发一条扣费事件，不再代替账本。
- `controller/v1/payments.py` 现码只有买积分 checkout 和 Webhook。回站 `checkout/{session_id}/status`、发票、订阅模板和账单门户不在这个文件里。Publisher 里也没有微信、支付宝、`3ds_processing`、`invoice.payment_action_required` 这些路径。赠送积分和年付按月续发的服务已经在，验收时仍要单独看过期赠送是否退出总额、同一期年付是否只发一次。
