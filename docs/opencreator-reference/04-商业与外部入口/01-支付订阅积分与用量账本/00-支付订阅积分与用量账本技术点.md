# 支付、订阅、积分与用量账本：这里面有哪些技术点

先把这块拆开。它不是“点了升级按钮积分就到账”，也不是“模型一开始跑就把 usage 写进账本”。这篇只讲用户付钱、积分入账、余额展示，以及模型执行前的扣费边界。

最短链路是：

```text
用户点击订阅或买积分
  → 同步打开 /payment-redirect
  → Publisher 创建 Stripe Checkout Session
  → 浏览器跳到 Stripe
  → Stripe 发送验签 Webhook
  → 发放充值积分或订阅积分
  → 写 credits_inout_record
  → 删除 Redis 余额缓存
  → 前端再读 GET /api/v2/user/info

模型节点准备执行
  → Consumer 在 Redis 三池里预扣
  → 执行成功后才写 usage_v2，并落到 Mongo
  → 前端用用量、入账、支付三张历史分别查询
```

所以结账 URL、回站完成页、账本入账，是三件事。预扣成功和 usage 已入账，也是两件事。

---

## 1. 前端只负责把用户送到 Stripe

用户点击支付时，浏览器要在同一次点击里打开窗口。Safari 会拦掉异步回调里的 `window.open`。

OpenCreator 的做法是：

```text
点击
  → openPaymentWindow()
  → 立刻打开 /payment-redirect?request_id=...
  → 支付参数写入 sessionStorage
  → 新页面再请求 checkout
  → 拿到 url 后跳 Stripe
```

OpenCreator 源码：[payment-window.ts](../../../../../opencreate/opencreator-frontend/src/utils/payment-window.ts)、[payment-redirect.tsx](../../../../../opencreate/opencreator-frontend/src/routes/payment-redirect.tsx)。

`/payment-redirect` 外包了 `Protected`。商业化开关关掉时，这一页直接停住，不创建 Checkout Session。

checkout 成功只返回：

- `url`
- `id`
- `mode`
- `status`

`url` 是 Stripe 托管页地址。浏览器还没付款，本地积分还没变。

---

## 2. 买积分和开订阅不是同一条结账

买积分：

```text
POST /api/v1/payments/checkout
```

请求里是金额、成功回跳、取消回跳。Stripe mode 是一次性 `payment`。

新订阅：

```text
POST /api/v2/payments/subscription/checkout
```

请求里是 `subscription_key`、`interval`、`price_id`、`payment_method`。Stripe mode 通常是 `subscription`。

已有订阅改套餐：

```text
PUT /api/v2/payments/subscription/plan
```

这条可能返回新的 checkout URL，也可能返回 `requires_action` 和 `client_secret`，让前端去做 3DS。本地订阅状态可以先写成 `3ds_processing`、`payment_failed` 或 `processing`。这些状态只说明发票还没结清，订阅积分要等后面的付清事件。

V1 仍保留同名结账和改套餐接口。前端 A/B 和旧弹窗还会打到 V1。不能凭 URL 上的 `v1` / `v2` 判断积分存在哪张表。

年付，以及月付金额超过门槛时，`/payment-redirect` 会先让用户选 Stripe、支付宝或微信。微信和支付宝年费走一次性支付，入账路径和 Stripe 周期订阅不同。

## 3. 回站页只做展示

Stripe 付完后回到：

```text
/credits/result?session_id=...
```

OpenCreator 源码：[credits.result.tsx](../../../../../opencreate/opencreator-frontend/src/routes/credits.result.tsx)、[PaymentResult.tsx](../../../../../opencreate/opencreator-frontend/src/components/checkout/PaymentResult.tsx)。

这一页显示支付完成，并用 `BroadcastChannel` 把 `session_id` 告诉原窗口。它不改积分。

旁边还有两口展示接口：

```text
GET /api/v1/payments/checkout/{session_id}/status
GET /api/v1/payments/invoice
```

`status` 读的是 Stripe Checkout Session 状态。`invoice` 给支付记录里的发票链接。两口都不发放积分。

用户看到的余额来自：

```text
GET /api/v2/user/info
```

返回里分开带：

- `credits`：充值积分展示值
- `subscription_credits`：当前有效订阅积分
- `gift_credits`：未过期赠送积分
- `subscription`：当前订阅
- `subscription_billing_state`：还能不能再开一条结账

Webhook 比回站页慢时，完成页已经出现，余额仍是旧的。排障先对验签事件和幂等键。

---

## 4. Webhook 先验证 Stripe 签名，再按事件类型分发

入账入口只有：

```text
POST /api/v1/payments/webhook
```

这条在登录白名单里，不走用户 JWT。安全边界是 `Stripe-Signature`。

OpenCreator 源码：[payments.py](../../../../../opencreate/opencreator-publisher/controller/v1/payments.py)、[stripe_utils.py](../../../../../opencreate/opencreator-publisher/utils/stripe_utils.py)。

`STRIPE_WEBHOOK_SECRET` 为空时直接拒绝。签名不对也拒绝。验签通过后，事件先按 `provider + event_id` 落库。已经成功处理过的同一事件直接跳过。

分发表里和积分有关的主要是：

| 事件 | 处理器 |
| --- | --- |
| `checkout.session.completed` / `checkout.session.async_payment_succeeded` | 结账完成。一次性买积分在这里入充值积分 |
| `invoice.paid` / `invoice.payment_succeeded` | 订阅发票付清，发订阅积分 |
| `customer.subscription.deleted` | 停用订阅积分 |
| `invoice.payment_failed` / `invoice.payment_action_required` | 记下支付失败或待操作，不发可花积分 |
| `charge.refunded` | 退款 |

延迟支付会先收到 `checkout.session.completed`，当时钱可能还没结算。处理器看到未结算就返回，等后面的 `async_payment_succeeded` 再读 Stripe 当前状态。定制工作流订单在完成处理器里提前返回，走自己的订单表，不进充值积分。

## 5. 可花积分是三池相加

```text
total = topup + active subscription + unexpired gift
```

| 池 | 存在哪里 | 什么时候增加 | 什么时候能花 |
| --- | --- | --- | --- |
| 充值积分 `topup` | `user.credits` | 一次性支付入账、后台、飞书、邀请等 | 一直算进总额 |
| 订阅积分 | `subscription_user_credits` | 订阅创建、续费、套餐变更且发票已付 | `status=active` 且未过期 |
| 赠送积分 | `gift_credits` | 系统赠送或续赠 | `expire_timestamp` 还没到 |

OpenCreator 源码：[unified_credits_service.py](../../../../../opencreate/opencreator-publisher/services/unified_credits/unified_credits_service.py)、[schemas.py](../../../../../opencreate/opencreator-publisher/services/unified_credits/schemas.py)。

查询快照以 Mongo 为准。消费端扣费以 Redis 为准。两边用同一套 key：

```text
opencreator:credit_balance_check:{user_id}
opencreator:subscription_user_credits:{user_id}
opencreator:gift_credits:{user_id}
```

写入用 cache aside：先写 Mongo，再删对应 Redis key。key 被删掉后，下一次扣费才会从 Mongo 回填。删除失败时，Mongo 已是新余额，Redis 仍可能是旧值，幂等锁继续留着，避免再加一次。

当前代码把这个缝隙记成后续工作：扣积分端以 Redis 为准，快照端仍以 Mongo 为准。

## 6. 充值加分用订单做幂等，并按用户等级换算

一次性支付结算后：

```text
CheckoutSessionCompletedProcessor
  → OrderService._process_completed_order_for_payment_v2()
  → UnifiedCreditsService.add_topup_credits_from_payment()
```

换算写在服务里：

- 用户等级 `3`：每美元 500 积分
- 其他用户：每美元 400 积分
- 金额单位是美分：`credits = cents * credits_per_dollar / 100`

幂等键是 `order_id`。Redis `SET NX` 占住 `opencreator:credits:idempotency:{order_id}`，占不到就当这次已经加过。Mongo 写入成功前失败会放开锁；写入成功后，即使删缓存失败也不放开锁。

同一笔还会写收支记录，`source=stripe_payment`，`event_type=recharge`，`credit_type=topup`。

## 7. 订阅积分等发票付清

周期订阅的积分不在 checkout 接口里发。

```text
invoice.paid / invoice.payment_succeeded
  → SubscriptionSucceedProcessor
  → SubscriptionManagementService.a_process_subscription_succeed()
  → SubscriptionCreditsRewardService.a_reward_subscription_credits()
  → UnifiedCreditsService.save_subscription_credits()
```

`billing_reason` 分成创建、续费、套餐变更。订阅状态必须是 `active` 才发积分。月付直接发这一期；年付启动按月续发任务。

订阅删除走 `a_deactivate_subscription_credits()`，停用订阅积分并删 Redis key。

`PUT /subscription/plan` 返回成功、3DS `client_secret` 或支付失败，都不等于新套餐积分已经可花。

## 8. 用量、入账、支付记录是三张历史

| 接口 | 事实 | 数据来源 |
| --- | --- | --- |
| `GET /api/v2/usage/history` | 模型消费 | `usage_v2` |
| `GET /api/v2/usage/income` | 积分入账 | `credits_inout_record`，方向 `in` |
| `GET /api/v2/payments/history` | 订单和支付 | 支付记录 |

收支记录上有 `credit_type`、`event_type`、`direction`、`amount`、`balance_before`、`balance_after`、`source`、`idempotency_key`。

记账很多地方走 `safe_create_record()`。记账失败会打错误日志，已完成的余额变更不回滚。所以余额和账本短时间可能对不上，需要补录，不能靠失败记账把积分扣回去。

---

## 9. 模型扣费在 Consumer，预扣先于 usage

Publisher 不在执行路径里扣模型费用。Consumer 在调用模型前：

```text
InvocationBillingService.reserve_deduction_for_route()
  → 按定价和订阅折扣算出 cost
  → CreditBalanceCheckServiceV2.check_for_pre_deduction()
```

预扣在一次 Lua 里完成：

1. 先扣订阅积分。
2. 再扣充值积分。
3. 最后扣未过期赠送积分。
4. 余额够，才写下 `opencreator:pending_deduction:{deduction_id}`。

这一步只改 Redis。`usage_v2` 还没有。

模型成功后，`queue_usage_once()` 把消费推进 `tasks/usage.py` 的 `handle_consume()`。那里才写 `usage_v2`、扣 Mongo 三池、写收支、删 pending，并把 `deduction_status` 收成 `deducted`。

模型失败走 `rollback_deduct()`，把 Redis 加回去并删 pending。失败回滚不写 usage。

`cost <= 0` 的调用不占坑，也不写 usage。

## 动手前要有的东西

### 前端

- Clerk 登录，以及 `getToken({ template: "__opencreator_jwt" })`
- `Protected` / `RequireAuth`
- 商业化开关
- 支付窗口和 `/payment-redirect`
- 用户信息里的三池字段

### Publisher

- 用户文档，含 `user_id`、`credits`、`system_level`
- Stripe Secret 和 `STRIPE_WEBHOOK_SECRET`
- Mongo、Redis
- 订单、订阅、三池积分、收支记录
- Webhook 验签和事件去重

### Consumer

- 模型定价
- Redis 三池 key
- `usage_v2`
- 预扣、回滚、消费入账任务

登录和 JWT 先看 [01-登录与JWT](../../01-用户入口/01-登录与JWT/01-登录与JWT.md)。Developer API、CLI 和飞书机器人只消费同一套账户能力，入口不在这篇展开。
