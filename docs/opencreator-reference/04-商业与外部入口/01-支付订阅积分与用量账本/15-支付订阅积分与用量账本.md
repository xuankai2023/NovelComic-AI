# OpenCreator 支付、订阅、积分与用量账本

## 职责

Publisher 承担 Stripe checkout、订阅变更、支付 Webhook、三类积分余额和收支/用量记录。Frontend 只发起结账并展示状态；支付成功与积分入账以验签后的 Webhook 和服务端账本为准。

三类积分是充值积分、有效订阅积分、未过期赠送积分：

```text
total = topup + active subscription + unexpired gift
```

## 入口

- 订阅结账：`POST /api/v2/payments/subscription/checkout`；套餐变更：`PUT /api/v2/payments/subscription/plan`。
- 单次买积分：`POST /api/v1/payments/checkout`。
- Stripe 回调：`POST /api/v1/payments/webhook`。
- 回站展示：`GET /checkout/{session_id}/status` 和 `/invoice`。
- 账本：`GET /api/v2/usage/history`、`/income`、`/payments/history`。
- 当前余额通常随用户信息/账户快照返回；CLI `/info` 也读取账户积分快照。

## 主链

```text
前端请求 checkout
  → Publisher 创建 Stripe Session
  → 返回 URL，浏览器跳 Stripe
  → Stripe 发送验签 Webhook
  → processor 更新订单/订阅
  → 发放或停用对应积分
  → 写 credits_inout_record
  → 删除 Redis 余额缓存
  → 前端回站刷新用户信息和历史

AI 节点准备执行
  → Consumer 读取计费配置并做余额检查/扣减
  → 记录 usage
  → Publisher 的历史接口供前端查询
```

checkout 返回 URL、回站 status 显示成功，都不能替代 Stripe Webhook 入账。

## 关键状态/消息

- 订阅生命周期由 Stripe 事件驱动，包括成功、更新、暂停、删除、支付失败/待操作。
- 充值加分以订单/事件 ID 作为幂等键，Redis `SET NX` 防止 Webhook 重放重复加分。
- 积分写入目前先写 Mongo，再删 Redis，让下一次消费侧读取回填。
- 收支记录包含 `credit_type`、`event_type`、`direction`、`amount`、前后余额、来源和幂等键。
- 用量历史是消费事实；入账历史是积分变动事实；支付历史是订单/支付事实，三者不能混成一张状态。
- 当前充值换算代码：Pro 每美元 500 积分，其他用户每美元 400 积分；以源码与线上配置演进为准。

## 跨仓边界

- Frontend 不直接加积分，也不以跳转结果确认到账。
- Publisher 拥有支付、订阅、用户积分池和面向用户的账本接口。
- Consumer 在执行路径做模型成本检查、预扣/扣减和 usage 记录，不处理 Stripe。
- opencreator-ai 回传 Provider usage 事实，但不拥有用户订阅和余额。
- Agent 与 Developer API 最终都消费同一用户账户能力，但各自入口和任务状态不同。

## 遗留/未启用

- `UnifiedCreditsService` 明确记录当前以 Mongo 为准，但扣积分端以 Redis 为准，并留有“后续重写为 Redis 权威”的 TODO；这是现实一致性缝隙。
- 积分收支记录多处采用 `safe_create_record`，记账失败会记录错误但不回滚已完成的余额变更，账本可能需补录。
- 老支付 V1 与订阅 V2 并存，不能只按 URL 版本推断新旧数据所有权。
- 回站轮询、支付记录与 Stripe Webhook 可能短时不同步，排障应优先核对验签事件和幂等键。
