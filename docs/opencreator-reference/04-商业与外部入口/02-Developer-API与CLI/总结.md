# Developer API 与 CLI 全链路笔记

这份不是接口清单，是给面试和迁移用的链路笔记。要讲清楚的不是“外部也能跑工作流”，而是 CLI 的 `ak_`、Developer 的 `sk_`、画布 Clerk JWT 为什么各验各的，以及 `202` 为什么只表示 run 已入队。

先把一句话背下来：

CLI 换出的 `ak_` 只读账户；`sk_` 代表 owner，用来创建 workflow 并入队；执行仍走原来的 DAG，外部靠 REST 轮询 `api:{task_id}`。

## 0. 先分清四段

`CLI 批准`：浏览器里的 Clerk Session 决定这台设备能否拿到 `ak_`。`device_code` 和后来的 key 留在 CLI 进程，批准页只见 `user_code`。

`CLI 调用`：`ak_` 读账户和积分，logout 时吊销自己。scope 固定是 `opencreator:user:read`。它不能创建 workflow run。

`Developer Key`：账户页用 Clerk JWT 创建 `sk_`。Open API 前缀 `/api/developer/v1` 只认这把 key。workflow 和 run 都记在 `owner_user_id` 下。

`Developer run`：`POST .../runs` 返回 `202` 和 `task_id` 后，结果靠 `GET /workflow-runs/{task_id}` 读 run 文档。没有画布的 `connection_id`、cursor、replay。

模型调用发生在 Consumer 执行 DAG 之后，由 `opencreator-ai` 处理那一次模型任务。`ak_` 和 `sk_` 停在 Publisher。

## 1. 三类凭据各管一段

| 凭据 | 形状 | 谁签发 | 能做什么 |
| --- | --- | --- | --- |
| Clerk Session JWT | 浏览器 session token | Clerk | 画布、账户页、CLI 批准页 |
| CLI API Key | `ak_` | Clerk API Keys，经 device flow 换出 | 读账户和积分，logout 时吊销自己 |
| Developer API Key | `sk_` | Publisher `developer_api_client` | 工作流资源、创建 run、轮询、选择、取消 |

跳过 Clerk 之后，各自还有第二道验签。`/api/developer/v1/*` 在主中间件白名单里，请求改由 `get_authenticated_api_client()` 处理。带 Clerk JWT、不带 `sk_`，同样是 `401`。

```text
X-API-Key 优先，否则读 Authorization: Bearer
  → 必须以 sk_ 开头
  → SHA-256 查 status=active
  → hmac.compare_digest 再比一次 hash
  → 可选的每分钟限流，超限 429
```

缺 key、前缀不对、hash 不中、已吊销，都是 `401`。限流 key 是 `opencreator:developer_rate:{client_id}`，第一次计数时设置 60 秒过期。

CLI 按路径拆开：

| 路径 | 谁验 |
| --- | --- |
| `POST /api/v1/cli/device/code`、`device/token` | 公开。`CLI_AUTH_ENABLED` 关闭时 `404`，打开后按 IP 限流 |
| `GET/POST /api/v1/cli/device/authorization` | 主中间件把验签留给路由。Clerk Session 的 issuer、audience、`azp`；POST 再验 `Origin` |
| `GET /cli/info`、`POST /cli/logout` | 只有 `Bearer ak_` 才跳过旧 JWT 解码，再由 `get_cli_principal()` 向 Clerk 验 key |

`ak_` 调 Open API 是 `401`。`sk_` 调 `/cli/info` 也是 `401`。

## 2. CLI 的状态在 Redis，批准页只见 user_code

`device/code` 返回 `device_code`、`user_code`、`verification_uri`、`verification_uri_complete`、`expires_in`、`interval`。浏览器从 hash 取 `user_code`，写入 sessionStorage，随即清掉 fragment。

```text
用户打开 /cli/authorize#user_code=...
  → 未登录则打开登录弹窗
  → GET /api/v1/cli/device/authorization
  → 返回 authorization_id、scopes、decision_nonce
  → POST 同一路径，decision = approve | deny
```

批准依赖一次性 `decision_nonce`。`approve` 还要求用户在 CLI allowlist 里，并且本地账户已经初始化，否则 `409`。nonce 不对是 `403`，重复决定是 `409`。页面加上 `noindex` 和 `no-referrer`。终态是 `approved`、`denied`、`expired`、`consumed` 时清掉本地 `user_code`。

Redis 状态从 `pending` 走到 `approved` 或 `denied`。换证时经过 `issuing`，成功后是 `issued`。`grant_type` 必须是 `urn:ietf:params:oauth:grant-type:device_code`。

轮询过快返回 `slow_down`，并加大 interval。其余错误是 `authorization_pending`、`access_denied`、`expired_token`、`temporarily_unavailable`。

换到的 `access_token` 以 `ak_` 开头，并带 `expires_in`、`scope`、`api_key_id`。claims 固定有 `credential_kind=opencreator_cli`、`credential_version=1`、`authorization_id`。scope 必须正好是 `["opencreator:user:read"]`，而且 key 必须有过期时间。对不上是 `403`。

`/cli/info` 返回用户、积分和凭据元数据。`/cli/logout` 吊销这把 Clerk key，成功是 `204`。之后同一把 `ak_` 再读 info 失败。

CLI 错误体是 `{ "detail": ... }`，并带 `Cache-Control: no-store`。同进程里的其它接口仍走 `responseBase`。

## 3. sk_ 明文会进库，鉴权只认 hash

账户页这三条都要 Clerk 用户：

```text
POST   /api/v3/developer/api-client
GET    /api/v3/developer/api-client
DELETE /api/v3/developer/api-client/{client_id}
```

创建时 `secrets.token_urlsafe(24)` 拼出 `sk_`，响应带回明文。文档里同时保存 `api_key` 和 `api_key_hash`，`key_suffix` 取最后 4 位。列表目前也会把库存的 `api_key` 返回给 owner。吊销把 `status` 写成 `revoked`。hash 查询要求 `active`，所以吊销后的 key 不能再进 Open API。吊销按 `client_id + owner_user_id` 更新，避免吊销别人的 Key。

Key 上决定权限的是：

- `owner_user_id`：workflow 和 run 都记在这个用户下。
- `allowed_flow_ids`：空列表表示该 owner 的 flow 都可访问；非空则 flow 必须在列表里，否则 `403`。
- `rate_limit_per_minute`：空则不限；有值才用 Redis 计数。

同一 owner 的两把 active Key，在 allowlist 为空时可以读到对方创建的 workflow。换一个 owner，按 `owner_user_id` 查不到，得到 `404`。

## 4. 模板列表要鉴权，workflow 归 owner

```text
GET  /api/developer/v1/templates?keyword=...
POST /api/developer/v1/workflows
POST /api/developer/v1/workflows/from-template
GET  /api/developer/v1/workflows/{flow_id}
PATCH /api/developer/v1/workflows/{flow_id}
GET  /api/developer/v1/workflows/{flow_id}/parameters
```

`GET /templates` 要先通过 `sk_` 鉴权。列表本身只按 keyword 取一页，不过滤 owner。

`POST /workflows` 给 owner 存一张空的 flow project。从模板复制时，用模板的 `share_id` 读分享图，再重写节点 id 和边 id。读取、更新、读参数都先过 `allowed_flow_ids`，再按 owner 查项目，没有就是 `404`。

复制出来的 `flow_id`，owner 的画布项目接口也能读到。这不是另一套图。

## 5. 202 表示 run 已入队

```text
POST /api/developer/v1/workflows/{flow_id}/runs
```

`inputs` 和 `input_overrides` 只能出现一个，出现的那份序列化后不超过 512KB。`user_selection` 单独也是 512KB。`idempotency_key` 可选，窗口 48 小时。`auto_select` 缺省是 `true`。

`start_run()` 按这个顺序：

```text
确认 flow 可访问
  → 幂等预占
  → owner 级 start lock
  → 按 owner 读 flow project，校验节点
  → has_sufficient_credits(required_amount=1)
  → insert developer_workflow_run，status=queued
  → channel_id = api:{task_id}
  → FlowService.enqueue_flow_task()
  → 202 { task_id, status: queued, trace_id }
```

积分不足是 `402`，这时还没有 queued 文档。幂等 key 已占但 run 还读不到是 `409`。start lock 失败是 `429`。入队异常会把已经写下的 run 更新为 `failed`。`202` 的含义是文档已写，并且入队调用返回成功。节点结果要等后面的 GET。

## 6. 回程写进 run 文档，调用方只轮询

MQ 的 `ws_id` 以 `api:` 开头时，走 `handle_reply_event()`。没有对应的画布 socket 时，只要 run 已更新，消息就 ack。落库的可恢复错误会 nack 重试，超过次数写入 developer event DLQ。

`start_flow` 把 run 写成 `running`。`auto_select_mode` 为真时，选择提交过程在内部是 `selection_submitting` 或 `selection_submitted`，序列化给客户端时显示为 `running`。为假时，对外状态是 `waiting_for_selection`，调用方再 `POST /workflow-runs/{task_id}/selection`。

`POST .../cancel` 先 `kill_flow_task`，再把状态写成 `cancel_requested`，HTTP 仍是 `202`。`cancelled` 要等后续终态事件。已经终态的 run 再取消是 `409`。

`GET /workflow-runs/{task_id}` 若发现 `queued`、`running` 或 `selection_submitting` 超过 30 分钟没有新事件，会把这条 run 写成 `failed`。查询按 `api_client_id` 隔离，别的 Key 得到 `404`。查询、结果、选择响应带 `no-store`。结果里的图片、视频、音频地址会换成 CDN。

账户页另有一条 Clerk JWT 列表，给 Key 管理弹层用：`GET /api/v1/task/api_client/list`。外部程序轮询仍走带 `sk_` 的 GET。内部试跑器自己填 base URL 和 `sk_`，用来对合同，不保存 run 的权威状态。

## 7. 同一份路由有两个进程入口

`register.py` 把 `developer_router` 挂进 Publisher 主进程，外面还有 Clerk 中间件和 `responseBase` 异常包装。`developer_api/app.py` 用同一份路由起独立进程，自带 `/health`、`/readyz`、索引和 MQ consumer，异常体保持 FastAPI 默认形状。

成功时的路径、`202` 和 run 文档一致。主进程上的 CLI 路径另外切回 `{ "detail": ... }`。

## 8. 文件编写顺序

Key 存储在批准页前面。CLI 依赖 Redis 和 Clerk API Keys，与 `sk_` 分开，放在 run 能轮询之后。

```text
Key 文档和 hash 查询
  → sk_ 鉴权和主中间件白名单
  → 挂上 /api/developer/v1
  → 账户页创建、列出、吊销
  → 模板和 workflow 资源
  → run 请求形状、幂等、202 入队
  → api: 回传、轮询、选择、取消
  → CLI Redis 状态和换证
  → 浏览器批准页
  → 内部试跑器
```

登录、flow project 和 `enqueue_flow_task()` 先就位，再从 Key 存储写起。账户页能创建 Key，只说明 Key 管理完成，不说明 run 已经能轮询。

## 9. 面试 1 分钟口述

外部有两把 key。CLI 走 device flow：`device/code` 给出 `user_code`，浏览器在 `/cli/authorize` 用 Clerk Session 批准，CLI 再轮询 `device/token` 换成 `ak_`。这把 key 的 scope 只有 `opencreator:user:read`，能读 `/cli/info`，logout 返回 `204` 并吊销自己。Developer Key 在账户页用 Clerk JWT 创建，明文 `sk_` 会进库，但 Open API 只按 SHA-256 查 `active` hash。`/api/developer/v1` 跳过 Clerk 之后必须再验 `sk_`，否则就是公开接口。模板列表要鉴权，不过滤 owner；workflow 归 `owner_user_id`。`POST .../runs` 先占幂等、拿 start lock、查至少 1 点积分，再写 `queued`，通道是 `api:{task_id}`，返回 `202`。Consumer 仍跑原来的 DAG。外部不连画布 WebSocket，用 GET 读 run 文档。自动选择时，选择过程对外仍是 `running`。取消的 `202` 是 `cancel_requested`，`cancelled` 等终态事件。

## 10. 面试官追问怎么答

如果问为什么白名单放行 Developer API 不是公开接口：

主中间件只表示不验 Clerk JWT。`get_authenticated_api_client()` 仍要求 `sk_` 前缀、active hash 和 `compare_digest`。没有这层，任何人都能创建别人的 run。

如果问 `ak_` 和 `sk_` 能不能互换：

不能。`ak_` 的 scope 是读账户，由 Clerk 签发，过期后 logout 吊销的也是 Clerk key。`sk_` 由 Publisher 保存，代表 owner 的 workflow 权限。打错入口都是 `401`。

如果问 `202` 为什么还要轮询：

`202` 只说明 run 文档已写，并且 `enqueue_flow_task()` 返回成功。节点状态在 MQ 回写 `api:{task_id}` 之后才出现在 GET 里。入队抛错时，这条文档会被改成 `failed`，调用方仍要读 GET。

如果问为什么 job 通道不用画布 WebSocket：

外部 SDK 没有 `connection_id`，也没有断线重放。`api:` 前缀让 MQ 把事件写进 `developer_workflow_run`。画布 socket 不存在时，run 更新成功就可以 ack。

如果问两把 Key 为什么有时能互相看见 workflow：

隔离维度是 `owner_user_id`，不是 `client_id`。同一 owner 且 `allowed_flow_ids` 为空时，另一把 active Key 可以读。run 查询再按 `api_client_id` 隔离，别的 Key 拿同一个 `task_id` 是 `404`。

如果问 30 分钟没事件为什么 GET 会改状态：

`queued`、`running`、`selection_submitting` 超过 30 分钟没有新事件，这次 GET 把 run 写成 `failed`，错误是超时未收到事件。这是读路径上的补偿，不是调用方声明失败。

## 11. NovelComic 当前实现自查

NovelComic 还没有 CLI device flow，也没有 `sk_` Open API。仓库里搜不到 `api_key_hash`、`/api/developer/v1`、`device/code` 或 `CLI_AUTH_ENABLED`。前端也没有 `/cli/authorize` 和 Developer Key 面板。

画布执行链已经有 `FlowService.enqueue_flow_task()`。`workflow_runs_v2` 会调用它，那是画布 run，通道不是 `api:{task_id}`，也没有 `developer_workflow_run`。

迁移不要从试跑器或批准页开始。登录、flow project 和入队先留着，再按 Key 文档、`sk_` 鉴权、workflow 资源、`202` 入队、MQ 回写、CLI 换证的顺序接。账户页能创建 Key 之前，外部程序没有 owner；有了 Key 之后，还要单独验收另一把 Key 读 `task_id` 得到 `404`，以及 `ak_` 不能打 Open API。
