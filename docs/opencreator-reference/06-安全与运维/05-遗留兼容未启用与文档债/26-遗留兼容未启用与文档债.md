# 26：遗留、兼容、未启用与文档债

## 判断规则

- 主链：当前产品调用且有完整状态/恢复语义。
- 兼容：为旧客户端、旧数据或滚动发布保留，仍可能执行。
- 旁路：启用但不属于画布主链，如 webhook、Developer API、运维口。
- 未启用：路由虽挂载，但被开关、410、缺配置或默认值明确关闭。
- 文档债：注释、README、命名或测试与现码状态不一致；不能据此推导运行事实。

## 五仓横切债

- 没有五仓 revision manifest，也没有 producer/consumer 同 job 的跨仓契约 required check。
- 同一业务事实被多个仓直接写入共享 Mongo；集合 owner 与索引 owner 没有统一机器可读清单。
- Publisher、Consumer、Agent 的 drain 语义不同；“旧实例退出”不能统一翻译成任务零损完成。
- JWT、内部 key、HMAC 和 provider webhook 的验签强度不一致；owner 主要是 `user_id`，尚不是组织租户模型。
- 积分逻辑分布在 Publisher、Consumer、Agent，Lua 和状态窗口并非共享实现。
- 有 checkpoint、清扫脚本和蓝绿脚本，但未见统一 RPO/RTO、备份恢复或 Game Day 证据。

## 不能越界的结论

- 路由被 `include_router`：只证明挂载，不证明功能对所有环境启用。
- 代码中有 worker/provider：只证明实现存在，不证明配置、密钥和流量存在。
- 标了 legacy：不等于可立即删除；先查调用、数据、滚动发布窗口和回滚路径。
- 标了 deprecated：不等于已经停用；只有 410、未注册或开关关闭能更强地证明入口状态。
- README 写了部署/测试：不等于机器执行；要读 workflow、脚本退出码和 `continue-on-error`。

## 偿债顺序

1. 给所有入口维护状态标签、Owner、调用方和删除条件。
2. 为 v1/v2/v3、旧 Agent chat、模型别名建立可观测调用量。
3. 先停止写旧格式，再迁移读，再移除 fallback，最后删路由/集合。
4. 把未启用能力改成显式 feature flag，并在 health/config dump 中暴露非秘密状态。
5. 用跨仓 manifest 验证删除动作；没有混部测试前，不把“看似无调用”当成安全删除。
