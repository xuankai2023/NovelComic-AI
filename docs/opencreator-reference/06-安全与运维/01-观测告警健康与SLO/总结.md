# 观测告警健康与 SLO 全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“服务有 `/health`”，而是一次 Run 怎样留下三张应用 ID，Consumer 怎样把领取延迟和日志挂上同一张 run ID，各仓探活怎样各看各的 body，飞书怎样只证明通知被收下，以及为什么这些信号还不是用户旅程 SLO。

先把一句话背下来：

OpenCreator 的观测把一次点运行拆成相关 ID、采样诊断、分仓探活和通知结果。HTTP 头、run ID、socket ID 各管一层；`flow.queue_delay` 只量领取；`/readyz` 只回答这台接不接新活；飞书 `code=0` 只表示文本被收下。旅程目标、错误预算和 Runbook 不在仓库里。

## 0. 先分清四类信号

| 信号 | 回答什么 | 现码落在哪 |
| --- | --- | --- |
| 相关 ID | 同一次操作的日志能不能对上 | HTTP 一张，run 一张，socket 再一张 |
| 诊断 | 采到的异常、行为和领取延迟 | Sentry、PostHog、`flow.queue_delay`、结构化日志 |
| 探活 | 这台现在接不接新活 | 各仓 `/health`、`/readyz` 语义不同 |
| SLO | 分子、分母、目标、Owner | 仓内没有已签字的口径 |

探活不插在 Run 证据链上。它回答这台实例现在接不接新活。

面试时一定要把这四类讲开。很多问题都来自把“日志对得上”“采到一条 issue”“探活 200”“飞书已发送”压成“系统健康”或“用户旅程达标”。

## 1. 一次创建留下三张 ID

`POST /api/v2/flow/runs` 会新造两次。WebSocket `accept` 之后还会再造一次。

| 张 | 谁造 | 写到哪 | 对得上什么 |
| --- | --- | --- | --- |
| HTTP | `TraceIDMiddleware.dispatch` | `RequestContext`、Sentry tag、响应头 `X-Trace-ID` | 这一次 HTTP 的 Publisher 日志 |
| run | `WorkflowRunV2Service.create_run` | `flow_task.trace_id`、命令、`202` body | 入队、Consumer、AI、回调 |
| socket | 事件 WebSocket `accept` 之后 | 该连接处理过程里的 `RequestContext` | 这条 socket 自己的日志 |

格式在 `generate_trace_id()`：

```text
1-{unix 秒的 8 位 hex}-{uuid4 前 24 位 hex}
```

这是应用自己的字符串，和 W3C `traceparent` 里的 trace-id 格式不同。

中间件不读入站 `X-Trace-ID` / `traceparent`。连打两次，响应头两张不同。客户端自己带来的值不会原样回到响应头。

`create_run` 也不读 `RequestContext`。新 run 过了幂等检查才 `generate_trace_id()`。continue、cancel、幂等重放都复用库里那张。dispatcher 以后换一条 HTTP 补发时，响应头会变，Mongo 里的 run ID 不变。

事件连接在 `websocket.accept()` 之后立刻再造一张，只服务当前连接上的日志。v2 派发显式传入 `command["trace_id"]`，所以 socket 刚写进 `RequestContext` 的那张不会盖掉 run 这张。

面试讲法：

报执行链，用 `202` body 或库里的 `trace_id`，加上 `flow_task_id`。响应头那张只用来查这一次 HTTP。

## 2. 入队同时带走三样

`enqueue_flow_task` 写进 `run_flow` 的观测字段：

| 字段 | 从哪来 | 后面谁用 |
| --- | --- | --- |
| `trace_id` | 命令上的 run ID | Consumer `set_trace_id`、AI 任务日志 |
| `sentry_trace` / `sentry_baggage` | `get_traceparent()` / `get_baggage()`，取不到是空字符串 | Consumer `continue_trace` |
| `publish_timestamp` | Publisher `publish` 时的 `time()` | `flow.queue_delay` |

`sentry_trace` 是 Sentry SDK 的续接头。它和应用 `trace_id` 是两个值。

消息缺 `trace_id`，Consumer 对不上这次 run。缺 `publish_timestamp`，就没有领取延迟样本，任务仍会跑。

## 3. Consumer 挂上消息里的 ID

`run_flow` 入口按这个顺序做，失败只跳过观测：

```text
set_trace_id(消息里的 trace_id)
有 publish_timestamp
  → queue_delay = max(0, round(now - publish_timestamp, 3))
  → distribution("flow.queue_delay")，attribute 只有 flow_run_type
有 sentry_trace
  → continue_trace
  → start_transaction(op="flow.run")
set_tag(trace_id, flow_task_id, flow_id, user_id, command_id)
```

logger 每次 patch `get_trace_id()`，空着打印 `N/A`。Consumer 里不要新造 ID。

模型回调一进来先 `set_trace_id(None)`。对上 invocation 之后，再按 callback、invocation metadata 或 flow 设回。上一条请求的 ContextVar 不会串到这条回调。

metric 和 `continue_trace` 的 `try` 失败只跳过观测。tag 写在后面单独的 `try` 里。

AI 日志在 `task.trace_id` 存在时把它并进 `logTask`。`queue_wait_ms` 留在 AI 队列，单独记。

## 4. `flow.queue_delay` 只量领取

```text
queue_delay = max(0, round(now - publish_timestamp, 3))
sentry_sdk.metrics.distribution("flow.queue_delay", queue_delay, unit="second")
```

起点是 Publisher `publish`，终点是 Consumer 进入 `run_flow`。

厂商执行、callback、Outbox、RabbitMQ、WebSocket 回灯、产物能不能打开，都在这个数之后。用户等了 90 秒、这个数是 0.2 秒，说明慢在领取之后。

AI 自己还有 `queue_wait_ms`：job 开始时间减任务 `created_at`。那是 AI 队列内部等待，和 `flow.queue_delay` 各记各的。

## 5. Sentry 是采样后的诊断

| 仓 | 采样 | 健康检查 | 会丢掉的异常 |
| --- | --- | --- | --- |
| Publisher | HTTP `0.2`，`mq_callback` `0.05`，profile `0.1` | `/health`、`/readyz` 为 `0` | `InsufficientCredits` |
| Consumer | 默认 `0.1`，`flow.run` `0.05`，profile `0.1` | 同上 | 积分、敏感内容、参数、文件、模型输出等一组 |
| Agent | 其余 `1.0` | 名字是 `/health`、`/readyz` 时为 `0` | SDK 失败时 `SafeSpan` 变空操作 |
| Frontend | 有 `VITE_SENTRY_DSN` 才初始化，`sendDefaultPii: false` | 浏览器侧不采服务端探活 | 无 DSN 则整个初始化跳过 |

`before_send` 把 `prompt`、`token`、`authorization` 等改成 `[FILTERED]`。

DSN 为空就跳过初始化，服务仍能启动。Publisher 未捕获异常才 `capture_exception`。已经变成明确业务响应的，留在业务分支。

面板上没有 issue，表示这条没被采样到，或被过滤了。条数也不是失败次数。

## 6. 探活按仓读 body

| 端点 | 通过 | 503 |
| --- | --- | --- |
| Publisher `/health`、`/health2` | 进程回包 | 这条路径不因依赖失败返回 503 |
| Publisher `/readyz` | 没有 `/tmp/publisher_maintenance`，body 带 `active_ws` | 维护文件在，`status=draining` |
| Publisher `/health/consumer` | blue、green 的 `/health` 都是 200，超时 5 秒 | 任一失败，body `status=degraded` |
| Consumer `/health` | `ok` + `instance_id` | 不在这里看积压 |
| Consumer `/readyz` | 不是 `DRAINING` / `STOPPED`，且已打开的门槛没超 | 排空，或 backlog / stale 超阈值 |
| AI `/health` | 进程回包 | 不查依赖 |
| AI `/readyz` | Mongo ping 且 Redis ping | 任一不通；body 仍带 `worker_heartbeat` |
| Agent `/health` | `{"status":"ok"}` | 公开口不查 Mongo、Redis、RabbitMQ |

Publisher `/readyz` 不探 Mongo、Redis，也不读 `/health/consumer` 的结果。`/health/consumer` 打的是 Consumer `/health`，不打 Consumer `/readyz`。

所以这三件事可以分开看到：

1. 没有维护文件时，Publisher `/readyz` 在 Mongo 断开时仍返回 200。
2. Consumer 积压很大、阈值仍是 0 时，`/readyz` 为 200，body 里有 `flow_resume_backlog`。`DRAINING` 则为 503。
3. blue 的 `/health` 失败时，`/health/consumer` 为 503，Publisher `/readyz` 仍按维护文件判断。

## 7. 阈值 0 表示比较关着

```text
READYZ_MAX_FLOW_RESUME_BACKLOG = 0
READYZ_MAX_STALE_WEBHOOK_INVOCATIONS = 0
```

只有配置 `> 0` 才拿指标去比。`0` 时积压再大，`/readyz` 仍可 200。

`DRAINING` / `STOPPED` 不看这两个数，直接 503。

`/readyz` 和 `/ops/consumer/status` 都会带 `flow_engine`：

- `flow_resume_backlog`
- `running_flow_count`
- `webhook_running_invocation_count`
- `stale_webhook_invocation_count`
- `pending_callback_count`
- `failed_event_outbox_count`

这些是当前计数。仓内没有把它们接成告警规则。排空怎么切流归蓝绿那组。

## 8. 飞书收下消息，心跳写在 Redis

`sendText` 发出去要同时满足：开着、有 `webhookUrl`、HTTP 成功、响应体里的数字 `code` 为 `0`。没开或没 URL 就直接返回。有 secret 时带 `timestamp` 和 HMAC-SHA256。文本超过 8000 字会截断。

| 通知 | 何时发 | 失败时 |
| --- | --- | --- |
| `AlertService.notifyCallbackDlq` | consumer-callback 进 DLQ | 只打 `alert.feishu.callback_dlq_failed`，DLQ 照写 |
| `ModelCallNotifier.notifyOnce` | 模型调用通知 | 先 `claimModelCallNotification`，认领不到就跳过 |

飞书 `code=0` 表示这条文本被收下。模型是否恢复、用户是否看到结果，要另查任务状态。webhook 配错时，callback 仍进入失败终态。同一 `ai_task_id` 的模型通知只发出一次。

Worker 启动时写一次心跳，之后每 30 秒写 `{prefix}:readyz:worker:worker`。TTL 用 `REDIS_DEFAULT_TTL_SECONDS`，默认 86400 秒。key 还在，只说明没过期，不说明这 30 秒内进程刚写过。

AI 的 `ready` 只看 `mongoOk && redisOk`。`worker_heartbeat` 缺失时，API 仍可以 200，body 里这个字段是 `null` 或一条旧时间。

## 9. 浏览器和 Agent 是旁路

Frontend 有 DSN 才初始化 Sentry，有 PostHog key 才打 `$pageview`、`Page_View`。开发走 `/ingest`，中国区域延迟 5 秒。`person_profiles` 用 `identified_only`。发送失败被吞掉。

WebSocket 连接、认证、attach 失败时 `captureException`。`connectionStatus === 'exhausted'` 时，任务盒子显示断线和重试。run 仍可能在 Consumer 里跑。

`useWorkflowRunner` 收下 `202` 后留下 `flow_task_id` / `flow_run_id`。body 里的 `trace_id` 有类型，不进 session。前端不生成 run 的 `trace_id`。

Agent 公开 `GET /health` 回 `{"status":"ok"}`。`GET /preview/active_runs` 和 `POST /preview/drain` 只放行 `127.0.0.1`、`::1`、`localhost`，其它来源 404。drain 把 `shutting_down` 设为 true，并返回当时的 `active_runs`。公开口不带这个数。

Agent PostHog 和 `SafeSpan` 在 key / SDK 失败时变成空操作，模型调用继续。

PostHog 是行为样本。国内延迟和采样都会让条数少于真实次数。

## 10. 报障时按哪张 ID 查

```text
202 body.trace_id 或 flow_task_id
  → Publisher 入队日志里的同一 trace_id
  → Consumer [trace_id=...] 和 flow.queue_delay
  → AI provider.* 日志里的同一 trace_id
  → Sentry 有这个 tag 就看样本
```

`/readyz` 返回 503 时先读 body：`draining` 还是 `degraded`，以及 `issues`、`flow_engine`。这是实例接新活的判定。

飞书路径独立：

```text
callback 进 DLQ → notifyCallbackDlq → sendText
模型通知 → claimModelCallNotification → sendText → mark sent / failed
```

排障按四格写：用户影响、已经对上的 ID 和日志、还缺的分母或目标、下一步补哪段证据。

## 11. 现码停在诊断

现在能拿来排障的是日志字段、Sentry tag、`flow.queue_delay` 和探活 JSON。

Publisher、Consumer 的依赖里可以出现 `opentelemetry-api`、`prometheus_client`。应用源码里没有 `TracerProvider`、exporter、Prometheus scrape。AI 指标类型停在 `QueueBacklogMetric`。五仓还没有一棵 span tree，也没有统一指标平台。

| 已有 | 能证明 | 要另写才算 SLO |
| --- | --- | --- |
| run `trace_id` | 日志对得上这条 run | 成功率 |
| Sentry issue / transaction | 采到的异常或慢样本 | 全量失败数 |
| `flow.queue_delay` | 领取段延迟 | 用户等待 |
| `/readyz` | 这台接不接新活 | 出片是否成功 |
| `flow_engine` | 当前积压、stale、失败 Outbox | 已上线告警 |
| 飞书结果 | 通知有没有被收下 | 故障已恢复 |

旅程口径要另写分子、分母、排除项和窗口：提交有没有明确结果、第一次执行迹象多久出现、会不会停在中间态、产物能不能打开、回调之后用户看不看得见、恢复会不会错账。目标值不在仓库里。没有目标，就没有错误预算，也没有带 Owner 和 Runbook 的告警。

## 12. 文件编写顺序

迁移时按依赖写，不要先补一张目标表：

1. `id_utils.py`、`request_context.py`、`trace_id_middlewares.py`：每个 HTTP 新造 `X-Trace-ID`。
2. `workflow_runs_v2.py`、`services/flow.py`：run 这张写入命令，入队带上 `sentry_trace` 和 `publish_timestamp`。
3. Consumer `trace_context.py`、`logger.py`、`tasks/flow.py`：挂上消息里的 ID，并打领取延迟。
4. 两侧 `sentry.py`：DSN 为空则跳过；健康检查不采样；预期业务异常丢掉。
5. Publisher、Consumer 的探活：维护文件、`active_ws`、排空状态、阈值默认 `0`、`/health/consumer`。
6. AI `heartbeat.ts`、`health.ts`：心跳写进 body，`ready` 只看 Mongo 和 Redis。
7. `feishu-webhook-client.ts`、`alert-service.ts`、`model-call-notifier.ts`：通知失败留在通知通道。
8. Agent `server.py`：公开 `/health` 只回 `ok`，drain 只留本机。
9. 前端 Sentry、PostHog、`exhausted` 断线提示。

面试讲法：

先有能对上的 run ID，再写日志和领取延迟，再按仓拆探活，最后接告警和浏览器诊断。项目还不能按同一张 ID 串日志时，先做仪表盘只会把不同的失败混在一张图上。

## 13. 和 NovelComic 当前实现的关系

本章要在已经能点 Run 的基础上，把证据和探活拆开：

- HTTP 头和 run ID 分开造。
- Consumer 用命令上的那张写日志和 `flow.queue_delay`。
- Publisher `/readyz` 看维护文件，Consumer `/readyz` 看排空和阈值，AI `/readyz` 看 Mongo 与 Redis。
- 飞书失败不改 callback 终态，也不改模型任务状态。
- 浏览器没有 DSN 和 PostHog key 时，画布主路径仍然可用。

所以当前实现不能说“有 `/health` 就完成了观测”。真正完整的验收要覆盖三张 ID、领取延迟、分仓探活和通知失败隔离。用户旅程的目标值和错误预算另开口径。

## 14. 面试 1 分钟口述

OpenCreator 的观测不是一个总健康分。用户点 Run 时，Publisher 中间件为这一次 HTTP 新造 `X-Trace-ID`，不读入站头。`create_run` 另造 run `trace_id`，格式是 `1-{unix hex}-{24 hex}`，写进 `flow_task`、命令和 `202` body。continue 复用这张。入队同时带走 run ID、Sentry 的 `sentry_trace` 和 `publish_timestamp`。事件 WebSocket 在 `accept` 之后再造一张，只给这条连接打日志，不盖掉命令上的 run ID。Consumer `set_trace_id` 之后，日志带 `[trace_id=...]`，空上下文打印 `N/A`；有 `publish_timestamp` 才打 `flow.queue_delay`，这个数只比较 publish 到 `run_flow` 入口。回调入口先清空 ContextVar。Sentry 按仓采样，健康检查采样为 0，积分不足这类预期异常不进 issue，没有 issue 也不等于没有失败。探活按 body 读：Publisher `/readyz` 看维护文件和 `active_ws`，`/health/consumer` 只打两边的 `/health`；Consumer 阈值默认 0，积压不导致 503，`DRAINING` 会 503；AI 的 `ready` 只看 Mongo 和 Redis，心跳只出现在 body 里；Agent 公开口只回 `ok`，drain 只允许本机。飞书要 HTTP 成功且 `code=0` 才算收下，失败停在 `alert.feishu.callback_dlq_failed` 或模型通知的 failed 标记。前端没有 DSN 也能跑，连接 `exhausted` 只显示断线，run 仍可能在跑。这些都能排障，但都还不是带目标和错误预算的 SLO。

## 15. 面试官追问怎么答

如果问为什么响应头和 body 的 `trace_id` 可以不同：

因为响应头是中间件为这一次 HTTP 新造的，body 是 `create_run` 另造并写进命令的 run ID。continue、幂等重放和入队都用库里那张。报执行链用 body 或 `flow_task_id`。

如果问浏览器断线后用哪张 ID 找回这次 Run：

会话里留的是 `flow_task_id` 和 `flow_run_id`。`202` body 的 `trace_id` 有类型，不进 session。WebSocket `exhausted` 只表示这条连接重试耗尽，run 状态保持原样。

如果问 `flow.queue_delay` 很小但用户等了很久：

这个分布只覆盖 Publisher `publish` 到 Consumer 进入 `run_flow`。模型执行、callback、Outbox、回灯和产物打开都在它后面。AI 队列内部等待看 `queue_wait_ms`。

如果问 `/readyz` 200 能不能当成功率：

不能当。Publisher 看的是维护文件和 active WebSocket，Consumer 在阈值仍为 0 时不拿积压做 503，AI 看的是 Mongo 和 Redis。出片是否成功要另写分子、分母和窗口。

如果问飞书发成功了是不是故障恢复了：

飞书 `code=0` 只表示这条文本被收下。callback 是否进入终态、模型任务是否仍是原状态，要看任务记录。发送失败时异常停在通知日志，不改那条业务路径。

如果问为什么没有 Sentry issue 不能说没有失败：

健康检查采样是 0，普通 HTTP 和 `flow.run` 也只采一小部分。`InsufficientCredits` 等预期异常会被 `before_send` 丢掉。面板条数是样本，不是全量失败数。

如果问 NovelComic 迁移时先做什么：

先让 `POST /api/v2/flow/runs` 的 run ID 落进命令和 `run_flow`，再让 Consumer 用这张 ID 打日志和 `flow.queue_delay`，然后按仓拆开 `/readyz`。不要先写旅程目标表，也不要把各仓探活合成一个依赖大检查。

## 16. NovelComic 当前实现自查

只看本章“观测告警健康与 SLO”，NovelComic 当前已经具备证据链和分仓探活：

- Publisher 每次请求新造 `X-Trace-ID`。入站自己带的头不会回到响应头，也不会变成 run ID。
- run 使用 `1-{unix hex}-{24 hex}`，写入 `flow_task`、命令和 `202` body。continue 复用创建时那张。
- 入队带上同一张 run `trace_id`、`sentry_trace` 和 `publish_timestamp`。
- 事件 WebSocket `accept` 之后另造一张，命令上的 run ID 不变。
- Consumer 日志能用 run 这张搜到；空上下文打印 `N/A`。有 `publish_timestamp` 才打 `flow.queue_delay`，attribute 只有 `flow_run_type`。
- 回调入口先清空 trace，避免串上一条请求。
- Sentry DSN 为空时跳过初始化。`/health`、`/readyz` 采样为 0。Publisher 丢掉 `InsufficientCredits`。
- Publisher `/readyz` 看 `/tmp/publisher_maintenance` 和 `active_ws`。`/health/consumer` 只打 blue/green 的 `/health`，超时 5 秒。一边失败时它 503，Publisher `/readyz` 仍按自己的规则。
- Consumer 两个 `READYZ_MAX_*` 默认 0。积压不导致 `/readyz` 503；`DRAINING` / `STOPPED` 会 503。body 带 `flow_engine`。
- AI 在 Mongo、Redis 都通且心跳缺失时 `/readyz` 为 200，body 带 `worker_heartbeat`。Mongo 不通则 503，心跳字段仍在。
- 飞书 HTTP 失败或 body `code!=0` 时，callback 仍走原终态，模型任务状态保持原路径。模型通知先认领。
- Agent 公开 `/health` 回 `ok`。非本机调用 `/preview/drain` 为 404。
- 前端无 DSN、无 PostHog key 时主路径可用。连接 `exhausted` 时任务盒子出现断线和重试，run 状态保持原样。

现有自动化和验收已经覆盖：

- `scripts/accept-observability-health-slo.py` 按编写顺序里的验收条目核对 ID、领取延迟、Sentry 过滤和 Publisher / Consumer 探活。
- AI 验收核对心跳不参与 `ready`，以及飞书失败留在通知通道。
- 前端验收核对空 DSN、空 PostHog key，以及 `exhausted` 断线提示。

仍按本章保持的边界：

- 没有已签字的旅程目标、错误预算、Owner 和 Runbook。
- `flow_engine` 是当前计数，没有接成告警规则。
- Worker 心跳 key 默认 TTL 86400 秒，key 还在只说明没过期。
- 应用源码里没有 `TracerProvider`、exporter 和 Prometheus scrape，也没有统一 span tree。
