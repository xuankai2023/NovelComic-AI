# 观测告警健康与 SLO：文件按什么顺序写

对照 [00-观测告警健康与SLO技术点.md](./00-观测告警健康与SLO技术点.md) 和 [01-观测告警健康与SLO.md](./01-观测告警健康与SLO.md)。01 讲运行时谁把哪张 ID 带到哪，这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖：先有能对上的 run ID，再写日志和领取延迟，再按仓拆探活，最后接告警和浏览器诊断。

工作流命令那组已经把 Run 派发出去。这一组不重写 DAG。仓库里没有旅程目标、错误预算和 Runbook，编写时也不要补一份目标表。

先背这份链路。

```text

  → opencreator-publisher/services/workflow_runs_v2.py
  → opencreator-publisher/services/flow.py
  → opencreator-publisher/controller/v2/flow_runs.py
  → opencreator-consumer/utils/trace_context.py
  → opencreator-consumer/logger/logger.py
  → opencreator-consumer/tasks/flow.py
  → opencreator-publisher/core/sentry.py
  → opencreator-consumer/core/sentry.py
  → opencreator-publisher/main.py
  → opencreator-consumer/main.py
  → opencreator-ai/packages/queues/src/heartbeat.ts
  → opencreator-ai/apps/worker/src/main.ts
  → opencreator-ai/apps/api/src/routes/health.ts
  → opencreator-ai/packages/runtime/src/feishu-webhook-client.ts
```

run 的 `trace_id` 先落进命令，Consumer 再挂上下文。探活按仓分开写。飞书写在失败路径后面。Sentry 和 PostHog 没有 DSN / key 时跳过初始化。

## 写之前先有的东西

缺这些不要开始本组：

1. `POST /api/v2/flow/runs` 已经能插入 run 并返回 202。
2. Publisher 已经能 `publish` 到 `run_flow`。
3. Consumer `run_flow` 已经能领到 `flow_task_id`、`flow_run_id`、`command_id`。
4. AI 任务文档有字段放 `trace_id`。
5. 配置位已经留出 Sentry DSN、PostHog key、飞书 webhook。值可以先空。

做完前置：点一次 Run，库里能看到这条 run。日志还不能按同一个 ID 串起来。

## 1. 先写 HTTP 这张

这张先不要写进 `flow_task`。

| 顺序 | 文件 | 职责 |
| --- | --- | --- |
| 1 | [id_utils.py](../../../../../opencreate/opencreator-publisher/utils/id_utils.py) | `generate_trace_id()` → `1-{unix hex}-{24 hex}` |
| 2 | [request_context.py](../../../../../opencreate/opencreator-publisher/common/context/request_context.py) | `set_trace_id` / `get_trace_id`，缺省 `"-"` |
| 3 | [trace_id_middlewares.py](../../../../../opencreate/opencreator-publisher/middleware/trace_id_middlewares.py) | 新造并写 `X-Trace-ID` |
| 4 | [register.py](../../../../../opencreate/opencreator-publisher/core/register.py) | `add_middleware(TraceIDMiddleware)` |

```text
generate_trace_id()
  → request.state.trace_id
  → RequestContext.set_trace_id
  → Sentry tag；SDK 还没初始化时，请求仍要成功
  → call_next
  → X-Trace-ID
```

做完：任意 Publisher 接口的响应头都有 `X-Trace-ID`。连打两次，两张不同。请求自己带的 `X-Trace-ID` 不会原样回到响应头。

## 2. 再写 run 这张，并放进命令

[workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py)

```text
新 run
  → trace_id = generate_trace_id()
  → task_doc.trace_id
  → command.trace_id
  → 202 body.trace_id
continue / cancel
  → task.trace_id，没有才再 generate
dispatch_command
  → enqueue_flow_task(trace_id=command["trace_id"])
```

`create_run` 不读 `RequestContext`。

[flow.py](../../../../../opencreate/opencreator-publisher/services/flow.py) 的 payload：

```text
trace_id
sentry_trace = get_traceparent()，取不到就是 ""
sentry_baggage
publish_timestamp = time()
```

事件 WebSocket 写在 [flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)：`accept` 之后再 `generate_trace_id()` 进 `RequestContext`。这张只给当前连接打日志。入队仍用命令上的 run ID。

做完：同一次创建，响应头和 body 的 `trace_id` 可以不同。body、Mongo、`run_flow` 消息三者相同。continue 仍用创建时那张。

## 3. 写 Consumer 挂接和领取延迟

消息里已经有 `trace_id` 和 `publish_timestamp` 之后再改 Consumer。Consumer 里不要新造 ID。

| 顺序 | 文件 | 职责 |
| --- | --- | --- |
| 1 | [trace_context.py](../../../../../opencreate/opencreator-consumer/utils/trace_context.py) | ContextVar |
| 2 | [logger.py](../../../../../opencreate/opencreator-consumer/logger/logger.py) | patch `trace_id=get_trace_id() or "N/A"` |
| 3 | [tasks/flow.py](../../../../../opencreate/opencreator-consumer/tasks/flow.py) | 入口设置、延迟、Sentry tag |

```text
set_trace_id(消息里的 trace_id)
有 publish_timestamp
  → queue_delay = max(0, round(now - publish_timestamp, 3))
  → distribution("flow.queue_delay")，attribute 只有 flow_run_type
有 sentry_trace
  → continue_trace + start_transaction
set_tag(...) 放在单独的 try
```

metric 和 `continue_trace` 失败时吞掉。回调路由开头 `set_trace_id(None)`，对上 invocation 后再设回。

做完：用 body 里的 `trace_id` 能搜到 Consumer 入口日志，行里带 `[trace_id=...]`。没有 `publish_timestamp` 时不打 `flow.queue_delay`，任务仍可跑。

## 4. 写 Sentry 过滤

ID 能对上之后再初始化两侧 Sentry。没有 DSN 就返回。

Publisher [sentry.py](../../../../../opencreate/opencreator-publisher/core/sentry.py)：

```text
/health、/readyz → 0
mq_callback → 0.05
其它 HTTP → 0.2
InsufficientCredits → before_send 丢弃
prompt / token / authorization → [FILTERED]
```

Consumer [sentry.py](../../../../../opencreate/opencreator-consumer/core/sentry.py)：

```text
/health、/readyz → 0
flow.run → 0.05
其它 → 0.1
预期业务异常名单 → before_send 丢弃
```

Publisher 未捕获异常在 [handler.py](../../../../../opencreate/opencreator-publisher/common/exception/handler.py) 里 `capture_exception`。已经变成明确业务响应的，留在业务分支。

做完：健康检查打再多次也不产生这些 transaction。积分不足不会变成 Publisher issue。采到的事件能按 `trace_id` tag 找到。

## 5. 按仓写探活

NovelComic 现在的 `/readyz` 把 Mongo、Redis、RabbitMQ 合成一个结果。这里按 OpenCreator 拆开写，三份结果各看各的 body。

### Publisher

[main.py](../../../../../opencreate/opencreator-publisher/main.py)

```text
GET /health   → 进程成功响应
GET /health2  → 200 {"status":"ok","code":200}
GET /readyz   → 数 active WebSocket
                存在 /tmp/publisher_maintenance：503 draining
                否则 200，body 带 active_ws
```

这一步不 ping Mongo、Redis、Consumer。

### Consumer

[main.py](../../../../../opencreate/opencreator-consumer/main.py)

先写 `_flow_engine_health_metrics()`，再写三个读口：

```text
GET /health → ok + instance_id
GET /readyz
  → DRAINING / STOPPED：503
  → 只有 READYZ_MAX_* > 0 才比较 backlog 和 stale
  → 默认 0：这两道比较关闭
  → 200 时也返回 flow_engine
GET /ops/consumer/status
  → intake、inflight、heartbeat、同一组 flow_engine
```

配置默认：

```text
READYZ_MAX_FLOW_RESUME_BACKLOG = 0
READYZ_MAX_STALE_WEBHOOK_INVOCATIONS = 0
```

### Publisher 再探 Consumer

仍写在 Publisher `main.py`，放在自己的 `/readyz` 之后：

```text
GET /health/consumer
  → 并行 GET CONSUMER_BLUE_URL/health
  → 并行 GET CONSUMER_GREEN_URL/health
  → timeout 5 秒
  → 都 200：200
  → 否则 503，body status=degraded
```

路径是 `/health`。Publisher `/readyz` 不读取这次结果。

做完三件事可以分开看到：

1. 没有维护文件时，Publisher `/readyz` 在 Mongo 断开时仍返回 200。
2. Consumer 积压很大、阈值仍是 0 时，`/readyz` 为 200，body 里有 `flow_resume_backlog`。`DRAINING` 则为 503。
3. blue 的 `/health` 失败时，`/health/consumer` 为 503，Publisher `/readyz` 仍按维护文件判断。

## 6. 写 AI 心跳和 ready

心跳先写，ready 再读。读出来放进 body，不放进 `ready`。

| 顺序 | 文件 | 职责 |
| --- | --- | --- |
| 1 | [heartbeat.ts](../../../../../opencreate/opencreator-ai/packages/queues/src/heartbeat.ts) | `writeWorkerHeartbeat` / `readWorkerHeartbeat` |
| 2 | [main.ts](../../../../../opencreate/opencreator-ai/apps/worker/src/main.ts) | 启动写一次，之后每 30 秒 |
| 3 | [health.ts](../../../../../opencreate/opencreator-ai/apps/api/src/routes/health.ts) | `/health`、`/readyz` |

```text
ready = mongoOk && redisOk
body 另带 worker_heartbeat，读失败则 null
key = {prefix}:readyz:worker:worker
TTL = REDIS_DEFAULT_TTL_SECONDS，默认 86400
```

TTL 保持这个默认值。key 还在只表示没过期。

日志沿 [logger.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/logger.ts) 和 [provider-worker.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/provider-worker.ts)：`task.trace_id` 存在时并进 `logTask`。`queue_wait_ms` 留在 AI 队列，单独记。

做完：停掉 worker、Mongo 和 Redis 仍通时，`/readyz` 为 200，`worker_heartbeat` 为 `null` 或一条旧时间。Mongo 不通则 503。

## 7. 写飞书通知

先写客户端，再写两个调用方。

[feishu-webhook-client.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/feishu-webhook-client.ts)

```text
没开或没 URL → return
有 secret → timestamp + sign
POST
  → HTTP 不成功：抛错
  → body.code 是数字且不是 0：抛错
```

[alert-service.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/alert-service.ts) 包住 callback DLQ。`sendText` 抛错时打 `alert.feishu.callback_dlq_failed`，异常停在这里。

[model-call-notifier.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/model-call-notifier.ts) 先 `claimModelCallNotification`。没认领到就返回。成功标记 sent，失败标记 failed。

做完：webhook 配错时，callback 仍进入失败终态。飞书 `code!=0` 时调用方能看见失败。同一 `ai_task_id` 的模型通知只发出一次。

## 8. 写 Agent 的存活口和本机排空

[sentry.py](../../../../../opencreate/opencreator-agent/creato/sentry.py)：DSN 空则跳过。`SafeSpan` 在 SDK 错误时变成空操作。除健康检查名以外采样 `1.0`。

[posthog.py](../../../../../opencreate/opencreator-agent/creato/posthog.py)：没 key 或未启用时，capture 是空操作。运行循环可以调用。

[server.py](../../../../../opencreate/opencreator-agent/creato/api/server.py)：

```text
GET /health → {"status":"ok"}
GET /preview/active_runs
POST /preview/drain
  → 只允许 127.0.0.1、::1、localhost
  → 其它来源 404
```

公开口保持进程存活这一个意思。依赖检查留在别的仓自己的 `/readyz`。

做完：从别的机器访问 `/preview/drain` 得到 404。本机调用后，`/health` 仍是 `ok`，active run 数只出现在 `/preview/active_runs`。

## 完整验收顺序

逐条勾完，这组才算写完。

1. `POST /api/v2/flow/runs` 的 `X-Trace-ID` 和 body `trace_id` 都在，而且可以不同。
2. 入站自己带的 `X-Trace-ID` 不会变成响应头。
3. Mongo 的 `flow_task.trace_id`、命令、`run_flow` 消息三者相同。
4. continue 复用创建时那张。
5. 事件 WebSocket `accept` 后的 `RequestContext` 是另一张，命令上的 run ID 不变。
6. Consumer 日志能用 run 这张搜到；空上下文打印 `N/A`。
7. 有 `publish_timestamp` 时打出 `flow.queue_delay`，比较的是 publish 到 `run_flow` 入口。
8. 回调入口不会带上一条请求的 `trace_id`。
9. Sentry DSN 为空时服务能启动。健康检查不采样。预期业务异常不进 issue。
10. Publisher `/readyz` 看维护文件和 `active_ws`。
11. Consumer 阈值保持 `0` 时，积压不导致 `/readyz` 503；`DRAINING` 会 503。body 里有 `flow_engine`。
12. Publisher `/health/consumer` 只打两边的 `/health`。一边失败时它 503，Publisher `/readyz` 仍按自己的规则。
13. AI：Mongo 和 Redis 通、worker 心跳缺失时 `/readyz` 为 200，body 带心跳字段。
14. 飞书 HTTP 失败或 `code!=0` 时，callback 终态和模型任务状态保持原路径。
15. Agent 公开 `/health` 回 `ok`。非本机调用 `/preview/drain` 为 404。
16. 前端无 DSN、无 PostHog key 时主路径可用。连接 `exhausted` 有断线提示。

验收到证据能对上、探活语义分开、告警失败留在通知通道。用户旅程的目标值和错误预算另开口径，不在这次编写里交付。
