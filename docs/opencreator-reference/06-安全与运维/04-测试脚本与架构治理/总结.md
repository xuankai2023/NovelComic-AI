# 测试脚本与架构治理全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“仓库里有 pytest”，而是一次改动的证据停在入口、本地、远程、阻断、五仓组合这五层的哪一层，以及为什么 CI 绿、contract 绿、部署成功各证明一件不同的事。

先把一句话背下来：

OpenCreator 五仓都有测试入口，远程自动跑的只有 Frontend 的 lint、type check 和 build。lint 和 type check 失败后 job 仍可以绿。没有 job checkout 第二个仓，也没有 revision manifest。夜间旧新组合和发布前冒烟都还没写成 workflow。

## 0. 先分清五层证据

```text
入口在
  → 本地能跑
  → 远程自动跑
  → 失败阻断
  → 五仓 commit 锁在同一份 manifest
```

| 层 | 现码 |
| --- | --- |
| 入口在 | 五仓都有测试文件或 `test:*` |
| 本地能跑 | Frontend 跑 `test:*`，AI 跑 `pnpm test`，Python 三仓跑 pytest |
| 远程自动跑 | 只有 Frontend `ci.yml` 会在 PR 上启动。它调用 lint、`tsc --noEmit`、build |
| 失败阻断 | lint 和 type check 写了 `continue-on-error`。build 失败或没有 `dist` 才让 job 失败。Agent 排水允许失败，外部 `/health` 记 warning |
| 组合被锁 | 没有 revision manifest，也没有同时 checkout 多仓的 job |

面试时一定要把这五层讲开。很多问题都来自把“文件在”“本地跑过”“PR 是绿的”“五个仓库各自绿过”压成“这一轮组合已经验过”。

审查时对着这张表往下看：

| 看到 | 接着核对 |
| --- | --- |
| 有测试 | 入口路径。这一层到文件为止 |
| CI 绿 | 这次 job 的命令，以及哪些步骤允许失败 |
| contract 绿 | 对端仓库有没有进同一个 job |
| 五仓都绿 | manifest 里五个 commit 是否写全 |
| 部署成功 | 关键冒烟是否非零阻断，旧实例是否走完可恢复排空 |

## 1. Frontend：PR 跑构建，不跑 test:*

`ci.yml` 在 PR 和 push 到 `main` / `master` / `develop` 时跑，Node `20.x`。

```text
checkout
  → pnpm install --frozen-lockfile
  → pnpm lint                  continue-on-error
  → pnpm exec tsc --noEmit     continue-on-error
  → pnpm build                 失败则 job 失败
  → dist 不存在则 exit 1
  → if: success() 打印 CI checks passed
```

build 读 `VITE_SERVER_URL`、`VITE_WEBSOCKET_URL`、`VITE_CLERK_PUBLISHABLE_KEY`、`VITE_POSTHOG_KEY`。secret 空着就用占位符，让构建步骤能跑完。

`package.json` 里和这条链相关、但 `ci.yml` 没有 `run:` 的脚本：

| 脚本 | 跑什么 |
| --- | --- |
| `test:workflow-reconnect` | reconnect policy、command journal、side-effect claim、resumable websocket。四条 node 命令用 `&&` 连接 |
| `test:onboarding-auth-flow` | 全局登录弹窗 |
| `test:cli-authorization` | CLI 授权 |
| `test:subscription-payment-safety` | 订阅结账和支付窗口 |
| `test:model-dropdown-order` | 模型下拉顺序 |

同文件还有 analytics、composer、agent UI 的 `test:*`。PR job 不调用它们。

面试讲法：

Frontend 远程绿，证明的是 lint、类型和 `dist` 这条构建链。reconnect、登录弹窗、CLI 授权和支付窗口要另看那四条 `test:*` 的退出码。lint 失败后 job 仍可能走到成功通知。

## 2. Publisher：断言在本地 pytest

本地是 `pytest`，`pytest==8.3.5`。

| 文件 | 断言 |
| --- | --- |
| `tests/middleware/test_auth_middleware.py` | 畸形 Bearer 进认证中间件 |
| `tests/services/test_workflow_runs_v2.py`、`tests/controller/test_flow_runs_v2.py` | 同一 `command_id` 的重放和冲突 |
| `tests/services/test_workflow_event_store.py` | `event_id` 稳定，`append_event` 返回 cursor |
| `tests/database/test_mq_v2.py` | v2 消息属性 |
| `tests/services/test_subscription_checkout_safety.py` | Stripe `idempotency_key` |
| `tests/developer_api/` | API key、workflow、template |

`workflows/README.md` 写了 `ci.yml`、`deploy.yml`、`deploy-prod.yml`。该目录现在只有这份 README。蓝绿 shell 在 `deploy/`，不在这个 PR job 里。

## 3. Consumer：单测在 unit_tests，外部脚本另放

本地是 `pytest tests/unit_tests`。没有 `.github/workflows`。

和命令、回调、事件有关的文件包括 command inbox、resume / DAG、callback parser、outbox、usage floor、模型映射、扣费和恢复。`test_flow_command_idempotency.py` 用假的 inbox：同一个 `command_id` 第二次 `find_one_and_update` 抛 `DuplicateKeyError`，状态机只进入一次。

打外部依赖的脚本留在本地或发布前：

| 脚本 | 动作 |
| --- | --- |
| `verify_webhook_pipeline.py` | 往 Mongo 写入 invocation，再投递模拟 callback |
| `verify_bluegreen_drain.py` | `POST /ops/consumer/drain` 后轮询，直到 `inflight_count` 和 `submitted_webhook_invocation_count` 都是 0。默认 300 秒 |
| `verify_redis_consistency.py` | 对比两套 Redis 的一次性脚本 |
| `run_real_opencreator_ai_e2e.py` | 走真实模型映射和执行 |

`verify_*.py` 和真实模型脚本不放进 PR job。`verify_bluegreen_drain.py` 也不代替 Publisher 和 Agent 的探活。

## 4. AI：schema 在本仓，对端另有一份 parser

```text
pnpm test       vitest run
pnpm typecheck  tsc -b
pnpm lint       eslint apps、packages、tests、scripts
```

`pnpm test` 会跑 `model-call-contracts.test.ts`：进程内解析创建任务和 callback 的 Zod schema，包括带 `client_context` 的请求。HMAC 在 `consumer-callback.ts` 的 `createSignature`，对 `timestamp.rawBody` 做 SHA-256 HMAC。

`test:kling-*`、`test:gemini-*-live`、`test:gpt-image-2-robin` 是单独的 `tsx` 脚本，请求外部 provider，不在 `pnpm test` 里。

Consumer 的 `test_provider_contract.py` 用假的 `submit` 断言本仓如何组请求。`test_callback_parser.py` 在 Consumer 里解析 payload。它们和 AI 的 schema 测试各跑各的，也不在同一个 job。没有 `.github/workflows`。

面试讲法：

一边 schema 通过，只说明这一仓能解析自己手里的 payload。同一轮要一起看，得把两个 commit 钉进夜间产物。只通过其中一边，产物写成「仓内解析通过」。

## 5. Agent：PR 不跑 pytest，部署允许排水失败

`pytest` 的路径是 `tests/`，`asyncio_mode = "auto"`。

| 文件 | 断言 |
| --- | --- |
| `test_agent_sse_protocol.py` | 帧含 `id`、`event`、`data`；`Last-Event-ID` 在 CORS 允许头里；终态是 `run.completed`、`run.failed`、`run.cancelled` |
| `test_agent_redis_run_store.py` | 按上次事件 id 回放；窗口被 trim 抛 `ResumeWindowExpiredError`；HITL 等待时 active run 还在 |
| `test_hitl_tool.py`、`test_hitl_advance.py` | HITL |
| `test_billing_costs.py` | 账单 |
| `test_model_guard.py` | 模型 guard |

HTTP `410` 写在 `server.py`。Redis 测试断言的是 `ResumeWindowExpiredError`。

`main-deploy.yml` 在 push `main` 或手动触发时切流，PR 不跑 pytest。和测试门有关的是这三处：

```text
drain --max-wait=900     continue-on-error
force_drain_skip         跳过排水，旧槽仍重启
外部 /health             60 秒内不通则 ::warning::，不 exit 1
```

排水超时写进成功通知的备注，job 仍可以成功。concurrency 组是 `prod-agent-deploy`，不取消正在跑的部署。排空在等哪个数，见蓝绿那一章。

允许失败的步骤要同时写 Owner 和到期日。没有这两项，红灯不挡合并。

## 6. 三层门现码都还没自动跑

| 层 | 证明 |
| --- | --- |
| PR 快速门 | 本仓这次改动，本仓轻量检查会红 |
| 夜间跨仓门 | manifest 里点名的旧新组合跑过。同日提交和各仓最新 HEAD 都不算这一层 |
| 发布前门 | 目标环境里登录、读项目、最短 run、callback、结果回传、WS/SSE 终态都通。只打 `/health` 只证明进程活着 |

仓库里还没有这些文件：

```text
publisher / consumer / ai / agent 的 .github/workflows/ci.yml
revision manifest
夜间多仓 workflow
发布前冒烟 workflow
业务仓 docs/adr/ADR-0001.md
```

按依赖补的顺序是：先改 Frontend `ci.yml`，去掉 lint 和 type check 的 `continue-on-error`，并跑上四条关键 `test:*`；再给另外四仓建 PR workflow；然后写 `revision-manifest.json` 和 `nightly-matrix.yml`；最后才写 `release-smoke.yml` 和 `docs/adr/ADR-0001.md`。

夜间清单：

```text
revision-manifest.json
  frontend     <commit>
  publisher    <commit>
  consumer     <commit>
  ai           <commit>
  agent        <commit>
  tests        本轮命令
  owner        失败时找谁
```

OpenCreator 五个目录是五份树，manifest 写五个 SHA。缺任何一个键，夜间 job 在跑测试之前失败。默认分支的 HEAD 不出现在清单里。

七格是新旧 Frontend/Publisher、新旧 Publisher/Consumer、新旧 AI/Consumer，再加上新 Agent 配 manifest 中的 Publisher 与 Consumer，创建 run、收到 SSE、走完一条 HITL。`model-call-contracts.test.ts` 和 `test_callback_parser.py` 要出现在同一轮产物里。外部模型单独一步，不代替这七格。

发布前冒烟放在切流之后、成功通知之前：

```text
目标 slot 的 /health、/readyz
  → 登录并取得 JWT
  → 读取自己的 flow project
  → 创建最短 workflow run
  → callback 进入 Consumer
  → RabbitMQ 把结果交回 Publisher
  → WS 或 SSE 收到终态
```

`/health` 已通、后面的 run 或 callback 失败，job 失败。外部 DNS 还没切完、通知 webhook 失败，可以 warning，日志写明它不证明 run 和 callback。Agent 外部 `/health` 要改成失败即 `exit 1`。排水超时仍继续发布，成功通知保留 timeout 备注。

探活 body 在观测那一章。冒烟只读那些字段。关键链失败要非零退出并成为 required check。非关键观测可以 warning。

面试讲法：

先有本仓红灯，再锁五仓 commit，最后才让发布前冒烟阻断。项目还没让 lint 失败挡住合并时，先做夜间矩阵只会把未阻断的本仓问题放大。

## 7. ADR 记决定，指标记逃到哪一层

业务仓没有 ADR 目录。学习目录里的 ADR 留在原处。

一条记录最少这些字段：编号、状态、背景、选择、替代方案、后果、Owner、证据路径、Review by、Superseded by。状态从 Proposed 到 Accepted。到复审日仍成立就保留。被替换时改成 Superseded，并指向新编号。状态还是 Proposed 时，文档里把它写成待复审。

`ADR-0001` 要记下的选择是：先写 PR 门，再写夜间清单和发布前阻断。替代方案是单独的发布仓、合并成一个仓库，或维持本地 pytest。后果是 runner 时间变长，逃逸可以记到 PR、夜间、发布前或生产。

指标记四类：CI p50/p95、排队时间和 runner 成本；flaky 次数和隔离期限；逃逸层；跨仓等待时间、回滚率和 MTTR。flaky 隔离写到期日，到期后修掉，或恢复为阻断。

## 8. 和 NovelComic 当前关系

NovelComic 这一章要补的文件已经在仓库里。口径和 OpenCreator 现码不同的地方，按当前脚本读。

已经落地的部分：

- 五仓 `ci.yml` 都在 PR 和 push `main` / `develop` 时跑。没有 `continue-on-error`。Frontend 是 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` 和 `dist` 检查。Python 三仓是 `uv run pytest`。AI 是 lint、typecheck、`vitest run`。
- `revision-manifest.json` 把五份树的 `new` / `old` 写成完整 SHA。五个目录在同一个 git 仓库里，一个 SHA 锁的是同一次提交里的五份树。要跑「新 Frontend + 旧 Publisher」，夜间 job 用两个 SHA 各做一个 worktree。清单里的 SHA 不等于默认分支 HEAD。缺键时不跑测试命令。
- `nightly-matrix.yml` 先校验，再跑七格，再单独跑外部模型。只通过 AI 或 Consumer 一边时，产物写成「仓内解析通过」。两边都过是「两边解析通过」。
- `release-smoke.yml` 和 `scripts/release_smoke.py` 在 `/health` 之后继续登录、读项目、创建最短 run、把 callback 送到 Consumer、确认 Publisher 上的 run 终态，并检查 WS 或 SSE 终态。这段失败退出码非零。外部 DNS 和通知 webhook 失败只记「不证明 run 和 callback」。
- 蓝绿脚本在记下成功之前调用这份冒烟。排空计数要 `RUN_VERIFY_BLUEGREEN_DRAIN` 或冒烟输入打开才跑。
- `docs/adr/ADR-0001.md` 带 Owner、证据路径和 Review by。Agent 排水超时仍继续，外部 `/health` 打不通则 `exit 1`。`main-deploy.yml` 里仍然没有 pytest。

当前还没收口的地方：

- ADR 状态是 Proposed，文档里写成待复审。Review by 是 2026-12-31。
- 四类指标只列在 ADR 里。仓库里没有采集 p50、flaky、逃逸层和 MTTR 的任务。当前没有隔离中的 flaky。
- 清单的外部步骤指向 `pnpm test:kling-image` 和 `run_real_opencreator_ai_e2e.py`。这两份入口不在当前仓库里。夜间 external 步骤真跑时会走到这两条命令。
- workflow 变红还不是 GitHub required check。挡住合并的分支保护不在仓库里。
- Frontend PR 跑的是 `pnpm test`，不是 OpenCreator 那四条 `test:*`。

所以当前不能说“五仓 CI 绿就完成了治理”。真正完整的验收还要 required check、ADR 复审，以及外部模型命令和指标采集对得上清单。

## 9. 面试 1 分钟口述

OpenCreator 的测试治理不是五仓共用一个 CI。Frontend 在 PR 上跑 lint、`tsc --noEmit` 和 build，Node 20。lint 和 type check 带 `continue-on-error`，build 失败或没有 `dist` 才让 job 失败。reconnect、登录、CLI 和支付那些 `test:*` 不在这个 job 里。Publisher 和 Consumer 的 pytest 在本地，Publisher 的 workflows 目录只有 README。AI 的 `pnpm test` 解析本仓 schema，Consumer 的 parser 另跑，两边不在同一个 job。Agent 的 pytest 也不上 PR。`main-deploy.yml` 推 main 时切流，排水 `continue-on-error`，外部 `/health` 只记 warning。所以 CI 绿只说明这次 job 里没被允许失败的步骤过了。五仓各自绿也不等于旧新组合验过，因为没有 manifest，也没有 job checkout 第二个仓。发布成功同样不能只看 `/health`。要补的顺序是先让本仓 PR 变红，再锁五个 commit 做夜间七格，最后把登录、run、callback 和终态放进切流之后的冒烟。允许失败必须写 Owner 和到期日。ADR 记这个决定，指标记缺陷逃到 PR、夜间、发布前还是生产。

## 10. 面试官追问怎么答

如果问为什么有 `test:workflow-reconnect` 还说 PR 没挡住重连：

因为 `ci.yml` 没有 `run:` 这条脚本。PR 绿只覆盖 lint、tsc 和 build。这条脚本失败与否，要看本地或以后补进 workflow 的退出码。

如果问 lint 报错了为什么成功通知还在：

Frontend 的 lint 和 type check 写了 `continue-on-error`。job 继续，后面的 `if: success()` 仍可能打印通过。build 失败或 `dist` 缺失才会让 job 失败。

如果问 AI 的 contract 测试绿了，callback 签名是不是两边一致：

只说明 AI 本仓的 schema 或 HMAC 函数通过了。Consumer 的 parser 在另一个仓库、另一次 pytest 里。没有把两个 commit 放进同一轮产物时，不能说这一轮组合验过。只过一边，记成「仓内解析通过」。

如果问 Agent 部署成功是不是 SSE 测试过了：

不是。`main-deploy.yml` 不跑 pytest。排水超时被 `continue-on-error` 吃掉，外部 `/health` 只记 warning。SSE 帧、`Last-Event-ID` 和 `ResumeWindowExpiredError` 在 `tests/` 里，要另有 PR workflow 才会在合并前变红。

如果问五个仓库今天都绿了，能不能发：

不能靠这个判断。夜间门要的是 manifest 里点名的旧 SHA 和新 SHA。同日提交和各仓最新 HEAD 都不算。缺键应在跑测试之前失败。

如果问 `/health` 200 能不能让部署记成功：

不能。发布前门还要登录、读自己的 flow project、创建最短 run、callback 进入 Consumer、结果回到 Publisher，以及 WS 或 SSE 终态。这段失败要非零退出。外部 DNS 和通知 webhook 可以 warning，日志写明它们不证明 run 和 callback。

如果问 NovelComic 迁移时先做什么：

先让各仓 `ci.yml` 在 lint、typecheck 和测试失败时变红，再写 manifest，让夜间 job 只 checkout 清单里的 commit。冒烟放在切流之后。不要把 `verify_bluegreen_drain.py` 当成 Publisher 和 Agent 的探活，也不要在没有 Owner 和到期日时把步骤标成允许失败。

## 11. NovelComic 当前实现自查

只看本章“测试脚本与架构治理”，NovelComic 当前已经具备三层门的文件：

- Frontend、Publisher、Consumer、AI、Agent 都有 PR workflow。一步失败，job 失败。Frontend 的成功通知放在 lint、typecheck、`pnpm test`、build 和 `dist` 检查之后。
- Python 三仓 PR 跑整个 `tests/`，不是只点名 OpenCreator 那一份文件列表。
- `revision-manifest.json` 的五个 `new` SHA 相同，五个里需要 `old` 的树共用另一个 SHA，并且这两个 SHA 不同，也都不是默认分支 HEAD。Agent 这一格只锁 `new`。
- 夜间 job 用 worktree 组合旧新树。七格失败、缺键或 SHA 写成 HEAD，job 失败。契约两边和外部模型分步留下产物。
- 发布前冒烟在目标 slot 的 `/health` 和 `/readyz` 之后继续跑登录、项目、最短 run、callback、Publisher 终态和 WS/SSE 终态。蓝绿脚本在成功通知前调用它。
- ADR-0001 写了 Owner `novelcomic-platform`、证据路径和 Review by `2026-12-31`。Agent 外部健康检查失败会让 release 退出。排水超时仍继续，并保留 timeout 备注。

现有自动化和验收已经覆盖：

- 清单缺键或写成默认分支 HEAD 时，不执行测试命令。
- 只通过契约一边时，日志是「仓内解析通过」。外部模型命令不进入七格，并且排在七格之后。
- 冒烟在端口不通或 callback 未被接受时非零退出。外部 DNS 和通知 webhook 失败只记 warning。

仍按本章保持的边界：

- ADR 仍是 Proposed，待复审。
- 四类指标还没有采集任务。没有隔离中的 flaky 步骤。
- `pnpm test:kling-image` 和 `run_real_opencreator_ai_e2e.py` 写在清单里，当前仓库没有这两份入口。
- job 变红还要配成 required check，才算挡住合并。
- `main-deploy.yml` 不跑 pytest。`verify_bluegreen_drain.py` 默认不在每次冒烟里。
