# 配置部署蓝绿与排空：文件按什么顺序写

对照 [00-配置部署蓝绿与排空技术点.md](./00-配置部署蓝绿与排空技术点.md) 和 [01-配置部署蓝绿与排空.md](./01-配置部署蓝绿与排空.md)。01 讲运行时谁切流量、谁等哪个数。这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖：先钉队列名和 slot 身份，再写领取闸和本机口，最后才写三套切流。Frontend 和 AI 的配置单独写，不进蓝绿脚本。

探活 body 在 [观测告警健康与 SLO](../01-观测告警健康与SLO/02.文件编写顺序.md)。这里只接脚本要读的字段。

```text
opencreator-publisher/core/config.py
  → opencreator-publisher/database/mq.py
  → opencreator-publisher/ec2/opencreator-publisher-blue.service
  → opencreator-publisher/main.py
  → opencreator-publisher/deploy/deploy-publisher-bluegreen-prod.sh
  → opencreator-consumer/ec2/opencreator-consumer-blue.service
  → opencreator-consumer/utils/drainable_consumer.py
  → opencreator-consumer/tasks/flow.py
  → opencreator-consumer/main.py
  → opencreator-consumer/deploy/deploy-consumer-bluegreen-prod.sh
  → opencreator-agent/creato/services/agent_redis_run_store.py
  → opencreator-agent/creato/api/server.py
  → opencreator-agent/scripts/deploy/agent-blue.service
  → opencreator-agent/scripts/deploy/deploy.sh
  → opencreator-agent/.github/workflows/main-deploy.yml
  → opencreator-frontend/vite.config.ts
  → opencreator-ai/packages/config/src/load-config.ts
```

green 单元和 blue 成对写，只改端口和 slot 名。运行时链路按 01 第六节，下面每节只写这一步新接上的契约。

---

## 写之前先有的东西

1. Publisher、Consumer、Agent 能连上同一套 Mongo、Redis、RabbitMQ。
2. Publisher `/readyz` 能返回 `active_ws`。Consumer `/health` 能返回 `instance_id`。Agent `/health` 返回 `{"status":"ok"}`。
3. v1 WebSocket 写入 `ws_global_map`。v2 连接在 `_connections`，事件在 Redis Event Store。
4. `run_flow`、`flow_resume`、`flow_maintenance` 已经能从各自的 Stream 领消息。
5. Agent 能把 checkpoint 写入 Redis。

做完前置：单进程能跑。还没有第二套端口，也没有入口切换。

---

## 1. 先钉身份和队列名

这一步不写发布脚本。

| 顺序 | 文件 | 职责 |
| --- | --- | --- |
| 1 | [config.py](../../../../../opencreate/opencreator-publisher/core/config.py) | `APP_ENV` 选环境文件；`PUBLISHER_DEPLOY_ID` 由单元文件覆盖 |
| 2 | [mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py) | `flow_result.{PUBLISHER_DEPLOY_ID}` 与 `flow_result.workflow.v2.{APP_ENV}` |
| 3 | [config.py](../../../../../opencreate/opencreator-consumer/core/config.py) | 三条队列名、`CONSUMER_INSTANCE_ID` |
| 4 | [schema.py](../../../../../opencreate/opencreator-agent/creato/config/schema.py) | `workflow.deploy_id` 从环境变量来 |

```text
Publisher blue  UVICORN_PORT=8001  PUBLISHER_DEPLOY_ID=blue
Publisher green UVICORN_PORT=8002  PUBLISHER_DEPLOY_ID=green
Consumer  blue  UVICORN_PORT=9000  CONSUMER_INSTANCE_ID=blue
Consumer  green UVICORN_PORT=9001  CONSUMER_INSTANCE_ID=green
Agent     blue  CREATO_API__PORT=18791  CREATO_WORKFLOW__DEPLOY_ID=agent-prod-blue
Agent     green CREATO_API__PORT=18792  CREATO_WORKFLOW__DEPLOY_ID=agent-prod-green
```

NovelComic Publisher 落在 `novelcomic-publisher/app/config.py`。现在的 v2 队列是固定的 `flow_result.workflow.v2`，这里改成带 `APP_ENV` 的名字，或留 `FLOW_V2_RESULT_QUEUE_NAME` 覆盖。

做完：两个 Consumer 的 `RUN_FLOW_QUEUE_NAME` 相同。两个 Publisher 的 v2 队列相同，实例队列分别是 `flow_result.blue` 和 `flow_result.green`。两个 Agent 的 reply queue 不同。

## 2. 写 Publisher 切流

[deploy-publisher-bluegreen-prod.sh](../../../../../opencreate/opencreator-publisher/deploy/deploy-publisher-bluegreen-prod.sh)

```text
预检通过
  → git pull --ff-only
  → 重启 standby，最多 80 秒 curl -fs /readyz
  → 备份 Nginx，改 upstream，nginx -t 失败则拷回
  → /opt/opencreator/active_publisher 写成新颜色
  → nohup：active_ws 为 0、读不到数字、或满 3600 秒 → systemctl stop
```

脚本不创建 `/tmp/publisher_maintenance`。状态文件写在后台排空之前。

做完：standby `/readyz` 失败时，Nginx 和状态文件仍是旧颜色。切流成功时旧进程还在，`/readyz` 仍是 200。

## 3. 写 Consumer 的领取闸

只改 `run_flow`。`flow_resume`、`flow_maintenance` 保持原来的 `@boost`。

| 顺序 | 文件 | 职责 |
| --- | --- | --- |
| 1 | [drainable_consumer.py](../../../../../opencreate/opencreator-consumer/utils/drainable_consumer.py) | `ACTIVE` / `DRAINING` / `STOPPED` |
| 2 | [tasks/flow.py](../../../../../opencreate/opencreator-consumer/tasks/flow.py) | `consumer_override_cls=DrainableRedisStreamConsumer` |
| 3 | [main.py](../../../../../opencreate/opencreator-consumer/main.py) | `drain`、`active`、`status` |

```text
opencreator:consumer:intake:{CONSUMER_INSTANCE_ID}
opencreator:consumer:inflight:{CONSUMER_INSTANCE_ID}
opencreator:consumer:heartbeat:{CONSUMER_INSTANCE_ID}

POST /ops/consumer/drain   → DRAINING，跳过 XREADGROUP
POST /ops/consumer/active  → ACTIVE
SCARD inflight = 0         → STOPPED，进程睡眠
启动见到 STOPPED           → 改回 ACTIVE
启动见到 DRAINING          → 保持
```

OpenCreator 现码对 inflight 只有 `SCARD`。NovelComic 要让这个数代表在途 `run_flow`，就在处理开始时 `SADD`，结束时 `SREM`。写入接上之前，`0` 只表示 set 为空。

`/readyz` 先看 intake：`DRAINING` / `STOPPED` 返回 503。观测那组的 `READYZ_MAX_*` 比较放在这之后。

做完：`POST /ops/consumer/drain` 之后，这份进程不再拉 `run_flow`。`flow_resume` 仍能拉到。`POST /ops/consumer/active` 之后恢复。

## 4. 写 Consumer 切流

[deploy-consumer-bluegreen-prod.sh](../../../../../opencreate/opencreator-consumer/deploy/deploy-consumer-bluegreen-prod.sh)

```text
启动 standby
  → GET /health → POST /ops/consumer/active → GET /readyz（120 秒）
  → Nginx 改到 9000 或 9001
  → 127.0.0.1:8000/health 的 instance_id 必须是新颜色
  → POST 旧端口 /ops/consumer/drain
  → inflight_count 为 0，或满 1800 秒 → systemctl stop
  → redis-cli：intake=STOPPED，DEL inflight，DEL heartbeat
  → /opt/opencreator/active_consumer 写成新颜色
```

[verify_bluegreen_drain.py](../../../../../opencreate/opencreator-consumer/scripts/verify_bluegreen_drain.py) 另要求 `submitted_webhook_invocation_count=0`。它不替换上面的生产脚本。

做完：对外 `/health` 的 `instance_id` 是新颜色。对不上时旧实例仍是 `ACTIVE`。脚本成功之后，PEL 和 webhook 还要单独看。

## 5. 写 Agent 的心跳、扫描和本机口

先写 [agent_redis_run_store.py](../../../../../opencreate/opencreator-agent/creato/services/agent_redis_run_store.py)：

```text
write_checkpoint / read_checkpoint / delete_checkpoint
refresh_instance_heartbeat     TTL 10 秒
is_instance_alive
add_active_run / remove_active_run / get_active_runs
```

NovelComic 的 store 已有 checkpoint 读写。这一步补心跳和 `agent:active_runs`。

再写 [server.py](../../../../../opencreate/opencreator-agent/creato/api/server.py)：

```text
实例 id = {pid}_{8 位 hex}
心跳在 shutting_down 之前约每 3 秒刷新
扫描先睡 15 秒，之后每 10 秒
  owner 心跳不在，status 为 running 或 queued
    有 checkpoint → _resume_agent_run
    没有 → 标中断

POST /preview/drain、GET /preview/active_runs
  只允许 127.0.0.1、::1、localhost，其它 404
drain → shutting_down=true
POST /v1/agent/runs → 503 INSTANCE_SHUTTING_DOWN
退出时最多再等 90 秒，非终态保留 checkpoint
```

`count` 来自 `_running_run_tasks`。扫描读 `agent:active_runs`。两处都留。

做完：本机 drain 之后新 run 为 503，`/health` 仍是 `ok`。其它地址打 `/preview/drain` 得到 404。心跳停止约 10 秒后，另一进程能扫到这条 run。

## 6. 写 Agent 的 ALB 发布

[deploy.sh](../../../../../opencreate/opencreator-agent/scripts/deploy/deploy.sh)：

```text
deploy-code   git reset --hard origin/main，uv sync，不重启
restart       最多 600 秒等 /health
drain         轮询 count，默认 900 秒，超时退出码 2
```

[main-deploy.yml](../../../../../opencreate/opencreator-agent/.github/workflows/main-deploy.yml)：

```text
恰好一个 healthy → 旧槽；另一色是目标
两边都 healthy → 失败
组为空 → 目标是 blue
deploy-code → restart 目标槽 → register → 约 240 秒内 healthy
  → deregister 旧槽
  → drain（continue-on-error）
  → restart 旧槽到新代码
外部 /health 失败记 warning
```

`force_drain_skip` 跳过 drain，仍重启旧槽。

做完：新槽未 healthy 时，旧槽还在目标组里。drain 超时后发布仍成功，非终态 checkpoint 还在 Redis。

## 7. 写 Frontend 构建注入和 AI 启动校验

[vite.config.ts](../../../../../opencreate/opencreator-frontend/vite.config.ts) 把公开 `VITE_*` 打进包。[deploy-cos.yml](../../../../../opencreate/opencreator-frontend/.github/workflows/deploy-cos.yml) 构建并上传。同分支后一次取消前一次。

[load-config.ts](../../../../../opencreate/opencreator-ai/packages/config/src/load-config.ts)：Mongo、Redis、`authKey`、`consumerWebhookSecret` 缺失则启动抛错。`ENABLE_BULL_BOARD`、`ALERT_FEISHU_ENABLED`、`MODEL_CALL_FEISHU_ENABLED`、`CONFIG_LOADER_ENABLED` 只有字符串 `true` 才开。

NovelComic AI 落在 `novelcomic-ai/packages/config/src/index.ts`。飞书开关保持默认关。

做完：浏览器包里是公开地址。AI 缺 `MONGODB_URI` 时进程不起。飞书 webhook 为空时不发通知。

## 完整验收顺序

1. 两个 Publisher 的 v2 队列名相同，实例队列分别带 `blue` 和 `green`。两个 Consumer 的三条队列名相同，`CONSUMER_INSTANCE_ID` 不同。两个 Agent 的 deploy id 不同。
2. Publisher standby `/readyz` 失败时，Nginx 和状态文件仍是旧颜色。
3. Publisher 切流成功后状态文件已是新颜色，旧进程仍在。`active_ws=0`、读不到数字、或满 1 小时，旧进程被停。没有维护文件时 `/readyz` 为 200。
4. `POST /ops/consumer/drain` 之后该实例不再拉 `run_flow`，`flow_resume` 在进程退出前仍可拉。
5. 对外 Consumer `/health` 的 `instance_id` 对不上新颜色时，脚本失败，旧实例仍是 `ACTIVE`。
6. Consumer 在 `inflight_count=0` 或 30 分钟后停旧进程并删除 inflight 键。PEL、outbox、webhook 另查。
7. 非本机调用 Agent `/preview/drain` 为 404。本机调用后新 run 为 503，`/health` 仍为 `ok`。
8. Agent drain 超时返回 2 时发布继续，旧槽重启到新代码，非终态 checkpoint 仍可被另一槽读到。两边都 healthy 时 workflow 失败。
9. Frontend 发布不启动第二套进程。AI 配置不合法时进程不起。
10. 回滚把 Publisher / Consumer 的 Nginx 和状态文件指回上一色，或把 Agent 上一槽重新 register。
