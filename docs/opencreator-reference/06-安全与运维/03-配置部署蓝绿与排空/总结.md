# 配置部署蓝绿与排空全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“有两套端口”，而是配置按仓怎么装，Publisher、Consumer、Agent 各自等哪一个数，这个数到 0 证明了什么，以及 Frontend 和 AI 为什么不进这三份切流脚本。

先把一句话背下来：

OpenCreator 五仓没有一套发布器。Publisher、Consumer、Agent 都是新实例先就绪，入口再切过去，然后分别等 `active_ws`、`inflight_count`、本进程 `count` 到 0 或到超时再停旧进程。Frontend 整包替换公开配置。AI 只在启动时用 Zod 拦住缺项。数到 0 只说明脚本正在看的那一项空了。

## 0. 先分清三个数

| 仓 | 脚本在等 | 到 0 说明 |
| --- | --- | --- |
| Publisher | `/readyz` 的 `active_ws` | 本进程 v1 `ws_global_map` 空了 |
| Consumer | `/ops/consumer/status` 的 `inflight_count` | `opencreator:consumer:inflight:{id}` 的 `SCARD` 是 0 |
| Agent | `/preview/active_runs` 的 `count` | 本进程 `_running_run_tasks` 空了 |

任务做完、回滚成功、Mongo / Redis / RabbitMQ 恢复，都不在这三列里。

面试时一定要把这三个数讲开。很多问题都来自把“入口已经指向新颜色”“旧进程还活着”“脚本看到 0”压成“这轮发布已经安全结束”。

## 1. 配置按仓装，slot 名只区分进程

| 仓 | 怎么装 | 切流时要对齐的名字 |
| --- | --- | --- |
| Frontend | Vite 构建期注入 `VITE_*` | API、WebSocket、Clerk、PostHog。这些是公开值 |
| Publisher | 没设 `APP_ENV` 读 `.env.local`，设了读 `.env.{APP_ENV}` | `APP_ENV` 拼稳定 v2 结果队列；`PUBLISHER_DEPLOY_ID` 拼实例队列 |
| Consumer | 同一套环境文件规则 | 三条队列名两边相同；`CONSUMER_INSTANCE_ID` 写成颜色 |
| AI | 启动时 `safeParse`，失败就抛 | 布尔开关默认关，字符串 `true` 才开 |
| Agent | 分组配置 | `workflow.deploy_id` 固定成 slot，两边各订一条结果队列 |

systemd 盖过代码里的随机默认值：

```text
Publisher  PUBLISHER_DEPLOY_ID=blue|green
           UVICORN_PORT=8001|8002
Consumer   CONSUMER_INSTANCE_ID=blue|green
           UVICORN_PORT=9000|9001
Agent      CREATO_WORKFLOW__DEPLOY_ID=agent-prod-blue|agent-prod-green
           CREATO_API__PORT=18791|18792
```

`PUBLISHER_DEPLOY_ID` 没设时，每次启动生成 `pub-{8位hex}`。钉成颜色名之后，重启仍用 `flow_result.blue` 或 `flow_result.green`。

面试讲法：

配置文件回答“连哪套资源”。slot 名回答“这一台进程是谁”。两边可以连同一套 Mongo、Redis、RabbitMQ，但不能共用同一个实例队列名。

## 2. Publisher：两条结果队列

`database/mq.py` 在 import 时定名：

```text
实例队列    flow_result.{PUBLISHER_DEPLOY_ID}
稳定 v2     FLOW_V2_RESULT_QUEUE_NAME
            没覆盖时：flow_result.workflow.v2.{APP_ENV}
```

v2 队列带 `x-single-active-consumer`。事件写入 Redis Event Store 之后，后一台 Publisher 上的 WebSocket 按 cursor 再读。实例队列按消息里的 `reply_queue` 回到当时那台进程。

停掉旧 Publisher 之后，v2 事件仍在稳定队列和 Event Store 里。`active_ws` 不参加这条恢复。

## 3. Publisher：切 Nginx，后台等 v1 连接

`/readyz`：

```text
存在 /tmp/publisher_maintenance
  → 503 {"status":"draining","active_ws"}
否则
  → 200 {"status":"ok","active_ws"}
```

`active_ws = len(ws_global_map)`，写入在 v1 `controller/v1/flow.py`。v2 连接在 `controller/v2/flow_runs.py` 的 `_connections`，不进这个数。

生产脚本 `deploy-publisher-bluegreen-prod.sh`：

```text
读 /opt/opencreator/active_publisher
  → 重启另一色
  → curl -fs http://127.0.0.1:{8001|8002}/readyz    最多 80 秒
  → sed Nginx upstream，nginx -t 失败则恢复备份
  → 状态文件写成新颜色
  → 后台每 10 秒读旧端口 active_ws
  → 0、unknown、或满 3600 秒 → systemctl stop
```

生产脚本不创建 `/tmp/publisher_maintenance`。旧 `/readyz` 在轮询期间仍是 200，脚本读 JSON 里的 `active_ws`。维护文件让 `/readyz` 变成 503，那是 `deploy-dev.sh`。

预检失败、standby 80 秒内不通、`nginx -t` 失败，脚本退出，状态文件保持旧颜色。成功通知在切流时已经发出，不等旧进程真正停掉。

reload 之后的新 HTTP 和新 WebSocket 进新进程。旧进程上已有的 v1 socket 留到断开或被停。v2 重连到新进程，事件从 Event Store 按 cursor 补。

面试讲法：

Publisher 第一次切入口时只承诺“新进程已经能答 `/readyz`”。它不承诺旧页面上的 v1 连接已经断开，也不用 `active_ws` 证明 v2 事件已经补完。

## 4. Consumer：只给 run_flow 装领取闸

`utils/drainable_consumer.py`：

```text
启动时
  键不存在或其它值 → ACTIVE
  已是 DRAINING     → 保持
  已是 STOPPED      → 改回 ACTIVE

拉取循环
  ACTIVE    → XREADGROUP >
  DRAINING  → 跳过 XREADGROUP；SCARD inflight 为 0 时写成 STOPPED
  STOPPED   → sleep 5，继续循环
```

三把键：

```text
opencreator:consumer:intake:{CONSUMER_INSTANCE_ID}
opencreator:consumer:inflight:{CONSUMER_INSTANCE_ID}
opencreator:consumer:heartbeat:{CONSUMER_INSTANCE_ID}    每圈 SETEX 30
```

`STOPPED` 不退出进程，避免 `Restart=always` 拉起来再抢消息。`flow_resume` 和 `flow_maintenance` 仍是普通消费者。

三个运维口在 `main.py`：

```text
POST /ops/consumer/drain   → intake=DRAINING
POST /ops/consumer/active  → intake=ACTIVE
GET  /ops/consumer/status  → intake_state、inflight_count、
                             submitted_webhook_invocation_count、
                             last_heartbeat、flow_engine
```

`/readyz` 读到 `DRAINING` 或 `STOPPED` 返回 503。`/ops/consumer/*` 由脚本打在 `127.0.0.1`，路由本身没有来源判断，不要挂进对用户开放的入口。

OpenCreator 现码对 inflight 只有 `SCARD`。`run_flow` 入站和出站都没有 `SADD` / `SREM`。`inflight_count=0` 表示这把 set 当前是空的。Stream PEL、inbox、outbox、待回调要另查。

两边在旧实例进入 `DRAINING` 之前，都用 consumer group `opencreator_group` 读同一条 `run_flow` 的 `>`。

## 5. Consumer：先核对颜色，再停旧进程

`deploy-consumer-bluegreen-prod.sh`：

```text
systemctl restart opencreator-consumer-{standby}
  → GET /health
  → POST /ops/consumer/active
  → GET /readyz                         最多 120 秒
  → Nginx 改到 9000 或 9001
  → GET 127.0.0.1:8000/health
     instance_id 必须是新颜色
  → POST 旧端口 /ops/consumer/drain
  → inflight_count 为 0，或满 1800 秒
  → 最多 5 次、间隔 2 秒看 intake 是否 STOPPED
  → systemctl stop
  → SET intake STOPPED
  → DEL inflight、DEL heartbeat
  → /opt/opencreator/active_consumer 写成新颜色
```

`instance_id` 对不上时脚本退出，旧实例还是 `ACTIVE`。状态文件写在旧进程停掉之后。

`verify_bluegreen_drain.py` 还要等 `submitted_webhook_invocation_count=0`。它不替换上面的生产脚本。生产脚本只等 `inflight_count`。停进程之后的 `DEL` 是删键，不是把 PEL 或 outbox 做完。

## 6. Agent：本机排水和另一槽接管

`agent_redis_run_store.py` 管 checkpoint、owner 心跳和 `agent:active_runs`。`server.py` 管本机口：

```text
GET /health → {"status":"ok"}

GET /preview/active_runs
POST /preview/drain
  → 来源限于 127.0.0.1、::1、localhost，其它 404

drain → shutting_down=true，返回 len(_running_run_tasks)
POST /v1/agent/runs 在 shutting_down 时 → 503 INSTANCE_SHUTTING_DOWN
```

实例身份和扫描：

```text
实例 id = {pid}_{uuid4 前 8 位}
心跳 agent:instance:{id}:heartbeat    TTL 10 秒，约每 3 秒刷新
checkpoint agent:run:{run_id}:checkpoint
集合 agent:active_runs

启动后先睡 15 秒，之后每 10 秒
  本进程已有这个 run → 跳过
  meta 不是 running / queued → 移出集合
  owner 心跳还在 → 跳过
  没有 checkpoint → 标中断
  有 checkpoint → _resume_agent_run
```

`shutting_down` 为 true 后心跳循环退出。进程退出时最多再等 90 秒，然后 cancel。非终态保留 checkpoint。

`count` 是进程内表。`agent:active_runs` 给孤儿扫描。部署脚本仍在等本进程的 `count`。心跳停掉约 10 秒后，另一槽才能认定 owner 已死。两件事各看各的时钟。

面试讲法：

本机 drain 拒绝的是新 run。已经在这台进程里的 run，要等 `count`。另一台能不能接上，看的是心跳过期和 checkpoint，不看 `/health`。`/health` 在 drain 之后仍是 `ok`。

## 7. Agent：ALB 先摘流量，再等 count

`deploy.sh` 的本机子命令：

```text
deploy-code   git reset --hard origin/main，uv sync，不重启
restart       最多 600 秒等 /health
drain         轮询 count，默认 900 秒，超时退出码 2
```

`main-deploy.yml`：

```text
describe-target-health
  恰好一个 healthy → 旧槽；另一色是目标
  两边都 healthy → 失败，不注册
  组为空 → 目标是 blue
  → deploy-code
  → restart 目标槽
  → register，约 240 秒内 healthy
  → deregister 旧端口
  → drain（continue-on-error）
  → restart 旧槽到新代码
```

新槽未 healthy 时，旧槽还在目标组里。drain 超时后发布仍成功，非终态 checkpoint 还在 Redis。`force_drain_skip` 跳过 drain，仍把旧槽重启到新代码。外部 `/health` 失败记 warning。

drain 期间旧槽拒绝新 run。ALB 已把新请求送到新槽。

## 8. Frontend 和 AI 停在配置

`deploy-cos.yml` 用 secret 还原 `.env.production`，再上传 COS。同一次推送会取消还在跑的上传。上传完成就是新包。没有第二套 Frontend 进程，也没有 drain。

`vite.config.ts` 把 `VITE_SERVER_URL`、`VITE_WEBSOCKET_URL`、`VITE_CLERK_PUBLISHABLE_KEY`、`VITE_STRIPE_PK`、`VITE_POSTHOG_KEY` 打进包。浏览器里是公开地址。

`load-config.ts` 里，Mongo、Redis、`authKey`、callback secret 缺失，进程起不来。`ENABLE_BULL_BOARD`、`ALERT_FEISHU_ENABLED`、`MODEL_CALL_FEISHU_ENABLED`、`CONFIG_LOADER_ENABLED` 只有字符串 `true` 才开。飞书 webhook 为空时不发通知。

模型任务还在 BullMQ、callback 和 Consumer 的 resume 上。它不出现在 Publisher 的 `active_ws` 里，也不被 Agent 的 `count` 代表。

## 9. 超时是这轮脚本的上限

| 动作 | 上限 | 到点之后 |
| --- | --- | --- |
| Publisher standby `/readyz` | 80 秒 | 脚本失败，流量还在旧实例 |
| Publisher 后台等 `active_ws` | 3600 秒 | 强停旧实例 |
| Consumer standby 就绪 | 120 秒 | 脚本失败 |
| Consumer 等 `inflight_count` | 1800 秒 | 强停，并删 inflight 键 |
| Agent 等 `/health` | 600 秒 | 本机脚本失败 |
| Agent 等 ALB healthy | 约 240 秒 | workflow 失败。还没 deregister 时，旧槽仍接流量 |
| Agent 等 `count` | 900 秒 | 退出码 2，发布继续 |
| Agent 进程退出时再等 | 90 秒 | cancel 剩余 run，非终态 checkpoint 保留 |

仓库里没有把这些数写成 RTO，也没有五仓共用的 revision 清单。Mongo、Redis、RabbitMQ、对象存储的备份和恢复演练不在这三份脚本里。

回滚沿入口做：Publisher / Consumer 把 Nginx 和状态文件指回上一色，Agent 把上一槽重新 register。

## 10. 三套入口差在哪

| | Publisher | Consumer | Agent |
| --- | --- | --- | --- |
| 入口 | Nginx `8001` / `8002` | Nginx，对外 `8000` 转到 `9000` / `9001` | ALB，`18791` / `18792` |
| 新实例就绪 | `curl -fs /readyz`，80 秒 | 先 `POST /ops/consumer/active`，再 `/readyz`，120 秒 | `/health` 600 秒，再等 ALB `healthy` 约 240 秒 |
| 状态文件 | `/opt/opencreator/active_publisher`，切流后立刻写 | `/opt/opencreator/active_consumer`，旧进程停掉之后写 | 目标组里的 healthy 槽，没有本地颜色文件 |
| 旧实例怎么停新活 | Nginx 已经不指过来。脚本不改 intake | `POST /ops/consumer/drain`，只停 `run_flow` 的 `XREADGROUP` | `POST /preview/drain`，新 run 返回 503 |
| 排空失败 | 后台满 3600 秒仍停。成功通知在切流时已经发出 | 前台满 1800 秒强停，并删 inflight 键 | 步骤 `continue-on-error`，退出码 2，旧槽重启到新代码 |
| 排空期间还在跑的 | 旧进程上的 v1 WebSocket | `flow_resume`、`flow_maintenance`，直到进程停 | 旧进程里已有的 run；心跳停掉后另一槽按 checkpoint 接管 |

## 11. 文件编写顺序

迁移时先钉队列名和 slot 身份，再写领取闸和本机口，最后才写三套切流。Frontend 和 AI 的配置单独写，不进蓝绿脚本。

```text
Publisher config.py / mq.py
  → Publisher 单元：8001 blue、8002 green
  → Publisher /readyz 报出 active_ws
  → deploy-publisher-bluegreen-prod.sh
  → Consumer 单元：9000 blue、9001 green
  → drainable_consumer.py
  → 只把 run_flow 换上这个消费者
  → /ops/consumer/drain|active|status
  → deploy-consumer-bluegreen-prod.sh
  → Agent checkpoint、心跳、agent:active_runs
  → /preview/drain 与 shutting_down
  → deploy.sh 与 main-deploy.yml
  → Frontend vite 公开值
  → AI load-config 启动校验
```

做完身份这一步时：两个 Consumer 的三条队列名相同，两个 Publisher 的 v2 队列相同，实例队列分别带颜色，两个 Agent 的 reply queue 不同。

面试讲法：

先有稳定队列名，再有第二套端口。名字还是随机的时候先写切流脚本，重启就会把结果送进一条再也找不到的队列。

## 12. 和 NovelComic 当前关系

NovelComic 这一章的骨架已经在仓库里，口径和 OpenCreator 有几处不同。

已经落地的部分：

- Publisher 按 `APP_ENV` 选环境文件。实例队列是 `flow_result.{deploy_id}`，稳定 v2 队列是 `flow_result.workflow.v2.{env}`，可用 `FLOW_V2_RESULT_QUEUE_NAME` 覆盖。
- Publisher `/readyz` 认维护文件和 `active_ws`。生产脚本不创建维护文件。standby 失败不改入口。状态文件写在后台排空之前。
- Consumer 只有 `run_flow` 走领取闸，并且入站 `SADD`、出站 `SREM`。切流后先核对对外 `instance_id`，再 drain。状态文件写在旧进程停掉之后。
- Agent 有心跳、孤儿扫描和本机 `/preview/drain`。ALB 发布在新槽 healthy 之后再摘旧槽。drain 超时仍保留 checkpoint。
- Frontend 只注入公开 `VITE_*`。AI 缺必填项时进程不起，飞书开关默认关。

当前口径不同的地方：

- `active_ws` 数的是 v2 `_workflow_sockets`。仓库里没有 v1 `ws_global_map`。
- inflight 的 `0` 表示没有正在处理的 `run_flow` 消息。OpenCreator 现码的 `0` 只表示那把 set 为空。
- 稳定 v2 队列在代码里声明为 durable，没有 `x-single-active-consumer`。事件仍先写入 Event Store 再 ACK。
- Publisher / Consumer 在记下成功之前会跑发布冒烟。冒烟失败会把 Nginx 指回去。
- `verify_bluegreen_drain.py` 默认不跑。打开 `RUN_VERIFY_BLUEGREEN_DRAIN=1` 后，webhook 计数没到 0 会让脚本失败；此时旧实例可能已经进入 `DRAINING`。
- Agent 配了外部健康地址时，`/health` 失败会让 release 退出。
- 仓库里没有 blue/green 的 systemd 单元文件。脚本使用主机上的 `novelcomic-publisher-blue` 这类单元名。
- `/ops/consumer/*` 仍没有来源限制。

所以当前不能说“脚本在仓库里就等于生产切流已经演练过”。真正完整的验收还要覆盖主机单元、入口回滚，以及 PEL、outbox、checkpoint 这些脚本没有等待的事实。

## 13. 面试 1 分钟口述

OpenCreator 的蓝绿不是五仓共用一个发布器。Frontend 构建时把公开 `VITE_*` 打进包，整包换上。AI 启动时 Zod 失败就不起进程。真正切流量的是 Publisher、Consumer、Agent，顺序都是新实例先就绪，再改入口，再等旧实例上的一个数。Publisher 用 Nginx 在 8001 和 8002 之间切。`/readyz` 在没有维护文件时仍是 200，后台等的是 v1 `ws_global_map` 的 `active_ws`，0、读不到或满 1 小时才停旧进程。v2 事件在稳定队列和 Event Store 里，不靠这个数恢复。Consumer 对外 8000 转到 9000 或 9001。先让 standby `active` 并通过 `/readyz`，再核对 `/health` 的 `instance_id`。对不上就停，旧实例仍是 `ACTIVE`。对上之后 `POST /ops/consumer/drain` 只停 `run_flow` 的新领取，`flow_resume` 继续跑到进程退出。`inflight_count` 到 0 或满 30 分钟就停旧进程并删键。OpenCreator 这个 0 只表示 set 为空。Agent 用 ALB 的 18791 和 18792。两边都 healthy 就失败。新槽 healthy 之后再摘旧槽，本机 `/preview/drain` 让新 run 返回 503，`/health` 仍是 ok。`count` 是本进程任务表，孤儿扫描另看心跳和 checkpoint。drain 超时退出码 2，发布继续，非终态 checkpoint 留下来。这些上限不是 RTO。回滚是把入口指回上一色。

## 14. 面试官追问怎么答

如果问为什么 `active_ws=0` 不能当成 v2 事件已经恢复：

因为 OpenCreator 的 `active_ws` 只数 v1 `ws_global_map`。v2 连接在另一张表里。停掉旧 Publisher 之后，v2 事件仍在稳定队列和 Event Store，后一台按 cursor 再读。

如果问生产排空时为什么还去打一个 200 的 `/readyz`：

生产脚本不创建 `/tmp/publisher_maintenance`。它要的是 HTTP 成功，再从 body 里取出 `active_ws`。把 `/readyz` 打成 503 `draining` 的是开发脚本里的维护文件。

如果问 Consumer `inflight_count=0` 能不能停机：

OpenCreator 生产脚本把它当成可以停的条件，或者等到 1800 秒强停。现码只有 `SCARD`，0 表示 set 为空。PEL、inbox、outbox 和待回调要另查。`verify_bluegreen_drain.py` 还会再等 webhook 计数，但它不替换生产脚本。

如果问 drain 之后 `flow_resume` 为什么还能拉到消息：

领取闸只换在 `run_flow` 上。`flow_resume` 和 `flow_maintenance` 仍是普通消费者，一直到 `systemctl stop`。`STOPPED` 自己不退出，是为了避免监督进程把它拉起来再抢 `run_flow`。

如果问 Agent `/health` 还是 ok，能不能再发新 run：

不能。drain 把 `shutting_down` 设为 true 之后，`POST /v1/agent/runs` 返回 503 `INSTANCE_SHUTTING_DOWN`。`/health` 只回答进程还在。`/preview/drain` 也只接受本机，其它来源 404。

如果问 drain 超时了这轮发布算不算失败：

Agent 这条不算。退出码 2 被 `continue-on-error` 吃掉，旧槽仍重启到新代码，非终态 checkpoint 留在 Redis。另一槽要等心跳 TTL 过去才能接管。Publisher 和 Consumer 的超时则会强停旧进程。

如果问两边 Agent 都 healthy 为什么不能发：

认槽需要恰好一个 healthy。两边都 healthy 时分不清谁是旧槽，workflow 失败，不注册。组为空时目标固定是 blue。

如果问 NovelComic 迁移时先做什么：

先把 Publisher 的实例队列和稳定 v2 队列、Consumer 的三条队列、Agent 的 deploy id 钉死，再写 `run_flow` 领取闸和本机 `/preview/drain`，最后才接 Nginx 或 ALB。不要先做第二套 Frontend 进程，也不要把 AI 模型任务算进 `active_ws`。

## 15. NovelComic 当前实现自查

只看本章“配置部署蓝绿与排空”，NovelComic 当前已经具备三套切流骨架：

- Publisher 能按 `APP_ENV` 和 `PUBLISHER_DEPLOY_ID` 分出 `flow_result.blue` / `flow_result.green`，以及两边相同的 `flow_result.workflow.v2.{env}`。
- Publisher `/readyz` 在维护文件存在时返回 503，否则返回 200 和 `active_ws`。生产脚本不创建维护文件。冒烟失败会把 Nginx 指回旧端口，此时状态文件还是旧颜色。
- Consumer 能按实例 id 进入 `ACTIVE` / `DRAINING` / `STOPPED`。`run_flow` 处理前后会改 inflight set。对外 `instance_id` 对不上时，脚本失败且旧实例保持 `ACTIVE`。
- Agent 本机 drain 后新 run 为 503，其它地址打 `/preview/drain` 为 404。心跳停止后，另一进程可以按 checkpoint 接管。ALB 在两边都 healthy 时不会继续注册。
- Frontend 发布是替换静态包。AI 缺必填配置时进程不起。

现有自动化和验收已经覆盖：

- Publisher 的环境文件、队列名、`/readyz`、standby 失败不改入口、`active_ws` 为 0 或读不到时停旧进程。
- Consumer 的 intake 三态、inflight 增减、切流核对 `instance_id`、超时删键，以及 verify 要 inflight 和 webhook 计数同时为 0。
- Agent 的本机来源限制、503、认槽、drain 超时继续和 `force_drain_skip`。
- Frontend 公开环境键，以及 AI 缺 `MONGODB_URI` 和字符串开关。
- 发布冒烟发生在 Publisher / Consumer 记下成功之前。

仍按本章保持的边界：

- `active_ws` 当前数的是 v2 `_workflow_sockets`。
- inflight 已经有入站和出站维护。`0` 表示没有正在处理的 `run_flow` 消息。PEL 和 outbox 仍要另查。
- 稳定 v2 队列没有在代码里声明 `x-single-active-consumer`。
- `RUN_VERIFY_BLUEGREEN_DRAIN` 默认关闭。打开后，校验失败发生在旧实例可能已经 `DRAINING` 的时点。
- Agent 外部 `/health` 在配置了地址时失败即退出。
- 仓库里没有 systemd 单元，也没有五仓 revision、RTO 和存储恢复演练。
- `/ops/consumer/*` 仍应只由本机脚本调用，不要挂进对用户开放的入口。

本章验收口径：

如果只验收“新实例先就绪，入口再切，三个数分别决定旧进程何时停，Frontend 和 AI 不进这三份脚本”，当前主骨架已经具备。  
如果按一次可回滚的生产发布验收，还要在主机上准备 blue/green 单元，并单独核对 PEL、outbox、Event Store 和 checkpoint。脚本看到 0，不代替这些事实。
