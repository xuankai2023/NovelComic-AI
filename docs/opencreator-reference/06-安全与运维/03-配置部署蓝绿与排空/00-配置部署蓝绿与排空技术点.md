# 配置部署蓝绿与排空：这里面有哪些技术点

先把这块拆开。每条都是后面对照 [01-配置部署蓝绿与排空.md](./01-配置部署蓝绿与排空.md) 时要认的边界。文件怎么串、按什么顺序写，分别在 01 和 [02.文件编写顺序.md](./02.文件编写顺序.md)。

五仓没有一套发布器。Frontend 在构建期把公开配置打进静态包，再整包换上。现码里把流量从旧实例挪到新实例的，是 Publisher、Consumer、Agent。AI 在启动时用 Zod 校验配置，仓库里没有蓝绿脚本。

三套的共同顺序是：新实例先就绪，入口再改过去，然后脚本轮询旧实例上的一个数，到 0 或到超时就停旧进程。这个数到 0，说明脚本在看的那一项空了。任务做完、回滚成功、存储恢复，要另看队列、事件库和各自的备份。

| 仓 | 脚本在等 | 到 0 说明 |
| --- | --- | --- |
| Publisher | `/readyz` 的 `active_ws` | 本进程 v1 `ws_global_map` 空了 |
| Consumer | `/ops/consumer/status` 的 `inflight_count` | `opencreator:consumer:inflight:{id}` 的 `SCARD` 是 0 |
| Agent | `/preview/active_runs` 的 `count` | 本进程 `_running_run_tasks` 空了 |

---

## 1. 配置按仓装，slot 名只区分进程

| 仓 | 怎么装 | 切流时要对齐的名字 |
| --- | --- | --- |
| Frontend | Vite 构建期注入 `VITE_*` | API、WebSocket、Clerk、PostHog。这些是公开值 |
| Publisher | 没设 `APP_ENV` 读 `.env.local`，设了读 `.env.{APP_ENV}` | `APP_ENV` 拼稳定 v2 结果队列；`PUBLISHER_DEPLOY_ID` 拼实例队列 |
| Consumer | 同一套环境文件规则 | `RUN_FLOW_QUEUE_NAME`、`FLOW_RESUME_QUEUE_NAME`、`FLOW_MAINTENANCE_QUEUE_NAME` 两边用同一套 |
| AI | 启动时 `safeParse`，失败就抛 | Bull Board、飞书、`CONFIG_LOADER_ENABLED` 默认关，字符串 `true` 才开 |
| Agent | 分组配置。`api.enabled`、`memory.enabled` 默认关 | `workflow.deploy_id` 固定成 slot，两边各订一条结果队列 |

systemd 把颜色写进环境变量，盖过代码里的随机默认值：

```text
Publisher  PUBLISHER_DEPLOY_ID=blue|green
Consumer   CONSUMER_INSTANCE_ID=blue|green
Agent      CREATO_WORKFLOW__DEPLOY_ID=agent-prod-blue|agent-prod-green
```

`PUBLISHER_DEPLOY_ID` 没设时，每次启动生成 `pub-{8位hex}`。单元文件钉成颜色名之后，重启仍用 `flow_result.blue` 或 `flow_result.green`。

## 2. Publisher 有两条结果队列

[mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py) 在 import 时定名：

```text
实例队列    flow_result.{PUBLISHER_DEPLOY_ID}
稳定 v2     FLOW_V2_RESULT_QUEUE_NAME
            没覆盖时：flow_result.workflow.v2.{APP_ENV}
```

v2 队列带 `x-single-active-consumer`。事件写入 Redis Event Store 之后，后一台 Publisher 上的 WebSocket 按 cursor 再读。实例队列按消息里的 `reply_queue` 回到当时那台进程。

停掉旧 Publisher 之后，v2 事件仍在稳定队列和 Event Store 里。`active_ws` 不参加这条恢复。

## 3. 三套切流差在入口、计数和失败以后

调用顺序在 01。这里只记差在哪。

| | Publisher | Consumer | Agent |
| --- | --- | --- | --- |
| 入口 | Nginx `8001` / `8002` | Nginx，对外 `8000` 转到 `9000` / `9001` | ALB，`18791` / `18792` |
| 新实例就绪 | `curl -fs /readyz`，80 秒 | 先 `POST /ops/consumer/active`，再 `/readyz`，120 秒 | `/health` 600 秒，再等 ALB `healthy` 约 240 秒 |
| 状态文件 | `/opt/opencreator/active_publisher`，切流后立刻写 | `/opt/opencreator/active_consumer`，旧进程停掉之后写 | 目标组里的 healthy 槽，没有本地颜色文件 |
| 旧实例怎么停新活 | Nginx 已经不指过来。脚本不改 intake | `POST /ops/consumer/drain`，只停 `run_flow` 的 `XREADGROUP` | `POST /preview/drain`，新 run 返回 503 |
| 排空失败 | 后台满 3600 秒仍 `systemctl stop`。成功通知在切流时已经发出 | 前台满 1800 秒强停，并删 inflight 键 | 步骤 `continue-on-error`，退出码 2，workflow 继续，旧槽重启到新代码 |
| 排空期间还在跑的 | 旧进程上的 v1 WebSocket | `flow_resume`、`flow_maintenance`，直到进程停 | 旧进程里已有的 run；心跳停掉后另一槽按 checkpoint 接管 |

Publisher 生产脚本不创建 `/tmp/publisher_maintenance`。旧 `/readyz` 在轮询期间仍是 200，脚本读 JSON 里的 `active_ws`。维护文件让 `/readyz` 变成 503 `draining`，那是 [deploy-dev.sh](../../../../../opencreate/opencreator-publisher/deploy-dev.sh)。

`active_ws = len(ws_global_map)`，写入在 v1 [flow.py](../../../../../opencreate/opencreator-publisher/controller/v1/flow.py)。v2 事件连接在 [flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py) 的 `_connections`。`active_ws` 只数 v1 那张表。

Consumer 的 inflight 键在业务路径里只有 `SCARD`。`run_flow` 入站和出站都没有 `SADD` / `SREM`。`inflight_count=0` 表示这把 set 当前是空的。Stream PEL、inbox、outbox、待回调要另查。停进程之后的 `DEL` 是删键。

生产脚本只等 `inflight_count`。[verify_bluegreen_drain.py](../../../../../opencreate/opencreator-consumer/scripts/verify_bluegreen_drain.py) 还要等 `submitted_webhook_invocation_count=0`。

两边在旧实例进入 `DRAINING` 之前，都用 consumer group `opencreator_group` 读同一条 `run_flow` 的 `>`。

Agent 的 `count` 是进程内 `_running_run_tasks`。Redis 的 `agent:active_runs` 给孤儿扫描用。`/preview/drain` 把 `shutting_down` 设为 true 之后，心跳不再刷新，TTL 10 秒。新实例每 10 秒扫描：owner 心跳不在、状态仍是 `running` 或 `queued`、又有 checkpoint，就恢复这条 run。部署脚本仍在等本进程的 `count`。两件事各看各的时钟。

`/preview/*` 只接受 `127.0.0.1`、`::1`、`localhost`，其它来源 404。`/ops/consumer/*` 由脚本打在 `127.0.0.1`，路由本身没有这层来源判断，不要挂进对用户开放的入口。来源限制见 [安全租户与内部鉴权](../02-安全租户与内部鉴权/00-安全租户与内部鉴权技术点.md)。

## 4. Frontend 和 AI 停在配置

[deploy-cos.yml](../../../../../opencreate/opencreator-frontend/.github/workflows/deploy-cos.yml) 用 secret 还原 `.env.production`，再 `pnpm deploy:cos`。同一次推送会取消还在跑的上传。上传完成就是新包。

[vite.config.ts](../../../../../opencreate/opencreator-frontend/vite.config.ts) 把 `VITE_SERVER_URL`、`VITE_WEBSOCKET_URL`、`VITE_CLERK_PUBLISHABLE_KEY`、`VITE_STRIPE_PK`、`VITE_POSTHOG_KEY` 打进包。

[load-config.ts](../../../../../opencreate/opencreator-ai/packages/config/src/load-config.ts) 里，Mongo、Redis、`authKey`、callback secret 缺失，进程起不来。模型任务还在 BullMQ、callback 和 Consumer 的 resume 上，不在 Publisher 的 `active_ws` 里。

## 5. 超时是这轮脚本的上限

| 动作 | 上限 | 到点之后 |
| --- | --- | --- |
| Publisher standby `/readyz` | 80 秒 | 脚本失败，流量还在旧实例 |
| Publisher 后台等 `active_ws` | 3600 秒 | 强停旧实例 |
| Consumer standby 就绪 | 120 秒 | 脚本失败 |
| Consumer 等 `inflight_count` | 1800 秒 | 强停，并删 inflight 键 |
| Agent 等 `/health` | 600 秒 | 本机脚本失败 |
| Agent 等 ALB healthy | 约 240 秒 | workflow 失败。还没 deregister 时，旧槽仍接流量 |
| Agent 等 `count` | 900 秒 | 退出码 2，发布继续 |
| Agent 进程退出时再等 | 90 秒 | cancel 剩余 run，非终态 checkpoint 保留 |

仓库里没有把这些数写成 RTO，也没有五仓共用的 revision 清单。Mongo、Redis、RabbitMQ、对象存储的备份和恢复演练不在这三份脚本里。

回滚沿入口做：Publisher / Consumer 把 Nginx 和状态文件指回上一色，Agent 把上一槽重新 register。

## 动手前要有的东西

探活 body 在 [观测告警健康与 SLO](../01-观测告警健康与SLO/00-观测告警健康与SLO技术点.md)。这一组只消费脚本真正读取的字段。

- Publisher `/readyz` 在没有维护文件时返回 200，body 带 `active_ws`。
- Consumer `/health` 带 `instance_id`。`/readyz` 在 `DRAINING` / `STOPPED` 时返回 503。
- Agent 公开 `/health` 回 `{"status":"ok"}`。
- 两边实例的队列名、Redis、Mongo、`APP_ENV` 指向同一套资源。slot 名区分本机进程和结果队列。
