# 22：安全、租户与内部鉴权

## 职责

- `opencreator-frontend` 从 Clerk 获取 JWT，只在请求/WS 握手时发送，不拥有服务端授权判定。
- `opencreator-publisher` 是主要用户入口，验证 Clerk JWT，并以 `sub → user_id` 约束项目、run 与结果访问。
- `opencreator-consumer` 的 workflow 内部 API 使用独立 `INTERNAL_API_KEY`，模型 callback 另验 AI HMAC。
- `opencreator-ai` 的任务 API 使用 `auth_key`，厂商 webhook 走各自验证，回调 Consumer 使用共享 HMAC secret。
- `opencreator-agent` 验 Clerk RS256 JWT 并按 session/resource 的 `user_id` 授权，同时对外抓取做 SSRF 防护。

## 入口

- Frontend HTTP：`Authorization: Bearer <Clerk JWT>`；WebSocket 打开后再发送 auth 消息。
- Publisher 普通 API：认证中间件验证 JWT；internal 路由接收 Base64 编码的 `INTERNAL_API_KEY`。
- Consumer snapshot API：依赖 `verify_internal_api_key`，使用常量时间比较。
- AI `/v1/*`：除 provider webhook 外要求 `auth_key` header。
- Agent chat/session API：Bearer JWT；可配置固定 public chat user，蓝绿控制仅允许 localhost。

## 主链

```text
Clerk session
  → Frontend getToken("__opencreator_jwt")
  → Publisher/Agent 验签并取 sub
  → 服务端忽略请求体中的 user_id，以认证主体查询资源
  → Mongo 查询携带 user_id / owner_user_id
```

```text
Publisher → Consumer snapshot
  → Base64(INTERNAL_API_KEY)
  → Consumer decode + compare_digest
```

```text
Consumer → AI task：auth_key
AI → Consumer callback：timestamp + HMAC(body) + idempotency key
外部厂商 → AI provider webhook：headers/payload 解析 + provider event identity
```

## 关键状态/消息

- 凭证不可混用：Clerk JWT 是用户身份；Developer/CLI API key 是客户端身份；`INTERNAL_API_KEY` 是服务身份；AI `auth_key` 是任务 API 凭证；OAuth token 是社交平台授权；Webhook secret 是消息真实性。
- Base64 只是编码，不是加密；内部密钥仍必须由 TLS、网络边界和 secret 管理保护。
- WebSocket HTTP upgrade 被中间件放行，真正鉴权发生在首条 auth 消息；`onopen` 不等于 authenticated。
- 租户边界应同时检查认证主体与资源 Owner；只验证 token 有效但按裸 `flow_id/session_id` 查询仍可能越权。
- ACK 不是鉴权：HTTP 2xx、RabbitMQ ACK、Redis ACK、`resume_ready` 都不能证明调用者有资源权限。

## 跨仓边界

- 用户 JWT 只应在用户入口传播；Publisher→Consumer、Consumer→AI 使用服务凭证，不能转发用户 JWT 代替内部鉴权。
- Consumer 是执行状态 Owner，但不应暴露用户公网 API；Publisher 承担用户授权与资源归属检查。
- AI 不拥有租户项目，只处理带稳定任务身份的模型调用；callback 结果必须回到 Consumer 做业务归属。
- Agent 可读取/修改用户 workflow 时必须继续携带认证用户上下文，不能因直连共享 Mongo 绕过 Publisher 的 Owner 约束。
- Frontend 中的 `user_id`、flow/session ID 都是不可信输入，最终主体必须来自服务端验签结果。

## 遗留/未启用

- Publisher internal Authorization 使用裸 Base64 值而非标准 `Bearer`，且中间件比较未使用 `compare_digest`；协议可用但需限制暴露面。
- Publisher 白名单较宽，包含部分 flow、S3/COS、模型配置路由；“白名单”只表示跳过统一中间件，需逐路由核验授权/签名。
- AI provider webhook 绕过全局 `auth_key`；统一服务会传入 headers 并做事件身份去重，但是否验签取决于 provider adapter，签名与重放窗口必须逐个审计。
- Agent JWT decode 现码只显式指定 RS256，未见 issuer/audience/azp 约束；public chat 固定用户配置会形成有意的免 JWT 路径。
- Agent SSRF 校验存在 DNS 解析与实际连接之间的 TOCTOU/DNS rebinding 风险，尚未见连接层 IP pinning。
- 多仓共享数据库仍扩大了绕过 API 授权的爆炸半径，当前不是强数据库级租户隔离。
