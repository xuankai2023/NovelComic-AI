# 安全租户与内部鉴权全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“接口有登录”，而是请求离开浏览器之后，用户 JWT、内部密钥、`auth_key`、回调 HMAC 和厂商 webhook 各过哪道门，以及 token 验过之后，查询里为什么还要再写一次 `user_id`。

先把一句话背下来：

OpenCreator 把钥匙按门分开。`sub` 是用户，`Base64(INTERNAL_API_KEY)` 是服务，`auth_key` 是模型任务，HMAC 是回调。查库条件里还要再写一次 `user_id`。HTTP `202`、队列 ACK、`resume_ready` 和回调 `200` 都只表示那一次传输。

## 0. 先分清四把钥匙

| 钥匙 | 谁拿着 | 过哪道门 |
| --- | --- | --- |
| `__opencreator_jwt` | 浏览器 | Publisher 普通 API、事件 WebSocket 首包、Agent 用户 API |
| `INTERNAL_API_KEY` | 服务之间 | Publisher `{prefix}/internal/*`，Consumer `/api/internal/*` |
| `auth_key` | Consumer 调 AI | 头名 `auth_key`，打在 AI `/v1/*` |
| `CONSUMER_WEBHOOK_SECRET` | AI 回调 Consumer | `x-oc-timestamp` + `x-oc-signature` |
| 厂商 webhook secret | 外部模型厂商 | `/v1/provider-webhooks/{provider}` |

`ak_` / `sk_` 是 CLI 和 Developer API 的钥匙，路由自己的依赖去验，中间件先放行。社交 OAuth token 用来发到外部平台。这两组不在这里展开。

`client_context.user_id` 写在任务体里，跟着模型调用走。AI 用它做日志和回传。租户判断仍看上面的钥匙和查询条件。

面试时一定要把这几把钥匙讲开。用户 JWT 打在 snapshot 或 `/v1/tasks` 上应该失败。`auth_key` 对上也不表示浏览器里的那个用户。

## 1. 用户主体是验签后的 sub

前端在发请求前取业务 JWT：

```text
getToken({ template: "__opencreator_jwt" })
  → requireToken()
  → Authorization: Bearer <token>
```

没取到 token 就不发，抛 `AuthNotReadyError`。401 文案里出现 signed out、another device 这类提示时，才打开会话冲突弹窗。

Publisher 普通 HTTP：

```text
路径不在白名单
  → 去掉 Bearer
  → jwt.decode(token, CLERK_PEM_PUBLIC_KEY, algorithms=["RS256"])
  → payload.sub
  → request.user = AuthUser(user_id=sub)
```

`sub` 为空是非法 token。过期是过期 token。浏览器这条只钉 RS256 和 `sub`。CLI 审批路由在中间件里把验签交给自己的依赖，由那边看 `iss` / `aud` / `azp`。

`get_authenticated_user` 返回 `request.user`，不再验一次签。白名单路由若仍依赖它，拿到 `user_id=""`。

面试讲法：

登录解决的是“当前请求是谁”。这一组解决的是“这个 `sub` 进了哪条查询”。

## 2. 资源权限写在查询条件里

| 资源 | 条件 |
| --- | --- |
| 编辑读取 flow | `find_one({ flow_id, user_id })` |
| 分享读取 flow | `find_one({ flow_id })` |
| run 创建、继续、取消、查询 | `user_id + flow_task_id`，或 `user_id + command_id` |
| 结果读取和更新 | 先写 `request.user_id = user.user_id` |

服务层传入的是 `user.user_id`。请求体里的同名字段覆盖不了它。

用户 A 的 JWT 读取用户 B 的 `flow_id` 或 `flow_task_id`，结果与不存在相同。只按 `flow_id` 或 `session_id` 查，会读到别人的资源。只按 `flow_id` 的函数留给分享读取。

这些信号只表示传输，不表示租户：

| 信号 | 收下的是什么 |
| --- | --- |
| HTTP `2xx` / `202` | 这次 HTTP |
| RabbitMQ ACK、Redis ACK | 队列里的这条消息 |
| WebSocket `resume_ready` | 恢复走到了这一事件 |
| AI 回调 `200` | 这次回调 body |
| 厂商 webhook `accepted` | 这次厂商通知 |

## 3. WebSocket 在首包鉴权

中间件看到可恢复事件连接就返回 `PUBLIC_USER`。`websocket.accept()` 之后才验签：

```text
accept
  → 15 秒内等第一条 JSON
  → event_type == "auth"
  → JwtService.get_user_id_with_backoff()
  → get_run_summary(user_id, flow_task_id)
  → event_type = authenticated
  → 下一条是 attach_flow
```

关闭码：

- 第一条不是 auth，或 token 空、验签失败：`4401`。
- run 不存在和 run 属于别人都收成 `WorkflowRunNotFound`：`4404`。
- 下一条不是 `attach_flow`：`4400`。

前端在 `onopen` 里连续发送 `auth` 和 `attach_flow`，不等回包。服务端按到达顺序处理。取 token 或发送失败关 `4003`。`connected` 写在收到 `resume_ready` 时。

cursor 和回放属于可恢复 WebSocket 那组。这里只要求：验完 auth 并确认 run 归属之前不回放事件。

## 4. 白名单只跳过统一 JWT

`WHITE_LIST` 命中、HTTP `OPTIONS`、以及放行的 WebSocket，返回 `PUBLIC_USER`。

除健康检查、文档、登录和 Clerk webhook 外，OpenCreator 现码还跳过对象存储、`v1/flow/*`、模型目录、模板、飞书、Developer API、分享 info、部分支付和社交 webhook。`v1/result/fetch` 已从名单里拿掉。`v2` 的 flow project 和 flow runs 留在 JWT 后面。

跳过之后，webhook 走自己的签名，Developer API 走自己的 `sk_`。名单只决定统一 JWT 跑不跑。

`/readyz`、`/health`、`/health2`、`/health/consumer` 在认证错误中间件里直接 `call_next`。

## 5. 内部密钥走服务门

两段都把 `INTERNAL_API_KEY` 做 Base64，放进 `Authorization`，没有 `Bearer` 前缀。Base64 只改编码。密钥仍靠 TLS、网络边界和 secret 保管。

| | Publisher 被调用 | Consumer 被调用 |
| --- | --- | --- |
| 路径 | `{prefix}/internal/*` | `/api/internal/workflow/{flow_task_id}/snapshot` |
| OpenCreator 比对 | `==`，Base64 无 `validate=True` | `compare_digest`，`validate=True` |
| NovelComic 比对 | `compare_digest`，`validate=True` | 同一套 |
| 通过后 | 服务身份，`user_id` 为空 | 不造用户 |
| 密钥未配置 | NovelComic 返回 `503` | `503`，`internal API is not configured` |
| 缺失或不相等 | `401` | `401` |

Publisher `POST .../internal/workflow/edit` 在密钥通过后，从请求体读 `user_id`，交给 `FlowService`。这是服务声明的资源主人。浏览器路由则用 `sub` 覆盖请求体。

同一把密钥还能走媒体人脸核身的 ingest / status。通过后用户是 `system:admin`。

快照调用顺序：

```text
事件 WebSocket 已 get_run_summary(user_id, flow_task_id)
  → Authorization: base64(INTERNAL_API_KEY)
  → 先 blue 再 green，超时 5 秒
  → 404 换下一台
  → flow_task_id 一致且 protocol_version == 2
```

Consumer 快照查询里没有 `user_id`。归属已经在拉快照之前由事件连接查过。用户 JWT 打在 snapshot 上得到 `401`。

## 6. AI 任务门是 auth_key

```text
URL 以 /v1/ 开头，且不是 /v1/provider-webhooks/
  → 头 auth_key 与 config.security.authKey 全等
  → 否则 401
```

`AUTH_KEY` 在配置 schema 里必填。Consumer 提交前若没有 `OC_AUTH_KEY` 或 `OPENCREATOR_AI_AUTH_KEY`，在本地抛错，请求发不出去。发出去时头名是 `auth_key`。

连接阶段失败会短退避重试。body 已经交给服务端的失败不重试。

`client_context.user_id` 留在任务体里。hook 读的是头。`Authorization: Bearer <用户 JWT>` 得到 `401`。

## 7. 回到 Consumer 的是 HMAC

AI 签名：

```text
rawBody = JSON.stringify(publicPayload)
timestamp = new Date().toISOString()
idempotencyKey = randomUUID() + ":" + timestamp
signature = HMAC-SHA256(secret, timestamp + "." + rawBody) 的 hex
```

头：`x-oc-timestamp`、`x-oc-signature`、`x-oc-idempotency-key`。

Consumer：

```text
POST /callbacks/models/{vendor}
配了 secret
  → 缺头或 compare_digest 失败：401 invalid_signature
没配
  → 继续 parse_callback，记成未验签放行
```

OpenCreator 的比对函数不看时间窗。NovelComic 在签名串对齐之后仍检查 `x-oc-timestamp`，超出容忍秒数仍是 `401`。

签名对上，说明 body 和这把 secret 匹配。结果归哪条 flow，回到 Consumer 上的 invocation。改一个字节 body，回调是 `401`。

## 8. 厂商 webhook 走自己的入口

```text
POST /v1/provider-webhooks/:provider
  → 不进 auth_key
tencent 且验签失败 → 403 invalid_signature
minimax 且 body.challenge 有值 → 200 { challenge }
其余 → handleWebhook → accepted
```

OpenCreator 的 `parseCoreProviderWebhook` 开头是 `void headers`，写入 provider event 时 `signature_verified` 固定为 `true`。`event_id` 去重发生在这之后，去重只挡重复通知。

NovelComic 让字段跟实际验签走：腾讯验过写 `true`，没验的厂商保持未验。其余厂商的验签若在各自 adapter 里，这条统一入口不会因签名错误拒绝它们。

## 9. Agent 再验 JWT，再对资源

```text
无 Authorization
  → public_chat_user_id 有值：用该用户；请求指定别人则 403
  → 未配置：401
有 Bearer
  → jwt.decode(RS256)
  → sub
  → 过期或非法 token：401
```

资源再对一次：

- `list_sessions` 传入认证 `user_id`。
- 单条 session 的 `user_id` 不同：`403`。
- run meta 缺失：`404`。`user_id` 不同：`403`。
- `get_workflow(flow_id, user_id)` 的 flow 条件是 `flow_id + user_id`。flow 文档对上之后，`flow_details` 再按 `flow_id` 取。
- 工具上下文缺少 `user_id` 或 `flow_id` 时返回错误文本。

Agent 与 Publisher 打同一份 Mongo。租户条件写在这条查询里。

`GET /preview/active_runs`、`POST /preview/drain` 只放行 `127.0.0.1`、`::1`、`localhost`，其它来源 `404`。公开 `/health` 不带 active run 数。

## 10. 对外抓取先看解析出来的地址

`validate_url_target` 只接受 `http` / `https`。解析后命中这些网段就拒绝：

- `0.0.0.0/8`
- `10/8`
- `100.64/10`
- `127/8`
- `169.254/16`
- `172.16/12`
- `192.168/16`
- `::1`
- `fc00::/7`
- `fe80::/10`

`validate_url_target` 在解析失败时拒绝。`validate_resolved_url` 在重定向之后再看最终地址；主机名解析失败时，这个函数返回通过。

web 抓取和远程图片都是先校验、再连接、重定向后再校验。两次解析之间，代码没有把第一次的 IP 钉进同一次 socket。`contains_internal_url` 扫命令字符串里的 URL。

所以 `127.0.0.1`、`169.254.169.254`、`10.0.0.0/8` 在抓取前被拒绝。公网 URL 仍能抓。重定向落到内网地址时，第二次校验拒绝。

## 11. 一次用户操作怎么换钥匙

浏览器读自己的项目：

```text
useHttp.requireToken()
  → GET /api/v2/flow/project/{flowId}
  → sub
  → find_one({ flow_id, user_id })
```

事件连接和快照：

```text
POST /api/v2/flow/runs
  → onopen 连续发送 auth、attach_flow
  → auth → get_run_summary(user_id, flow_task_id) → authenticated → attach_flow
cursor 不可用
  → Base64(INTERNAL_API_KEY)
  → Consumer compare_digest
  → get_snapshot(flow_task_id)
```

模型提交和回调：

```text
Consumer 已有 auth_key
  → POST AI /v1/tasks
  → auth-key hook
  → HMAC(timestamp + "." + rawBody)
  → POST Consumer /callbacks/models/{vendor}
厂商通知
  → POST /v1/provider-webhooks/{provider}
```

Agent 改用户的图：

```text
agent-chat.api 带 Bearer
  → RS256 → sub
  → session / run 的 user_id
  → get_workflow(flow_id, user_id)
```

## 12. 文件编写顺序

迁移时按依赖写：

1. `useHttp.tsx`、`jwt.py`、`auth_middleware.py`：业务 HTTP 把 `sub` 放进 `request.user`。WebSocket upgrade 仍能进来。
2. `dao/flow.py`、`workflow_runs_v2.py`、结果路由：编辑、run、结果的查询带 `user_id`。分享读取继续只按 `flow_id`。
3. `workflow-resumable-websocket.ts` 和事件路由：首包 auth，归属通过才 `authenticated`。
4. snapshot 客户端和两侧内部路由：Base64 内部密钥。Publisher 用 `compare_digest` 和 `validate=True`。
5. `task_client.py` 和 `auth-key.ts`：头 `auth_key`。厂商 webhook 路径直接返回。
6. `consumer-callback.ts` 和 Consumer 回调入口：签名串对齐，NovelComic 保留时间窗。
7. 厂商 webhook：腾讯失败 `403`。`signature_verified` 跟实际验签走。
8. Agent `server.py` 和 `workflow_dao.py`：`sub` 再对 session、run、flow。
9. `network.py`：抓取前解析，重定向后再验一次。

面试讲法：

先让 `sub` 进查询，再换服务密钥。项目查询还只按 `flow_id` 时，先做内部密钥会把“谁能读这张图”留在门外。

## 13. 和 NovelComic 当前实现的关系

本章要在登录和执行链已经能跑的基础上，把钥匙拆开：

- 用户路由继续用 `sub`，请求体里的 `user_id` 进不了查询。
- `/internal` 和 snapshot 改验 Base64 内部密钥。
- `/v1/tasks` 认 `auth_key`。厂商 webhook 绕过这把头。
- 回调用 `timestamp + "." + rawBody`。时间窗保留。密钥为空单独记成未验签放行。
- Agent 的 `user_id` 来自验签后的 `sub`，再按 session、run、flow 查。
- 抓取前拒绝内网和元数据地址，重定向后再验最终 URL。

所以当前实现不能说“中间件验了 JWT 就完成了租户”。真正完整的验收要覆盖四把钥匙、查询条件、WebSocket 关闭码和抓取前的地址检查。

## 14. 面试 1 分钟口述

OpenCreator 的租户不是一道总登录。浏览器用 `__opencreator_jwt` 打 Publisher，中间件按 RS256 取出 `sub`，写进 `request.user`。编辑 flow、run 和结果的查询再带这个 `user_id`；分享读取才只按 `flow_id`。请求体里的 `user_id` 覆盖不了 `sub`。事件 WebSocket 的 upgrade 先放行，`accept` 之后第一条必须是 auth，`get_run_summary(user_id, flow_task_id)` 通过才回 `authenticated`，下一条必须是 `attach_flow`。别人的 run 关 `4404`。快照不再带用户 JWT，Publisher 用 Base64 内部密钥打 Consumer，Consumer 用 `compare_digest` 比对；NovelComic 的 Publisher 内部路由也用这套比较，密钥通过后资源主人来自请求体。Consumer 调 AI 时头是 `auth_key`，用户 JWT 打在 `/v1/tasks` 上是 `401`。AI 回调用 `HMAC-SHA256(secret, timestamp + "." + rawBody)`，改一个字节是 `401`；NovelComic 另外拒绝时间窗外的时间戳，密钥没配则记成未验签放行。厂商通知走 `/v1/provider-webhooks/{provider}`，不进 `auth_key`；腾讯签名错误是 `403`，没验的厂商 `signature_verified` 保持未验。Agent 再验同一类 JWT，session 和 run 的 `user_id` 不同是 `403`，flow 查询同时带 `flow_id` 和 `sub`。对外抓取在连接前拒绝回环、内网和元数据地址，重定向落到内网时第二次拒绝。HTTP `202`、ACK 和回调 `200` 都只表示那一次传输。

## 15. 面试官追问怎么答

如果问为什么验过 JWT 还可能读到别人的图：

因为 token 只给出 `sub`。查询若只按 `flow_id` 或 `session_id`，条件里没有这个 `user_id`。编辑接口要调用带 `user_id` 的函数。只按 `flow_id` 的函数留给分享读取。

如果问 WebSocket 为什么不在握手头里带 JWT：

upgrade 在中间件里放行。浏览器在 `onopen` 后发第一条 `auth`，服务端用同一套 RS256 取 `sub`，再按 `user_id + flow_task_id` 查 run。没过这步不回放事件。

如果问用户 JWT 能不能拿来拉 snapshot 或创建模型任务：

不能。snapshot 认 Base64 内部密钥，缺密钥或密钥错误是 `401`，密钥未配置是 `503`。`/v1/tasks` 认头 `auth_key`，Bearer 用户 JWT 仍是 `401`。

如果问 HMAC 对上是不是这条 run 属于当前用户：

HMAC 只说明回调 body 和 `CONSUMER_WEBHOOK_SECRET` 匹配。结果归哪条 flow，看 Consumer 上的 invocation。用户能不能看这条 run，仍看之前那次 `user_id + flow_task_id`。

如果问厂商返回 accepted 是不是签名已经验过：

腾讯签名错误会在统一入口返回 `403`。MiniMax 的 challenge 会先回显。其余厂商若没有在这条入口验签，NovelComic 把 `signature_verified` 留成未验。`event_id` 去重只挡重复通知。

如果问 Agent 为什么有的接口是 403，Publisher 的别人的 flow 却像不存在：

Agent 先按 ID 找到 session 或 run，再比较文档上的 `user_id`，不同就 `403`，缺失是 `404`。Publisher 的编辑读取把 `user_id` 写进同一条查询，对不上就和没有这份文档一样。两条都要保证条件里有认证用户。

如果问内网地址为什么还要验两次：

第一次在连接前用 `validate_url_target`，解析失败就拒绝。重定向之后用 `validate_resolved_url` 看最终 URL。第二次在主机名解析失败时返回通过，而且没有把第一次解析到的 IP 钉进这次 socket。

## 16. NovelComic 当前实现自查

只看本章“安全租户与内部鉴权”，NovelComic 当前已经把四道门和资源查询接上：

- 前端没取到 `__opencreator_jwt` 不发业务 HTTP。Publisher 把 `sub` 写入 `request.user`。
- 编辑 flow、run、结果的查询带认证 `user_id`。请求体里的 `user_id` 改变不了这些条件。分享读取仍只按 `flow_id`。
- 可恢复事件 WebSocket 先放行 upgrade。首包不是 auth 为 `4401`，run 属于别人为 `4404`，下一条不是 `attach_flow` 为 `4400`。
- snapshot 和 Publisher `/internal` 使用 Base64 内部密钥，`compare_digest` 加 `validate=True`。无密钥或密钥错误为 `401`，密钥未配置为 `503`。用户 JWT 打在 snapshot 上为 `401`。
- 内部密钥通过后，Publisher 编辑的资源主人来自请求体里的 `user_id`。`/api/internal/model-config/*` 走这道服务门，不再出现在 JWT 白名单里。
- AI `/v1/*` 比对头 `auth_key`。`/v1/provider-webhooks/` 绕过。缺头、头不匹配、用用户 JWT 代替，都是 `401`。
- 回调签名串是 `timestamp + "." + rawBody`。改一个字节为 `401`。时间窗外仍为 `401`。密钥未配置是未验签放行。
- 腾讯 webhook 签名错误为 `403`。`signature_verified` 只在腾讯验过时为 `true`。
- Agent 验 RS256，`user_id` 来自 `sub`。非法 JWT 为 `401`。别人的 session 或 run 为 `403`。未配置 `public_chat_user_id` 时，无 Bearer 为 `401`。flow 条件含认证 `user_id`。
- 抓取前拒绝回环、内网和 `169.254.169.254`。重定向到内网时第二次拒绝。本机 `/preview/drain` 仍只接受 `127.0.0.1`、`::1`、`localhost`。

现有自动化和验收已经覆盖：

- `scripts/accept-security-tenant-internal-auth.py` 按 10 条验收顺序核对用户查询、WebSocket 关闭码、内部密钥、回调时间窗和 Agent `sub`。
- AI 验收核对 `auth_key` 与腾讯 `403`。
- 前端验收核对未登录不发业务 HTTP。
- Agent 网络测试核对内网地址和重定向后的第二次拒绝。

仍按本章保持的边界：

- `sk_` / `ak_` 的路由依赖在 Developer API 那组。
- 登录发码、画布页面前禁、DAG、cursor 和厂商 payload 字段分别看对应那组。
- 回调密钥未配置时继续解析，这个分支是未验签放行。
- `validate_resolved_url` 在主机名解析失败时返回通过。两次解析之间没有把 IP 钉进同一次 socket。
- 非腾讯厂商若没有单独验签，统一入口不会因签名错误拒绝它们，事件上的 `signature_verified` 保持未验。

本章验收口径：

如果只验收“用户 JWT、内部密钥、`auth_key`、HMAC 和厂商入口各过各的门，查询条件里还有认证 `user_id`”，当前主链路已经具备。  
登录怎么发 token、画布怎么拦未登录页面、事件怎么回放、厂商 body 怎么归一化，不在这组里算完成。
