# 安全租户与内部鉴权：这里面有哪些技术点

这一组只讲请求离开浏览器之后，哪把钥匙过哪道门，资源按谁的 `user_id` 查。登录怎么换成 Session，在 [登录与 JWT](../../01-用户入口/01-登录与JWT/01-登录与JWT.md)。画布页面前端门禁在 [画布登录门禁与项目加载](../../01-用户入口/02-画布登录门禁与项目加载/01-画布登录门禁与项目加载.md)。文件怎么串，看 [01](./01-安全租户与内部鉴权.md)；先写哪份，看 [02](./02.文件编写顺序.md)。

先背一句话：

```text
sub 是用户；
Base64(INTERNAL_API_KEY) 是服务；
auth_key 是模型任务；
HMAC 是回调。
查库条件里还要再写一次 user_id。
```

三条链：

```text
Clerk Session
  → getToken("__opencreator_jwt")
  → Publisher / Agent 验 RS256，取 sub
  → 查询条件带 user_id
```

```text
Publisher 要快照
  → Authorization: Base64(INTERNAL_API_KEY)
  → Consumer decode + compare_digest
  → /api/internal/workflow/{flow_task_id}/snapshot
```

```text
Consumer 提交模型
  → 头 auth_key
  → AI /v1/* 比对 config.security.authKey
  → HMAC 回调 Consumer
外部厂商 → /v1/provider-webhooks/{provider}
  这条在 auth_key hook 里直接返回
```

---

## 1. 钥匙按门分开

| 钥匙 | 谁拿着 | 过哪道门 |
| --- | --- | --- |
| `__opencreator_jwt` | 浏览器 | Publisher 普通 API、事件 WebSocket 首包、Agent 用户 API |
| `ak_` / `sk_` | CLI / Developer API | 路由自己的依赖。中间件先放行。见 [Developer API 与 CLI](../../04-商业与外部入口/02-Developer-API与CLI/01-Developer-API与CLI.md) |
| `INTERNAL_API_KEY` | 服务之间 | Publisher `{FASTAPI_API_PREFIX}/internal/*`，Consumer `/api/internal/*` |
| `auth_key` | Consumer 调 AI | 头名 `auth_key`，打在 AI `/v1/*` |
| `CONSUMER_WEBHOOK_SECRET` | AI 回调 Consumer | `x-oc-timestamp` + `x-oc-signature` |
| 厂商 webhook secret | 外部模型厂商 | `/v1/provider-webhooks/{provider}` |
| 社交 OAuth token | 发到外部平台 | [社交发布](../../04-商业与外部入口/03-社交发布飞书与外部Webhook/00-社交发布飞书与外部Webhook技术点.md) |

`client_context.user_id` 写在任务体里，跟着模型调用走。AI 用它做日志和回传，租户判断仍看上面的钥匙和查询条件。

## 2. 用户主体是验签后的 sub

Publisher 普通 HTTP 进 [auth_middleware.py](../../../../../opencreate/opencreator-publisher/middleware/auth_middleware.py)，再进 [jwt.py](../../../../../opencreate/opencreator-publisher/services/jwt.py)：

```text
路径不在白名单
  → 去掉 Bearer
  → jwt.decode(token, CLERK_PEM_PUBLIC_KEY, algorithms=["RS256"])
  → payload.sub
  → request.user = AuthUser(user_id=sub)
```

浏览器这条只钉 RS256 和 `sub`。CLI 审批路由在中间件里 `return None`，`iss` / `aud` / `azp` 由那条路由的依赖验。

[get_authenticated_user](../../../../../opencreate/opencreator-publisher/dependencies/authenticated_user.py) 返回 `request.user`，不再验一次签。

用户路由把这个 `user_id` 写进查询，并覆盖请求体里的同名字段。结果接口是 `request.user_id = user.user_id`。项目编辑读取是 `find_one({ flow_id, user_id })`。run 的创建、继续、取消、查询把 `user_id=user.user_id` 传进 `WorkflowRunV2Service`，库条件是 `user_id + flow_task_id` 或 `user_id + command_id`。

分享读取是另一条函数：[get_workflow_project_by_flow_id](../../../../../opencreate/opencreator-publisher/dao/flow.py) 只按 `flow_id`。编辑画布走带 `user_id` 的那条。

## 3. WebSocket 在首包鉴权

中间件看到 `conn_type == "websocket"` 就返回 `PUBLIC_USER`。upgrade 完成之后，[flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py) 的 `workflow_run_events_v2` 才验签：

```text
websocket.accept()
  → 15 秒内等第一条 JSON
  → event_type == "auth"
  → token / userToken / user_token，可去掉 Bearer 前缀
  → JwtService.get_user_id_with_backoff()
  → get_run_summary(user_id, flow_task_id)
  → 发出 event_type=authenticated
  → 下一条必须是 attach_flow
```

前端在 `onopen` 里连续发送 `auth` 和 `attach_flow`，不等回包。服务端按到达顺序处理。token 失败关 `4401`。`get_run_summary` 把“run 不存在”和“run 属于别人”都收成 `WorkflowRunNotFound`，关 `4404`。下一条不是 `attach_flow` 关 `4400`。前端把状态标成 `connected`，发生在收到 `resume_ready` 时。

cursor 和回放在 [可恢复 WebSocket](../../02-执行与实时回程/03-可恢复WebSocket/01-可恢复WebSocket.md)。

## 4. 白名单跳过这层 Clerk JWT

`WHITE_LIST` 命中后返回 `PUBLIC_USER`，`user_id=""`。

除健康检查、文档、登录和 Clerk webhook 外，现码还跳过：

- `{prefix}/v1/flow/*`
- `{prefix}/v1/s3/*`、`v1/cos/*`、`v2/s3/*`、`v2/cos/*`
- `{prefix}/v1/models/*`、`v1/templates/*`
- `{prefix}/v1/feishu/*`
- `{prefix}/developer/v1/*`
- 分享 info、部分支付和社交 webhook

`v1/result/fetch` 已从名单里注释掉。`v2` 的 flow project 和 flow runs 留在 JWT 后面。

跳过之后，webhook 走自己的签名，Developer API 走自己的 `sk_`。名单只决定统一 JWT 跑不跑。

## 5. 内部密钥有两段

两段都把 `INTERNAL_API_KEY` 做 Base64，放进 `Authorization`，没有 `Bearer` 前缀。Base64 只改编码，密钥仍靠 TLS、网络边界和 secret 保管。

| | Publisher 被调用 | Consumer 被调用 |
| --- | --- | --- |
| 路径 | `{FASTAPI_API_PREFIX}/internal/*` | `/api/internal/workflow/{flow_task_id}/snapshot` |
| 比对 | `==` | `secrets.compare_digest` |
| Base64 | `b64decode`，无 `validate=True` | `b64decode(..., validate=True)` |
| 通过后 | `PUBLIC_USER`，`user_id=""` | 依赖返回 `None`，不造用户 |
| 密钥未配置 | 比对失败 | `503`，`internal API is not configured` |

[controller/internal/workflow.py](../../../../../opencreate/opencreator-publisher/controller/internal/workflow.py) 的 `POST .../edit` 在密钥通过后，从请求体读 `user_id`，交给 `FlowService`。这是服务声明的资源主人。浏览器路由则用 `sub` 覆盖请求体。

同一把密钥还能走两条兼容路径，通过后用户是 `system:admin`：

```text
{prefix}/v3/media-face-verifications/ingest
{prefix}/v3/media-face-verifications/status
```

Consumer 快照按 `flow_task_id` 取，查询里没有 `user_id`。事件 WebSocket 先 `get_run_summary(user_id, flow_task_id)`，再 [WorkflowSnapshotClient.fetch](../../../../../opencreate/opencreator-publisher/services/workflow_snapshot_client.py)。客户端按 blue、green 依次试，超时 5 秒，`404` 换下一台。返回对象要对上 `flow_task_id`，且 `protocol_version == 2`。

## 6. AI 任务门是 auth_key

[auth-key.ts](../../../../../opencreate/opencreator-ai/apps/api/src/plugins/auth-key.ts) 的 `preHandler`：

```text
URL 以 /v1/ 开头，且不是 /v1/provider-webhooks/
  → 头 auth_key 与 config.security.authKey 全等
  → 否则 401
```

`AUTH_KEY` 在配置 schema 里必填。Consumer 提交前若没有 `OC_AUTH_KEY` 或 `OPENCREATOR_AI_AUTH_KEY`，在本地抛错，请求发不出去。发出去时头名是 `auth_key`。

## 7. 回到 Consumer 的是 HMAC

[createSignature](../../../../../opencreate/opencreator-ai/packages/runtime/src/consumer-callback.ts)：

```text
HMAC-SHA256(secret, timestamp + "." + rawBody) → hex
```

| 头 | 值 |
| --- | --- |
| `x-oc-timestamp` | ISO 时间 |
| `x-oc-signature` | 上面的 hex |
| `x-oc-idempotency-key` | `{uuid}:{timestamp}`，每次投递新造 |

Consumer `POST /callbacks/models/{vendor}`：配了 `CONSUMER_WEBHOOK_SECRET` 或 `OPENCREATOR_AI_CALLBACK_SECRET` 时，用 `hmac.compare_digest` 比对，失败 `401` / `invalid_signature`。没配则打日志后继续 `parse_callback`。比对函数不看时间窗。

签名对上，说明 body 和这把 secret 匹配。结果归哪条 flow，回到 Consumer 上的 invocation。字段见 [AI 提交轮询 Webhook](../../03-AI网关/03-AI提交轮询Webhook产物与回调/01-AI提交轮询Webhook产物与回调.md)。

## 8. 厂商 webhook 走自己的入口

`/v1/provider-webhooks/:provider` 不进 `auth_key`。路由把 headers 传进 `handleWebhook`。

[parseCoreProviderWebhook](../../../../../opencreate/opencreator-ai/packages/core/src/model-runtime.ts) 开头是 `void headers`。写入 provider event 时，`signature_verified` 固定为 `true`。`event_id` 去重发生在这之后，去重只挡重复通知。

路由里单独验的是 `provider === "tencent"`：`verifyTencentWebhookSignature` 失败返回 `403`。MiniMax 的 `challenge` 在进业务归一化之前以 `200` 回显。其余厂商的验签在各自 adapter；这条统一入口不会因签名错误拒绝它们。

## 9. Agent 再验 JWT，再对资源

[server.py](../../../../../opencreate/opencreator-agent/creato/api/server.py) 的 `_authenticate_agent_request`：

```text
无 Authorization，且配置了 public_chat_user_id
  → 使用该固定用户，token=""
  → 请求里的 public user 与配置不同 → 403
无 Authorization，且未配置
  → 401
有 Bearer
  → jwt.decode(RS256)
  → sub
  → 过期或非法 token → 401
```

这里同样只钉 RS256 和 `sub`。

资源再对一次：session 文档和 run meta 的 `user_id` 必须等于认证用户，否则 `403`。对不上的 active run 不交给当前用户。[WorkflowDAO.get_workflow](../../../../../opencreate/opencreator-agent/creato/dao/workflow_dao.py) 按 `flow_id + user_id` 查 flow；flow 文档对上之后，`flow_details` 再按 `flow_id` 取。Agent 与 Publisher 打同一份 Mongo，租户条件写在这条查询里。

`GET /preview/active_runs`、`POST /preview/drain` 只放行 `127.0.0.1`、`::1`、`localhost`，其它来源 `404`。公开 `/health` 不带 active run 数。

## 10. 对外抓取先看解析出来的地址

[validate_url_target](../../../../../opencreate/opencreator-agent/creato/security/network.py) 只接受 `http` / `https`。`getaddrinfo` 之后，命中 `0.0.0.0/8`、`10/8`、`100.64/10`、`127/8`、`169.254/16`、`172.16/12`、`192.168/16`、`::1`、`fc00::/7`、`fe80::/10` 就拒绝。解析失败也拒绝。

`validate_resolved_url` 在重定向之后再看最终地址。主机名解析失败时，这个函数返回通过。web 抓取和 Bedrock 远程图片都是先校验、再连接、重定向后再校验。两次解析之间，代码没有把第一次的 IP 钉进同一次 socket。`contains_internal_url` 扫命令字符串里的 URL。

## 11. 资源权限在查询条件里

| 信号 | 收下的是什么 |
| --- | --- |
| HTTP `2xx` / `202` | 这次 HTTP |
| RabbitMQ ACK、Redis ACK | 队列里的这条消息 |
| WebSocket `resume_ready` | 恢复走到了这一事件 |
| AI 回调 `200` | 这次回调 body |
| 厂商 webhook `accepted` | 这次厂商通知 |

用户能不能读这张图、这条 run、这个 session，看查询里的 `user_id` 或 `owner_user_id`。token 验过之后，查询若只按 `flow_id` 或 `session_id`，会读到别人的资源。只按 `flow_id` 的函数留给分享读取。
