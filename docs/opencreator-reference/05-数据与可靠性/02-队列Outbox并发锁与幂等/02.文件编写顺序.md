# 队列、Outbox、并发锁与幂等：文件按什么顺序写

对照 [00-队列Outbox并发锁与幂等技术点.md](./00-队列Outbox并发锁与幂等技术点.md) 和 [01-队列Outbox并发锁与幂等.md](./01-队列Outbox并发锁与幂等.md)。01 讲运行时谁认领谁，这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖：先有身份和唯一索引，再写 claim，再写“落盘之后才 ACK”。

工作流命令那组已经把 Run、continue、cancel 和事件名串起来。这一组不重写 DAG，只把那些调用收成 lease、CAS 和分层 ACK。

先背这份链路。

```text
src/lib/workflow-command-journal.ts
  → opencreator-publisher/services/workflow_runs_v2.py
  → opencreator-publisher/tasks/flow.py
  → opencreator-consumer/services/workflow/flow_command_inbox_service.py
  → opencreator-consumer/tasks/flow.py
  → opencreator-consumer/services/workflow/flow_node_state_service.py
  → opencreator-consumer/tasks/flow_resume.py
  → opencreator-consumer/services/invocation/model_invocation_planner.py
  → opencreator-consumer/services/invocation/model_invocation_service.py
  → opencreator-ai/packages/db/src/task-repository.ts
  → opencreator-ai/packages/queues/src/queue-names.ts
  → opencreator-ai/packages/runtime/src/consumer-callback.ts
  → opencreator-consumer/main.py
  → opencreator-consumer/services/invocation/invocation_finalizer.py
  → opencreator-consumer/services/workflow/flow_event_publish_service.py
  → opencreator-publisher/services/workflow_event_store.py
  → opencreator-publisher/database/mq.py
  → src/lib/workflow-side-effect-claim.ts
  → opencreator-consumer/tasks/setup.py
```

原则：按这条链从前往后写。claim 写在副作用前面，ACK 写在持久化后面。不要先把 RabbitMQ 自动 ACK 打开，再回头补 Event Store。AI 队列和 HTTP 回调在 Outbox 前面，因为节点事件是 Finalizer 之后才产生的。

## 写之前先有的东西

缺这些不要开始本组：

1. 上一组的索引已经生效：`workflow_command (user_id, command_id)`、Inbox `command_id`、Outbox `event_id`。
2. `POST /api/v2/flow/runs` 已经能插入命令并返回 202。
3. Redis Stream `run_flow` 和 RabbitMQ v2 reply 队列已经能通。
4. Event Store 有 Stream 和 `event_id` Hash 的键名。
5. AI 任务创建入口已经存在。

做完前置：点 Run 能跑通一次。还没要求进程崩溃后的重投是安全的。

## 2. 先把两行事实放进同一个事务，再写派发 lease

OpenCreator 对照：

[services/workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py)

`create_run()` 在派发之前：

```text
command_id = req.command_id or req.client_request_id
  → _resolve_command_replay()
       相同 payload：返回原 flow_task_id
       不同 payload：409
  → 校验 DAG
  → mongo session.start_transaction()
       insert flow_task          status=pending，dispatch_state=pending
       insert workflow_command
  → DuplicateKeyError 再走一遍 replay
  → 事务提交之后才 dispatch_command()
```

`_claim_command()`：

```text
query:
  pending 且 next_attempt_at <= now
  或 dispatching 且 lease_expires_at <= now
update:
  status = dispatching
  lease_token
  lease_expires_at
```

`dispatch_command()` 只对 claim 到的行调用 publish。成功后把状态写成 `dispatched`。发给执行仓的 `command_id` 用 `_wire_command_id(user_id, command_id)`。

失败走 `_finish_claim(error)`，把 `flow_task.dispatch_state` 写成 `pending_retry`。`workflow_command_dispatcher_forever()` 每 `WORKFLOW_COMMAND_DISPATCH_INTERVAL_SECONDS`（默认 2 秒）调用 `dispatch_due_commands()`，再 claim 同一行。这一跳还在 Publisher，不要等到 Consumer 的维护扫描。

做完：事务回滚时 `flow_task` 和 `workflow_command` 都不存在。两个并发派发里只有一个进入 `dispatching`。把 Redis 弄断一次，命令停在 `pending_retry`，循环恢复后仍是原来的 `command_id`。

## 4. 写 Consumer Inbox

OpenCreator 对照：

[flow_command_inbox_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_command_inbox_service.py)

按这个顺序写方法：

```text
payload_hash()
claim_command()
mark_completed()
mark_failed()
claim_due_redelivery()
mark_redelivery_enqueued()
mark_redelivery_failed()
```

`claim_command()` 用 `find_one_and_update(..., upsert=True)`。`DuplicateKeyError` 时读 `_id = command_id` 的现有行，比较 `protocol_version`、`command_type`、`flow_task_id`、`flow_run_id`、`payload_hash`。有差异就 `conflict=true`。

`mark_completed()` / `mark_failed()` 的过滤条件包含 `status=processing` 和 `lease_token`。完成才写 `expires_at`。失败要 `$unset expires_at`。

做完：同一 payload 第二次 `claimed=false` 且 `conflict=false`。改一个身份字段后 `conflict=true`。用错误的 `lease_token` 调用 `mark_completed()`，行仍是 `processing`。

## 5. 把 claim 放进 run_flow 入口

OpenCreator 对照：

[tasks/flow.py](../../../../../opencreate/opencreator-consumer/tasks/flow.py)

```text
校验 protocol_version = 2
  → command_id 必须在
  → 先把运输体写进 redelivery_payload，再 claim_command()
  → claimed=false：return，不执行副作用
  → start：
       SET opencreator:flow_start_lock:{run_id} NX
       锁被占住且 flow_run_state 不存在
         → raise，外面 mark_failed
       已有 run 且 start_initialized
         → return，然后 mark_completed
       已有 run 但还没 start_initialized
         → 继续铺节点，不新建 run_id
       否则 init_flow_run
  → init_nodes
  → seed_user_selection_outputs
  → 再读一次 run，cancel 已经赢了就走 kill tail，不发 start_flow
  → publish start_flow
  → handle_resume.aio_push(reason=start)
  → mark_start_initialized
  → mark_completed(lease_token)
异常
  → mark_failed(lease_token, error)
```

`start_initialized` 在 `aio_push` 之后写。claim 成功、锁成功，都不等于节点表已经铺完。锁的默认 TTL 是 `FLOW_START_LOCK_TTL_SECONDS`，300 秒。

做完：同一条 Stream 消息送两次，`init_flow_run()` 只发生一次。进程死在 `init_nodes` 之前，Inbox 是 `failed` 或 lease 过期，不是 `completed`。

## 8. 写 Outbox

OpenCreator 对照：

[flow_event_publish_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_event_publish_service.py)

先写 `stable_event_id()`，再写 `_claim_event()`、`_publish_claimed()`、`publish()`、`replay_due_events()`。

```text
publish()
  → 补 flow_task_id / run_id / command_id / protocol_version / trace_id
  → _claim_event(event_id, insert_document)
  → claim 不到：读 status，返回
  → _publish_claimed()
       → publish_message()
       → 带 publish_lease_token 把 status 改成 sent
       → 写 expires_at
```

不要在这里开 Mongo session 去包住节点更新。现码没有这个事务。窗口留给下一组的 `reconcile_terminal_flow_events()`。

做完：同一个 `event_id` 调用 `publish()` 两次，RabbitMQ 只被要求发送一次，只要第一把 lease 还活着或行已经是 `sent`。lease 过期后的重投可以再发，Publisher 侧再用 `event_id` 收成一条。

## 10. 把 ACK 放在 append_event 之后

OpenCreator 对照：

[database/mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py)

`workflow_v2_mq_callback()` 的顺序固定：

```text
校验 protocol_version=2 和字段对齐
  → 终态不被旧事件回退
  → append_event()
  → 更新 last_event_cursor（只接受更晚的 cursor）
  → message.ack()
```

形状不合法且还没开始落库：`reject(requeue=False)`。`append_event()` 已经开始之后失败：`nack(requeue=True)`。重复事件在 `append_event()` 返回原 cursor 之后仍然 ACK。

做完：Event Store 写入抛错时，消息走 nack 重入队，不走 ACK。同一条消息再投，Event Store 里仍然只有一个 `event_id`。

## 完整验收顺序

按这个顺序验，不要跳：

1. 超时重试携带同一把 `command_id`。
2. 确定性 409 之后，下一次点击换成新的 `command_id`。
3. Publisher 并发派发只有一个 `dispatching` lease。
4. Stream 消息里的 `command_id` 是 `wire_command_id`。
5. Inbox 对相同身份的第二次 claim 返回 `claimed=false`。
6. Inbox 对相同 `command_id`、不同 `payload_hash` 返回 `conflict=true`。
7. 错误 `lease_token` 不能把 Inbox 标成 `completed`。
8. `completed` 行有 `expires_at`，`failed` 行没有。
9. 节点状态 CAS 只有一方成功。
10. resume 锁的持有者才删除这把锁。
11. 同一 `event_id` 在 lease 有效时不会第二次 `publish_message`。
12. 消息已经发出但 `sent` 更新失败时，Publisher 仍按 `event_id` 返回原 cursor。
13. `append_event()` 失败时 RabbitMQ 不 ACK。
14. `append_event()` 对重复事件返回原 cursor 时，RabbitMQ ACK。
15. 旧命令的事件不能把已经终态的 `flow_task.status` 改回去。
16. 前端同一 `event_id + scope` 的 effect 只跑一次，失败后可以再跑。
17. AI callback 的 `x-oc-idempotency-key` 每次不同，去重靠 `ai_task_id` / attempt / provider event。
18. Agent `run_flow` 投递不绕过 Consumer Inbox。
19. 维护调度锁让同一种 command 只有一个实例入队。
20. 关掉调度开关后，没有新的周期扫描，已有 lease 仍拒绝第二份副作用。

这组做完的标准是：重投命令不会做第二次业务，重投事件不会变成第二条逻辑事件，ACK 落在对应事实写完之后。只把队列消费掉，或者只在按钮上 disable 两秒，都不算完成。
