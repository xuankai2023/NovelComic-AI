# 队列、Outbox、并发锁与幂等全链路笔记

这份不是队列名单，是给面试和迁移用的认领笔记。要讲清楚的不是“消息进了 Redis 就做完了”，而是一次点击怎么用 `command_id` 只承认一次副作用，一条节点变化怎么用 `event_id` 至少送到一次，以及每一层 ACK 到底确认了什么。

先把一句话背下来：

OpenCreator 的工作流副作用走两条账，中间没有跨库大事务。命令账从 `command_id` 走到 Inbox lease，事件账从 `event_id` 走到 Outbox、RabbitMQ 和 Event Store。ACK 发生在事实落盘之后。Inbox 承认命令一次，Outbox 至少投递一次。

## 0. 先分清五层身份

| 层 | 身份 | 落点 | 挡住什么 |
| --- | --- | --- | --- |
| 用户意图 | `command_id` | 前端 journal、Publisher `workflow_command` | 同一次点击开第二个 run |
| 执行认领 | Inbox 的 `command_id` + `payload_hash` | `flow_command_inbox` | 同一道命令做两次副作用；换了 payload 则是冲突 |
| 节点迁移 | 当前 `status`、`execution_claim_token` | `flow_node_state` | 两个 worker 同时把节点推走 |
| 逻辑事件 | `event_id` | Outbox、Event Store、前端 handler | 同一条事件写两次、推两次副作用 |
| 厂商任务 | `ai_task_id`、`idempotency_key`、provider 三元组 | AI Mongo | 同一任务、同一次尝试、同一条厂商事件插两行 |

AI 每次 HTTP callback 还会带一个新的 `x-oc-idempotency-key`，值是 `randomUUID:timestamp`。这把钥匙每次投递都变。业务去重要靠 `ai_task_id` 和 provider 身份。

面试时一定要把这五层讲开。Stream 确认了运输，Inbox 才确认副作用。callback 的 `accepted` 确认 HTTP 已收下，Finalizer 才确认结果落库。Rabbit 确认 Publisher 已落 Event Store，不确认浏览器已经画完。

## 1. 一条命令要过完的认领

中间不能跳：

```text
1. getOrCreateWorkflowCommand()
2. create_run() 事务写入 flow_task + workflow_command
3. dispatch_command()
     失败 → dispatch_state=pending_retry
     dispatcher_forever 每 2 秒再 _claim_command()
4. Redis Stream run_flow
5. claim_command()，先存 redelivery_payload
6. start 锁
     没有 durable run 且锁被占住 → 抛错 → mark_failed
     已 start_initialized → return → mark_completed
     有半截 run → 继续 init_nodes
7. init_flow_run → init_nodes → seed → start_flow → resume → mark_start_initialized
8. resume 锁 → transition_status → 先写 execution_plans → 再 submit
9. AI createOrGet(idempotency_key)
     provider-execution → artifact-processing → consumer-callback
10. POST /callbacks/models/{vendor}
      验签 → handle_callback_fast
      对不上 → pending_model_callback，响应仍是 accepted
11. InvocationFinalizer claim finalize_status
      写 results / usage，再聚合节点
12. Outbox claim → RabbitMQ
13. append_event() 之后 message.ack()
14. WebSocket replay
15. runWorkflowSideEffectOnce(event_id, scope)
```

事件账嵌在第 12 步之后，不是另一条无关的管道。

## 2. 前端：稳定意图，再抑制本地副作用

`getOrCreateWorkflowCommand(operationKey, request, prefix)` 先看 `sessionStorage` 的 `workflow:v2:pending_commands`。已有这把 `operationKey` 时，返回第一次的 `commandId` 和第一次的 payload。没有则生成 `wf_` / `continue_` / `cancel_` 前缀的新 id。

超时、断网、5xx 不调用 `abandonWorkflowCommand()`。确定性的 400、401、403、404、409、422 才丢掉这把 id。服务端已经收下时，`completeWorkflowCommand()` 清掉记录，下一次点击才是新命令。

journal 让重试带着同一把 `command_id`。服务端是否接成同一次 run，还要看 `workflow_command` 的唯一索引和 payload 比对。

`runWorkflowSideEffectOnce(eventId, scope, effect)` 的键是 `scope:eventId`。有 `navigator.locks` 时先 `locks.request("workflow-v2:" + claimKey)`，没有则直接读改 localStorage。24 小时内的同一键返回 false。effect 失败会 `releaseClaim()`。存储坏了时返回 true，宁肯让副作用再跑一次，也不要卡住界面。

积分入账的真正唯一键仍是服务端 `credits_inout_record.idempotency_key`。节点变色不走这把 claim，因为每个打开的 tab 都要更新自己的画布。没有 Web Locks 时，两个标签页可能同时通过 localStorage 检查。这是 best-effort，不是服务端唯一索引。

## 3. Publisher：派发 lease

`workflow_runs_v2.py` 的 `_claim_command()` 用 `find_one_and_update`，只认两类到期行：

```text
status = pending，并且 next_attempt_at 已到
status = dispatching，并且 lease_expires_at 已到
  → status = dispatching
  → lease_token、lease_expires_at
```

`dispatch_command()` 在 claim 成功之后把 payload 交给 `FlowTask.run_flow.publish()`。队列名是 `run_flow`，broker 是 Redis Stream。发出去之后命令状态写成 `dispatched`。失败则命令回到 `pending`，`flow_task.dispatch_state` 写成 `pending_retry`。`workflow_command_dispatcher_forever()` 每 2 秒再走同一把 lease。

payload 里的 `command_id` 填 `wire_command_id`。Consumer Inbox 认的是这把派发身份。用户看见的 `command_id` 留在 Publisher。回程再用 `wire_command_id` 查回 `client_command_id`。

这把 lease 解决的是两个 Publisher 进程同时派发同一道命令。它不代替 Consumer Inbox。

## 4. Inbox：认还是冲突

Consumer `FlowTask.run_flow()` 收到消息后，任何 init、continue、cancel 之前都要先 `claim_command()`。`claimed=false` 时，后面的副作用不执行。`conflict=true` 时不能当成重试再跑一遍。

身份字段：

```text
command_id
protocol_version
command_type
flow_task_id
flow_run_id
payload_hash
```

`payload_hash` 是 canonical JSON 的 SHA-256。认领条件是这行还不存在，或者它已经是到期的 `processing` / 到期的 `failed`。成功则写成 `processing`，带上新的 `lease_token`，默认 lease 300 秒（`FLOW_COMMAND_INBOX_LEASE_SECONDS`），并清掉 `expires_at`。claim 时把完整运输体写进 `redelivery_payload`。

唯一索引冲突时再读现有行。身份字段一致：已经有人认领或已经完成，这次 `claimed=false`。任一身份字段不同：`conflict=true`。

完成和失败都要带原来的 `lease_token`：

```text
mark_completed(command_id, lease_token)
  processing → completed
  写 expires_at

mark_failed(command_id, lease_token, error)
  processing → failed
  写 next_attempt_at
  清掉 expires_at
```

token 对不上，更新行数为 0。失败行留在库里等重投，不交给 TTL。

`claim_due_redelivery()` 再找执行 lease 已过期、并且 redelivery lease 也过期的行。恢复服务把 `redelivery_payload` 原样推回 `run_flow`。重投出去的仍是原来的 `command_id`。新的 Stream 消息进 Inbox 时，身份相同才能再次 claim。

## 5. start 锁、节点 CAS、resume 锁

start 锁是 `opencreator:flow_start_lock:{run_id}`。三种结果要分开讲：

```text
锁被别人拿着，而且 flow_run_state 还不存在
  → 抛错，mark_failed，不能 mark_completed
已经 start_initialized
  → 直接 return，然后 mark_completed
库里有 run、但还没 start_initialized
  → 接着铺节点，修复半截 bootstrap
```

把“锁被占住、库里还没有 run”标成 completed，会把一次没做完的启动藏起来。

节点状态迁移在 `transition_status()`：

```text
run_id + node_id + status ∈ from_statuses
  → 才把 status 写成新值
```

两个 worker 同时把 `idle` 改成 `running`，只有一个 `matched_count=1`。后来的那个不再执行提交。

模型节点先把 `execution_plans` 写进 `flow_node_state`，再按 `result_id` 提交。提交不确定时 `mark_submit_uncertain`，不新造 `result_id`。`owns_execution_claim()` 要求节点仍是 `RUNNING` 且 `execution_claim_token` 还是自己的。恢复把过期执行打回队列时，`requeue_orphaned_execution()` 用 plan token 和 claim token 做 CAS。旧 worker 的 token 失效，计划和原来的 `result_id` 留在节点上。

同一条 run 的推进还有：

```text
SET opencreator:flow_resume_lock:{run_id} token EX FLOW_RESUME_LOCK_TTL_SECONDS NX
```

默认 TTL 300 秒。拿不到锁就直接返回。`finally` 里先读出现值，等于自己的 token 才删除，避免删掉下一任的锁。这把锁缩小的是两个 resume 同时扫 ready 节点。锁过期之后，CAS 仍然要能挡住重复提交。

## 6. AI 队列和回调

`TaskRepository.createOrGet` 遇到已存在的 `idempotency_key` 返回 existing，不插第二行。BullMQ 阶段：

```text
provider-execution        调厂商
artifact-processing       产物
consumer-callback         签名回调 Consumer
consumer-callback-dlq     回调失败的死信
media-face-verification   人脸检测
```

BullMQ job 完成，只说明 AI 这一段做完了。Consumer 节点要等签名 callback，再进 Finalizer。DLQ 里有一条，说明自动投递停了，不等于 Consumer 节点已经失败收尾。

callback 请求头：

```text
x-oc-timestamp
x-oc-signature          HMAC，密钥是 consumer webhook secret
x-oc-idempotency-key    每次投递新生成
```

Consumer 先验签。对上 invocation 后写 callback 状态，再调度 finalize。对不上则 upsert `pending_model_callback`，HTTP 仍返回 `accepted`，`matched` 可以是 false。`accepted` 只表示 HTTP 收下了。`finalize_scheduled` 才表示收尾已排队。

签名也不能代替 RabbitMQ 的账号权限。用户 JWT、`x-oc-signature`、内部 `INTERNAL_API_KEY` 是三把不同的凭证。

## 7. Finalizer 与 Outbox

Finalizer 认领时，`finalize_status` 必须还在可认领集合里。认领后写成 `running`，`finalize_attempt_count + 1`。认领失败就停。然后写 `results`、确认或回滚 usage、发 `node_status`。`finalize_status=done` 才表示节点侧收尾写完。

Outbox 的类注释写着 transactional outbox。现码的 `publish()` 自己插入 Outbox 行，不和节点状态更新包在同一个 Mongo session 里。状态先落库、进程再死掉，可能出现“状态已变、Outbox 还没有这行”。终态缺口由清扫那组补 `finish_flow` / `flow_killed`。

一条逻辑事件的 `event_id`：

```text
stable_event_id(*parts)
  → canonical JSON
  → SHA-256 前 32 位
  → wfe_{digest}
```

`_claim_event()` 能接住 `pending`、到期的 `failed`、到期的 `publishing`。接住之后写成 `publishing`，lease 默认 30 秒（`FLOW_EVENT_OUTBOX_PUBLISH_LEASE_SECONDS`）。唯一键冲突说明这行已经是 `sent`，或者另一把活 lease 还在，当前调用直接返回。

`_publish_claimed()` 先 `publisher.publish_message()`，再按 `event_id + publishing + publish_lease_token` 更新成 `sent`，并写 `expires_at`。默认保留 7 天。如果消息已经发出，更新 `sent` 时 lease 对不上，代码打 warning 并仍然返回成功。下一轮可能再投一次。Publisher 用同一个 `event_id` 回到原来的 cursor。

`replay_due_events()` 单条失败会把这行标成 `failed` 并写延迟，然后继续下一条，不让一个坏目的地堵住整批。

这是至少一次，不是恰好一次。

## 8. RabbitMQ ACK 在 Event Store 之后

`workflow_v2_mq_callback()`：

```text
解码 JSON
  → protocol_version 必须是 2
  → header 和 body 的 event_id / flow_run_id / command_id 不能互相打架
  → 用 wire_command_id 查回 client_command_id
  → 终态 flow_task 不被旧事件改回去
  → cancel_requested 在终态事件到来之前保持
  → 旧 command_id 不能把公开状态改回 running
  → WorkflowEventStore.append_event()
  → 用更晚的 cursor 更新 flow_task
  → message.ack()
```

Event Store 的 Lua：

```text
HGET event_id
  已存在 → 返回原来的 cursor，inserted=0
不存在 → XADD events
       → HSET event_id → cursor
       → EXPIRE
       → PUBLISH 唤醒
```

OpenCreator 的键名是 `opencreator:wf:{flow_task_id}:events` 和 `opencreator:wf:{flow_task_id}:event_ids`。通知频道是 `opencreator:workflow:v2:event-notifications`。频道消息只用于唤醒。replay 读 Stream。

重复投递也会走到 `append_event()`。只要这次调用返回了，就可以 ACK。ACK 认的是“Event Store 已经能按这个 `event_id` 找到 cursor”，不只认“这次是不是新 XADD”。

形状不合法、并且还没开始落库：`reject(requeue=False)`。已经开始落库之后失败：`nack(requeue=True)`。这两种都不是“已经持久化”的 ACK。

WebSocket 发出去之后没有再向 RabbitMQ 要一次 ACK。连接不在线，事件已经在 Stream 里。

## 9. 四次确认各管一层

| 确认 | 发生时机 | 确认了 | 还没确认 |
| --- | --- | --- | --- |
| Redis Stream 消费位移 | Consumer 收下 `run_flow` | 运输层这条消息处理过 | Inbox 一定 claim 成功 |
| Inbox `completed` | `mark_completed(lease_token)` | 这把命令的副作用做完 | 事件已经到浏览器 |
| AI callback 2xx | Consumer HTTP 返回成功 | 这次回调请求被接受 | Finalizer 已完成 |
| RabbitMQ ACK | `append_event()` 返回之后 | Event Store 有这个 `event_id` | 浏览器已经应用 |
| WebSocket cursor | 前端持久化 `event_cursor` | 这个连接处理到哪 | 服务端可以丢掉事件 |

维护调度锁只管“谁来发扫描”。`opencreator:flow_maintenance_scheduler:{command}` 用 `SET NX`，拿到锁的实例才把命令推进 `flow_maintenance`。调度锁过期，不代表业务副作用可以做第二次。`FLOW_MAINTENANCE_SCHEDULER_ENABLED` 关掉之后，lease 和唯一索引仍在，只是没有人周期重投。

## 10. Agent 不参加画布 Outbox

`task_publisher.run_flow` 的队列默认是 `run_flow`。参数外形和 Publisher / Consumer 的 `run_flow` 对齐。OpenCreator 现码里这个函数体不执行 DAG。Agent 不写 `flow_command_inbox`，也不写画布 Outbox。

Agent 自己的 run 在 `RedisRunStore`：`acquire_session_run_lock`、`append_event`、`write_checkpoint`。`ResumeWindowExpiredError` 表示 Agent SSE 的事件窗过期。它和画布 WebSocket 的 `RESUME_WINDOW_EXPIRED` 不是同一把 Redis 键，也不能用画布 `event_cursor` 去续 Agent run。

## 11. 文件编写顺序

迁移时 claim 写在副作用前面，ACK 写在持久化后面：

1. `workflow-command-journal.ts`：超时复用 `command_id`，确定性 4xx 才放弃。
2. Publisher `workflow_runs_v2.py`：`pending / dispatching` lease，发出 `wire_command_id`。
3. Publisher `tasks/flow.py`：只负责把 `run_flow` 发到 Redis Stream。
4. Consumer `flow_command_inbox_service.py`：身份、lease、conflict、redelivery。
5. Consumer `tasks/flow.py`：start / continue / cancel 之前先 claim，再加 start 锁。
6. `flow_node_state_service.py` 和 `flow_resume.py`：CAS 与 resume 锁。
7. AI `task-repository.ts`、队列名、`consumer-callback.ts`。
8. Consumer callback 入口和 `invocation_finalizer.py`。
9. `flow_event_publish_service.py`：稳定 `event_id` 和 publish lease。
10. `workflow_event_store.py` 和 Publisher `database/mq.py`：先 `append_event()`，后 ACK。
11. `workflow-side-effect-claim.ts`。
12. `tasks/setup.py`：维护调度锁。

不要先把 RabbitMQ 自动 ACK 打开，再回头补 Event Store。AI 队列和 HTTP 回调在 Outbox 前面，因为节点事件是 Finalizer 之后才产生的。

## 12. 和 NovelComic 当前迁移关系

上一组已经把唯一索引放在启动路径上。本章把那些写入收成 lease、CAS 和分层 ACK。

当前落点：

- 前端 journal 会在不确定失败时留着命令身份。
- Publisher 派发前有 lease，Stream 里的命令身份是 `wire_command_id`。
- Consumer 在三种命令之前 claim，冲突不再执行。
- 节点迁移带当前状态，resume 释放锁时核对 token。
- Outbox 至少投递一次，Publisher 在 Event Store 返回之后 ACK。
- AI callback 的 header 幂等键每次新建，业务去重落在任务身份上。

所以当前迁移不能说“Redis 里有一条 `run_flow` 就幂等了”。真正的验收要看到 Inbox 只认一次、CAS 失败的一方不再提交、重复 `event_id` 回到原 cursor 之后才 ACK。

## 13. 面试 1 分钟口述

OpenCreator 把一次点击拆成命令账和事件账。前端 journal 在超时后复用 `command_id`，Publisher 用 `pending / dispatching` lease 派发，Redis Stream 里放的是 `wire_command_id`。Consumer 先 `claim_command()`，身份相同就不再做副作用，身份变了标 conflict。start 锁被占住且还没有 run 时不能把 Inbox 标完成。节点用带当前状态的 CAS，模型提交靠 `execution_claim_token`，resume 再用一把会核对 token 的 run 锁。AI 用 `idempotency_key` 收重复任务，BullMQ 跑完只说明厂商这段做完；HTTP `accepted` 之后还要 Finalizer 把 `finalize_status` 收成 done。事件先写成稳定 `event_id` 的 Outbox，发出去和标 `sent` 是两步，所以是至少一次。Publisher 校验 v2 消息后先 `append_event()`，重复 `event_id` 返回原 cursor，然后才 ACK。浏览器的积分和统计再用 `event_id + scope` 做本地 claim，节点变色不走这把锁。Agent 可以往 `run_flow` 投消息，但不写画布 Inbox 和 Outbox。

## 14. 面试官追问怎么答

如果问为什么不能把节点更新和 Outbox 放进一个大事务：

现码的 `publish()` 自己插入 Outbox，不和节点状态包在同一个 Mongo session 里。状态已经变、进程再死掉时，可能还没有这行事件。终态缺口由下一组按稳定 `event_id` 补 `finish_flow` / `flow_killed`。幂等靠的是 `event_id`，不是跨库事务。

如果问 Stream 消费成功但节点没动：

先看 Inbox。`claimed=false` 说明同一身份已经被认过。`conflict=true` 说明 payload 或命令类型变了，不能当重试。Stream 位移只说明运输层处理过这条消息。

如果问 resume 锁过期之后会不会重复提交模型：

会进入下一次 resume，但节点 CAS 和 `execution_claim_token` 还在。锁只减少同时扫 ready 节点的次数。旧 token 失效后，新 worker 仍用原来的 `result_id`，不新造一次计划。

如果问 callback 返回 accepted 但结果没写上：

`accepted` 只表示 HTTP 收下了。对不上 invocation 时会留下 `pending_model_callback`，`matched` 可以是 false。对上之后还要 Finalizer 认领 `finalize_status`。认领失败就停，不会两个人一起写 `results`。

如果问同一条事件到了两次怎么办：

Outbox 允许至少一次。发送成功但没标上 `sent` 时，下一轮用同一个 `event_id` 再投。Event Store 的 Lua 先 `HGET`，已有 cursor 就返回，`inserted=0`，然后仍然 ACK。前端积分走 side-effect claim，画布颜色可以再应用一次。

如果问 `x-oc-idempotency-key` 为什么每次都变：

它标识这一次 HTTP 投递，不标识这一次 AI 任务。重试会换新值。真正挡住第二行的是 `ai_task.idempotency_key`、`(ai_task_id, attempt)` 和 provider event 三元组。

如果问 NovelComic 迁移时先做什么：

先让 Publisher 的派发 lease 和 Consumer Inbox 挡住重复命令，再让节点 CAS 挡住重复提交，然后把 Outbox 的 `event_id` 和“先落 Event Store、后 ACK”接上。不要先开自动 ACK。Agent 的 session 锁不要写进 `flow_command_inbox`。

## 15. NovelComic 当前实现自查

只看本章“队列、Outbox、并发锁与幂等”，NovelComic 当前已经具备主交付：

- 前端 journal 在超时、断网、5xx 时留着 `command_id`，确定性 4xx 才 abandon，成功收下后清掉记录。
- Publisher `_claim_command()` 只领到期的 `pending` 和到期的 `dispatching`。Stream 消息里的 `command_id` 是 `wire_command_id`。派发失败把 `dispatch_state` 写成 `pending_retry`。
- Consumer 在 start、continue、cancel 之前 claim。相同身份不再执行，身份变化标 conflict。完成和失败都核对 `lease_token`。失败清掉 `expires_at`。过期命令按 `redelivery_payload` 重投原来的 `command_id`。
- start 锁被占住且没有 durable run 时抛错并 `mark_failed`。已初始化直接返回。半截 run 继续铺节点。
- `transition_status()` 带 `from_statuses`。孤儿执行用 plan token 和 claim token CAS 回队列，`result_id` 保留。resume 锁 TTL 300 秒，释放前核对 token。
- AI `createOrGet` 按 `idempotency_key` 返回已有任务。callback 每次生成新的 `x-oc-idempotency-key`，并用 `x-oc-signature` 验签。
- Finalizer 先把 `finalize_status` 收成 `running`。Outbox 用 `wfe_` 事件号和 30 秒 publish lease。发出后 lease 丢失会 warning，并依赖同一个 `event_id`。
- Publisher 先 `append_event()`，再用更晚的 cursor 更新 `flow_task`，最后 ACK。畸形且未落库的消息 reject 且不重入队。落库失败 nack 并重入队。终态和 `cancel_requested` 不被旧事件改回去。
- 前端非 UI 副作用按 `event_id + scope` claim。维护调度有独立 Redis 锁，可以关掉。Agent 往 `run_flow` 投消息，不写画布 Inbox；自己的 run 锁在 `RedisRunStore`。

现有自动化已经覆盖：

- Inbox 同 payload 不二次认领，身份变化冲突，过期 lease 可再领，错误 lease 不能完成。
- Publisher 两个 dispatcher 只有一个能领到同一用户的命令，Redis 失败后重试仍是原 `command_id`。
- MQ 回调先落库再 ACK，重复 `event_id` 不产生第二条 Stream 记录，畸形消息不落库。
- start 锁缺失 run 时不把命令标完成。resume 锁使用配置 TTL。到期 Outbox 重放保持原 `event_id`。
- AI 重复幂等键返回 existing，两次 callback header 不同。
- 前端同一副作用第二次跳过，失败后可以再试。关掉维护调度后不再塞扫描。Agent 不能抢走别人的 session run 锁。

和 OpenCreator 现码相比，要单独记住的差别：

- Event Store 在线键是 `workflow:v2:events:{flow_task_id}` 和 `workflow:v2:event-cursors:{flow_task_id}`。去重仍是先看 `event_id` 再写入。没有 Redis client 时还会 upsert Mongo `workflow_events`，在线 replay 仍走 Redis。
- OpenCreator ACK 之后有 `flow.v2_mq_ack_without_event_persist` 这颗零值指标。NovelComic 目前没有上报它。
- Agent 的 `task_publisher` 会真正把消息写入 `run_flow`。它仍然不写 `flow_command_inbox` 和画布 Outbox。

本章验收口径：

如果验收“同一命令只认领一次，节点 CAS 挡住重复提交，同一 `event_id` 重投后回到原 cursor 再 ACK，前端积分副作用只做一次”，当前主交付已经具备。  
状态更新和 Outbox 插入仍然不是一个 Mongo 事务。终态事件缺口、lease 过期后的补偿扫描，属于清扫那一组。
