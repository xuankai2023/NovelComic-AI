# 清扫、恢复、快照与补偿：这里面有哪些技术点

这一组只讲进程死掉、回调晚到、事件没写进 Outbox 之后，系统怎么把已经认领的工作再推回可继续的状态。队列那组已经说明 lease 和 ACK。这里讲谁来扫、扫到了补哪一步、快照和 cursor 各回答什么。

先背一句话：

```text
claimed 还不是 start_initialized；
cursor 补的是漏掉的事件；
snapshot 读的是当前状态。
```

队列那组的每一跳都可能停在中间。补偿要接回同一跳，而不是从 Run 重新开始。

```text
停在 Publisher 派发
  flow_task.dispatch_state = pending_retry
  → workflow_command_dispatcher_forever
  → 同一把 command_id 再 dispatch
  这是 Publisher 自己的循环，每 2 秒一次
  不进 flow_maintenance

停在 Inbox 已 claim、run 还没 start_initialized
  → redeliver_due_workflow_commands
  → 用当初的 redelivery_payload 推回 run_flow
  → command_id 不变
  → start 锁还在且库里没有 run：抛错，Inbox 标 failed，等下一轮
  → 库里有半截 run：继续 init_nodes，不新建 run_id
  recover_running_flows 看到未 start_initialized 会跳过
  两条扫描不能对调

停在计划已写入、invocation 还没插齐
  → recover_running_flows
  → 只处理已 start_initialized 的 v2
  → recover_orphaned_planned_nodes
  → CAS 回队列，expected_result_ids 不变
  → handle_resume(reason=recover)
  → resume 复用 execution_plans，不再 plan_node

停在 webhook 一直不回来
  → mark_timed_out_invocations
  → ModelInvocationService.complete(status=timeout)
  → 扣费和结果还没齐时，再由 reconcile_pending_deductions 收尾

停在回调比 invocation 更早
  → POST /callbacks/models/{vendor} 仍返回 accepted，matched=false
  → pending_model_callback.status=pending
  → replay_pending_callbacks
  → parse_callback + handle_callback_fast
  → 对上之后 schedule finalize，行改成 replayed

停在 HTTP 已 accepted、finalize 没写完
  → recover_stuck_finalize
  → pending/failed 超过 60 秒，或 running 的 finalize_started_at 超过 60 秒
  → running 这一支 force=true
  → 再 claim finalize_status

停在 invocation 已终态、usage / result / 模型事件还没齐
  → reconcile_pending_deductions
  → usage_v2 里已经 deducted 的，先 mark_usage_confirmed
  → finalize_terminal_invocation
  → 节点事件进 Outbox

停在 run 已 success/failed/stopped、终态事件没进 Outbox
  → reconcile_terminal_flow_events
  → stable_event_id("finish_flow"|"flow_killed", run_id)
  → publish
  → mark_terminal_event_outbox_recorded
  不补 node_status

停在 Outbox 已有行、RabbitMQ 还没稳定送到
  → replay_due_outbox_events
  → 同一 event_id 再 publish
  → Publisher append_event 返回原 cursor 后才 ACK

停在 Event Store 已有事件、浏览器断了
  → 新连接 attach_flow(last_event_cursor)
  → cursor 还在：replay，不拉 snapshot
  → 发 resume_ready
  不断开连接不会 cancel

停在 cursor 已经过期
  → Publisher 用 Base64(INTERNAL_API_KEY)
  → 先问 CONSUMER_BLUE_URL，404 再问 GREEN
  → GET /api/internal/workflow/{flow_task_id}/snapshot
  → 校验 flow_task_id 和 protocol_version=2
  → 先发 flow_snapshot，再从 latest replay
  → resume_ready
  快照也失败：resume_error RESUME_WINDOW_EXPIRED，close 4409
```

八类 `flow_maintenance` 命令只覆盖 Consumer 这一侧。Publisher 的派发重试、浏览器的 cursor、AI 的 callback 队列是另外三截，要接到上面同一条链上，不能各写各的“重跑”。

调度本身：

```text
FLOW_MAINTENANCE_SCHEDULER_ENABLED
  → 每 10 秒看一轮
  → 每种 command 一把 opencreator:flow_maintenance_scheduler:{command}
  → 拿到锁才推进 flow_maintenance
Inbox 重投默认 10 秒一轮
running 恢复默认 300 秒一轮
其余默认 60 秒一轮
```

## 1. 维护入口收八类命令

[flow_maintenance.py](../../../../../opencreate/opencreator-consumer/tasks/flow_maintenance.py) 的 `handle_maintenance(command)`：

| command | 做什么 |
| --- | --- |
| `redeliver_due_workflow_commands` | 把过期 Inbox 按原 payload 推回 `run_flow` |
| `mark_timed_out_invocations` | webhook 调用超时标 `timeout` |
| `recover_running_flows` | 把仍在 running、且可以恢复的 run 再送进 resume |
| `reconcile_terminal_flow_events` | 终态 run 缺 Outbox 事件时补 `finish_flow` / `flow_killed` |
| `replay_pending_callbacks` | 重放还停在 `pending` 的模型回调 |
| `recover_stuck_finalize` | 把卡住的 Finalizer 再 claim |
| `reconcile_pending_deductions` | 成功补确认、失败补回滚 |
| `replay_due_outbox_events` | 再发布到期 Outbox |

`replay_failed_outbox_events` 走同一条 `replay_due_outbox_events()`。未知 command 只打 warning。

调度在 [tasks/setup.py](../../../../../opencreate/opencreator-consumer/tasks/setup.py)。`FLOW_MAINTENANCE_SCHEDULER_ENABLED` 为假时，循环不起。默认间隔不一样：

| command | 配置 | 默认 |
| --- | --- | --- |
| `redeliver_due_workflow_commands` | `FLOW_COMMAND_INBOX_SWEEP_INTERVAL_SECONDS` | 10 秒 |
| `recover_running_flows` | `FLOW_RECOVER_RUNNING_INTERVAL_SECONDS` | 300 秒 |
| 其余六类 | `FLOW_MAINTENANCE_INTERVAL_SECONDS` | 60 秒 |

循环本身每 10 秒醒一次，没到间隔就跳过。每种 command 还要先拿到 `opencreator:flow_maintenance_scheduler:{command}`。有维护任务，也不表示所有窗口共用一个 RTO。

## 2. Inbox 重投仍用原来的 command_id

[flow_recovery_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_recovery_service.py) 的 `redeliver_due_workflow_commands()`：

```text
claim_due_redelivery()
  → 取出 redelivery_payload 和 redelivery_lease_token
  → FlowTask.run_flow.aio_push(**payload)
  → mark_redelivery_enqueued()
```

payload 是 claim 时存下来的运输体，里面的 `command_id` 不变。推回去之后，Inbox 按同一身份再决定认不认。缺 payload 或 lease token 时 `mark_redelivery_failed()`，不另造一把命令 id。

每轮条数默认 `FLOW_COMMAND_INBOX_REDELIVERY_LIMIT`。

---

## 3. running 恢复先看 bootstrap 完了没有

`recover_running_flows()` 只查：

```text
status = running
flow_resume_queue = 当前 FLOW_RESUME_QUEUE_NAME
并且
  protocol_version 不是 2
  或 protocol_version = 2 且 start_initialized = true
```

查出来之后再挡一层：`protocol_version == 2` 且 `start_initialized` 仍为假，直接跳过并打日志。命令可以已经 `claimed`，节点表还没铺完。这种 run 不能当成可 resume 的 running。

对已经初始化的 v2，还会先跑 `recover_orphaned_planned_nodes()`。然后这些情况才把 `run_id` 送进 `FlowResumeTask.handle_resume(reason="recover")`：

- 节点上已经有 `pending_resume`
- 刚刚把孤儿计划重排成功
- `ready_nodes()` 还有可跑节点，并且 `mark_pending_resume(true)` 没有失败
- `all_terminal()` 为真，需要再进 resume 去收尾

---

## 4. 孤儿计划按原来的 result_id 重排

`recover_orphaned_planned_nodes()` 只处理同时满足这些条件的节点：

```text
is_active 不是 false
status = RUNNING
有 execution_plans、execution_plan_token、execution_claim_token、started_at
started_at 早于 stale_before
expected_result_ids 里还有没落成 invocation 的 result_id
```

`stale_before` 是现在减去 `FLOW_RUNNING_NODE_ORPHAN_SECONDS`，默认 300 秒。

然后 `requeue_orphaned_execution()` 做 CAS：旧 claim token 失效，计划里的 `result_id` 仍留着。下一轮 resume 用这批 id 再提交。invocation 的唯一键挡住“恢复和迟到的旧 worker 各提交一次”。

没有 `execution_plans` 的旧节点不进这条重排。

---

## 5. 终态补偿只补 run 级那一条事件

`reconcile_terminal_flow_events()` 的过滤：

```text
protocol_version = 2
status ∈ success / failed / stopped
terminal_event_outbox_recorded ≠ true
按 updated_at 升序
条数默认 FLOW_TERMINAL_EVENT_RECONCILE_LIMIT
```

`stopped` 补 `flow_killed`，另外两种补 `finish_flow`。`event_id` 用：

```text
FlowEventPublishService.stable_event_id(event_name, run_id)
```

同一 run、同一事件名，补多少次都是同一个 `event_id`。发布之后 `mark_terminal_event_outbox_recorded(run_id, event_id)`。

这是状态和 Outbox 不在一个事务时的窗口。它不补每一个节点事件，也不补每一次 invocation。节点过程事件如果没进 Outbox，这条扫描不会逐条重造。

---

## 6. 回调收下了，还不等于 Finalizer 写完

`replay_pending_callbacks()` 找 `pending_model_callback.status = pending`，默认最多 100 条。按 vendor 找 provider，`parse_callback()` 之后走 `ModelInvocationService.handle_callback_fast()`。需要收尾就 `InvocationFinalizer.run_finalize_async()`。成功把这行标成 `replayed`，异常标成 `failed`。

`pending_model_callback` 的 `(vendor, external_task_id)` 不是唯一索引。并发早到可以有多行。重放按行处理，不先合并成一条。

`recover_stuck_finalize()` 的截止时间在代码里写成 60 秒，不是上面的 300 秒配置：

```text
finalize_status ∈ pending / failed，且 updated_at 早于 60 秒
或 finalize_status = running，且 finalize_started_at 早于 60 秒
```

`running` 那一支调用时带 `force=true`。条数用 `PENDING_DEDUCTION_RECONCILE_LIMIT`。HTTP callback 已经 2xx，只要 `finalize_status` 还不是 `done`，这条扫描仍会再推一次。

---

## 7. 扣费补偿看的是确认、回滚和结果写没写完

`reconcile_pending_deductions()` 找已经终态、但侧写还没齐的 invocation：

```text
success，并且 usage_status / result_write_status / model_status_event_status 还有没完成的
failed 或 timeout，并且 rollback_status / result_write_status / model_status_event_status 还有没完成的
```

成功且能在 `usage_v2` 里找到 `deduction_id` 对应的 `deduction_status=deducted`，先 `mark_usage_confirmed_by_deduction_id()`。然后一律 `finalize_terminal_invocation()`。

usage 行已经扣过，和 invocation 上的 `usage_status` 已经写成 confirmed，是两步。补偿把它们再对齐。

---

## 8. 到期 Outbox 再走原来的 event_id

`replay_due_outbox_events()` 就是 `FlowEventPublishService.replay_due_events()`。它 claim 的是 `pending`、到期的 `failed`、到期的 `publishing`。发出去之后仍用原来的 `event_id` 标 `sent`。

`sent` 表示 broker 投递这一步做过了。Publisher 还要 `append_event()` 成功才 ACK。补偿把消息再送上 RabbitMQ，不代替 Event Store，也不代替浏览器 replay。

## 9. snapshot 是几次读取拼出来的视图

[workflow_snapshot_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/workflow_snapshot_service.py) 的 `get_snapshot()` 分四次查：

```text
flow_task
flow_run_state，按 updated_at 取最新一条
flow_node_state，按 node_id 排序
flow_event_outbox，status=sent，按 created_at 取最后一条
```

`flow_task` 和 `flow_run` 都没有时返回空。有一个就组装：

```text
protocol_version = 2
flow_task_id
flow_run_id
status          run 优先，否则 task
last_event_id   最后一条 sent 事件
flow_task
flow_run_state
flow_node_state
```

没有 Mongo snapshot transaction。读的过程中节点状态可以变。这是某一次读到的诊断和恢复视图，不是事件日志，也不是某一时刻的事务快照。

内部路由：

```text
GET /api/internal/workflow/{flow_task_id}/snapshot
Authorization = Base64(INTERNAL_API_KEY)
```

[controller/internal/auth.py](../../../../../opencreate/opencreator-consumer/controller/internal/auth.py) 用 `compare_digest` 比对解码后的密钥。没配密钥返回 503，缺头或密钥不对返回 401。找不到快照返回 404。

## 10. Publisher 按 blue、green 各试一次

[workflow_snapshot_client.py](../../../../../opencreate/opencreator-publisher/services/workflow_snapshot_client.py)

```text
CONSUMER_BLUE_URL
CONSUMER_GREEN_URL
超时 5 秒
404 → 试下一个
其他 HTTP 错误或校验失败 → 记 last_error，试下一个
两个都没有 → WorkflowSnapshotUnavailable
```

拿到 JSON 之后还要：

```text
flow_task_id 与请求一致
protocol_version = 2
```

没有多数派，也没有版本号仲裁。先返回合格快照的那一侧就被采用。

WebSocket 在 [controller/v2/flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)。`cursor_is_available()` 为假时才 `WorkflowSnapshotClient.fetch()`。失败发送 `resume_error`，`code=RESUME_WINDOW_EXPIRED`，然后 `close(4409)`。成功则把 cursor 换成 `latest_cursor`，先发 `event_type=flow_snapshot`，再 `replay`。终态 run 还会把 replay 上沿补到最新，避免 `resume_ready` 用连接开始时的旧状态盖住已经结束的 run。最后才发 `resume_ready`。

## 11. 前端恢复的完成信号是 resume_ready

[workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts) 把 cursor 放在 `sessionStorage` 的 `workflow:v2:cursor:{flowTaskId}`。重连发送 `attach_flow`，带 `last_event_cursor`。

```text
收到事件 → 记下 event_cursor
收到 flow_snapshot → 用快照认识当前状态
收到 resume_ready → 这次恢复完成，开始接实时事件
收到 resume_error → 停止把这次连接当成已经接上
```

关掉页面、断掉 WebSocket，都不会发 cancel。服务端 run 继续，等下一次 attach。

## 12. AI 重投到 Consumer，Agent 快照是另一份

AI 的自动重试在 BullMQ `consumer-callback`。另外有脚本：

[scripts/replay-consumer-callbacks.ts](../../../../../opencreate/opencreator-ai/scripts/replay-consumer-callbacks.ts)

它把指定 `ai_task_id` 再放进 `consumer-callback`，job id 形如 `callback-replay-{aiTaskId}-{timestamp}`。每次运行都是新 job。脚本存在，不等于所有永久失败都已经自动补过。补到 Consumer 之后，仍要经过 Finalizer，才会变成节点事实。

Agent 的 [workflow_snapshot.py](../../../../../opencreate/opencreator-agent/creato/core/tools/opencreator/workflow_snapshot.py) 校验的是请求里带来的画布快照：`schema_version` 为 1 或 2、有 `snapshot_hash`、有 `captured_at_utc_ms`、`flow_id` 对得上、nodes / edges 是对象列表。这是给工具看的当前画布，不是 Consumer 的 v2 执行快照。

Agent run 自己的恢复在 [agent_redis_run_store.py](../../../../../opencreate/opencreator-agent/creato/services/agent_redis_run_store.py)。`ensure_resume_available()` 失败抛 `ResumeWindowExpiredError`。那是 Agent 事件窗，不是画布 cursor。

## 动手前要有的东西

1. Inbox、Outbox、节点 CAS、resume 锁已经按上一组工作。
2. `start_initialized` 会在 v2 start 铺完节点后写上。
3. 模型节点会先落 `execution_plans` 和 `expected_result_ids`。
4. Publisher Event Store 能判断 cursor 还在不在，并能 `replay`。
5. Consumer 内部端口和 `INTERNAL_API_KEY` 能配到 Publisher 的 blue/green 地址上。

做完这组后，验收目标是：

```text
未 start_initialized 的 v2 running 不会被恢复扫描推进
终态缺事件时补出稳定的 finish_flow 或 flow_killed
callback 2xx 但 Finalizer 卡住时能再跑
cursor 还在就 replay
cursor 不在就拿到 snapshot 或明确的 4409
resume_ready 之后前端才当恢复完成
关掉 WebSocket 不会把 run 取消
```
