# 清扫、恢复、快照与补偿：文件按什么顺序写

对照 [00-清扫恢复快照与补偿技术点.md](./00-清扫恢复快照与补偿技术点.md) 和 [01-清扫恢复快照与补偿.md](./01-清扫恢复快照与补偿.md)。01 讲运行时谁补哪一步，这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖：先有能单独调用的恢复函数，再挂到周期任务，再让断线走 snapshot，最后才把前端的 `resume_ready` 接上。

队列那组已经有 Inbox、Outbox、CAS 和“落盘之后 ACK”。这一组不重写那些 claim，只在它们失败或过期之后把工作再送回去。

先背这份链路。

```text
opencreator-publisher/services/workflow_runs_v2.py
  → opencreator-consumer/services/workflow/flow_recovery_service.py
  → opencreator-consumer/tasks/flow_maintenance.py
  → opencreator-consumer/tasks/setup.py
  → opencreator-consumer/tasks/flow.py
  → opencreator-consumer/tasks/flow_resume.py
  → opencreator-consumer/main.py
  → opencreator-consumer/services/invocation/invocation_finalizer.py
  → opencreator-consumer/services/workflow/flow_event_publish_service.py
  → opencreator-publisher/database/mq.py
  → opencreator-consumer/services/workflow/workflow_snapshot_service.py
  → opencreator-consumer/controller/internal/auth.py
  → opencreator-consumer/controller/internal/workflow.py
  → opencreator-publisher/services/workflow_snapshot_client.py
  → opencreator-publisher/controller/v2/flow_runs.py
  → src/lib/workflow-resumable-websocket.ts
  → opencreator-ai/scripts/replay-consumer-callbacks.ts
```

原则：补偿接回原链停下的那一跳。Publisher 派发重试写在最前，因为它发生在 Consumer 扫描之前。snapshot 和 `resume_ready` 写在事件能重新进 Event Store 之后。

---

## 写之前先有的东西

缺这些不要开始本组：

1. Inbox 已有 `claim_due_redelivery()`、`redelivery_payload`、`mark_redelivery_enqueued()`。
2. Outbox 已有 `replay_due_events()` 和 `stable_event_id()`。
3. v2 start 在节点铺完后会写 `start_initialized`。
4. 模型节点会把 `execution_plans`、`execution_plan_token`、`execution_claim_token`、`expected_result_ids` 落在 `flow_node_state`。
5. Event Store 已有 `cursor_is_available()`、`latest_cursor()`、`replay()`。
6. WebSocket 已经能 `attach_flow`。还没要求 cursor 过期时有 snapshot。

做完前置：正常 Run 能跑完。杀掉进程之后，过期命令和缺的终态事件还不会自己回来。

## 1. 派发失败先在 Publisher 重试

Consumer 扫描接不到这一跳。命令还没进 Redis Stream 时，只有 Publisher 自己的循环能继续。

OpenCreator 对照：

[workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py)

```text
dispatch_command() 抛错
  → _finish_claim(error)
  → flow_task.dispatch_state = pending_retry
workflow_command_dispatcher_forever()
  → 每 WORKFLOW_COMMAND_DISPATCH_INTERVAL_SECONDS（默认 2 秒）
  → dispatch_due_commands()
  → 再 _claim_command() 同一行
  → 再发 run_flow
```

做完：Redis 发布失败后，`workflow_command` 仍是原来的 `command_id`。两秒后的循环能再次派发。这一步不创建 `flow_command_inbox`。

## 2. 再写恢复服务里可以单测的扫描

OpenCreator 对照：

[flow_recovery_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_recovery_service.py)

按这个顺序写方法。每一段都能不挂调度就调用。

### 2.1 重投命令

```text
redeliver_due_workflow_commands()
  → claim_due_redelivery()
  → run_flow.aio_push(**redelivery_payload)
  → mark_redelivery_enqueued()
失败
  → mark_redelivery_failed()
```

不要在这里生成新的 `command_id`。

### 2.2 超时调用

```text
mark_timed_out_invocations()
  webhook + submitting/running + updated_at 早于 WEBHOOK_CALLBACK_TIMEOUT_SECONDS
  → ModelInvocationService.complete(status="timeout")
opencreator_ai 使用 OC_AI_WORKER_TIMEOUT_ERROR_CODE
```

### 2.3 孤儿计划

```text
recover_orphaned_planned_nodes(run_id, stale_before)
  只处理有 execution_plans 的 RUNNING 节点
  expected_result_ids 仍有缺失
  → requeue_orphaned_execution()
```

CAS 失败的节点不要放进返回列表。

### 2.4 running flow

```text
recover_running_flows()
  查询就排除 v2 且未 start_initialized
  循环里再跳过一次
  v2 先跑孤儿重排
  pending_resume / ready_nodes / all_terminal 才返回 run_id
```

这一步只返回 `run_id` 列表，自己不调用 `handle_resume`。调用放在维护任务里，避免恢复服务和 resume 任务互相导入成环。`redeliver` 里对 `FlowTask` 的 import 也保持函数内导入。

### 2.5 终态事件

```text
reconcile_terminal_flow_events()
  v2 + success/failed/stopped + terminal_event_outbox_recorded 不是 true
  stopped → flow_killed
  其他 → finish_flow
  event_id = stable_event_id(event_name, run_id)
  publish()
  mark_terminal_event_outbox_recorded()
```

不要在这里补 `node_status`。

### 2.6 回调、Finalizer、扣费、Outbox

```text
replay_pending_callbacks()
  → main.py 同一条 parse_callback + handle_callback_fast
  → matched 之后 schedule_finalize
  → pending 行改成 replayed

recover_stuck_finalize()
  → invocation_finalizer.run_finalize_async
  → running 分支 force=true，截止 60 秒

reconcile_pending_deductions()
  → usage_v2 已 deducted 的先 mark_usage_confirmed
  → finalize_terminal_invocation
  → 节点事件进 Outbox

replay_due_outbox_events()
  → replay_due_events()
  → 同一 event_id
  → Publisher append_event 之后才 ACK
```

`replay_failed_outbox_events` 直接等于 `replay_due_outbox_events`。这四段都回到队列那组已经写过的下一跳，不另开一条修复 run。

做完：用一条过期 Inbox、一条缺终态事件的 v2 run、一条缺 invocation 的 RUNNING 计划节点，分别调用对应方法。命令 id、event id、result id 都和原来相同。回调补偿对上之后，走的是 `POST /callbacks/models/{vendor}` 后面的 Finalizer，不是新的节点 id。

## 3. 写维护任务分发

OpenCreator 对照：

[flow_maintenance.py](../../../../../opencreate/opencreator-consumer/tasks/flow_maintenance.py)

```text
handle_maintenance(command, reason)
  redeliver_due_workflow_commands
  mark_timed_out_invocations
  recover_running_flows
      → 对每个 run_id handle_resume.aio_push(reason="recover")
  reconcile_terminal_flow_events
  replay_pending_callbacks
  recover_stuck_finalize
  reconcile_pending_deductions
  replay_failed_outbox_events 和 replay_due_outbox_events
未知 command → warning，返回
```

队列名 `FLOW_MAINTENANCE_QUEUE_NAME`，默认 `flow_maintenance`。`max_retry_times=0`。维护任务自己失败时，不要让 funboost 把同一条扫描无限重试；下一轮调度会再推。

做完：手动 push `reconcile_terminal_flow_events`，只补终态事件。push 一个不认识的 command，数据库没有新写入。

## 4. 把调度和锁挂上启动

OpenCreator 对照：

[tasks/setup.py](../../../../../opencreate/opencreator-consumer/tasks/setup.py)

在 `register_task()` 里启动 `flow_maintenance` 消费者。`FLOW_MAINTENANCE_SCHEDULER_ENABLED` 为真时再启动 `_maintenance_scheduler()`。

间隔按 command 分开，不要写成一个数字：

```text
redeliver_due_workflow_commands  → FLOW_COMMAND_INBOX_SWEEP_INTERVAL_SECONDS
recover_running_flows            → FLOW_RECOVER_RUNNING_INTERVAL_SECONDS
其他                             → FLOW_MAINTENANCE_INTERVAL_SECONDS
```

每轮先 `SET opencreator:flow_maintenance_scheduler:{command} NX`。拿到锁才 `aio_push`。循环 `sleep 10`。

做完：开两个 Consumer，同一种 command 在一个间隔里只有一次入队。把开关设成 false，重启后不再有新的调度消息。

get_snapshot(flow_task_id)

## 8. 把 snapshot 接进 WebSocket resume

OpenCreator 对照：

[controller/v2/flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)

attach 处理顺序：

```text
解析 last_event_cursor，缺省 0-0
cursor_is_available 为假
  → fetch snapshot
  → 失败：resume_error code=RESUME_WINDOW_EXPIRED，close 4409
  → 成功：cursor 改成 latest_cursor
注册连接，旧的同一 connection_id close 4001
有 snapshot 就先发 flow_snapshot
replay
run 已终态时，把 replay 补到最新 cursor
发 resume_ready
```

`resume_ready` 里带 `event_cursor`、`latest_event_cursor`、`status`、`connection_id`。终态判断放在 replay 之后再读一次 `get_run_summary()`，避免握手开始时的旧状态盖住刚刚写完的终态。

做完：cursor 仍在 Event Store 里时，不请求 Consumer snapshot，直接 replay。cursor 失效且 snapshot 成功时，客户端先看到 `flow_snapshot` 再看到 `resume_ready`。snapshot 也失败时，连接以 4409 结束。

[workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts)

## 完整验收顺序

按这个顺序验，不要跳：

1. 过期 Inbox 被重投后，`command_id` 和 `payload_hash` 与第一次相同。
2. 重投后的第二次执行在身份相同且仍完成时，不再初始化第二份 run。
3. webhook 调用超过 `WEBHOOK_CALLBACK_TIMEOUT_SECONDS` 被标成 `timeout`。
4. `opencreator_ai` 的超时错误带来源 `oc-ai-worker` 和 `callback_timeout`。
5. v2、`running`、`start_initialized` 不是 true 的 run 不会被送进 `handle_resume`。
6. 已初始化、计划还缺 invocation、并且 `started_at` 已过期的 RUNNING 节点被 CAS 回队列，`result_id` 不变。
7. 没有 `execution_plans` 的节点不进孤儿重排。
8. `success` / `failed` / `stopped` 且还没记下终态 Outbox 的 v2 run，会补出稳定 `event_id`。
9. 同一条终态补偿再跑一次，不会产生第二个 `event_id`。
10. 补偿不创建缺失的 `node_status` 事件。
11. `pending_model_callback` 重放成功后变成 `replayed`，失败变成 `failed`。
12. `finalize_status=running` 且开始时间早于 60 秒时，以 `force=true` 再进 Finalizer。
13. `usage_v2` 已经 `deducted` 的成功调用，补偿先标 usage confirmed，再收尾。
14. 到期 Outbox 再发布时仍使用原 `event_id`。
15. 调度开关关闭后，不再出现新的 `flow_maintenance` 命令。
16. 两个实例里，同一 command 的调度锁只有一个能入队。
17. snapshot 在读取期间允许状态变化，返回体仍带 `protocol_version=2`。
18. 错误的内部密钥得到 401，未知 `flow_task_id` 得到 404。
19. 蓝 404、绿合格时，Publisher 采用绿。两边都不合格时，WebSocket 得到 `RESUME_WINDOW_EXPIRED` 和 4409。
20. cursor 仍可用时不拉 snapshot。
21. snapshot 成功时，`flow_snapshot` 出现在 `resume_ready` 之前。
22. 终态 run 的 `resume_ready.status` 与最新 `flow_task` 一致。
23. 前端在 `resume_ready` 之前不把恢复当成完成。
24. 断开 WebSocket 不产生 cancel 命令。
25. AI replay 脚本使用新的 job id，并且不直接写节点状态。
26. Agent 请求快照和 Consumer v2 snapshot 的字段对不上时，不能互相替代。

这组做完的标准是：崩溃后的命令、计划和终态事件能沿原身份补上；断线后的浏览器要么从 cursor 接上，要么拿到当前快照，要么得到明确的恢复失败。只把页面刷新后再点一次 Run，不算完成。
