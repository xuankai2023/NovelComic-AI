# 清扫、恢复、快照与补偿全链路笔记

这份不是定时任务清单，是给面试和迁移用的补偿笔记。要讲清楚的不是“过一会儿再扫一遍”，而是进程停在哪一跳，就用原来的 `command_id`、`result_id` 或 `event_id` 把那一跳接回去；cursor 还在就补事件，cursor 不在就读当前状态。

先把一句话背下来：

OpenCreator 的恢复分成三件事。Consumer 的维护扫描把过期命令、卡住的节点和缺的终态事件再推进去。Publisher 在 cursor 失效时向 Consumer 要当前 snapshot。浏览器带着 `last_event_cursor` 重连，等到 `resume_ready` 才算接上。`claimed` 还不是 `start_initialized`，cursor 补的是漏掉的事件，snapshot 读的是当前状态。

## 0. 先分清三件事

`维护扫描` 只覆盖 Consumer 这一侧的八类 `flow_maintenance` 命令。Publisher 派发失败由自己的 dispatcher 每 2 秒重试，不进这个循环。

`执行快照` 是 cursor 已经不在 Event Store 里时，Publisher 用内部密钥向 Consumer 要的当前视图。它由四次读取拼成，不是事件日志，也不是某一时刻的事务快照。

`浏览器重连` 带着 sessionStorage 里的 cursor attach。cursor 还在就 replay。收到 `resume_ready` 才把这次恢复当成完成。关掉页面不会 cancel。

AI 的 callback 重投和 Agent 的请求级画布快照留在各自入口。它们都不执行 Consumer 的 DAG 清扫，也不能用画布 cursor 去续 Agent run。

面试时一定要把这三件事讲开。很多问题都来自把“再扫一次”“拉一份当前状态”“把漏掉的事件补上”压成一件事。

## 1. 停在哪一跳，就接回那一跳

```text
派发失败
  → Publisher dispatcher_forever
  → 同一 command_id 再 dispatch
  不经过 flow_maintenance

Inbox 已认领，start_initialized 还是假
  → redeliver_due_workflow_commands
  → 原 redelivery_payload
  → run_flow 再 claim
  → 没有 run 且 start 锁还在：抛错，mark_failed
  → 有半截 run：继续 init_nodes
  recover_running_flows 这一跳要跳过

计划已落库，invocation 不齐，run 已 start_initialized
  → recover_running_flows
  → recover_orphaned_planned_nodes
  → 原 result_id
  → handle_resume(reason=recover)
  → 复用 execution_plans

webhook 超时
  → mark_timed_out_invocations
  → complete(status=timeout)
  → reconcile_pending_deductions

回调早到
  → accepted 且 matched=false
  → pending_model_callback
  → replay_pending_callbacks
  → handle_callback_fast
  → schedule finalize

finalize 卡住
  → recover_stuck_finalize
  → 再 claim finalize_status
  → results / usage / node_status

run 已终态，Outbox 没有终态事件
  → reconcile_terminal_flow_events
  → 稳定 event_id
  → RabbitMQ
  → append_event
  → ACK

Outbox 到期
  → replay_due_outbox_events
  → 同一 event_id

浏览器断线，cursor 还在
  → attach_flow
  → replay
  → resume_ready

cursor 不在
  → 内部密钥拉 snapshot
  → flow_snapshot
  → 从 latest replay
  → resume_ready
  失败则 4409
```

两条扫描不能对调。未初始化的 v2 交给命令重投。已经铺完节点、计划还没变成 invocation 的，才交给 running 恢复。

## 2. 调度只负责把命令放进队列

`FLOW_MAINTENANCE_SCHEDULER_ENABLED` 为真时，循环每 10 秒看一轮。每种 command 一把锁：

```text
opencreator:flow_maintenance_scheduler:{command}
值是 CONSUMER_INSTANCE_ID，否则是 pid
过期秒数是 max(interval - 1, 1)
NX
```

没拿到锁，这一轮不 push。`last_run` 仍会更新，所以没抢到的实例要再等一个间隔。

| command | 默认间隔 |
| --- | --- |
| `redeliver_due_workflow_commands` | 10 秒 |
| `recover_running_flows` | 300 秒 |
| 其余六类 | 60 秒 |

队列名默认 `flow_maintenance`，broker 是 Redis Stream。`handle_maintenance()` 只分发。`recover_running_flows` 是唯一会继续把每个 `run_id` 送进 `FlowResumeTask.handle_resume(reason="recover")` 的。其余命令在恢复服务内部做完计数。未知 command 只打 warning，不执行副作用。

开关关掉之后，没有人周期重投。Inbox lease、Outbox lease 和唯一索引仍在。

窗口不是一个数。webhook 超时默认 1800 秒。孤儿计划默认 300 秒。Finalizer 卡住在代码里写成 60 秒。有维护任务，也不表示所有窗口共用一个 RTO。

## 3. Inbox 重投和半截 bootstrap

`redeliver_due_workflow_commands()` 循环 `claim_due_redelivery()`：

```text
取出 redelivery_payload 和 redelivery_lease_token
  → FlowTask.run_flow.aio_push(**payload)
  → mark_redelivery_enqueued()
```

payload 是 claim 时存下来的运输体，里面的 `command_id` 不变。缺 payload 或 lease token 时 `mark_redelivery_failed()`，不另造一把命令 id。推回去之后，Inbox 仍用 `payload_hash` 判断这是重试还是冲突。

start 侧的三种结果仍由上一组的锁决定：

```text
锁被别人拿着，而且库里没有 run
  → 抛错，Inbox 标 failed，等下一轮
已经 start_initialized
  → 直接返回
库里有半截 run
  → 继续 init_nodes，不新建 run_id
```

`recover_running_flows()` 的查询已经排除“v2 且未 `start_initialized`”。循环里再跳过一次。命令可以已经 `claimed`，节点表还没铺完。这种 run 不能当成可 resume 的 running。

## 4. 已初始化之后才恢复计划和终态

对已经初始化的 v2，先跑 `recover_orphaned_planned_nodes()`。节点要同时满足：

```text
is_active 不是 false
status = RUNNING
有 execution_plans、execution_plan_token、execution_claim_token、started_at
started_at 早于 FLOW_RUNNING_NODE_ORPHAN_SECONDS
expected_result_ids 里还有没落成 invocation 的 result_id
```

CAS 成功才把节点算进恢复列表，并 `mark_pending_resume(true)`。旧 claim token 失效，计划里的 `result_id` 仍留着。下一轮 resume 复用 `execution_plans`，不再重新 plan。invocation 的唯一键挡住恢复和迟到的旧 worker 各提交一次。没有 `execution_plans` 的旧节点不进这条重排。

没有孤儿时，仍可能因为 `pending_resume`、`ready_nodes()` 或 `all_terminal()` 把 run 送回 resume。resume 自己还有 run 锁和节点 CAS，所以和还活着的 worker 重叠时，第二次提交会被挡住。

`reconcile_terminal_flow_events()` 只处理 v2 终态，并且 `terminal_event_outbox_recorded` 不是 true：

```text
stopped → flow_killed
success / failed → finish_flow
event_id = stable_event_id(event_name, run_id)
```

同一 run、同一事件名，补多少次都是同一个 `event_id`。发布之后记下 `terminal_event_outbox_recorded`。这是状态和 Outbox 不在一个事务时的窗口。它不补每一个 `node_status`，也不补每一次 invocation。

## 5. 回调、Finalizer 和扣费是三条扫描

`mark_timed_out_invocations()` 找 webhook 模式、状态还在 `submitting` / `running`、并且 `updated_at` 早于 `WEBHOOK_CALLBACK_TIMEOUT_SECONDS` 的调用。默认 1800 秒。`vendor=opencreator_ai` 时用 `OC_AI_WORKER_TIMEOUT_ERROR_CODE`，来源标成 `oc-ai-worker`。其他厂商写成 `webhook callback timeout`。然后 `complete(status="timeout")`。这一步把调用推进终态。扣费回滚和结果写入如果没做完，还要靠扣费补偿。

`replay_pending_callbacks()` 找 `pending_model_callback.status=pending`，默认最多 100 条。按 vendor 找 provider，`parse_callback()` 之后走 `handle_callback_fast()`。需要收尾就立刻 `run_finalize_async()`，再把行写成 `replayed`。异常写成 `failed`。这张表没有唯一约束，并发早到可以有多行，重放按行处理，不先合并成一条。

`recover_stuck_finalize()` 用固定的 60 秒：

```text
pending / failed 且 updated_at 早于 60 秒
running 且 finalize_started_at 早于 60 秒 → force=true
```

`force` 只加在已经是 `running` 的那一支，用来接过没写完的 lease。HTTP callback 已经 2xx，只要 `finalize_status` 还不是 `done`，这条扫描仍会再推一次。

`reconcile_pending_deductions()` 找已经终态、但侧写还没齐的 invocation。成功且能在 `usage_v2` 里找到 `deduction_status=deducted`，先把 invocation 标成 usage confirmed，再 `finalize_terminal_invocation()`。账本已经扣过，和 invocation 上的标志已经写成 confirmed，是两步。补偿把它们再对齐，不会再扣一次。

`replay_due_outbox_events()` 就是 `replay_due_events()`。`replay_failed_outbox_events` 是同一个函数。它 claim `pending`、到期的 `failed`、到期的 `publishing`，发出去之后仍用原来的 `event_id`。`sent` 表示 broker 投递这一步做过了。Publisher 还要 `append_event()` 成功才 ACK。

## 6. snapshot 是四次读取

`WorkflowSnapshotService.get_snapshot(flow_task_id)`：

```text
flow_task.find_one({ flow_task_id })
flow_run_state.find_one({ flow_task_id }, sort updated_at desc)
flow_node_state.find({ run_id }).sort(node_id)
flow_event_outbox.find_one({ flow_task_id, status: sent }, sort created_at desc)
```

两边都没有时返回空。有一个就组装 `protocol_version=2`，并带上原始 `flow_task`、`flow_run_state`、`flow_node_state`。`status` 优先用 run。`last_event_id` 来自最后一条 sent 事件。`ObjectId` 和日期会收成字符串。没有事务把这四次读锁在同一点。

内部路由：

```text
GET /api/internal/workflow/{flow_task_id}/snapshot
Authorization = Base64(INTERNAL_API_KEY)
```

没配 `INTERNAL_API_KEY` 返回 503。没有 Authorization、Base64 解不开、`compare_digest` 失败，都返回 401。找不到快照返回 404，`detail` 是 `workflow snapshot not found`。头上没有 `Bearer` 前缀。

Publisher 的 `WorkflowSnapshotClient.fetch()` 依次请求 blue、green，超时 5 秒。空地址丢掉，重复地址只留一次。404 继续下一个。响应不是对象、`flow_task_id` 不一致、`protocol_version` 不是 2，都算失败并试下一个。全部失败抛 `WorkflowSnapshotUnavailable`。先返回合格快照的那一侧就被采用。

WebSocket attach 里，cursor 默认 `0-0`，也接受 `last_event_cursor` / `event_cursor` / `cursor`。`cursor_is_available()` 为假时才拉 snapshot。失败发送 `resume_error`，`code=RESUME_WINDOW_EXPIRED`，然后 `close(4409)`。成功则先发 `flow_snapshot`，`event_id` 是 `snapshot-` 加快照内容 SHA-256 的前 24 位。它是这一次连接上的说明，不是 Outbox 里那条 `wfe_` 事件。然后再 replay。终态 run 把 replay 上沿补到最新，避免 `resume_ready` 退回旧状态。最后才发 `resume_ready`。

## 7. 前端以 resume_ready 为完成信号

```text
读 sessionStorage workflow:v2:cursor:{flowTaskId}
连接
  → auth
  → attach_flow { last_event_cursor }
  → 普通事件：保存 event_cursor，交给 handler
  → flow_snapshot：用当前状态补画面
  → resume_ready：恢复完成
  → resume_error：不要把节点当成已经同步
```

`setWorkflowResumeCursor()` 只写 sessionStorage。服务端 run 的状态仍以 `flow_task`、`flow_run_state` 和 Event Store 为准。刷新页面会再走 attach。它不调用 cancel，也不调用 start。

## 8. AI 重投和 Agent 快照不进清扫服务

自动路径是 worker 的 `consumer-callback` 队列，失败可以进 `consumer-callback-dlq`。手工脚本检查 Consumer 健康后，对每个 `ai_task_id` 入队：

```text
Queue("consumer-callback")
jobId = callback-replay-{aiTaskId}-{Date.now()}
```

新的 job id 保证这次入队不会被旧 job 的完成记录吞掉。Consumer 侧仍用 `ai_task_id`、attempt 和 invocation 去重。脚本存在，不等于所有永久失败都已经自动补过。补到 Consumer 之后，仍要经过 Finalizer，才会变成节点事实。

Agent 的 `RedisRunStore.ensure_resume_available(last_event_id)` 失败抛 `ResumeWindowExpiredError`，带上 `run_id`、`last_event_id`、`earliest_event_id`。那是 Agent 事件窗。

`normalize_request_workflow_snapshot()` 接受请求里已经带上的画布。`schema_version` 要是 1 或 2，`snapshot_hash` 非空，`captured_at_utc_ms` 有值，nodes / edges 是对象列表，`flow_id` 对得上。不合格返回空。这份快照给 Agent 工具理解当前画布。它没有 `flow_run_state`，也没有 Consumer 的 `last_event_id`。

## 9. 文件编写顺序

迁移时先接回半截命令，再补终态事件，最后才开放 cursor 失效后的快照：

1. `flow_command_inbox_service.py`：过期命令仍能取出当初的 `redelivery_payload`。
2. `flow_recovery_service.py`：八类扫描各自补原来的身份，不新造 id。
3. `flow_maintenance.py`：`handle_maintenance()` 只分发，未知命令不执行。
4. `tasks/setup.py`：按 command 分间隔，锁和总开关分开。
5. `workflow_snapshot_service.py` 和内部路由：四次读取，密钥用 `compare_digest`。
6. Publisher `workflow_snapshot_client.py`：blue 再 green，校验 `flow_task_id` 和协议版本。
7. `flow_runs.py`：cursor 还在就 replay；不在就 snapshot 或 4409；最后 `resume_ready`。
8. `workflow-resumable-websocket.ts`：`resume_ready` 才算恢复完成，断线不 cancel。
9. AI `replay-consumer-callbacks.ts` 和 Agent `workflow_snapshot.py` 留在各自入口。

不要在刷新时重新 POST `/runs` 来假装恢复。那样会新开一条命令，而不是接回原来的 run。

## 10. 和 NovelComic 当前迁移关系

上一组已经有 Inbox、CAS、Outbox lease 和“落盘之后 ACK”。本章把停在这些跳中间的工作接回去。

当前落点：

- 八类命令都进维护分发，调度间隔和开关已经分开。
- 未初始化的 v2 不会被 running 恢复推进。
- 终态缺事件会补稳定的 `finish_flow` 或 `flow_killed`。
- cursor 失效时会拉内部快照，失败则 4409。
- 前端要等到 `resume_ready`。

所以当前迁移不能说“有一个定时任务就恢复了”。真正的验收要看到补偿沿用原身份，以及浏览器在 `resume_ready` 之前不把画面当成已经接上。

## 11. 面试 1 分钟口述

OpenCreator 的清扫不是把整条 run 再跑一遍。Publisher 自己的 dispatcher 每 2 秒重试派发失败，不进 `flow_maintenance`。Consumer 调度每 10 秒看一轮，Inbox 重投 10 秒，running 恢复 300 秒，其余 60 秒，每种命令还要先拿到自己的 Redis 锁。过期 Inbox 用当初的 `redelivery_payload` 推回 `run_flow`，`command_id` 不变。v2 还没 `start_initialized` 时，running 恢复会跳过，避免把半截 bootstrap 当成可 resume。已经初始化且计划过期的节点，按原来的 `result_id` CAS 回队列，再 `handle_resume(reason=recover)`。终态 run 缺事件时只补一条稳定的 `finish_flow` 或 `flow_killed`。callback 早到、Finalizer 超过 60 秒、扣费标志没对齐，各有一条扫描。Outbox 到期仍用原来的 `event_id`。浏览器 cursor 还在就 replay；不在就用 `Base64(INTERNAL_API_KEY)` 先问 blue 再问 green。快照是四次读取拼出的当前视图。失败发 `RESUME_WINDOW_EXPIRED` 并关闭 4409。前端只有收到 `resume_ready` 才算恢复完成。关掉 WebSocket 不会 cancel。

## 12. 面试官追问怎么答

如果问为什么 claimed 之后不能直接 resume：

Inbox 认领只说明这把命令被接住了。`start_initialized` 才说明 run 和节点铺完。未初始化的 v2 如果进 `recover_running_flows`，会在节点表还不完整时去找 ready 节点。这条 run 要等命令重投把 bootstrap 补完。

如果问终态补偿为什么不把每个节点事件补一遍：

状态更新和 Outbox 插入不是一个事务，窗口里最需要补的是 run 已经结束、浏览器却没看到结束。`stable_event_id(event_name, run_id)` 保证补多少次都是同一条。节点过程事件没进 Outbox 时，这条扫描不会逐条重造。

如果问 snapshot 和 replay 能不能互相代替：

cursor 还在时，replay 补的是漏掉的事件，不需要当前视图。cursor 已经被裁掉时，事件正文补不回来，只能先给一份当前 run / node 状态，再从 latest 接实时事件。这份视图没有事务，读的过程中节点可以变。它也不是 `wfe_` 事件。

如果问 blue 和 green 不一致听谁的：

没有多数派，也没有版本号仲裁。先返回合格快照的那一侧就被采用。404 才试下一个。`flow_task_id` 或 `protocol_version` 不对，也算失败并试下一个。两个都失败才是 `WorkflowSnapshotUnavailable`，然后 4409。

如果问 callback 返回了 accepted，节点为什么还停着：

`accepted` 只表示 HTTP 收下了。对不上 invocation 的行停在 `pending_model_callback`。对上之后 Finalizer 还可能停在 `running`。60 秒扫描用 `force=true` 接过没写完的 lease。AI 脚本把任务放回 `consumer-callback`，也要再经过 Finalizer 才变成节点事实。

如果问关掉页面算不算取消：

不算。WebSocket 是订阅通道。服务端 run 继续，下一次 attach 用 cursor 或 snapshot 接上。停止要走 cancel 命令。

如果问 NovelComic 迁移时先做什么：

先让未初始化的 v2 只走命令重投，再让终态补偿和 Outbox 重放沿用稳定 `event_id`。然后接内部快照和 4409。最后让前端以 `resume_ready` 为完成信号。不要用重新 POST `/runs` 代替恢复。

## 13. NovelComic 当前实现自查

只看本章“清扫、恢复、快照与补偿”，NovelComic 当前已经具备主交付：

- 八类维护命令都进 `handle_maintenance()`。失败的 Outbox 重放和到期重放是同一个函数。未知命令只 warning。
- 调度间隔是 Inbox 10 秒、running 恢复 300 秒、其余 60 秒。锁前缀是 `opencreator:flow_maintenance_scheduler:`。总开关可以关掉整段调度。
- 维护消费组是 `novelcomic_consumer_group`。一条扫描失败会 ACK，`max_retry_times=0`，下一轮由调度再推。
- Inbox 重投使用原来的 payload 和 `command_id`。推送失败不另造命令。
- v2 未 `start_initialized` 会被跳过。孤儿 RUNNING 节点按原 `result_id` CAS 回队列。没有 `execution_plans` 的节点不进重排。
- 终态补偿发布稳定的 `finish_flow` 或 `flow_killed`，并写下 `terminal_event_outbox_recorded`。它不补 `node_status`。
- pending callback、60 秒 Finalizer、扣费侧写各有一条扫描。到期 Outbox 保持原 `event_id`。
- snapshot 由四次读取拼成。内部接口用 Base64 内部密钥，503 / 401 / 404 分开。Publisher 先 blue 后 green，校验任务 id 和协议版本。
- cursor 不可用时拉快照。失败是 `RESUME_WINDOW_EXPIRED` 和 4409。成功先发 `flow_snapshot`，再 replay，最后 `resume_ready`。
- 前端 cursor 在 `workflow:v2:cursor:{flowTaskId}`。`flow_snapshot` 先补画面，`resume_ready` 才算完成。断线不 cancel。
- AI replay 脚本每次使用新的 `callback-replay-{aiTaskId}-{timestamp}`。Agent 请求级画布快照不读执行状态。

现有自动化已经覆盖：

- 重投保持命令身份，第二次 start 不新建 run，失败不另造 id。
- webhook 超时对 `opencreator_ai` 使用专用错误码。
- 孤儿 CAS 失败或不带计划的节点不会进入恢复列表。未初始化 v2 被跳过。
- 终态补偿要求协议版本 2，重复补写仍是同一个 `event_id`。
- pending callback 失败会把行标成 `failed`。running finalize 超过 60 秒会 force。扣费先确认 usage 再写同一条结果。
- blue 404 会改问 green。内部密钥错误是 401，没有快照是 404。
- cursor 过期返回 4409。还在窗口内的 cursor 不拉 snapshot。`flow_snapshot` 之后仍要等 `resume_ready`。

和 OpenCreator 现码相比，要单独记住的差别：

- 消费组名字是 `novelcomic_consumer_group`。调度锁前缀仍沿用 `opencreator:`。
- 终态 status 还包括 `completed` 和 `killed`。`killed` 与 `stopped` 补 `flow_killed`，`completed`、`failed`、`success` 补 `finish_flow`。
- running 恢复除了当前 resume 队列，也会看 `flow_resume_queue` 缺失或为空的 run。未初始化 v2 的跳过仍在。
- 维护消息失败后不再重试同一条 Stream 记录，下一轮完全靠调度重新 push。

本章验收口径：

如果验收“未初始化的 v2 不被 running 恢复推进，终态缺事件能补稳定事件，cursor 还在就 replay，不在就 snapshot 或 4409，`resume_ready` 之后才算接上，断线不 cancel”，当前主交付已经具备。  
snapshot 的四次读取仍然没有包进同一个 Mongo 事务。它是某一次读到的当前视图。
