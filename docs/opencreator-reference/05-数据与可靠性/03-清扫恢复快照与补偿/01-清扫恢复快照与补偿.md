# OpenCreator 是怎么做清扫、恢复、快照与补偿的

## 一、先说结论

OpenCreator 的恢复分成三件不同的事。

```text
维护扫描：Consumer 周期把过期命令、卡住的节点、缺的终态事件、到期 Outbox 再推进去
执行快照：Publisher 在 cursor 失效时，向 Consumer 要当前 run / node 视图
浏览器重连：带着 last_event_cursor attach，等到 resume_ready
```

AI 可以重投 callback。Agent 有自己的 run 事件窗和请求级画布快照。它们都不执行 Consumer 的 DAG 清扫。

补偿要接回队列那组停下的那一跳。完整接法是：

```text
派发失败
  → Publisher dispatcher_forever
  → 同一 command_id 再 dispatch
  不经过 flow_maintenance

Inbox 已认领，start_initialized 还是假
  → redeliver_due_workflow_commands
  → 原 redelivery_payload
  → run_flow 再 claim
  → 没有 run 且 start 锁还在：抛错，mark_failed
  → 有半截 run：继续 init_nodes
  recover_running_flows 这一跳要跳过

计划已落库，invocation 不齐，run 已 start_initialized
  → recover_running_flows
  → recover_orphaned_planned_nodes
  → 原 result_id
  → handle_resume(reason=recover)
  → 复用 execution_plans

webhook 超时
  → mark_timed_out_invocations
  → complete(status=timeout)
  → reconcile_pending_deductions

回调早到
  → accepted 且 matched=false
  → pending_model_callback
  → replay_pending_callbacks
  → handle_callback_fast
  → schedule finalize

finalize 卡住
  → recover_stuck_finalize
  → 再 claim finalize_status
  → results / usage / node_status

run 已终态，Outbox 没有终态事件
  → reconcile_terminal_flow_events
  → 稳定 event_id
  → RabbitMQ
  → append_event
  → ACK

Outbox 到期
  → replay_due_outbox_events
  → 同一 event_id

浏览器断线，cursor 还在
  → attach_flow
  → replay
  → resume_ready

cursor 不在
  → 内部密钥拉 snapshot
  → flow_snapshot
  → 从 latest replay
  → resume_ready
  失败则 4409
```

调度循环只负责把 Consumer 的八类命令放进 `flow_maintenance`。Publisher 派发重试和浏览器 attach 不在这个循环里，但它们补的是同一条 run。

读代码时抓住一个边界：扫描成功只说明补偿动作发出去了。事件要进 Event Store，浏览器要 replay 或吃下 snapshot，用户才看得到。

## 二、调度和八类命令

相关文件：

1. [tasks/setup.py](../../../../../opencreate/opencreator-consumer/tasks/setup.py)
2. [tasks/flow_maintenance.py](../../../../../opencreate/opencreator-consumer/tasks/flow_maintenance.py)
3. [services/workflow/flow_recovery_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_recovery_service.py)
4. [core/config.py](../../../../../opencreate/opencreator-consumer/core/config.py)

### 1. 谁可以发起扫描

`register_task()` 启动 `flow_maintenance` 的消费者。只有 `FLOW_MAINTENANCE_SCHEDULER_ENABLED` 为真，才 `create_task(_maintenance_scheduler())`。

调度表：

```text
redeliver_due_workflow_commands   FLOW_COMMAND_INBOX_SWEEP_INTERVAL_SECONDS   默认 10
mark_timed_out_invocations        FLOW_MAINTENANCE_INTERVAL_SECONDS           默认 60
replay_pending_callbacks          同上
recover_stuck_finalize            同上
reconcile_pending_deductions      同上
replay_due_outbox_events          同上
recover_running_flows             FLOW_RECOVER_RUNNING_INTERVAL_SECONDS       默认 300
reconcile_terminal_flow_events    FLOW_MAINTENANCE_INTERVAL_SECONDS           默认 60
```

锁：

```text
opencreator:flow_maintenance_scheduler:{command}
值是 CONSUMER_INSTANCE_ID，否则是 pid
过期秒数是 max(interval - 1, 1)
NX
```

没拿到锁，这一轮不 push。`last_run` 仍会更新，所以没抢到的实例要再等一个间隔。

### 2. handle_maintenance 只分发

[flow_maintenance.py](../../../../../opencreate/opencreator-consumer/tasks/flow_maintenance.py) 按 command 调 `FlowRecoveryService`。`recover_running_flows` 是唯一会继续 `aio_push` 的：对返回的每个 `run_id` 调用 `FlowResumeTask.handle_resume(reason="recover")`。其余命令在恢复服务内部做完计数。

队列是 `FLOW_MAINTENANCE_QUEUE_NAME`，默认 `flow_maintenance`，broker 是 Redis Stream，消费组 `opencreator_group`。

## 三、FlowRecoveryService 每一类补什么

### 1. 过期命令

`redeliver_due_workflow_commands()` 循环 `claim_due_redelivery()`。合法行：

```text
FlowTask.run_flow.aio_push(**redelivery_payload)
FlowCommandInboxService.mark_redelivery_enqueued(command_id, redelivery_lease_token)
```

推送抛错则 `mark_redelivery_failed()`。payload 里的 `command_id` 就是当初 claim 时的那把。Inbox 仍用 `payload_hash` 判断这是重试还是冲突。

### 2. 超时的 webhook 调用

`mark_timed_out_invocations()`：

```text
execution_mode = webhook
status ∈ submitting / running
updated_at < now - WEBHOOK_CALLBACK_TIMEOUT_SECONDS
```

默认超时 1800 秒。`vendor=opencreator_ai` 时错误码用 `OC_AI_WORKER_TIMEOUT_ERROR_CODE`，来源标成 `oc-ai-worker`，阶段是 `callback_timeout`。其他厂商写成 `webhook callback timeout`。然后 `ModelInvocationService.complete(..., status="timeout")`。

这一步把调用推进终态。扣费回滚和结果写入如果没做完，还要靠 `reconcile_pending_deductions()`。

### 3. 正在跑的 flow

`recover_running_flows()` 的查询已经排除“v2 且未 `start_initialized`”。循环里再跳过一次，避免条件写松之后把半截 bootstrap 放进来。

v2 且已初始化时，先 `recover_orphaned_planned_nodes()`。孤儿节点要：

```text
RUNNING
有 execution_plans、execution_plan_token、execution_claim_token、started_at
started_at 早于 FLOW_RUNNING_NODE_ORPHAN_SECONDS（默认 300 秒）
expected_result_ids 中有的 result_id 还没有 invocation
```

CAS 成功才把 `node_id` 算进恢复列表，并 `mark_pending_resume(run_id, true)`。

没有孤儿时，仍可能因为 `pending_resume`、`ready_nodes()` 或 `all_terminal()` 把 run 送回 resume。resume 自己还有 run 锁和节点 CAS，所以和还活着的 worker 重叠时，第二次提交会被挡住。

### 4. 缺终态事件的 run

`reconcile_terminal_flow_events()` 只处理 v2 的 `success`、`failed`、`stopped`，并且 `terminal_event_outbox_recorded` 不是 true。

```text
stopped → FlowKilledEvent，event_id = stable_event_id("flow_killed", run_id)
其他   → FinishFlowEvent，event_id = stable_event_id("finish_flow", run_id)
```

`publish()` 使用 run 上记下的 `flow_task_result_queue`、`ws_id`、`reply_queue`、`command_id`。然后 `FlowRunStateService.mark_terminal_event_outbox_recorded()`。

节点级 `node_status` 不在这张清单里。用户中间过程如果缺事件，不能指望这条扫描补齐。

### 5. 早到或没消化完的回调

`replay_pending_callbacks(limit=100)` 读 `status=pending`。provider 没有 `parse_callback` 就跳过。解析成功且 invocation 带 `_schedule_finalize` 时，立刻 `run_finalize_async()`，再把 pending 行写成 `replayed`。异常写成 `failed` 并记下 `error`。

### 6. 卡住的 Finalizer

`recover_stuck_finalize()` 用固定的 60 秒，不是 `FLOW_MAINTENANCE_INTERVAL_SECONDS`：

```text
pending / failed 且 updated_at < now - 60s
running 且 finalize_started_at < now - 60s → force=true
```

每条调用 `InvocationFinalizer.run_finalize_async(invocation_id, force=...)`。`force` 只加在已经是 `running` 的那一支，用来接过没写完的 lease。

### 7. 扣费和结果侧写

`reconcile_pending_deductions()` 看 invocation 已经是 `success`、`failed` 或 `timeout`，但确认、回滚、结果写入、模型状态事件还有空缺。

成功路径如果 `usage_v2` 里已经有 `deduction_status=deducted`，先把 invocation 标成 usage confirmed，再 `finalize_terminal_invocation()`。这样不会因为账本已经扣过，就再扣一次；也会把 invocation 上的标志补齐。

### 8. 到期 Outbox

`replay_due_outbox_events()` 把 limit 交给 `replay_due_events()`，默认 `FLOW_EVENT_OUTBOX_REPLAY_LIMIT`。`replay_failed_outbox_events` 是同一个函数。

## 四、执行快照

相关文件：

1. [services/workflow/workflow_snapshot_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/workflow_snapshot_service.py)
2. [controller/internal/workflow.py](../../../../../opencreate/opencreator-consumer/controller/internal/workflow.py)
3. [controller/internal/auth.py](../../../../../opencreate/opencreator-consumer/controller/internal/auth.py)
4. [services/workflow_snapshot_client.py](../../../../../opencreate/opencreator-publisher/services/workflow_snapshot_client.py)
5. [controller/v2/flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)

### 1. Consumer 拼四次读取

`WorkflowSnapshotService.get_snapshot(flow_task_id)`：

```text
flow_task.find_one({ flow_task_id })
flow_run_state.find_one({ flow_task_id }, sort updated_at desc)
flow_node_state.find({ run_id }).sort(node_id)
flow_event_outbox.find_one({ flow_task_id, status: sent }, sort created_at desc)
```

返回体固定 `protocol_version: 2`，并带上原始 `flow_task`、`flow_run_state`、`flow_node_state`。`ObjectId` 和日期会收成字符串。没有事务把这四次读锁在同一点。

路由挂在内部 router 上，依赖 `verify_internal_api_key`。找不到返回 404，`detail` 是 `workflow snapshot not found`。

密钥比对：

```text
没配 INTERNAL_API_KEY → 503
没有 Authorization → 401
Base64 解不开 → 401
compare_digest 失败 → 401
```

Publisher 发送的头就是 `base64(INTERNAL_API_KEY)`，没有 `Bearer` 前缀。

### 2. Publisher 怎么用这份快照

`WorkflowSnapshotClient.fetch()` 依次请求：

```text
{CONSUMER_BLUE_URL}/api/internal/workflow/{flow_task_id}/snapshot
{CONSUMER_GREEN_URL}/api/internal/workflow/{flow_task_id}/snapshot
```

空地址丢掉，重复地址只留一次。404 继续下一个。响应不是对象、`flow_task_id` 不一致、`protocol_version` 不是 2，都算失败并试下一个。全部失败抛 `WorkflowSnapshotUnavailable`。

WebSocket attach 里：

```text
cursor 默认 0-0，也接受 last_event_cursor / event_cursor / cursor
cursor_is_available 为假
  → latest_cursor()
  → fetch snapshot
  → 失败：resume_error RESUME_WINDOW_EXPIRED，close 4409
  → 成功：后面的 replay 从 latest 起
先注册连接；同一 connection_id 的旧连接 close 4001
若有 snapshot：发 flow_snapshot
  event_id = snapshot-{sha256 前 24 位}
  event_cursor = 当前采用的 cursor
  replayed = true
再 WorkflowEventStore.replay()
若 run 已终态：把 replay 上沿延到 latest，避免 resume_ready 退回旧状态
发 resume_ready
```

`flow_snapshot.event_id` 来自快照内容的哈希。它是这一次连接上的说明，不是 Outbox 里那条 `wfe_` 事件。

## 五、前端：cursor 和 resume_ready

相关文件：

[workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts)

```text
读 sessionStorage workflow:v2:cursor:{flowTaskId}
连接
  → auth
  → attach_flow { last_event_cursor }
  → 普通事件：保存 event_cursor，交给 handler
  → flow_snapshot：用当前状态补画面
  → resume_ready：恢复完成
  → resume_error：不要把节点当成已经同步
```

`setWorkflowResumeCursor()` 只写 sessionStorage。服务端 run 的状态仍以 `flow_task`、`flow_run_state` 和 Event Store 为准。

刷新页面会再走 attach。它不调用 cancel，也不调用 start。

## 六、AI callback 重投

相关文件：

1. [packages/runtime/src/consumer-callback.ts](../../../../../opencreate/opencreator-ai/packages/runtime/src/consumer-callback.ts)
2. [packages/queues/src/queue-names.ts](../../../../../opencreate/opencreator-ai/packages/queues/src/queue-names.ts)
3. [scripts/replay-consumer-callbacks.ts](../../../../../opencreate/opencreator-ai/scripts/replay-consumer-callbacks.ts)

自动路径是 worker 的 `consumer-callback` 队列，失败可以进 `consumer-callback-dlq`。

手工路径是脚本：检查 Consumer 健康，然后对每个 `ai_task_id`：

```text
Queue("consumer-callback")
jobId = callback-replay-{aiTaskId}-{Date.now()}
```

新的 job id 保证这次入队不会被旧 job 的完成记录吞掉。Consumer 侧仍用 `ai_task_id`、attempt 和 invocation 去重。脚本跑完只表示任务回到 AI 队列。节点是否 success，要看 Consumer Finalizer 和后面的 Outbox。

## 七、Agent 的两份恢复

相关文件：

1. [creato/services/agent_redis_run_store.py](../../../../../opencreate/opencreator-agent/creato/services/agent_redis_run_store.py)
2. [creato/core/tools/opencreator/workflow_snapshot.py](../../../../../opencreate/opencreator-agent/creato/core/tools/opencreator/workflow_snapshot.py)

`RedisRunStore` 管的是 Agent run：会话锁、事件追加、checkpoint、实例心跳、`ensure_resume_available(last_event_id)`。窗过期抛 `ResumeWindowExpiredError`，带上 `run_id`、`last_event_id`、`earliest_event_id`。

`normalize_request_workflow_snapshot()` 接受请求里已经带上的画布：

```text
schema_version ∈ {1, 2}
snapshot_hash 非空
captured_at_utc_ms 有值
nodes、edges 是对象列表
flow_id 或 workflow_id 等于这次请求的 flow
```

不合格返回空。这份快照给 Agent 工具理解当前画布。它没有 `flow_run_state`，也没有 Consumer 的 `last_event_id`。

## 八、和 NovelComic 对照

搬这组时，最小可交付：

1. 八类维护命令都进 `handle_maintenance()`，未知命令不执行副作用。
2. 调度按 command 分开间隔，并且可以用开关整个关掉。
3. Inbox 重投使用当初的 `redelivery_payload`，不新造 `command_id`。
4. v2 且没有 `start_initialized` 的 running run 会被跳过。
5. 带 `execution_plans` 的过期 RUNNING 节点按原 `result_id` CAS 回队列。
6. 终态补偿只补 `finish_flow` / `flow_killed`，`event_id` 稳定。
7. pending callback、卡住的 Finalizer、未完成的扣费确认各有一条扫描。
8. snapshot 由 Consumer 生成，Publisher 用内部密钥去拉，并校验 `flow_task_id` 和 `protocol_version`。
9. cursor 失效时，要么 `flow_snapshot` 再 replay，要么 `resume_error` 加 4409。
10. 前端以 `resume_ready` 作为恢复完成。断线不触发 cancel。
11. AI replay 脚本和 Agent 画布快照留在各自入口，不写进 `FlowRecoveryService`。

只做定时任务、只在刷新时重新 POST `/runs`、或只把最后一次 WebSocket 消息留在内存里，都还没有这组的恢复。
