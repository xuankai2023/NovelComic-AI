# 数据集合、索引与所有权全链路笔记

这份不是集合清单，是给面试和迁移用的所有权笔记。要讲清楚的不是“Mongo 里有哪些表”，而是一次点击的事实先落在谁那里、哪一列身份被唯一索引保住、TTL 到底删的是什么，以及浏览器里的三把钥匙为什么不能当成服务端幂等。

先把一句话背下来：

OpenCreator 五仓可以连同一套 Mongo，状态机不共享。Publisher 写入口事实，Consumer 写执行事实，AI 写厂商任务事实，Agent 写会话事实，前端只留 command journal、cursor 和副作用 claim。逻辑身份靠启动时的唯一索引；TTL 只删已经写了 `expires_at` 的终态行。

## 0. 先分清三件事

`共享库` 只表示几个进程连得上同一批集合。Publisher 的 `mongo.py` 里可以声明 `flow_run_state`，Agent 也可以读 `flow_task` 和 `results`。能看见，不代表可以改 DAG，也不代表可以改节点状态。

`唯一索引` 回答“这是不是同一条事实”。`(user_id, command_id)`、Inbox 的 `command_id`、Outbox 的 `event_id`、`ai_task_id` 各自挡住自己那一层的第二行。它们不能互相借用。

`TTL` 回答“终态行什么时候可以物理删掉”。`expireAfterSeconds=0` 要等文档上有 `expires_at`。失败和进行中的行会把这个字段清掉。TTL 删除发生时，业务已经结束。它不是“跑完了”的信号。

面试时一定要把这三件事讲开。很多问题都来自把“表能连上”“插不进第二行”“行被删了”压成一件事。

## 1. 一次点击的落库顺序

顺序不能倒着读。倒过来会把“句柄能看见”当成“这仓可以改”：

```text
sessionStorage pending_commands
  → 事务：flow_task + workflow_command          Publisher
  → 派发失败则 flow_task.dispatch_state=pending_retry
  → dispatcher_forever 再领同一行
  → Redis Stream run_flow                       不是 Mongo
  → flow_command_inbox                          Consumer，先于 run
  → flow_run_state
  → flow_node_state                             含 execution_plans
  → model_invocation
  → ai_task / attempt / provider_event / callback_delivery
                                                AI
  → 对不上则 pending_model_callback             Consumer
  → results + usage_v2
  → flow_node_state 终态或 select
  → flow_event_outbox
  → Redis events + event_ids                    Publisher
  → flow_task.last_event_cursor / status
  → sessionStorage cursor
  → localStorage side_effect_claims
```

`create_run()` 用 Mongo session 把 `flow_task` 和 `workflow_command` 放进同一个事务。`DuplicateKeyError` 再查 replay，不留下只有 task 没有 command 的行。派发在事务提交之后，所以命令行可以停在 `pending`，由 `workflow_command_dispatcher_forever()` 每 2 秒补派发。

浏览器那三把存储丢了，服务端从 `flow_task` 到 Event Store 的行还在。

## 2. Publisher：入口事实

`database/mongo.py` 用 `db["集合名"]` 列出 Owner 句柄：用户、画布项目、`flow_task`、`workflow_command`、订单和支付、`webhook_event`、`subscription_checkout_intent`、`credits_inout_record`、Developer API 四张表、`media_face_verifications`、`asset_library_items`、`agent_skills`。

同一文件还连 admin 库里的模板和目录。模板不是画布运行事实。

`flow_run_state` 和 `flow_node_state` 也有句柄。Publisher 可以读。运行状态迁移的写入在 Consumer。`results` 和 `usage_v2` 同样是可读句柄，确认写入在 Consumer。

`core/register.py` 的 `register_init()` 先 `test_mongo()`，再按固定顺序调用：

```text
ensure_developer_indexes()
ensure_invite_indexes()
ensure_credits_inout_indexes()
ensure_subscription_checkout_intent_indexes()
ensure_b2b_signal_indexes()
ensure_media_face_verifications_indexes()
ensure_user_preferences_indexes()
ensure_asset_library_indexes()
ensure_agent_skill_indexes()
ensure_agent_catalog_indexes()
ensure_workflow_v2_indexes()
```

索引没建完，不开始收工作流结果。Developer API 如果是独立进程，会在自己的启动里再调一次 `ensure_developer_indexes()`。索引函数本身要能重复执行。

`ensure_workflow_v2_indexes()` 把命令身份钉死：

```text
flow_task (user_id, client_request_id) 唯一，partial string
  名字 flow_task_user_client_request_unique
workflow_command (user_id, command_id) 唯一
  名字 workflow_command_user_command_unique
workflow_command.wire_command_id 唯一，partial string
  名字 workflow_command_wire_unique
workflow_command (status, next_attempt_at, updated_at)
  名字 workflow_command_dispatch_due
workflow_command.expires_at TTL，expireAfterSeconds=0
  名字 workflow_command_terminal_ttl
```

`client_request_id` 和 `wire_command_id` 用 `partialFilterExpression: {$type: "string"}`。字段还不是字符串时，不占用唯一槽。

面试讲法：

Publisher 第一次接 HTTP 时写的是入口事实。节点是否 `running`，不由这张 `flow_task` 单独决定。

## 3. Consumer：执行事实，以及四条不能失败的索引

Consumer 不用启动时的全局 `db`。`_CollectionProxy` 按当前 event loop 取 client，再取集合。集合名和 Publisher 主库对齐，两边看到的是同一批集合。

执行 Owner：

| 集合 | 唯一或扫描要点 |
| --- | --- |
| `flow_run_state` | `run_id` 唯一；另有 `flow_run_v2_start_recovery`、`flow_run_v2_terminal_event_reconcile` |
| `flow_node_state` | `(run_id, node_id)` 唯一 |
| `model_invocation` | `invocation_id`；另有 `(run_id, node_id, result_id, attempt)`；厂商任务是 `(vendor, external_task_id)` 且仅字符串 |
| `flow_command_inbox` | `command_id` 唯一，文档 `_id` 也是这把命令 |
| `flow_event_outbox` | `event_id` 唯一 |
| `results` | `(run_id, result_id)` 唯一 |
| `usage_v2` | `deduction_id` 唯一，仅字符串 |
| `pending_model_callback` | `(vendor, external_task_id)` 普通索引，不是唯一 |

`pending_model_callback` 允许并发早到的回调留下多行。清扫那组再处理它们。

`init_consumer_v1_indexes()` 逐条 `create_index`。名字属于下面四条时，失败会 `raise`，`test_mongo()` 随后 `sys.exit()`：

```text
flow_event_outbox_event_id_unique
flow_event_outbox_sent_ttl
flow_command_inbox_command_id_unique
flow_command_inbox_terminal_ttl
```

其余失败只 warning，包括 `flow_run_state.run_id` 唯一索引。这个差别要留在代码里：不要把所有索引都改成失败退出，也不要把这四条降成 warning。

Inbox 必须先于 run / node。认领失败不能把同一道命令初始化两次。锁还在、库里还没有 run 时，Inbox 标 `failed`，不能标 `completed`。

## 4. AI：厂商任务事实

集合名集中在 `packages/db/src/collections.ts` 的 `COLLECTIONS`：

```text
ai_task
ai_task_attempt
ai_provider_event
ai_callback_delivery
provider_reason_mapping
provider_reason_unknown
media_face_verifications
```

`ensureMongoIndexes()` 和幂等直接相关的键：

```text
ai_task.ai_task_id                         唯一
ai_task.idempotency_key                    唯一，字段存在才参与
ai_task (status, updated_at)               扫描
ai_task_attempt (ai_task_id, attempt)      唯一
ai_provider_event (provider, provider_request_id, event_id) 唯一
ai_callback_delivery (ai_task_id, attempt) 唯一
```

`apps/api/src/server.ts` 和 `apps/worker/src/main.ts` 都在连上 Mongo 之后调用它。两边谁先启动都可以。

`idempotency_key` 缺省的两行可以共存。一旦写成同一个字符串就冲突。`ai_task_id` 插入两次，第二次失败。

人脸集合可以单独配库。AI 侧只建 `media.url`、`face_providers.byteplus.asset_id`，以及两者的复合键。用户维度唯一键 `(user_id, media.id)` 在 Publisher。

## 5. Agent：会话事实，共享集合只警告

Agent 同时拿多个库。自己的 Owner 在 agent 库：`agent_sessions`、`agent_messages`、`agent_chat_messages`、`agent_events`、`agent_tool_traces`、`agent_message_feedback`、`memories`。主库上的 `flow`、`flow_task`、`results`、积分、`usage_v2` 是只读或受控读。

`ensure_indexes()` 先绑自己的集合，再绑共享集合。`_safe_create_index()` 只吞 `OperationFailure` 85 和 86：

| code | 含义 |
| --- | --- |
| 85 | 键相同，名字或选项不同 |
| 86 | 同一个名字，键规格不同 |

其他错误继续抛，启动失败。

Agent 自己的唯一键：

```text
agent_chat_messages (session_id, message_id)
agent_events (session_id, event_id)
agent_message_feedback (session_id, turn, user_id)
```

`agent_tool_traces.completed_at` 使用 `expireAfterSeconds=2592000`。不要把它写成 `workflow_command` 那种 `expires_at`。

共享集合上 Agent 仍会尝试 `flow_task (flow_task_id, user_id)`，名字是 `flow_task_user_idx`。它和 Publisher 已有的 `flow_task_*` 不是同一套名字。撞上 85/86 时进程照样起来。上线后要单独对键，不能把 warning 当成“已经等价”。

`memories` 的 Atlas / Vector Search 索引不存在时只 warning，不阻断启动。索引检查失败，不把记忆检索的所有权交出去。

## 6. Frontend：三把客户端钥匙

| 存储 | 键 | 回答的问题 |
| --- | --- | --- |
| `sessionStorage` | `workflow:v2:pending_commands` | 同一次点击的 `command_id` |
| `sessionStorage` | `workflow:v2:cursor:{flowTaskId}` | 浏览器看到哪一条事件 |
| `localStorage` | `workflow:v2:side_effect_claims` | 积分、toast、埋点是否已经在本机做过 |

副作用 claim 最多大约 24 小时、最多 5000 条。节点 `data.status` 不走这里，每个打开的 tab 都要更新自己的画布。

journal 写入失败时，当前这次 HTTP 仍带着刚生成的 `command_id`。刷新之后如果存储里没有它，重试就会变成新命令。服务端唯一索引保的是同一个 `command_id` 不会开第二行。

cursor 只回答浏览器位置。Event Store 才回答服务器已经收下哪一条。

## 7. 同一条 run 的身份不能互相借用

| 身份 | 落点 | 唯一方式 |
| --- | --- | --- |
| 用户命令 | Publisher `workflow_command` | `(user_id, command_id)` |
| 派发线 | 同一行的 `wire_command_id` | 单独唯一索引，仅字符串 |
| 公开任务 | Publisher `flow_task` | `flow_task_id`，外加用户和 `client_request_id` |
| 执行认领 | Consumer `flow_command_inbox` | `command_id` |
| 执行头 | Consumer `flow_run_state` | `run_id` |
| 节点 | Consumer `flow_node_state` | `(run_id, node_id)` |
| 模型尝试 | Consumer `model_invocation` | `invocation_id` 和 `(run_id, node_id, result_id, attempt)` |
| 厂商任务 | AI `ai_task` | `ai_task_id`、存在时的 `idempotency_key` |
| 厂商事件 | AI `ai_provider_event` | `(provider, provider_request_id, event_id)` |
| 逻辑事件 | Consumer `flow_event_outbox` | `event_id` |
| replay 游标 | Publisher Redis Hash + Stream | `event_id → cursor` |
| 浏览器位置 | `sessionStorage` cursor | 跟着 `flowTaskId` |

`event_id` 进了 Outbox，还要再进 Event Store，浏览器才有 cursor。`command_id` 进了 Publisher，还要变成 Inbox 的 `command_id`，执行副作用才会被认一次。

公开读接口要把 `user_id` 放进查询。只拿 `flow_task_id` 或 `run_id` 能定位一行，不能证明这行属于当前用户。

## 8. TTL 只碰写了过期时间的终态

已经按 `expires_at` + `expireAfterSeconds=0` 写的包括：

- `workflow_command`，索引名 `workflow_command_terminal_ttl`
- `flow_command_inbox`，索引名 `flow_command_inbox_terminal_ttl`
- `flow_event_outbox`，索引名 `flow_event_outbox_sent_ttl`
- `developer_idempotency`
- `subscription_checkout_intent`

Inbox 的 `mark_completed()` 才写 `expires_at`。`mark_failed()` 清掉它。Outbox 要到 `sent` 才写。非终态命令、失败命令、还在跑的结账认领，都不能靠 TTL 宣布结束。

订阅结账多一步：`state` 不是 `completed` / `expired` / `failed` 的行，先 `$unset expires_at`，再挂 TTL。活着的支付认领不能因为旧的过期字段被删掉。

扫描索引是另一类。`workflow_command (status, next_attempt_at, updated_at)`、Inbox 的 lease / retry、Outbox 的 `(status, next_attempt_at)`、`model_invocation (status, updated_at)`、`flow_task` 上带 `user_id` 的 active run 索引，都只说明查询能走索引。窗口和补偿不在本章。

## 9. 同名集合的索引必须规格兼容

Consumer 和 Publisher 都会给这些共享集合建索引：

```text
credits_inout_user_direction_created
credits_inout_event_created
credits_inout_idempotency_unique
b2b_signal_events_event_id_unique
b2b_signal_notifications_user_signal_unique
```

键序、`unique`、`partialFilterExpression` 要和对方保持一致。后启动的一侧接到 85 或 86，说明规格没有对齐。Agent 把这两种降成 warning，是为了共享集合上已经有索引时进程还能起来。能启动，不能代替部署核对。

`media_face_verifications` 是受控共享，不是随便直写的先例。协议上的回写身份是媒体 URL 加 BytePlus asset ID。用户项目和运行态不能照这张表互相改。

## 10. Event Store 不在这些 Mongo 集合里

工作流 replay 的事件正文在 Publisher Redis：

```text
opencreator:wf:{flow_task_id}:events
opencreator:wf:{flow_task_id}:event_ids
```

Owner 是 Publisher 的 `workflow_event_store.py`。`event_id → cursor` 是 Redis Hash，事件流是 Redis Stream。同一个 `event_id` 重放时返回原 cursor。

Consumer 的 `flow_event_outbox` 是发出去之前的账。浏览器重连读的是 Event Store，不是 Outbox。

## 11. 文件编写顺序

迁移时按依赖写，不要从清扫补偿开始：

1. Publisher `database/mongo.py`：固定集合名，写 `ensure_workflow_v2_indexes()`。
2. `services/workflow_runs_v2.py`：同一事务写 `flow_task` 和 `workflow_command`。
3. `core/register.py`：`test_mongo()` 成功之后、后台任务之前挂上全部 `ensure_*_indexes()`。
4. Consumer `database/mongo.py`：`_CollectionProxy` 和 `init_consumer_v1_indexes()`，四条失败退出。
5. AI `collections.ts`、`mongo.ts`，再挂到 API 和 worker。
6. Agent `creato/database/mongo.py`：自己的唯一索引，共享集合 85/86 只 warning。
7. 前端三个文件只核对键名：journal、cursor、副作用 claim。

面试讲法：

先有集合名和唯一键，后面的队列、清扫才有地方落身份。项目还没分清 Owner 时，先写补偿任务只会把第二行越补越多。

## 12. 和 NovelComic 当前迁移关系

NovelComic 前面的命令、执行和事件组已经会往这些集合里写行。本章补的是索引和 Owner，不再重写 Run 按钮。

当前落点：

- Publisher 启动会建命令和公开任务的唯一键，并在事务里同时插入两行。
- Consumer 启动会建 Inbox / Outbox 的四条必需索引，失败则进程退出。
- AI API 和 worker 都会建厂商任务唯一键。
- Agent 会建会话唯一键，共享集合冲突降为 warning。
- 前端三把钥匙已经分开，存储失败不阻止本次请求。

所以当前迁移不能说“配置里写了集合名就完成了”。真正的验收是启动路径上的 `create_index`，以及该失败的那四条会失败退出。

## 13. 面试 1 分钟口述

OpenCreator 的数据所有权不是“大家连同一个 Mongo”。Publisher 在 `register_init()` 里建入口索引，`ensure_workflow_v2_indexes()` 用 `(user_id, command_id)` 和部分唯一的 `wire_command_id` 保住命令身份，`create_run()` 把 `flow_task` 和 `workflow_command` 放进同一个事务。Consumer 用集合代理写运行态，Inbox 的 `command_id` 和 Outbox 的 `event_id` 这两条唯一索引加上对应 TTL，创建失败就退出；`run_id` 唯一索引失败只 warning。模型计划进 `model_invocation` 之后，AI 用 `ai_task_id`、attempt 和 provider event 三元组做唯一，API 和 worker 都会建索引。对不上的回调进 `pending_model_callback`，这张表没有唯一约束。Agent 写自己的 session 和 event，共享集合遇到 Mongo 85/86 只警告。浏览器的 journal、cursor、副作用 claim 是三把不同的本地钥匙，丢了也不会删掉服务端已经收下的行。TTL 只删除写了 `expires_at` 的终态；replay 正文在 Redis Event Store，不在 Outbox。

## 14. 面试官追问怎么答

如果问为什么 Publisher 声明了 `flow_run_state` 还说自己不是 Owner：

句柄只说明这个进程能连上这张表。节点从 `idle` 走到 `running`、`select`、`success` 的写入在 Consumer。Publisher 读得到运行快照，不负责那次状态迁移。

如果问为什么 `202` 之后还要唯一索引：

`202` 只表示这次 HTTP 受理了命令。超时重试会再打一次。`(user_id, command_id)` 保证同一用户的同一道命令不会插出第二行；payload 不同则走冲突，而不是再开一条 run。

如果问 `partial` 唯一和普通唯一差在哪：

普通唯一从第一行就占槽。`partialFilterExpression: {$type: "string"}` 让字段还没写成字符串时先落库，身份出现后才唯一。`wire_command_id` 还不是字符串时，不触发 `workflow_command_wire_unique`。

如果问 TTL 能不能当作任务完成：

不能。`expireAfterSeconds=0` 只看 `expires_at` 到点没有。完成路径才写这个字段，失败路径会清掉它。订阅结账还会在挂 TTL 之前，把非终态行的 `expires_at` 去掉，避免活文档被收走。

如果问浏览器清缓存会不会让服务端再执行一次：

会变成一次新命令，因为 journal 丢了，下一次点击生成新的 `command_id`。已经写进 Mongo 的旧命令还在，旧 `command_id` 仍然插不进第二行。cursor 丢了只影响浏览器从哪条事件接着看，不影响 Event Store 里已经收下的事件。

如果问 85/86 warning 能不能当成索引已经对齐：

不能。85 是选项冲突，86 是键规格冲突。Agent 吞掉它们是为了共享集合上已有索引时还能启动。部署时仍要对名字、键序、unique 和 partial。其他错误必须让进程退出。

如果问 NovelComic 迁移时先做什么：

先在 Publisher 启动路径上建命令唯一索引，并把 `flow_task` 与 `workflow_command` 放进同一事务。然后让 Consumer 的四条 v2 索引失败退出，再让 AI 的 API 和 worker 都建 `ai_task` 唯一键。最后核对 Agent 的 85/86 和前端三把钥匙。不要并行让两个仓都去改运行态。

## 15. NovelComic 当前实现自查

只看本章“数据集合、索引与所有权”，NovelComic 当前已经具备主交付：

- Publisher `register_init()` 在 Mongo 连通之后、后台任务之前调用全部 `ensure_*_indexes()`，其中包括 `ensure_workflow_v2_indexes()`。
- `workflow_command_user_command_unique`、`workflow_command_wire_unique`、`flow_task_user_client_request_unique` 都在启动路径上，并带上 partial string 和终态 TTL。
- `create_run()` 同一事务写两行；事务失败时两张表都没有这把 `command_id`。
- 非终态 `subscription_checkout_intent` 会先被清掉 `expires_at`，再挂 TTL。
- Consumer `_CollectionProxy` 与 Publisher 使用同一主库集合名。四条 v2 索引失败退出，`flow_run_state.run_id` 失败只 warning。`pending_model_callback` 不是唯一索引。
- `credits_inout_record` 和 B2B 集合上，Publisher 与 Consumer 使用同名索引。
- AI API 和 worker 都会 `ensureMongoIndexes()`。人脸集合只有 URL 和 BytePlus asset ID，用户唯一键在 Publisher。
- Agent 自己的 message、event、feedback 唯一索引已建，tool trace 按 `completed_at` 保留 30 天。85/86 只 warning，其他错误继续抛。
- 前端 journal、cursor、副作用 claim 使用三个不同的存储键。写失败被吞掉，当前请求仍发出。

现有自动化已经覆盖：

- Publisher 索引可重复创建，重复命令插入失败，结账活文档的 `expires_at` 被清掉，索引失败时不启动 dispatcher。
- `create_run()` 成功时两行都在，事务失败时两行都没有。
- Consumer 必需索引失败 `sys.exit(1)`，非必需索引失败只 warning，同一厂商任务的早到回调可以留下两行。
- AI 重复 `ai_task_id` 和重复 `idempotency_key` 失败。
- Agent 共享索引冲突打 warning，其他索引错误让启动失败。
- 前端清掉 `sessionStorage` 后会生成新的 `command_id`，三把钥匙不会写进彼此的存储。

和 OpenCreator 现码相比，要单独记住的差别：

- 集合名按 NovelComic 现库：用户是 `users`，项目是 `flow_projects`，执行结果是 `node_results`，目录是 `agent_catalog`。Owner 职责对齐，名字不完全相同。
- Event Store 在线路径使用 `workflow:v2:events:{flow_task_id}` 和 `workflow:v2:event-cursors:{flow_task_id}`。没有 Redis client 时还会 upsert Mongo `workflow_events`。本章的 replay 事实仍以 Redis 为准。
- Developer API 不是独立进程，`ensure_developer_indexes()` 只在 Publisher 启动里调用一次。
- Agent 还没有 OpenCreator 那层 `memories` Atlas / Vector Search 索引检查，目前只有 `payload.user_id` 普通索引。

本章验收口径：

如果验收“每张事实表有 Owner，逻辑身份有唯一索引，四条 v2 索引失败会挡住启动，TTL 只碰写了 `expires_at` 的终态，浏览器三把钥匙分开”，当前主交付已经具备。  
如果按 OpenCreator 的集合名、Redis key 和 memories 向量索引逐项对齐，还要单独看命名和 Atlas 检查。扫描窗口、lease 和补偿不在本章，它们属于清扫那一组。
