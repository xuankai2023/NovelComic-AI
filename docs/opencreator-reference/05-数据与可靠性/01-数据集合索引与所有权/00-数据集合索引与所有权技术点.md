# 数据集合、索引与所有权：这里面有哪些技术点

这一组只讲事实落在哪、谁能改、索引保的是哪一种身份。工作流怎么跑、队列怎么投、清扫怎么补，分别在相邻两组。这里先把集合 Owner 和索引规格钉住。

先背一句话：

```text
共享库不等于共享所有权；
唯一索引保住逻辑身份；
TTL 只删终态，不宣布完成。
```

一次点击要落到这些事实，顺序不能倒：

```text
1. 浏览器 sessionStorage
     workflow:v2:pending_commands
     记下 command_id。这里还不是 Mongo。

2. Publisher 同一事务
     insert flow_task          status=pending，dispatch_state=pending
     insert workflow_command   (user_id, command_id) 唯一
     事务失败就两行都没有。不要先有 task、后补 command。

3. Publisher 派发
     workflow_command：dispatching → dispatched
     线上的身份是 wire_command_id
     Redis Stream run_flow
     派发失败把 flow_task.dispatch_state 写成 pending_retry
     workflow_command_dispatcher_forever 每 2 秒再领到期命令

4. Consumer Inbox
     flow_command_inbox，_id 和 command_id 都是这把命令
     同时存下 redelivery_payload
     这一行先于任何 run / node

5. Consumer 执行头
     SET opencreator:flow_start_lock:{run_id}
     锁还在、库里还没有 run：抛错，Inbox 标 failed，不能标 completed
     然后 flow_run_state（run_id 唯一）
     flow_node_state（run_id + node_id 唯一）
     种子 user_selection
     发出 start_flow
     推进 resume
     最后才写 start_initialized

6. 模型计划
     计划写回 flow_node_state：
     execution_plans、expected_result_ids、execution_plan_token、execution_claim_token
     然后才有 model_invocation
     唯一键是 invocation_id，以及 (run_id, node_id, result_id, attempt)

7. AI 任务
     ai_task，idempotency_key 已存在就返回原来的任务
     ai_task_attempt (ai_task_id, attempt)
     ai_provider_event (provider, provider_request_id, event_id)
     ai_callback_delivery (ai_task_id, attempt)

8. 回调对单
     对上 model_invocation：写 callback_status，再调度 finalize
     对不上：upsert pending_model_callback
     HTTP 仍返回 accepted。matched 可以是 false

9. 收尾事实
     Finalizer 把 finalize_status 收成 running
     results 用 (run_id, result_id) 唯一
     usage_v2 用 deduction_id 唯一
     flow_node_state 再迁到 success / failed / select

10. 事件事实
      flow_event_outbox，event_id 唯一
      Publisher Redis：
        opencreator:wf:{flow_task_id}:events
        opencreator:wf:{flow_task_id}:event_ids
      然后更新 flow_task.last_event_cursor 和公开 status

11. 浏览器再记两把
      sessionStorage workflow:v2:cursor:{flowTaskId}
      localStorage  workflow:v2:side_effect_claims
```

索引在进程启动时建好，插在这条链的每一跳前面。浏览器那三把存储丢了，服务端 2 到 10 步的行还在。

启动建索引的顺序是：

```text
Publisher register_init
  → ensure_*_indexes，其中 ensure_workflow_v2_indexes 钉住第 2 步
Consumer test_mongo
  → init_consumer_v1_indexes
  → 第 4 步和第 10 步的四条索引失败则退出
AI api 与 worker
  → ensureMongoIndexes，钉住第 7 步
Agent
  → ensure_indexes
  → 共享集合撞 85/86 只 warning，不改第 5 步的 Owner
```

## 1. 五仓各管一块事实

OpenCreator 五仓可以连同一套 Mongo，集合句柄也可以互相看见。所有权看的是谁负责状态迁移。

| 仓 | 文件证据 | 这层拥有 | 可以看见但不当 Owner |
| --- | --- | --- | --- |
| Publisher | [database/mongo.py](../../../../../opencreate/opencreator-publisher/database/mongo.py) | 用户、项目、`flow_task`、`workflow_command`、支付、Developer API、素材库 | 运行态迁移 |
| Consumer | [database/mongo.py](../../../../../opencreate/opencreator-consumer/database/mongo.py) | `flow_run_state`、`flow_node_state`、`model_invocation`、Inbox、Outbox | 用户资料、公开命令状态 |
| AI | [collections.ts](../../../../../opencreate/opencreator-ai/packages/db/src/collections.ts) | `ai_task`、attempt、provider event、callback delivery | 画布项目 |
| Agent | [database/mongo.py](../../../../../opencreate/opencreator-agent/creato/database/mongo.py) | session、message、event、tool trace、记忆 | 工作流执行状态机 |
| Frontend | command journal、cursor、副作用 claim | 这一次浏览器里的重试和去重 | Mongo 事实 |

Publisher 的 `mongo.py` 里也声明了 `flow_run_state`、`flow_node_state`。那是共享库上的句柄。节点从 `idle` 走到 `running` / `select` / `success`，仍然由 Consumer 写。

Agent 会读 `flow`、`flow_task`、`results`、积分和 `usage_v2`。读得到，不代表可以改 DAG。

```text
  → ensure_invite_indexes()
  → ensure_credits_inout_indexes()
  → ensure_subscription_checkout_intent_indexes()
  → ensure_b2b_signal_indexes()
  → ensure_media_face_verifications_indexes()
  → ensure_user_preferences_indexes()
  → ensure_asset_library_indexes()
  → ensure_agent_skill_indexes()
  → ensure_agent_catalog_indexes()
  → ensure_workflow_v2_indexes()

Consumer test_mongo()
  → init_consumer_v1_indexes()

AI apps/api 与 apps/worker
  → ensureMongoIndexes()

```

证据：

- [core/register.py](../../../../../opencreate/opencreator-publisher/core/register.py)

## 3. 唯一索引保护逻辑身份

这些唯一键决定“这是不是同一条事实”：

| 集合 | 唯一键 | 挡住什么 |
| --- | --- | --- |
| `workflow_command` | `(user_id, command_id)` | 同一用户的同一道命令插第二次 |
| `workflow_command` | `wire_command_id`，仅字符串字段 | 派发身份重复 |
| `flow_task` | `(user_id, client_request_id)`，仅字符串字段 | 同一客户端请求另开一条公开任务 |
| `flow_command_inbox` | `command_id` | Consumer 把同一道命令再初始化一次 |
| `flow_event_outbox` | `event_id` | 同一条逻辑事件再插一行 |
| `flow_run_state` | `run_id` | 同一次 run 两份执行头 |
| `flow_node_state` | `(run_id, node_id)` | 同一次 run 里同一个节点两行 |
| `model_invocation` | `invocation_id`；另有 `(run_id, node_id, result_id, attempt)` | 同一次计划的同一次尝试两行 |
| `model_invocation` | `(vendor, external_task_id)`，仅字符串字段 | 同一个厂商任务两行 |
| `results` | `(run_id, result_id)` | 同一个结果身份两行 |
| `usage_v2` | `deduction_id`，仅字符串字段 | 同一笔预扣确认两次 |
| `ai_task` | `ai_task_id`；`idempotency_key` 在字段存在时唯一 | 同一个 AI 任务或同一把幂等键两行 |
| `ai_task_attempt` | `(ai_task_id, attempt)` | 同一次尝试两行 |
| `ai_provider_event` | `(provider, provider_request_id, event_id)` | 同一条厂商事件两行 |
| `ai_callback_delivery` | `(ai_task_id, attempt)` | 同一次回调投递记录两行 |
| `credits_inout_record` | `idempotency_key`，仅字符串字段 | 同一笔积分流水两行 |

`partialFilterExpression` 的意思是：字段还没写成字符串时，不参与这条唯一约束。空文档可以先落库，真正的身份出现后才唯一。

## 4. 扫描索引保护的是恢复，不是完成

恢复任务按状态和时间找“该处理的那一批”。这些索引给扫描用：

| 集合 | 键 | 谁在扫 |
| --- | --- | --- |
| `workflow_command` | `(status, next_attempt_at, updated_at)` | Publisher 派发到期命令 |
| `flow_command_inbox` | `(status, lease_expires_at)`、`(status, next_attempt_at)` | 过期 lease 和失败重试 |
| `flow_event_outbox` | `(status, next_attempt_at)`、`(status, publish_lease_expires_at)` | 到期 Outbox |
| `flow_run_state` | `flow_run_v2_start_recovery`、`flow_run_v2_terminal_event_reconcile` | 已初始化的 running run、缺终态事件的 run |
| `model_invocation` | `(status, updated_at)` | 超时和卡住的调用 |
| `ai_task` | `(status, updated_at)` | AI 侧按状态找任务 |
| `flow_task` | `(user_id, protocol_version, status, updated_at)` 以及带 `flow_id` 的那条 | 当前用户的 active run |

有扫描索引，只说明查询能走索引。扫描窗口、lease 和补偿规则在清扫那一组。

## 5. TTL 只在写了过期时间之后才删

OpenCreator 里多数终态保留用的是：

```text
create_index("expires_at", expireAfterSeconds=0)
```

`expireAfterSeconds=0` 表示：文档上的 `expires_at` 到点就删。业务代码必须先把终态行的 `expires_at` 写上，TTL 才会动手。

已经这样写的包括：

- `workflow_command.expires_at`，索引名 `workflow_command_terminal_ttl`
- `flow_command_inbox.expires_at`，索引名 `flow_command_inbox_terminal_ttl`
- `flow_event_outbox.expires_at`，索引名 `flow_event_outbox_sent_ttl`
- `developer_idempotency.expires_at`
- `subscription_checkout_intent.expires_at`

订阅结账还有一步额外保护：非 `completed` / `expired` / `failed` 的行会先 `$unset expires_at`，再挂 TTL。活着的支付认领不能因为旧的过期字段被删掉。

Inbox 的 `mark_completed()` 才写 `expires_at`。`mark_failed()` 会清掉 `expires_at`，失败行留着等重试。Outbox 要到 `sent` 才写 `expires_at`。

Agent 的 `agent_tool_traces` 是另一种 TTL：`completed_at` 加 `expireAfterSeconds=2592000`，大约 30 天。这是从完成时间起算的固定保留，和 `expires_at` 到点删除不是同一套写法。

TTL 删除之后，业务已经结束。它不是“跑完了”的信号。

## 6. 租户条件要进查询，不能只靠资源 ID

用户侧查询通常是 `user_id` 再加资源 ID：

- `flow_task`：`(user_id, flow_id, protocol_version, status, updated_at)`
- `credits_inout_record`：`(user_id, direction, created_at)`
- `asset_library_items`：`(user_id, library_kind, url)` 唯一
- `user_preferences`：`user_id` 唯一
- `agent_sessions`：`(user_id, updated_at)`
- `agent_message_feedback`：`(session_id, turn, user_id)` 唯一

只拿 `flow_task_id` 或 `run_id` 能定位一行，不能证明这行属于当前用户。公开读接口要把 Owner 条件放进查询或放进查完后的校验。索引里有 `user_id`，调用方仍要自己带上。

## 7. 浏览器里有三把不同的钥匙

| 钥匙 | 存在哪 | 键名 | 用来做什么 |
| --- | --- | --- | --- |
| 命令 journal | `sessionStorage` | `workflow:v2:pending_commands` | 同一次点击复用 `command_id` |
| 事件 cursor | `sessionStorage` | `workflow:v2:cursor:{flowTaskId}` | 重连时从哪个位置 replay |
| 副作用 claim | `localStorage` | `workflow:v2:side_effect_claims` | 积分、统计这类本地副作用只做一次 |

证据：

- [workflow-command-journal.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-command-journal.ts)
- [workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts)
- [workflow-side-effect-claim.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-side-effect-claim.ts)

隐私模式、清站点数据、换浏览器，这三把都会丢。服务端还要靠 `workflow_command`、Event Store 和唯一索引。浏览器丢了 journal，下一次点击会生成新的 `command_id`，服务端会把它当成新命令。

## 8. 同名集合的索引必须键序和选项都兼容

Consumer 和 Publisher 都会给这些共享集合建索引，名字和键要保持一致：

- `credits_inout_record`：`credits_inout_user_direction_created`、`credits_inout_event_created`、`credits_inout_idempotency_unique`
- `b2b_signal_events` / `b2b_signal_notifications` / `b2b_signal_user_actions`

Agent 启动时对共享集合用 `_safe_create_index()`。Mongo 返回：

- `85` IndexOptionsConflict：键相同，名字或选项不同
- `86` IndexKeySpecsConflict：同一个名字，键规格不同

这两种都只打 warning，然后继续启动。代码注释把它们当成“名字不同、功能等价”。`86` 也可能是真的键不一样。能启动，不能代替部署时去对一下索引规格。

Consumer 更严的只有四条，失败会 `raise`，进程起不来：

```text
flow_event_outbox_event_id_unique
flow_event_outbox_sent_ttl
flow_command_inbox_command_id_unique
flow_command_inbox_terminal_ttl
```

其余 Consumer 索引失败只 warning。`flow_run_state.run_id` 唯一索引创建失败，不会挡住本次启动。

## 9. `media_face_verifications` 是受控共享，不是随便直写的先例

Publisher 和 AI 都会碰 `media_face_verifications`。AI 可以用 `mediaFaceVerification.dbName` 指到另一库，默认仍可能和主库同名。

Publisher 的定位键包括：

- `(user_id, media.id)` 唯一
- `(user_id, media.url)`
- `(media.url, face_providers.byteplus.asset_id)`

AI 的定位键是：

- `media.url`
- `face_providers.byteplus.asset_id`
- 两者的复合键

协议上的回写身份是媒体 URL 加 BytePlus asset ID。这张表可以跨仓更新检测结果。用户项目、`flow_task`、运行态不能照这个例子互相改。

Agent 还会检查 Atlas / Vector Search 索引，并尝试给 `memories` 补 `payload.user_id` 过滤字段。索引不存在时只 warning，不阻断启动。

## 10. Event Store 不在这些 Mongo 集合里

工作流 replay 的事件正文在 Publisher Redis：

```text
opencreator:wf:{flow_task_id}:events
opencreator:wf:{flow_task_id}:event_ids
```

`event_id → cursor` 是 Redis Hash，事件流是 Redis Stream。Owner 是 Publisher 的 [workflow_event_store.py](../../../../../opencreate/opencreator-publisher/services/workflow_event_store.py)。Consumer 的 `flow_event_outbox` 是发出去之前的账，不是浏览器 replay 的游标表。

## 动手前要有的东西

这组接在前面的命令、AI 任务和账本之后。那些组已经会往集合里写行。这里补的是索引和 Owner，不再写一遍 Run 按钮。

1. 本地 Mongo 能连上，Publisher、Consumer、AI、Agent 知道自己的库名。
2. 工作流命令那组已经会写 `flow_task` 和 `workflow_command`。
3. Consumer 已经会写 run、node、invocation、Inbox、Outbox。
4. AI 已经会写 `ai_task`。
5. Agent 已经会写自己的 session 集合，并只读共享的 workflow 集合。

做完这组后，验收目标是：

```text
启动能建成唯一索引
  → 重复 command_id / event_id / ai_task_id 插不进第二行
  → 四个 v2 必需索引失败时 Consumer 不起
  → 终态行写了 expires_at 才会被 TTL 清掉
  → 活着的 checkout intent 不会被 TTL 提前删
  → Agent 的 85/86 不让进程退出，同时部署侧能对出索引规格
```
