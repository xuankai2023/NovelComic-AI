# Agent 工具、Skills 与 MCP：文件编写顺序

这篇只回答一个问题：NovelComic 如果要照 OpenCreator 接上 Agent 工具、仓内 Skills、产品 Agent Skills 和 MCP 适配，应该先写哪些文件、每一步完成到什么程度。

运行时原理见 [01-Agent工具Skills与MCP.md](./01-Agent工具Skills与MCP.md)，机制拆解见 [00-Agent工具Skills与MCP技术点.md](./00-Agent工具Skills与MCP技术点.md)。本文按依赖排序，不按用户在聊天窗口里看到的顺序排序。

命名约定：

- Agent 服务路径默认按 OpenCreator 的 `opencreator-agent/` 写。
- Publisher 路径默认在 `novelcomic-publisher/` 下。
- 如果 NovelComic 后续新建独立 agent 包，可以保持同名模块结构，路径前缀替换即可。
- MCP 这一轮先写适配代码和边界，不默认启用动态注册。

本组目标不是“技能列表能显示”，而是 Agent 运行时能形成清楚分层：

```text
Tool Registry
  → 管可执行工具

SkillsLoader
  → 管仓内 SKILL.md 指令材料

Publisher Agent Skills
  → 管用户侧技能资产

MCP client
  → 管外部工具协议适配
```

---

## 总体顺序

```text
creato/core/tools/base.py
  → creato/core/tools/registry.py
  → creato/core/profile.py
  → creato/core/factory.py
  → creato/agents/main/profile.py
  → creato/core/tools/filesystem.py
  → creato/core/skills/loader.py
  → creato/agents/main/prompt.py
  → creato/core/tools/subagent.py
  → creato/core/tools/mcp.py
  → creato/core/loop.py
  → schemas/agent_skills.py
  → dao/agent_skills.py
  → services/agent_skill_media.py
  → services/agent_skills.py
  → controller/v3/agent_skills.py
```

这个顺序有一个原则：先有可执行工具模型，再把工具装进 Agent；先有仓内 Skill Loader，再谈 `load_skill`；最后再接 MCP 适配和用户产品技能。

可以按四段推进：

```text
运行时工具骨架
  → base.py / registry.py / profile.py / factory.py

主 Agent 装配
  → main/profile.py / filesystem.py / skills/loader.py / prompt.py

外部能力边界
  → subagent.py / mcp.py / loop.py

产品技能资产
  → schemas / dao / services / controller
```

---

## 写之前必须已有

这些能力不在本文新写范围内，但缺少任何一项，后续链路都会对不上：

1. Agent 服务能启动，并能调用 LLM provider。
2. 有明确的 workspace 概念，至少能传给 `AgentContext`。
3. 已经有用户消息进入 Agent loop 的入口。
4. Publisher 已有认证中间件，可以拿到当前 `user_id`。
5. 如果要保存用户侧 Agent Skills，Mongo 或项目当前数据库访问层已经可用。
6. 如果要接工作流工具，前面专题中的 run、事件和结果查询能力已经存在。

完成基线：用户能发一条普通消息，Agent 能返回自然语言；此时可以还没有任何工具。

## 1. 先写 Tool 抽象

OpenCreator 对照：

[base.py](../../../../../opencreate/opencreator-agent/creato/core/tools/base.py)

先定义所有工具都要遵守的形状：

```text
Tool
  → name
  → description
  → parameters
  → execute(**kwargs)
  → cast_params()
  → validate_params()
  → to_schema()

ToolResult
  → success
  → content
  → error
```

核心要求：

- `parameters` 使用 JSON Schema object。
- `to_schema()` 输出 LLM provider 可识别的 function schema。
- `cast_params()` 只做保守类型转换，不吞业务错误。
- `validate_params()` 至少支持 required、类型、enum、长度、范围和数组 item。

完成标准：写一个最小 echo 工具，传合法参数能执行；缺 required 字段会返回校验错误；字符串 `"1"` 能按 integer schema 转成数字。

---

## 2. 写 Tool Registry

OpenCreator 对照：

[registry.py](../../../../../opencreate/opencreator-agent/creato/core/tools/registry.py)

Registry 要提供：

```text
register(tool)
unregister(name)
get(name)
has(name)
get_definitions()
execute(name, params)
tool_names
```

执行顺序必须固定：

```text
查工具
  → cast_params()
  → validate_params()
  → execute()
  → 返回 string / ToolResult
```

注意不要把 Registry 做成全局单例。它应该是 Agent 实例级对象，由 `AgentFactory.build()` 创建。

完成标准：注册两个工具后，`get_definitions()` 能返回两个 function schema；调用不存在的工具会返回明确错误；参数错误不会进入工具 `execute()`。

OpenCreator 对照：

[profile.py](../../../../../opencreate/opencreator-agent/creato/core/profile.py)

这一层先定义数据结构，不急着放业务工具：

```text
AgentContext
  → workspace
  → restrict_to_workspace
  → workflow_dao
  → workflow_engine
  → api_config
  → 外部服务配置和 client

AgentProfile
  → name
  → description
  → system_prompt
  → tool_factories
  → inline_skills
  → loadable_skills
  → model
  → max_iterations

AgentInstance
  → tools
  → system_prompt
  → model
  → max_iterations
```

完成标准：可以创建一个空 Profile，并用空工具集合构造 AgentInstance。

## 4. 写 AgentFactory

OpenCreator 对照：

[factory.py](../../../../../opencreate/opencreator-agent/creato/core/factory.py)

Factory 是装配中心：

```text
build(profile, depth=0)
  → tools = ToolRegistry()
  → 注册 profile.tool_factories
  → 根据 profile skill allowlist 过滤 SkillsLoader
  → 如有 loadable_skills，注册 LoadSkillTool
  → 如有 subagent profile 且 depth < 3，注册 SubagentTool
  → 生成 system prompt
  → 返回 AgentInstance
```

完成标准：同一个 Profile 连续 build 两次，得到两个不同的 Registry；给其中一个 Registry 注册临时工具，不影响另一个实例。

## 5. 写主 Agent Profile

OpenCreator 对照：

[profile.py](../../../../../opencreate/opencreator-agent/creato/agents/main/profile.py)

第一轮只放最小工具：

```text
_read_file
_web_search
_web_fetch
```

等基础链路通了，再增加业务工具：

```text
_get_workflow_results
_run_workflow
_get_workflow
_get_node_spec
_edit_workflow
_update_canvas_node
_search_templates
_use_template
```

Profile 中先声明少量 `loadable_skills`，比如：

```text
workflow-core
planning-core
```

完成标准：Agent 启动后 LLM provider 能看到这些工具定义；移除 Profile 中某个 factory 后，该工具不会出现在定义列表里。

## 6. 写 filesystem 工具和 load_skill 工具

OpenCreator 对照：

[filesystem.py](../../../../../opencreate/opencreator-agent/creato/core/tools/filesystem.py)

先写两类工具：

```text
ReadFileTool
  → 解析相对路径
  → 限制 workspace
  → 支持 offset / limit
  → 返回带行内容的文本

LoadSkillTool
  → 接收 name
  → skills_loader.load_skill(name)
  → 返回完整 SKILL.md
```

`ReadFileTool` 可以允许额外读取内置 Skills 目录，但不要顺手放开整个文件系统。`LoadSkillTool` 不直接读任意路径，只通过 loader 缓存按 name 取内容。

完成标准：`read_file` 不能读 workspace 外文件；`load_skill("missing")` 返回明确错误；有 allowlist 的 skill 可以被加载。

---

## 7. 写 SkillsLoader

OpenCreator 对照：

[loader.py](../../../../../opencreate/opencreator-agent/creato/core/skills/loader.py)

先实现扫描和缓存：

```text
SkillsLoader()
  → 遍历 builtin skills 目录
  → 找 SKILL.md
  → 解析 flat frontmatter
  → 校验 name 与目录一致
  → 检查 requires_bins / requires_env
  → 缓存 SkillInfo
```

需要支持的方法：

```text
filtered(allowed_names)
list_skills()
load_skill(name)
load_skills_for_context(skill_names)
build_skills_summary()
get_always_skills()
reload()
```

必须写清楚 frontmatter 限制：

- 只支持平铺 `key: value`。
- `requires_bins`、`requires_env` 是逗号分隔。
- `always: true` 才算常驻。
- `name` 必须和目录名一致。

完成标准：放入两个测试 `SKILL.md`，一个 always，一个非 always；always skill body 能进入 prompt，非 always skill 只出现在 summary，并可通过 `load_skill` 加载完整内容。

## 8. 写 system prompt 组装

OpenCreator 对照：

[prompt.py](../../../../../opencreate/opencreator-agent/creato/agents/main/prompt.py)

system prompt 至少要接收：

```text
skills_loader
tool_names
```

组装时要区分：

```text
always skills
  → 注入正文

loadable skills
  → 注入 name / description / trigger summary

tool_names
  → 告诉模型当前可执行工具集合
```

完成标准：Profile allowlist 删除某个 skill 后，prompt 中不再出现它；新增 always skill 后，body 会进入 prompt。

---

## 9. 写 SubagentTool

OpenCreator 对照：

[subagent.py](../../../../../opencreate/opencreator-agent/creato/core/tools/subagent.py)

如果 NovelComic 第一轮不做子 Agent，可以先留空或不注册。但如果要对齐 OpenCreator，规则要按 Factory 写：

```text
depth < 3
  → 注册 SubagentTool

depth >= 3
  → 不注册
```

完成标准：主 Agent 可以把任务交给一个子 Profile；子 Agent 再创建子 Agent 时受深度限制，不会无限递归。

## 10. 写 MCP wrapper，但先不启用

OpenCreator 对照：

[mcp.py](../../../../../opencreate/opencreator-agent/creato/core/tools/mcp.py)

先写独立适配层：

```text
MCPToolWrapper
  → name = mcp_{server}_{tool}
  → description = tool_def.description
  → parameters = normalize_schema(tool_def.inputSchema)
  → execute() 调 session.call_tool()

connect_mcp_servers()
  → stdio
  → SSE
  → streamable HTTP
  → list_tools()
  → enabled_tools 过滤
  → register wrapper
```

schema 归一化要支持：

```text
type: ["x", "null"]
oneOf / anyOf nullable
object 缺 properties / required
```

完成标准：用 mock MCP session 返回两个工具，能包装成 `mcp_server_tool` 并注册到 Registry；超时或异常返回错误文本。

---

## 11. 在 AgentLoop 保留 MCP 生命周期边界

OpenCreator 对照：

[loop.py](../../../../../opencreate/opencreator-agent/creato/core/loop.py)

如果按当前 OpenCreator 代码口径迁移，`_connect_mcp()` 先保持禁用：

```text
async def _connect_mcp(self):
    return
```

但可以保留生命周期字段：

```text
_mcp_servers
_mcp_stack
_mcp_connected
_mcp_connecting
close_mcp()
```

这样文档和代码一致：MCP 适配代码存在，动态注册未启用。

如果后续要启用，再补：

```text
await connect_mcp_servers(self._mcp_servers, instance.tools, self._mcp_stack)
```

并处理配置来源、鉴权、server 白名单、工具白名单、超时和关闭。

完成标准：当前 Agent 运行时不会出现动态 MCP 工具；关闭 Agent 时不会泄露 MCP stack；文档不宣称已启用。

## 12. 写 Publisher Agent Skills schema

OpenCreator 对照：

[agent_skills.py](../../../../../opencreate/opencreator-publisher/schemas/agent_skills.py)

产品技能 schema 和仓内 `SKILL.md` 是两套东西。先写用户资产字段：

```text
GenerateAgentSkillDraftRequest
CreateAgentSkillRequest
UpdateAgentSkillRequest
AgentSkillItem
AgentSkillListResponse
```

核心字段：

```text
title
description
cover_url
video_url
original_prompt
scenes
ai_tags
source_type
generation_metadata
```

校验规则要包含：

- title 非空且有最大长度。
- description 有最大长度。
- scenes 数量有上下限，并去重去空。
- ai_tags 数量和单项长度有限制。
- original_prompt 非空，且保留用户原始内容。
- source_type 为 `video` / `prompt` / `file`。

完成标准：非法标题、空 scenes、超长 prompt、source_type 缺必要字段都会被 schema 拒绝。

## 13. 写 DAO

OpenCreator 对照：

[agent_skills.py](../../../../../opencreate/opencreator-publisher/dao/agent_skills.py)

DAO 只负责数据访问：

```text
list_personal(user_id, page, page_size, query_text)
get_personal(user_id, skill_id)
create_personal(user_id, request)
update_personal(user_id, skill_id, updates)
delete_personal(user_id, skill_id)
```

查询必须按 `user_id` 和 `status=active` 隔离。更新和删除也必须带 `user_id` 条件，删除建议软删为 `status=deleted`，避免用户改到或重新查到别人的技能。

完成标准：A 用户创建的 skill，B 用户 list、update、delete 都拿不到。

```text
generate_text_metadata(source_text)

normalize_compiled_values()
```

文本文件限制要明确：

```text
支持 .txt / .md / .yaml / .yml

```

完成标准：prompt 或文本文件能生成 title、description、scenes、ai_tags；不支持的文件类型返回 400；过大文本返回 413。

## 15. 写 AgentSkillsService

OpenCreator 对照：

[agent_skills.py](../../../../../opencreate/opencreator-publisher/services/agent_skills.py)

服务层编排：

```text
list_personal()
  → DAO list
  → AgentSkillListResponse

generate_draft()
  → 校验 source_type
  → 文本或视频理解
  → 组装 AgentSkillDraft

create_personal()
  → 校验用户拥有的素材 URL
  → DAO create

update_personal()
  → 校验用户拥有的封面 URL
  → DAO update

delete_personal()
  → DAO delete
```

注意：这层不把产品技能写入 `creato/core/skills/`，也不调用 `SkillsLoader.reload()`。它只是维护用户侧资产。

完成标准：创建、更新、删除都按 user_id 生效；生成草稿不持久化用户数据；返回结构和 schema 一致。

## 16. 写 Controller

OpenCreator 对照：

[agent_skills.py](../../../../../opencreate/opencreator-publisher/controller/v3/agent_skills.py)

路由：

```text
GET    /api/v3/agent-skills/personal
POST   /api/v3/agent-skills/generate-draft
POST   /api/v3/agent-skills
PATCH  /api/v3/agent-skills/personal/{skill_id}
DELETE /api/v3/agent-skills/personal/{skill_id}
```

每个接口都要走认证：

```text
user: AuthUser = Depends(get_authenticated_user)
```

错误处理：

- 草稿生成失败返回对应 4xx。
- 素材 URL 不属于当前用户时返回 404 或客户端错误。
- 更新和删除找不到自己的 skill 时返回 not found。

完成标准：未登录不能访问；登录用户只能操作自己的技能；草稿、创建、更新、删除都有稳定响应。

## 17. 最后接前端产品技能目录

这一步不是 Agent 运行时必需，但如果 NovelComic 要有用户侧技能管理页面，再接前端：

```text
api/modules/agent-skills.ts
  → listPersonalAgentSkills()
  → generateAgentSkillDraft()
  → createAgentSkill()
  → updateAgentSkill()
  → deleteAgentSkill()

页面 / 组件
  → 个人技能列表
  → 草稿生成
  → 新建 / 编辑 / 删除
```

前端文案要避免把产品技能描述成“已经自动变成 Agent 运行时工具”。更准确的说法是“保存为个人技能资产”。

完成标准：用户能看到、创建、编辑、删除自己的技能卡片；刷新后数据仍在；不会影响仓内 `load_skill` 列表。

## 完整验收

按下面顺序验，不要只验 UI：

1. Agent 启动后，Profile 中声明的工具会出现在 LLM tool definitions。
2. 未声明的工具不会出现在当前 Agent 实例。
3. 同一 Profile 连续 build 得到独立 Registry。
4. 工具参数会先 cast，再 validate，再 execute。
5. 参数错误不会进入工具业务逻辑。
6. `SkillsLoader` 能扫描仓内 `SKILL.md`，并拒绝目录名和 frontmatter name 不一致的 skill。
7. Profile allowlist 外的 skill 不会进入 summary，也不能被 `load_skill` 加载。
8. `always: true` 且 requirements 满足的 skill body 会进入 system prompt。
9. 非 always skill 只出现在 summary，模型调用 `load_skill` 后才拿到完整内容。
10. SubagentTool 受深度限制，最大深度为 3。
11. MCP wrapper 能包装 mock server 工具，但当前主循环不会动态注册真实 MCP 工具。
12. Publisher Agent Skills 可以按用户增删改查。
13. A 用户不能读取、更新或删除 B 用户技能。
14. 产品 Agent Skills 不会自动写入仓内 SkillsLoader。
15. 文档、接口和运行时口径一致：MCP 适配存在，但动态注册未启用。

验收口径：工具、Skills、MCP 和产品技能目录必须分层清楚。只完成技能卡片 CRUD，不算完成 Agent 工具与 Skills；只写 MCP client 代码但没有启用，也不能写成现网动态 MCP 能力。
