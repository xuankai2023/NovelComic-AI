# Agent 工具、Skills 与 MCP 全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“技能列表能显示”，而是 Agent 运行时如何按 Profile 装配工具，仓内 `SKILL.md` 如何进入模型上下文，MCP 适配代码为什么存在却没有启用，以及 Publisher 上的产品 Agent Skills 为什么不能当成运行时 Loader。

先把一句话背下来：

OpenCreator 把 Agent 能力拆成三层：Tool Registry 负责可执行工具，SkillsLoader 负责把仓内 `SKILL.md` 变成模型可读说明，MCP 代码负责把外部 MCP server 的工具包装成原生 Tool。当前主链里 Profile 装配的内建工具和仓内 Skills 生效，动态 MCP 注册代码存在但没有启用；Publisher Agent Skills 是用户资产，不是运行时扫描源。

## 0. 先分清四个概念

`Tool`：可执行函数，有 name、description、parameters 和 execute。

`Registry`：当前 Agent 实例的工具表，每次 build 都新建。

`Skill`：仓内 `SKILL.md` 指令材料，帮助模型理解什么时候怎么使用能力。

`MCP`：外部工具协议适配层，当前代码存在但主循环没有动态注册。

面试时一定要把这四个东西讲开。很多问题都来自把产品技能卡片、仓内说明和可执行工具当成同一个东西。

## 1. Agent Profile 声明能力范围

主 Agent Profile 声明三类关键内容：

```text
tool_factories
inline_skills
loadable_skills
```

`tool_factories` 是工具工厂列表，不是工具实例。比如 `_read_file`、`_web_search`、`_run_workflow`、`_edit_workflow`。

`loadable_skills` 是主 Agent 可以按需加载的技能 allowlist。当前主 Profile 包含 `weather`、`workflow-core`、`video-review`、`editing-core`、`preset-authoring`、`planning-core`。

仓里有别的 `SKILL.md` 不代表这个 Agent 就能加载。`inline_skills` 也参与 allowlist 过滤，但 Skill 是否常驻注入仍看 `SKILL.md` 自己的 `always: true`。

## 2. AgentFactory 每次 build 都重新装配

```text
AgentFactory.build(profile)
  → tools = ToolRegistry()
  → for factory in profile.tool_factories:
        tools.register(factory(context))
  → allowed_skills = inline_skills + loadable_skills
  → filtered_skills = skills_loader.filtered(allowed_skills)
  → 如果有 loadable_skills，注册 LoadSkillTool
  → 如果有 subagent profile 且 depth < 3，注册 SubagentTool
  → build system prompt
  → 返回 AgentInstance
```

Registry 是实例级对象。工具如果需要 workspace、dao、API config、workflow engine，要通过 factory 从 `AgentContext` 注入，不要假设全局单例里总有正确上下文。

## 3. ToolRegistry 暴露定义并统一执行

LLM 调用之前，Agent loop 会把工具定义给 provider：

```text
ToolRegistry.get_definitions()
  → tool.to_schema()
```

每个工具 schema 形状是 `type=function`，里面有 name、description、parameters。

当模型返回 tool call 时，不是直接调用工具函数，而是：

```text
ToolRegistry.execute(name, params)
  → 查工具是否存在
  → cast_params()
  → validate_params()
  → await tool.execute(**params)
```

找不到工具或参数校验失败时，Registry 返回错误文本，并提示模型换一种方式。这层解决的是“模型传参形状不完全稳定”，但不是业务兜底。

## 4. 内建工具由 Profile 工厂接入业务系统

主 Profile 中的工具工厂会把 Agent 能力接到不同服务：读文件、搜网页、跑工作流、改画布、查模板、理解媒体、创建任务。

共同点是它们都被包装成 `Tool`，再由同一个 Registry 执行。NovelComic 迁移时，应该先把最小可用工具闭环写出来，再逐步增加工具，不要一次性把所有业务 API 都暴露给模型。

`run_workflow` 可以调用工作流服务，但 run 命令幂等仍要由 Publisher 的 command id、Consumer inbox 和事件回程链保证。工具系统不替代下游授权和状态机。

## 5. SkillsLoader 启动时扫描仓内 Skills

初始化流程：

```text
SkillsLoader()
  → 遍历 creato/core/skills/*
  → 找每个目录下的 SKILL.md
  → 解析 frontmatter
  → 校验 name 与目录名
  → 检查 requires_bins / requires_env
  → 缓存 SkillInfo
```

frontmatter 只支持平铺单行字段，不支持嵌套 YAML 或数组对象写法。这个限制要写进 NovelComic 的技能规范，否则加载器会忽略或跳过字段。

正常运行中不会每次调用都重新读磁盘。修改 `SKILL.md` 后要重启或 `reload()`。

## 6. Skills 进入模型上下文有两种方式

第一种是 always skill：

```text
always=true
  → available=true
  → get_always_skills()
  → load_skills_for_context()
  → body 进入 system prompt
```

第二种是按需加载：

```text
always=false
  → build_skills_summary()
  → 模型看到 name / description / trigger
  → 模型调用 load_skill(name)
  → 完整 SKILL.md 返回给模型
```

`load_skill` 本身也是工具。只有 Profile 有 `loadable_skills` 时，`AgentFactory` 才会注册它。

## 7. Skill 不是可执行插件

Skill 的作用是告诉模型什么时候使用某个能力，给出步骤、约束、示例和验收口径。它不直接执行动作。

因此迁移时不能只建一个产品技能表就认为 Agent 拥有了新能力。必须同时回答两个问题：

- 模型知道如何使用这个能力吗？
- Registry 里真的有可执行工具吗？

## 8. Subagent 也走工具系统

`AgentFactory.build()` 会检查是否有 subagent profile。如果有，且当前深度小于 3，就注册 `SubagentTool`。递归深度被限制住，避免无限套娃。它和普通工具一样进入 Tool Registry，也一样受 Profile 控制。

## 9. MCP 代码把外部工具包装成原生 Tool

连接流程：

```text
connect_mcp_servers(mcp_servers, registry, stack)
  → 按 server config 选择 stdio / sse / streamableHttp
  → ClientSession.initialize()
  → session.list_tools()
  → MCPToolWrapper(session, server_name, tool_def)
  → registry.register(wrapper)
```

包装后的工具名是 `mcp_{server_name}_{tool_name}`。注册前会做一次 OpenAI 兼容的 schema 归一化。执行失败应返回错误文本，不能拖垮整个 Agent loop。

## 10. 当前主循环没有启用动态 MCP

`AgentLoop._connect_mcp()` 当前直接返回，注释是受限聊天 rollout 下不注册动态 MCP 工具。

因此当前代码口径是：MCP client 和 wrapper 代码存在，但动态 MCP server 工具不会注册进主 Agent Registry。文档和 NovelComic 迁移都必须保留这个边界。除非同时恢复 `_connect_mcp()`，并补好 server 配置、鉴权、白名单、超时、生命周期关闭和观测，否则不要宣称动态 MCP 已启用。

## 11. Publisher Agent Skills 是用户资产

Publisher 提供：

```text
GET    /api/v3/agent-skills/personal
POST   /api/v3/agent-skills/generate-draft
POST   /api/v3/agent-skills
PATCH  /api/v3/agent-skills/personal/{skill_id}
DELETE /api/v3/agent-skills/personal/{skill_id}
```

这些接口用于维护用户的个人技能目录、生成草稿、保存标题 / 描述 / 封面 / 视频 / 原始 prompt / 场景 / 标签。它不是 Agent 进程启动时扫描的 `SKILL.md`，也不会自动变成 `load_skill` 能加载的运行时 Skill。

## 12. 文件编写顺序

按三个层次迁移：

```text
运行时工具层
  → Tool / ToolResult / ToolRegistry / AgentProfile / AgentFactory

仓内技能层
  → SkillsLoader / SKILL.md 规范 / load_skill / system prompt 注入

产品技能层
  → Publisher agent-skills API / dao / schema / media draft generation
```

MCP 可以先落代码结构和配置模型，但默认保持未启用。不要先做技能卡片 UI，再回头补 Registry 和参数校验。

## 13. 面试 1 分钟口述

OpenCreator 的 Agent 能力不是一个插件市场。每次 `AgentFactory.build()` 都会按 Profile 的 `tool_factories` 创建新的 `ToolRegistry`，把 `read_file`、`run_workflow`、`edit_workflow` 这类工具装配到当前实例。模型看到的是 JSON Schema 工具定义；真正调用时 Registry 先做参数转换和校验，再执行。仓内 Skills 来自 `creato/core/skills/*/SKILL.md`，还要过 Profile allowlist。`always=true` 的正文进 system prompt，其他技能只先暴露摘要，模型需要时再 `load_skill`。Skill 本身不执行动作，只教模型怎么用工具。MCP 适配层能把远端工具包装成 `mcp_{server}_{tool}`，但当前 `_connect_mcp()` 直接返回，所以动态 MCP 不是现网能力。Publisher 的 `/api/v3/agent-skills` 是用户产品目录，不会被运行时 Loader 扫描。工具调用也不替代下游工作流的命令幂等和授权。

## 14. 面试官追问怎么答

如果问 Skill 是不是插件：

不是。Skill 是给模型看的说明材料。没有对应 Tool，Skill 不会凭空执行外部动作。

如果问为什么每次都新建 Registry：

因为工具闭包绑定的是这次请求的 workspace、用户和 dao。跨会话复用会串数据和越权。

如果问仓里有 `SKILL.md` 为什么主 Agent 看不到：

还要过 Profile allowlist，还要满足 `requires_bins` / `requires_env`。扫描到不等于对这个 Agent 可见。

如果问 Publisher 技能和仓内 Skill 能不能合成一张表：

不能。一个是用户资产和素材化能力，一个是版本控制里的运行提示。当前运行时不会从 Publisher API 加载技能正文。

如果问 MCP 到底有没有接通：

代码有，主循环没启用。面试和文档都必须说“适配层存在，动态注册未启用”。

如果问 `run_workflow` 工具是不是已经保证了工作流幂等：

没有。它只是调用封装。幂等、inbox、事件回程仍在 Publisher / Consumer。

## 15. NovelComic 当前实现自查

本章运行时已经按三层落地，文档口径和代码一致：

- `novelcomic-agent` 有 `Tool`、`ToolRegistry`、`AgentFactory` 和 `SkillsLoader`。Agent 启动后，Profile 声明的工具会进入 LLM tool definitions。
- 工具参数先 cast，再 validate，再 execute。仓内 `SKILL.md` 受 Profile allowlist 约束。`always: true` 且 requirements 满足的正文进入 system prompt，其他技能只出现在 summary，模型调用 `load_skill` 后才拿到全文。
- `SubagentTool` 最大深度为 3。
- MCP wrapper 和 `connect_mcp_servers()` 能包装外部工具，但 `AgentLoop._connect_mcp()` 直接返回。适配层存在，动态注册未启用。
- Publisher `/api/v3/agent-skills` 是用户资产的增删改查。A 用户不能读取、更新或删除 B 用户的技能。这些记录不会写入仓内 SkillsLoader。
- 前端个人技能页面调用的是这组产品接口。技能卡片不是运行时 Skill Loader，也不会变成模型工具。

验收不能只看技能卡片。工具、仓内 Skills、MCP 适配和产品技能目录要分层通过。只写了 MCP client 但没有启用，也不能写成现网动态 MCP 能力。
