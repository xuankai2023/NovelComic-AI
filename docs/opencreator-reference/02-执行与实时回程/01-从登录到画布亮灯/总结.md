# 从登录到画布亮灯全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“点了 Run 返回 202”，而是用户登录之后，前端怎么读取 flow project，Publisher 怎么只受理命令，Consumer 怎么推进 DAG，事件怎么先落到 Event Store，WebSocket 怎么按 cursor 回放，以及前端 handler 怎样把节点写成 `running` / `success`。

先把一句话背下来：

OpenCreator 的画布亮灯横跨前端、Publisher、Consumer、AI 和消息基础设施。登录只建立身份，打开画布只读取项目；点击 Run 后 Publisher 返回 `202 Accepted`，真正执行在 Consumer；事件先写入 Event Store，再由可恢复 WebSocket 推回浏览器，前端 handler 成功处理后节点才亮灯。

## 0. 先分清四个状态

`有 session` 只表示 Clerk 登录完成，前端能取 `__opencreator_jwt`。它不表示项目已加载，也不表示模型已开始跑。

`有 nodes / edges` 只表示 flow project 已读进画布 store。用户此时能看到图，但本次执行还没有开始。

`有 flow_task_id` 只表示 Publisher 已经受理这次 Run 命令。它不表示节点完成，也不表示画布已经变色。

`节点变成 running / success` 才是亮灯。它必须等 Consumer 发布事件、Publisher 写入 Event Store、WebSocket 投递、前端 handler 成功改 `node.data.status`。

面试时一定要把这四个状态讲开。很多问题都来自把“已登录”“画布可见”“命令受理”“节点亮灯”压成一件事。

## 1. 登录：只建立用户身份

OpenCreator 前端用 `RequireAuth` 包住受保护页面。未登录时打开登录弹窗，登录成功后 Clerk session 激活。

业务请求发出去前，再由 HTTP client 取业务 JWT：

```text
getToken({ template: "__opencreator_jwt" })
```

Publisher 的认证中间件验证这个 JWT，并把用户身份放进请求上下文。登录阶段不读取项目、不创建 run、不连接本次 run 的 WebSocket。

面试讲法：

登录解决的是“当前请求是谁”。它不启动 DAG，也不点亮节点。

## 2. 进入画布：读取 flow project

路由匹配 `/canvas/{flowId}` 后，前端读取：

```text
GET /api/v2/flow/project/{flowId}
```

后端按 `flow_id + user_id` 查项目。读取成功后，nodes / edges 写入画布 store。历史结果接口 `POST /api/v3/result/all_batch_fetch` 只负责补旧结果，不代表当前 run 已经产生事件。

这一步的详细门禁、草稿合并和样式，属于上一组“画布登录门禁与项目加载”。本章只要记住：画布可见不等于开始执行。

## 3. 点击 Run：创建稳定命令

执行入口在 `workflow-runtime-provider.tsx` 和 `useWorkflowRunner.ts`。

一次 Run 的前端顺序是：

```text
runAll()
  → 从当前 nodes / edges 组装 flow_task
  → getOrCreateWorkflowCommand()
  → postCreateWorkflowRun()
  → POST /api/v2/flow/runs
```

`workflow-command-journal.ts` 会为这次点击生成稳定 `client_request_id` / `command_id`。如果 HTTP 超时或 5xx，重试仍使用原 id，避免创建多个 run。

`flow.ts` 里运行相关接口包括：

- `postCreateWorkflowRun()`：创建 run。
- `postContinueWorkflowRun()`：HITL 选择后继续。
- `postCancelWorkflowRun()`：取消 run。
- `getWorkflowRun()`：查询单个 run。
- `getActiveWorkflowRuns()`：刷新后找回 active run。

## 4. Publisher：收下命令，不直接执行

Publisher 的 `flow_runs.py` 暴露运行 API：

```text
POST /api/v2/flow/runs
POST /api/v2/flow/runs/{flow_task_id}/continue
POST /api/v2/flow/runs/{flow_task_id}/cancel
GET  /api/v2/flow/runs
GET  /api/v2/flow/runs/{flow_task_id}
```

`create_run()` 做的是命令事实，不是 DAG 执行：

```text
计算 command_id
  → 相同 command_id + 相同 payload：返回原 run
  → 相同 command_id + 不同 payload：409
  → 新命令：写 flow_task 和 workflow_command
```

成功时返回 `202 Accepted`。响应至少包含 `flow_task_id`、`flow_run_id`、`trace_id`、`status`、`idempotent_replay`。

面试讲法：

Publisher 第一次接 HTTP 时只承诺“命令收下了”，不承诺“结果生成了”。页面不能在 `202` 后直接标 success。

## 5. Dispatcher：把 pending 命令投递到 run_flow

OpenCreator 用 dispatcher 把已受理命令送进执行队列：

```text
workflow_command_dispatcher_forever()
  → dispatch_due_commands()
  → FlowService.enqueue_flow_task()
  → FlowTask.run_flow.publish()
  → Redis Stream run_flow
```

Publisher 侧 `tasks/flow.py` 只声明发布端，队列名是 `run_flow`，broker 是 `REDIS_STREAM`。Consumer 才是真正的消费端。

为什么要解耦：HTTP 入口只负责受理和幂等，执行可以异步、可重试、可恢复。

## 6. Consumer：领取命令并推进 DAG

Consumer 的 `tasks/flow.py` 消费 `run_flow`。v2 命令先经过：

```text
FlowCommandInboxService.claim_command()
```

没领到就直接返回，避免重复执行同一命令。领到后按固定顺序初始化：

```text
FlowRunStateService.init_flow_run()
  → FlowNodeStateService.init_nodes()
  → FlowEventPublishService.publish(start_flow)
  → FlowResumeTask.handle_resume(reason="start")
```

`flow_resume.py` 负责找 ready 节点。普通输入节点可以在 Consumer 本地完成；需要模型的节点进入 `_submit_plan()`。

## 7. AI：只处理模型节点

Consumer 通过 `task_client.py` 调用 AI：

```text
POST {OC_API_URL}/v1/tasks
```

AI 入口返回 `202`。provider 调用、轮询、webhook、产物归一化和回调 Consumer 由 AI 网关专题展开。对“画布亮灯”来说，关键是 Consumer 能把模型节点提交出去，并把 AI 回调转成 workflow event。

登录、打开画布、创建 run 都不会直接调用模型。

## 8. 回程事件：outbox 到 Event Store

Consumer 不直接给浏览器发消息。节点状态变化先进入 outbox，再发到 RabbitMQ：

```text
FlowEventPublishService.publish()
  → Mongo outbox
  → RabbitMQ v2 reply queue
```

Publisher 消费 v2 reply queue：

```text
校验 protocol_version=2
  → WorkflowEventStore.append_event()
  → 更新 flow_task.last_event_cursor / status
  → ACK RabbitMQ
```

ACK 必须发生在 `append_event()` 成功之后。浏览器当时是否在线，不影响 RabbitMQ ACK。同一个 `event_id` 重放时返回原 cursor，不生成第二条逻辑事件。

面试讲法：

事件先可靠落地，再推给浏览器。WebSocket 不在线也不能丢事件。

## 9. WebSocket：按 cursor 恢复事件

拿到 `flow_task_id` 后，前端连接：

```text
WS /api/v2/flow/runs/{flow_task_id}/events/{connection_id}
```

握手顺序：

```text
open
  → auth(JWT)
  → authenticated
  → attach_flow(last_event_cursor)
  → replay
  → resume_ready
```

`onopen` 只表示网络握手完成。前端只有收到 `resume_ready`，才能认为这条运行事件流真正可用。

命令通道和事件通道不能混：

| 通道 | 作用 |
| --- | --- |
| REST + Redis Stream `run_flow` | 把“开始 / 继续 / 取消”送进执行系统 |
| RabbitMQ + Event Store + WebSocket | 把执行结果和节点状态送回浏览器 |

## 10. 前端 handler：真正改节点状态

`useWebSocketFlow.ts` 按 `event_type` 分发：

- `start_flow`
- `node_status`
- `llm_model_ready`
- `llm_model_status`
- `finish_flow`
- `flow_killed`
- `workflow_error`

`useWorkflowRunner.ts` 把它们变成画布状态：

- `onNodeRunning`：记录当前节点，把结果标成 `running`。
- `onLlmModelReady`：写入占位结果，并调用 `setRunningNodeStatus(node_id)`。
- `onNodeSuccess`：重置运行态，调用 `setSucessNodeStatus()`，再写入节点结果。

状态写入点：

- `useNodeStatusManager.ts`：写 `running` / `idle`。
- `workflow-runtime-provider.tsx`：写 `success`、暂停态、选择态。

transport 层只有在 handler 成功后才保存 `event_cursor`。handler 失败时连接会断开，下一次从上一条成功事件继续回放。

只拿到 `202`、只看到 WebSocket 连上，都不等于画布亮灯。

## 11. 三类去重各管一层

| 机制 | 解决的问题 | 身份 | 存放位置 |
| --- | --- | --- | --- |
| command journal | 同一次点击重试不能创建多个 run | `client_request_id` / `command_id` | 前端 `sessionStorage` + Publisher `workflow_command` |
| event cursor | 断线后从哪条事件继续读 | Redis Stream cursor | Event Store + 前端 `sessionStorage` |
| side-effect claim | 多 tab 不重复执行本地副作用 | `event_id` + scope | 前端 `localStorage` |

`workflow-side-effect-claim.ts` 只管 toast、埋点、积分刷新这类本地副作用。节点状态更新不走它，因为每个打开的 tab 都应该刷新自己的画布。

## 12. 刷新和取消

刷新页面不会停止 Consumer 上正在跑的 run。重新进入画布时：

```text
重新读取 flow project
  → getActiveWorkflowRuns(flowId)
  → 读取 sessionStorage cursor
  → attach_flow(last_event_cursor)
  → replay
  → resume_ready
```

真正停止执行必须调用：

```text
POST /api/v2/flow/runs/{flow_task_id}/cancel
```

关闭页面或 WebSocket 断开，只是前端不再接收事件；后端 run 会继续推进，后续进入画布仍可按 cursor 恢复。

## 13. 文件编写顺序

迁移到 NovelComic 时，不要从裸 WebSocket 开始。按依赖顺序更稳：

1. `workflow-command-journal.ts`：同一次点击复用命令身份。
2. `api/modules/flow.ts`：封装 create / continue / cancel / active run。
3. `schemas/workflow_runs_v2.py` 和 `services/workflow_runs_v2.py`：写 `flow_task + workflow_command`。
4. `controller/v2/flow_runs.py`：HTTP 入口统一返回 `202`。
5. `services/flow.py` 和 `tasks/flow.py`：dispatcher 发布 `run_flow`。
6. Consumer inbox、run state、node state、`flow_resume.py`。
7. AI `task_client.py` 和 `/v1/tasks`。
8. Consumer outbox、RabbitMQ、Publisher Event Store。
9. `workflow-resumable-websocket.ts`、`useWebSocketFlow.ts`、handler。

面试讲法：

先有命令事实，再有执行事实，再有事件事实。项目还没稳定、命令还不能幂等时，先做实时推送只会把问题放大。

## 14. 和 NovelComic 当前迁移关系

NovelComic 第 1 章已经完成登录与 JWT，第 2 章已经能按当前用户加载 flow project。

本章要在这个基础上打通亮灯：

- 前端要用 command journal 提交 `POST /api/v2/flow/runs`。
- Publisher 要写 `workflow_command` 并 dispatch 到 Redis Stream。
- Consumer 要 claim start 命令、初始化 durable 状态、推进 ready 节点。
- 事件要先入 Event Store，再走 v2 WebSocket。
- `runAll()` 不能在 HTTP 返回后立刻结束运行态。

所以当前迁移不能说“接口返回 202 就完成了”。真正完整的验收要覆盖命令幂等、DAG 推进、事件落地、cursor 恢复和前端 handler。

## 15. 面试 1 分钟口述

OpenCreator 的画布亮灯不是登录后自动跑模型。用户先过 Clerk 登录，前端用 `__opencreator_jwt` 读取 `GET /api/v2/flow/project/{flowId}`，这时只能看到图。点击 Run 后，前端用 command journal 生成稳定 `command_id`，调用 `POST /api/v2/flow/runs`。Publisher 验 JWT、校验 DAG、同事务写 `flow_task` 和 `workflow_command`，返回 `202 Accepted` 和 `flow_task_id`。dispatcher 把命令发到 Redis Stream `run_flow`。Consumer claim 命令后初始化 run 和节点，用 `FlowResumeTask` 找 ready 节点；输入节点本地完成，模型节点提交 opencreator-ai。执行事件先走 Consumer outbox 和 RabbitMQ，Publisher 写入 Event Store 后再 ACK。前端按 `flow_task_id` 建 WebSocket，首帧 auth，第二帧 attach cursor，收到 `resume_ready` 后才认为连接可用。真正亮灯发生在前端 handler 把 `node_status` 写成 `running` 或 `success`。刷新只断开物理连接，不取消 run；停止必须调 cancel。

## 16. 面试官追问怎么答

如果问为什么 `202` 不等于节点成功：

因为 `202` 只是 Publisher 受理命令。节点是否执行、模型是否完成、画布是否变色，都要等 Consumer 事件回到 Event Store 并被前端 handler 消费。

如果问为什么打开画布不直接连 WebSocket：

打开画布只读取项目定义和历史结果，还没有 `flow_task_id`。WebSocket 是某次 run 的事件通道，必须等点击 Run 后才能连接。

如果问浏览器断线会不会丢事件：

不会按设计丢。Consumer 事件先落 Publisher Event Store，ACK 发生在写入成功之后。浏览器回来后用 cursor replay。

如果问关闭 WebSocket 是不是停止任务：

不是。WebSocket 只是事件订阅通道。停止必须调用 `POST /api/v2/flow/runs/{flow_task_id}/cancel`。

如果问三类去重有什么区别：

`command_id` 防止同一次点击创建多个 run；`event_cursor` 决定从哪条事件继续读；`event_id` 的 side-effect claim 防止 toast 这类本地副作用重复执行。节点状态每个 tab 都要自己更新，不走 side-effect claim。

如果问 NovelComic 迁移时先做什么：

先保证登录、项目读取和画布 store 稳定，再补 command journal 和 `POST /api/v2/flow/runs`，然后接 dispatcher、Consumer inbox、Event Store 和可恢复 WebSocket。不要并行保留两套 run 协议。

## 17. NovelComic 当前实现自查

只看本章“从登录到画布亮灯”，NovelComic 当前已经具备主链路骨架：

- 登录后能读取自己的 flow project，并把 nodes / edges 写入画布 store。
- 前端已有 `workflow-command-journal.ts`，Run 会生成稳定命令身份。
- `POST /api/v2/flow/runs` 能返回 `202`、`flow_task_id`、`flow_run_id`、`trace_id`。
- Publisher 已有 `workflow_command`、dispatcher 和 Redis Stream `run_flow`。
- Consumer 能 claim start 命令、初始化 run / nodes，并推进基础输入节点。
- 模型节点能提交 AI task，事件能经 outbox / RabbitMQ 进入 Event Store。
- 前端已有 v2 WebSocket：auth、attach、按 cursor 存本地，handler 能写节点状态。

现有自动化和验收已经覆盖：

- 前端 flow API 带 JWT 创建、继续、取消和查询 active run。
- command journal 复用同一命令身份。
- Publisher 创建 run 返回 `202`。
- Consumer inbox claim 和 start 初始化。

仍需按本章继续确认或补齐的点：

- Consumer 目前只实现 start，不处理 continue / cancel 命令。
- 模型 callback 聚合、HITL select 和后继推进还不完整。
- Publisher 的 continue / cancel 更多是改本地 run 状态和写事件，没有完整 dispatch 到 Consumer kill tail。
- WebSocket 已有协议骨架，但心跳、generation、cursor 过期和 snapshot 恢复还要对齐。
- “刷新后 cursor replay 让节点重新亮灯”还缺少完整端到端验收。

本章验收口径：

如果只验收“登录后能打开自己的画布，点击 Run 能进入命令通道并看到基础节点状态变化”，当前主骨架已经具备。  
如果按 OpenCreator 完整亮灯验收，还需要继续补 HITL、真正 cancel、模型回调聚合、刷新恢复和连接保护。
