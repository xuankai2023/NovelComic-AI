# 从登录到画布亮灯：技术点

这条链不是“用户一登录就开始跑模型”，也不是“HTTP 返回 202 就算节点亮了”。OpenCreator 把它拆成四个阶段：

1. 登录：浏览器拿到 Clerk session。
2. 进入画布：前端读取 flow project，渲染 nodes / edges。
3. 提交运行命令：Publisher 收下命令，返回 `202 Accepted`。
4. 执行回程：Consumer 推进 DAG，事件进入 Event Store，WebSocket 按 cursor 回放，前端 handler 改节点状态。

最短路径如下：

```text
Clerk session
  → getToken("__opencreator_jwt")
  → GET /api/v2/flow/project/{flowId}
  → POST /api/v2/flow/runs
  → Publisher 落 command / flow_task，返回 202
  → dispatcher 发布 Redis Stream run_flow
  → Consumer claim command，初始化 run 和节点
  → FlowResumeTask 推进 DAG
  → 需要模型时 POST opencreator-ai /v1/tasks
  → Consumer outbox 发布 RabbitMQ v2 reply queue
  → Publisher append Event Store，再 ACK RabbitMQ
  → WebSocket attach_flow(last_event_cursor)
  → replay / live event
  → handler 写 node.data.status
```

## 1. 登录只建立身份上下文

登录链路只负责让浏览器拥有 Clerk session。OpenCreator 前端通过 [RequireAuth.tsx](../../../../../opencreate/opencreator-frontend/src/features/auth/components/RequireAuth.tsx) 判断是否可以渲染受保护页面。

业务 API 请求不会直接用 Clerk session，而是在请求前按需取业务 JWT：

```text
getToken({ template: "__opencreator_jwt" })
```

Publisher 校验这个 JWT，并从 `sub` 中得到当前用户。到这里为止，还没有读取项目、没有创建 run、没有提交模型，也没有连接本次 run 的 WebSocket。

---

## 2. 打开画布只读取项目快照

进入 `/canvas/{flowId}` 后，前端读取项目：

```text
/canvas/{flowId}
  → RequireAuth
  → GET /api/v2/flow/project/{flowId}
  → setNodes() / setEdges()
```

OpenCreator 对应文件：

- 前端：[canvas.$flowId.tsx](../../../../../opencreate/opencreator-frontend/src/routes/canvas.$flowId.tsx)
- 后端：[workflow_project.py](../../../../../opencreate/opencreator-publisher/controller/v2/workflow_project.py)

这一步拿到的是可编辑的图。历史结果可以通过 `POST /api/v3/result/all_batch_fetch` 补齐，但那只是旧结果快照，不代表本次点击 Run 已经开始。

---

## 3. 点击 Run 进入命令通道

点击 Run 后，前端先生成稳定命令身份，再提交：

```text
POST /api/v2/flow/runs
```

OpenCreator 对应文件：

- 前端接口：[flow.ts](../../../../../opencreate/opencreator-frontend/src/api/modules/flow.ts)
- 后端路由：[flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)

成功返回 `202 Accepted`，响应至少包含：

| 字段 | 含义 |
| --- | --- |
| `flow_task_id` | 本次逻辑执行实例，WebSocket 按它订阅 |
| `flow_run_id` | 这轮 run 的状态记录 |
| `trace_id` | 贯穿 Publisher、Consumer、AI 的追踪 id |
| `status` | 创建时通常是 `pending` |
| `idempotent_replay` | 是否复用了同一个命令的旧 run |

`202` 只表示命令被 Publisher 受理。节点是否执行、模型是否完成、画布是否变色，都要等后续事件。

---

## 4. command id 保证点击幂等

超时、网络失败或 5xx 时，前端重试必须继续使用同一个命令身份。OpenCreator 用 [workflow-command-journal.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-command-journal.ts) 把未完成意图放进 `sessionStorage`。

核心规则：

- 同一 `operationKey` 未完成时，复用第一次生成的 id 和 payload。
- `400 / 401 / 403 / 404 / 409 / 422` 这类明确拒绝，才放弃本地命令。
- 服务端事件带回对应 `client_command_id` 后，前端清掉本地记录。

Publisher 以 `command_id` 做服务端幂等；缺省时使用 `client_request_id`。相同 id 和相同 payload 返回原 run，`idempotent_replay=true`；相同 id 但 payload 不同返回冲突。

## 5. Dispatcher 把命令送进执行系统

`create_run()` 不直接执行 DAG。它先落 `flow_task` 和 `workflow_command`，再由 dispatcher 扫描可派发命令：

```text
workflow_command_dispatcher_forever()
  → dispatch_due_commands()
  → FlowService.enqueue_flow_task()
  → FlowTask.run_flow.publish()
  → Redis Stream run_flow
```

相关文件：

- [workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py)
- [flow.py](../../../../../opencreate/opencreator-publisher/services/flow.py)
- [tasks/flow.py](../../../../../opencreate/opencreator-publisher/tasks/flow.py)

Publisher 的 `tasks/flow.py` 只是发布端声明：队列名是 `run_flow`，broker 是 `REDIS_STREAM`。真正消费在 Consumer 仓库的同名任务中。

---

## 6. Consumer 领取后推进 DAG

Consumer 消费 `run_flow` 后，第一步是认领命令：

```text
FlowCommandInboxService.claim_command()
```

没领到说明同一命令已经被处理，当前消息直接返回。领到后才进入运行初始化：

```text
claim_command()
  → FlowRunStateService.init_flow_run()
  → FlowNodeStateService.init_nodes()
  → FlowEventPublishService.publish(start_flow)
  → FlowResumeTask.handle_resume(reason="start")
```

相关文件：

- [tasks/flow.py](../../../../../opencreate/opencreator-consumer/tasks/flow.py)
- [flow_command_inbox_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_command_inbox_service.py)
- [flow_run_state_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_run_state_service.py)
- [flow_node_state_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_node_state_service.py)
- [flow_resume.py](../../../../../opencreate/opencreator-consumer/tasks/flow_resume.py)

普通节点在 Consumer 本地推进。模型节点进入 `_submit_plan()`，并通过 [task_client.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/task_client.py) 调用 `opencreator-ai`。

## 7. 模型节点才进入 AI

AI 入口是 [tasks.ts](../../../../../opencreate/opencreator-ai/apps/api/src/routes/tasks.ts)：

```text
POST /v1/tasks
  → CreateAiTaskRequestSchema
  → TaskService.createTask()
  → 202
```

模型调用是 DAG 中某个节点的一步，不是登录或打开画布时发生的动作。provider 选择、轮询、webhook、产物归一化和回调 Consumer，归到 AI 网关专题。

---

## 8. 事件先可靠落地，再推给浏览器

Consumer 不直接依赖浏览器连接。节点状态变化先形成稳定 `event_id`，再进入 outbox：

```text
节点状态变化
  → FlowEventPublishService.stable_event_id()
  → Mongo outbox
  → RabbitMQ v2 reply queue
```

Publisher 消费 v2 reply queue 时，顺序必须是：

```text
校验 protocol_version=2
  → WorkflowEventStore.append_event()
  → 更新 flow_task cursor / status
  → ACK RabbitMQ
```

相关文件：

- Consumer 发布：[flow_event_publish_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_event_publish_service.py)
- Consumer MQ：[database/mq.py](../../../../../opencreate/opencreator-consumer/database/mq.py)
- Publisher MQ：[mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py)
- Event Store：[workflow_event_store.py](../../../../../opencreate/opencreator-publisher/services/workflow_event_store.py)

ACK 必须在 Event Store 写成功之后。WebSocket 是否在线不影响 ACK；浏览器断线时，事件仍保存在 Redis Stream，稍后按 cursor 补读。

---

## 9. WebSocket 只负责恢复和投递事件

拿到 `flow_task_id` 后，前端连接：

```text
WS /api/v2/flow/runs/{flow_task_id}/events/{connection_id}
```

握手顺序固定：

```text
open
  → auth(JWT)
  → authenticated
  → attach_flow(last_event_cursor)
  → replay
  → resume_ready
```

命令和事件不能混在一起理解：

| 通道 | 作用 |
| --- | --- |
| REST + Redis Stream `run_flow` | 把“开始 / 继续 / 取消”送进执行系统 |
| RabbitMQ + Event Store + WebSocket | 把执行结果和节点状态送回浏览器 |

前端传输层在 handler 成功返回后才保存新的 `event_cursor`。如果 handler 抛错，本地 cursor 停在上一条成功事件，重连后可重新回放。

---

## 10. 画布亮灯发生在前端 handler

WebSocket 只把事件送到前端。真正让节点变色的是 handler 更新画布 store：

- [useWebSocketFlow.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWebSocketFlow.ts)：按 `event_type` 分发。
- [useWorkflowRunner.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWorkflowRunner.ts)：把事件转成节点运行态、结果和恢复动作。
- [useNodeStatusManager.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useNodeStatusManager.ts)：写 `running` / `idle`。
- [workflow-runtime-provider.tsx](../../../../../opencreate/opencreator-frontend/src/components/canvas/workflow-runtime-provider.tsx)：写 `success`、暂停态和选择态。

常见状态：

- `running`：节点正在执行。
- `success`：节点完成，结果可以画出来。
- `select`：DAG 进入 HITL 等待用户选择。
- `failed` / `workflow_error`：节点或整次 run 失败。

只拿到 `202`、只看到 WebSocket 连上，都不等于画布亮灯。

---

## 11. 三类去重各管一层

| 机制 | 解决的问题 | 身份 | 存放位置 |
| --- | --- | --- | --- |
| command journal | 同一次点击重试不能创建多个 run | `client_request_id` / `command_id` | 前端 `sessionStorage` + Publisher `workflow_command` |
| event cursor | 断线后从哪条事件继续读 | Redis Stream cursor | Event Store + 前端 `sessionStorage` |
| side-effect claim | 多 tab 不重复执行本地副作用 | `event_id` + scope | 前端 `localStorage` |

[workflow-side-effect-claim.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-side-effect-claim.ts) 只管 toast、埋点、积分刷新这类本地副作用。节点状态更新不走它，因为每个打开的 tab 都应该刷新自己的画布。

## 动手前置条件

开始实现这条链之前，至少要有：

- Clerk 登录已完成，`getToken({ template: "__opencreator_jwt" })` 可用。
- Publisher 能验 JWT，并把当前用户放进请求上下文。
- `/canvas/$flowId` 能读取自己的 flow project，并把 nodes / edges 放入画布 store。
- `POST /api/v3/result/all_batch_fetch` 可以返回历史结果；没有结果时返回空数组。
- Redis、RabbitMQ、Mongo 能被 Publisher 和 Consumer 同时访问。

Agent 会话的 SSE 不承载这条画布运行回程。画布亮灯必须走 run 命令、Event Store 和可恢复 WebSocket 这一套。
