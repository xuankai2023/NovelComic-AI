# 从登录到画布亮灯：文件编写顺序

这篇只回答一个问题：NovelComic 如果要照 OpenCreator 接上完整亮灯链，应该先写哪些文件、每一步完成到什么程度。

运行时原理见 [01-从登录到画布亮灯.md](./01-从登录到画布亮灯.md)，机制拆解见 [00-从登录到画布亮灯技术点.md](./00-从登录到画布亮灯技术点.md)。本文按依赖排序，不按用户在浏览器里看到的顺序排序。

命名约定：

- Publisher 路径默认在 `novelcomic-publisher/` 下。
- 前端路径默认从 `src/` 开始。
- Consumer 和 AI 文件保留仓库前缀。
- OpenCreator 现码中的项目加载 hook 叫 `useOneFlow`；NovelComic 同职责 hook 可继续叫 `useWorkflowProject`。

这条链不要只做到 `202`。本轮目标是：点击 Run 后，命令能进入 Consumer，事件能进入 Event Store，前端能通过可恢复 WebSocket 收到事件并把节点写成 `running` / `success`。

## 写之前必须已有

这些能力不在本文新写范围内，但缺少任何一项，后续链路都会对不上：

1. Clerk 登录完成，前端能通过 `getToken({ template: "__opencreator_jwt" })` 取业务 JWT。
2. Publisher 能验 JWT，并把当前用户写入请求上下文。
3. `/canvas/{flowId}` 能读取自己的 flow project，nodes / edges 已进入画布 store。
4. `POST /api/v3/result/all_batch_fetch` 能返回历史结果；没有结果时返回空数组。
5. Redis、RabbitMQ、Mongo 能被 Publisher 和 Consumer 同时使用。

完成基线：登录后打开 `/canvas/{flowId}`，能看到保存过的节点和边。此时点击 Run 可以尚未亮灯。

## 1. 前端命令身份

先写 [workflow-command-journal.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-command-journal.ts)。目标是让同一次点击在超时或 5xx 后重试时继续使用同一条命令。

核心行为：

```text
getOrCreateWorkflowCommand(operationKey, request, prefix)
  → 查 sessionStorage["workflow:v2:pending_commands"]
  → 有未完成记录：返回原 commandId 和原 payload
  → 没有记录：生成 wf_ / continue_ / cancel_ 前缀的新 id
```

清理记录只发生在两类场景：

- 明确拒绝：`400 / 401 / 403 / 404 / 409 / 422`。
- 服务端事件带回对应 `client_command_id`，调用 `completeWorkflowCommandById()`。

完成标准：同一 `operationKey` 连续调用两次，第二次返回第一次的 id 和 payload；换 payload 但旧命令未结束时，也继续返回第一次的 payload。

## 2. 前端 run API

补齐 [flow.ts](../../../../../opencreate/opencreator-frontend/src/api/modules/flow.ts) 中运行相关接口。项目读取接口已经在画布加载专题写过，这里只补 run 命令。

需要的函数：

- `postCreateWorkflowRun()`：创建 run。
- `postContinueWorkflowRun()`：HITL 选择后继续。
- `postCancelWorkflowRun()`：取消 run。
- `getWorkflowRun()`：查询单个 run。
- `getActiveWorkflowRuns()`：刷新后查询 active run。

创建请求至少包含：

| 字段 | 说明 |
| --- | --- |
| `client_request_id` | command journal 生成的稳定 id |
| `command_id` | 可选；为空时服务端使用 `client_request_id` |
| `flow_id` | 当前画布项目 |
| `flow_task` | 本次要执行的 nodes / edges |
| `start_ids` / `end_ids` | 子图范围 |
| `run_mode` | `global` / `selected_nodes` / `single_node` |

完成标准：前端能发出 OpenCreator v2 形状的创建、继续和取消请求，不再只传 `flow_id + input_values`。

## 3. Publisher schema 和 202 路由

先定请求和响应，再写服务。

文件：

- [schemas/workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/schemas/workflow_runs_v2.py)
- [controller/v2/flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)

响应体至少包含：

| 字段 | 说明 |
| --- | --- |
| `flow_task_id` | WebSocket 订阅使用的逻辑执行实例 |
| `flow_run_id` | 本轮 run 状态记录 |
| `trace_id` | 跨服务追踪 |
| `status` | 创建时为 `pending` |
| `idempotent_replay` | 是否复用旧命令 |

路由行为：

```text
POST /api/v2/flow/runs
  → get_authenticated_user
  → WorkflowRunV2Service.create_run()
  → 202
```

完成标准：合法请求返回 `202` 和完整响应字段；此时可以还不往 Redis Stream 发消息。

## 4. Publisher 命令落库和幂等

写 [services/workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py)。

`create_run()` 的固定规则：

```text
command_id = request.command_id or request.client_request_id
  → 相同 command_id + 相同 payload：返回原 flow_task，idempotent_replay=true
  → 相同 command_id + 不同 payload：409
  → 新 command：插入 flow_task 和 workflow_command
```

`flow_task` 初始为 `pending`。`workflow_command` 初始为待派发状态。不要在 `create_run()` 里直接跑 DAG。

完成标准：同一个 `client_request_id` 打两次，第二次返回原 `flow_task_id`；相同 id 换 payload 返回冲突。

## 5. Dispatcher 和 Redis Stream

写 Publisher 派发链：

- [services/flow.py](../../../../../opencreate/opencreator-publisher/services/flow.py)
- [tasks/flow.py](../../../../../opencreate/opencreator-publisher/tasks/flow.py)
- [services/workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py) 中的 dispatcher 循环

派发顺序：

```text
workflow_command_dispatcher_forever()
  → dispatch_due_commands()
  → _dispatch_claimed()
  → FlowService.enqueue_flow_task()
  → FlowTask.run_flow.publish()
```

`enqueue_flow_task()` 要组装：

- `dag`
- `command_id`
- `protocol_version=2`
- `reply_queue=V2_REPLY_QUEUE_NAME`
- `reply_channel_id=v2:{flow_task_id}`

Publisher 的 `tasks/flow.py` 只负责发布，配置为：

```text
queue_name = run_flow
broker_kind = REDIS_STREAM
```

完成标准：创建 run 后，Redis Stream `run_flow` 中出现带 `command_id` 和 `protocol_version=2` 的消息；`flow_task.status` 进入 `running`，命令状态进入 `dispatched`。

## 6. Consumer 命令领取和 run 初始化

Redis Stream 有消息后，再写 Consumer 入口。

文件顺序：

1. [flow_command_inbox_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_command_inbox_service.py)
2. [flow_run_state_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_run_state_service.py)
3. [flow_node_state_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_node_state_service.py)
4. [tasks/flow.py](../../../../../opencreate/opencreator-consumer/tasks/flow.py)

Consumer 收到 start 命令后：

```text
claim_command()
  → init_flow_run()
  → init_nodes()
  → publish(start_flow)
  → FlowResumeTask.handle_resume(reason="start")
```

`claim_command()` 必须以 `command_id` 做持久认领。没领到就返回，不允许同一命令初始化两次。

完成标准：一条 `run_flow` 消息被消费后，Mongo 中出现本次 run 和节点状态；重复投递同一 `command_id` 不会重复初始化。

## 7. DAG 推进和 AI 提交

先写 Consumer 的 DAG 推进，再接 AI。

文件：

- [flow_resume.py](../../../../../opencreate/opencreator-consumer/tasks/flow_resume.py)
- [task_client.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/task_client.py)
- [tasks.ts](../../../../../opencreate/opencreator-ai/apps/api/src/routes/tasks.ts)

`FlowResumeTask.handle_resume()` 查找 ready 节点。普通节点在 Consumer 本地推进；模型节点进入 `_submit_plan()`。提交前要确认当前 worker 仍持有有效 `execution_claim_token`。

AI 提交：

```text
OpenCreatorAITaskClient.submit()
  → POST {OC_API_URL}/v1/tasks
```

AI 入口：

```text
POST /v1/tasks
  → CreateAiTaskRequestSchema
  → TaskService.createTask()
  → 202
```

provider、轮询、webhook 和产物回调详见 [14-AI提交轮询Webhook产物与回调](../../03-AI网关/03-AI提交轮询Webhook产物与回调/14-AI提交轮询Webhook产物与回调.md)。这一轮至少要把模型任务提交和回调入口接上，否则模型节点不会产生后续 workflow event。

完成标准：模型节点能在 AI 侧创建 `ai_task_id`；AI 回调后，Consumer 能继续推进节点状态。

## 8. Consumer outbox 和 v2 reply queue

写事件发布链：

- [flow_event_publish_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_event_publish_service.py)
- [database/mq.py](../../../../../opencreate/opencreator-consumer/database/mq.py)

事件发布顺序：

```text
stable_event_id(...)
  → outbox claim
  → MessagePublisher
  → RabbitMQ v2 reply queue
```

消息体必须包含：

- `protocol_version=2`
- `event_id`
- `flow_task_id`
- `flow_run_id`
- `command_id`
- `event_type`
- `payload`

完成标准：`start_flow` 和 `node_status` 先出现在 outbox，再进入 v2 reply queue；同一个 `event_id` 重试不会插入第二条逻辑事件。

## 9. Publisher Event Store 和 ACK 顺序

先写存储，再写 MQ 回调。

文件：

- [workflow_event_store.py](../../../../../opencreate/opencreator-publisher/services/workflow_event_store.py)
- [database/mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py)

Event Store 行为：

```text
append_event(flow_task_id, event)
  → 追加 Redis Stream
  → 重复 event_id 返回原 cursor
  → 新事件发布 opencreator:workflow:v2:event-notifications
```

MQ 回调行为：

```text
workflow_v2_mq_callback()
  → 校验 protocol_version=2
  → append_event()
  → 更新 flow_task.last_event_cursor / status
  → message.ack()
```

ACK 必须在 `append_event()` 成功之后。WebSocket 是否连接不参与 ACK 决策。

完成标准：往 v2 reply queue 投递合法事件后，Redis Stream 出现 cursor；重复 `event_id` 返回原 cursor；Redis 写失败时 RabbitMQ 消息不会被 ACK。

## 10. 可恢复 WebSocket 后端

有 Event Store 后，再开放浏览器订阅。

继续写 [flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)：

```text
WS /api/v2/flow/runs/{flow_task_id}/events/{connection_id}
  → accept()
  → 等待 auth
  → JwtService.get_user_id_with_backoff()
  → get_run_summary(user_id, flow_task_id)
  → authenticated
  → attach_flow(last_event_cursor)
  → replay
  → resume_ready
  → _event_loop()
```

`workflow_event_notification_listener_forever()` 只负责叫醒连接；事件正文仍从 Event Store 按 cursor 读取。

完成标准：run 已产生事件后再连接，能收到错过的事件，再收到 `resume_ready`；订阅别人的 `flow_task_id` 会在认证后被拒绝。

## 11. 可恢复 WebSocket 前端

写 [workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts)。

连接顺序：

```text
connect()
  → 发送 event_type=auth, protocol_version=2, token
  → 收到 authenticated
  → 发送 event_type=attach_flow, last_event_cursor
  → 等待 replay 和 resume_ready
```

不要保留把 `type`、`token`、`cursor` 塞进同一帧的旧写法。帧格式和重连参数以 [03-可恢复WebSocket](../03-可恢复WebSocket/03-可恢复WebSocket.md) 为准。

完成标准：断线重连后，前端能用 `sessionStorage` 中该 `flow_task_id` 的 cursor 续读；handler 成功后才保存新 cursor。

## 12. 前端事件分发和节点状态

WebSocket 能收到事件后，再接画布状态。

文件顺序：

1. [useWebSocketFlow.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWebSocketFlow.ts)
2. [useNodeStatusManager.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useNodeStatusManager.ts)
3. [useWorkflowRunner.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWorkflowRunner.ts)
4. [workflow-runtime-provider.tsx](../../../../../opencreate/opencreator-frontend/src/components/canvas/workflow-runtime-provider.tsx)

职责：

- `useWebSocketFlow.ts`：按 `event_type` 分发 `node_status`、`llm_model_ready`、`finish_flow` 等事件。
- `useNodeStatusManager.ts`：把单个节点写成 `running` / `idle`。
- `useWorkflowRunner.ts`：创建 run 后调用 `startWebSocketForFlow()`，并把事件交给节点状态和结果 handler。
- `workflow-runtime-provider.tsx`：`runAll()` 进入 runner；`setSucessNodeStatus()` 写 `node.data.status = success`。

`setSucessNodeStatus` 是 OpenCreator 源码里的函数名，拼写保持原样。

重要约束：`runAll()` 不能在 HTTP `202` 返回后立刻把运行态清掉。运行态要由 workflow event 驱动。

完成标准：点击 Run 后，对应节点先变成 `running`，完成后变成 `success`，结果写回节点。只看到 `202` 或只看到 WebSocket 连接成功，都不算完成。

## 13. 副作用认领和刷新恢复

最后补前端本地去重和刷新恢复。

文件：

- [workflow-side-effect-claim.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-side-effect-claim.ts)
- [useWorkflowRunner.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWorkflowRunner.ts)

副作用认领：

```text
runWorkflowSideEffectOnce(eventId, scope, effect)
  → localStorage claim
  → 同一 eventId + scope 只执行一次
```

适用对象是积分刷新、toast、埋点等本地副作用。节点 `data.status` 不走这里，因为每个打开的 tab 都要更新自己的画布。

刷新恢复：

```text
进入画布
  → getActiveWorkflowRuns(flowId)
  → 读取 sessionStorage cursor
  → attach_flow
  → replay
```

完成标准：运行中刷新页面，节点能从 cursor 之后继续变色；两个 tab 同时在线时，节点都更新，但同一条本地副作用只执行一次。

## 完整验收

按下面顺序验，不要跳过中间件和消息层：

1. 未登录访问 `/canvas/{flowId}` 会进入登录流程。
2. 登录后能看见自己的 nodes / edges。
3. 第一次点击 Run 返回 `202`、`flow_task_id`、`flow_run_id`。
4. 用同一个 `client_request_id` 再提交，返回原 run，`idempotent_replay=true`。
5. 改 payload 但复用同一 command id，返回冲突。
6. Redis Stream `run_flow` 有这条命令，Consumer inbox 只认领一次。
7. 模型节点能创建 AI task；普通节点不进入 `/v1/tasks`。
8. `start_flow` 和 `node_status` 先在 outbox，再进入 v2 reply queue。
9. Publisher 在 `append_event()` 成功之后才 ACK RabbitMQ。
10. WebSocket 先 `auth`，再 `attach_flow`，最后收到 `resume_ready`。
11. 对应节点先变成 `running`，完成后变成 `success`。
12. 运行中刷新页面，能查到 active run，并按 cursor 补齐错过事件。
13. 调 cancel 后 run 停止；只关闭页面时，run 继续并可在下次进入后接上。

验收口径：命令、Stream、Consumer、AI 提交、outbox、Event Store、WebSocket 和节点状态必须形成闭环。只完成 `202` 或只完成 WebSocket，都不算“从登录到画布亮灯”。
