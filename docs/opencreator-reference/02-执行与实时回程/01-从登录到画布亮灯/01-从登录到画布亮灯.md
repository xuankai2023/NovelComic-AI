# OpenCreator 是怎么做到从登录到画布亮灯的

这篇按运行时视角讲一遍“谁调用谁”。如果要看技术机制，读 [00-从登录到画布亮灯技术点.md](./00-从登录到画布亮灯技术点.md)。如果要按 NovelComic 的实现顺序落文件，读 [02.文件编写顺序.md](./02.文件编写顺序.md)。

## 一句话结论

OpenCreator 的画布亮灯链路横跨前端、Publisher、Consumer、AI 和消息基础设施。前端负责登录、读取项目、提交命令和更新画布；Publisher 负责验用户、受理命令、保存事件和提供可恢复 WebSocket；Consumer 负责认领命令、推进 DAG 和发布执行事件；AI 只在模型节点需要时进入。

```text
登录
  → 读取画布项目
  → 点击 Run，提交稳定 command
  → Publisher 返回 202
  → dispatcher 投递 run_flow
  → Consumer 推进 DAG
  → 模型节点提交 AI
  → Consumer 发布 workflow event
  → Publisher 写 Event Store
  → WebSocket 回放事件
  → 前端 handler 改 node.data.status
```

必须分清四个状态：

- 有 session：用户已登录。
- 有 nodes / edges：画布项目已加载。
- 有 `flow_task_id`：运行命令已受理。
- 节点变成 `running` / `success`：执行事件已回到前端并被 handler 消费。

---

## 1. 登录：只建立用户身份

OpenCreator 前端用 [RequireAuth.tsx](../../../../../opencreate/opencreator-frontend/src/features/auth/components/RequireAuth.tsx) 包住受保护页面。未登录时打开登录弹窗，登录成功后 Clerk session 激活。

业务请求真正发出去前，再由 [useHttp.tsx](../../../../../opencreate/opencreator-frontend/src/lib/useHttp.tsx) 取业务 JWT：

```text
getToken({ template: "__opencreator_jwt" })
```

Publisher 的认证中间件验证这个 JWT，并把用户身份放进请求上下文。登录阶段不读取项目、不创建 run、不连接本次 run 的 WebSocket。

---

## 2. 进入画布：读取 flow project

路由 [canvas.$flowId.tsx](../../../../../opencreate/opencreator-frontend/src/routes/canvas.$flowId.tsx) 匹配 `/canvas/{flowId}`，再通过项目 hook 读取：

```text
GET /api/v2/flow/project/{flowId}
```

OpenCreator 的项目 hook 是 [use-one-flow.ts](../../../../../opencreate/opencreator-frontend/src/features/canvas-workflow/hooks/flow/use-one-flow.ts)。NovelComic 同职责 hook 是 `useWorkflowProject`。

读取成功后，nodes / edges 写入画布 store。用户此时能看到图，但本次执行还没有开始。历史结果接口 `POST /api/v3/result/all_batch_fetch` 只负责补旧结果，不代表当前 run 已经产生事件。

---

## 3. 点击 Run：创建稳定命令

执行入口在 [workflow-runtime-provider.tsx](../../../../../opencreate/opencreator-frontend/src/components/canvas/workflow-runtime-provider.tsx) 和 [useWorkflowRunner.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWorkflowRunner.ts)。

一次 Run 的前端顺序是：

```text
runAll()
  → 从当前 nodes / edges 组装 flow_task
  → getOrCreateWorkflowCommand()
  → postCreateWorkflowRun()
  → POST /api/v2/flow/runs
```

[workflow-command-journal.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-command-journal.ts) 会为这次点击生成稳定 `client_request_id` / `command_id`。如果 HTTP 超时或 5xx，重试仍使用原 id，避免创建多个 run。

[flow.ts](../../../../../opencreate/opencreator-frontend/src/api/modules/flow.ts) 里运行相关接口包括：

- `postCreateWorkflowRun()`：创建 run。
- `postContinueWorkflowRun()`：HITL 选择后继续。
- `postCancelWorkflowRun()`：取消 run。
- `getWorkflowRun()`：查询单个 run。
- `getActiveWorkflowRuns()`：刷新后找回 active run。

---

## 4. Publisher：收下命令，不直接执行

Publisher 的 [flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py) 暴露运行 API：

```text
POST /api/v2/flow/runs
POST /api/v2/flow/runs/{flow_task_id}/continue
POST /api/v2/flow/runs/{flow_task_id}/cancel
GET  /api/v2/flow/runs
GET  /api/v2/flow/runs/{flow_task_id}
```

请求和响应结构在 [workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/schemas/workflow_runs_v2.py)。创建请求必须带 `client_request_id`、`flow_task`、`start_ids`、`end_ids`，可选 `command_id`。

[workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py) 的 `create_run()` 做三件事：

```text
计算 command_id
  → 相同 command_id + 相同 payload：返回原 run
  → 相同 command_id + 不同 payload：409
  → 新命令：写 flow_task 和 workflow_command
```

成功时返回 `202 Accepted`。这一步只是“命令已受理”，不是“节点已执行完成”。

---

## 5. Dispatcher：把 pending 命令投递到 run_flow

OpenCreator 用 dispatcher 把已受理命令送进执行队列：

```text
workflow_command_dispatcher_forever()
  → dispatch_due_commands()
  → FlowService.enqueue_flow_task()
  → FlowTask.run_flow.publish()
  → Redis Stream run_flow
```

相关文件：

- [workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py)
- [flow.py](../../../../../opencreate/opencreator-publisher/services/flow.py)
- [tasks/flow.py](../../../../../opencreate/opencreator-publisher/tasks/flow.py)

Publisher 侧 [tasks/flow.py](../../../../../opencreate/opencreator-publisher/tasks/flow.py) 只声明发布端，队列名是 `run_flow`，broker 是 `REDIS_STREAM`。Consumer 才是真正的消费端。

---

## 6. Consumer：领取命令并推进 DAG

Consumer 的 [tasks/flow.py](../../../../../opencreate/opencreator-consumer/tasks/flow.py) 消费 `run_flow`。v2 命令先经过：

```text
FlowCommandInboxService.claim_command()
```

没领到就直接返回，避免重复执行同一命令。领到后按固定顺序初始化：

```text
FlowRunStateService.init_flow_run()
  → FlowNodeStateService.init_nodes()
  → FlowEventPublishService.publish(start_flow)
  → FlowResumeTask.handle_resume(reason="start")
```

涉及文件：

- [flow_command_inbox_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_command_inbox_service.py)
- [flow_run_state_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_run_state_service.py)
- [flow_node_state_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_node_state_service.py)
- [flow_resume.py](../../../../../opencreate/opencreator-consumer/tasks/flow_resume.py)

[flow_resume.py](../../../../../opencreate/opencreator-consumer/tasks/flow_resume.py) 负责找 ready 节点。普通节点在 Consumer 本地推进；需要模型的节点进入 `_submit_plan()`。

---

## 7. AI：只处理模型节点

Consumer 通过 [task_client.py](../../../../../opencreate/opencreator-consumer/services/opencreator_ai/task_client.py) 调用 AI：

```text
POST {OC_API_URL}/v1/tasks
```

AI 入口在 [tasks.ts](../../../../../opencreate/opencreator-ai/apps/api/src/routes/tasks.ts)：

```text
POST /v1/tasks
  → CreateAiTaskRequestSchema
  → TaskService.createTask()
  → 202
```

provider 调用、轮询、webhook、产物归一化和回调 Consumer 由 AI 网关专题展开。对“画布亮灯”来说，关键是 Consumer 能把模型节点提交出去，并把 AI 回调转成 workflow event。

---

## 8. 回程事件：outbox 到 Event Store

Consumer 不直接给浏览器发消息。节点状态变化先进入 outbox，再发到 RabbitMQ：

```text
FlowEventPublishService.publish()
  → Mongo outbox
  → RabbitMQ v2 reply queue
```

核心文件：

- [flow_event_publish_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_event_publish_service.py)
- [database/mq.py](../../../../../opencreate/opencreator-consumer/database/mq.py)

Publisher 的 [mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py) 消费 v2 reply queue：

```text
校验 protocol_version=2
  → WorkflowEventStore.append_event()
  → 更新 flow_task.last_event_cursor / status
  → ACK RabbitMQ
```

[workflow_event_store.py](../../../../../opencreate/opencreator-publisher/services/workflow_event_store.py) 把事件追加到 Redis Stream。同一个 `event_id` 重放时返回原 cursor，不生成第二条逻辑事件。

ACK 必须发生在 `append_event()` 成功之后。浏览器当时是否在线，不影响 RabbitMQ ACK。

---

## 9. WebSocket：按 cursor 恢复事件

拿到 `flow_task_id` 后，前端通过 [workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts) 连接：

```text
WS /api/v2/flow/runs/{flow_task_id}/events/{connection_id}
```

握手顺序：

```text
open
  → auth(JWT)
  → authenticated
  → attach_flow(last_event_cursor)
  → replay
  → resume_ready
```

后端 WebSocket 入口也在 [flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)。`workflow_event_notification_listener_forever()` 只用来叫醒连接；事件正文仍从 Event Store 按 cursor 读取。通知丢失不会丢事件，下一轮读取仍能补上。

---

## 10. 前端 handler：真正改节点状态

[useWebSocketFlow.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWebSocketFlow.ts) 接收事件并按类型分发：

- `start_flow`
- `node_status`
- `llm_model_ready`
- `llm_model_status`
- `finish_flow`
- `flow_killed`
- `workflow_error`

[useWorkflowRunner.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useWorkflowRunner.ts) 接住这些回调，把它们变成画布状态更新：

- `onNodeRunning`：记录当前节点，把结果标成 `running`。
- `onLlmModelReady`：写入占位结果，并调用 `setRunningNodeStatus(node_id)`。
- `onNodeSuccess`：重置运行态，调用 `setSucessNodeStatus()`，再写入节点结果。

`setSucessNodeStatus` 是 OpenCreator 源码里的函数名，拼写保持原样。

状态写入点：

- [useNodeStatusManager.ts](../../../../../opencreate/opencreator-frontend/src/components/headBar/hooks/useNodeStatusManager.ts)：写 `running` / `idle`。
- [workflow-runtime-provider.tsx](../../../../../opencreate/opencreator-frontend/src/components/canvas/workflow-runtime-provider.tsx)：写 `success`、暂停态、选择态。

transport 层只有在 handler 成功后才保存 `event_cursor`。handler 失败时连接会断开，下一次从上一条成功事件继续回放。

---

## 11. 刷新和取消

刷新页面不会停止 Consumer 上正在跑的 run。重新进入画布时：

```text
重新读取 flow project
  → getActiveWorkflowRuns(flowId)
  → 读取 sessionStorage cursor
  → attach_flow(last_event_cursor)
  → replay
  → resume_ready
```

真正停止执行必须调用：

```text
POST /api/v2/flow/runs/{flow_task_id}/cancel
```

关闭页面或 WebSocket 断开，只是前端不再接收事件；后端 run 会继续推进，后续进入画布仍可按 cursor 恢复。

---

## 12. 和 NovelComic 的迁移边界

NovelComic 目前已有登录、项目读取，以及一个能返回 `202` 的 run 入口。但要对齐 OpenCreator 的“画布亮灯”，还要补齐以下链路：

- 创建请求体从 `flow_id + input_values` 升级为 `client_request_id + flow_task + start_ids + end_ids`。
- 前端加入 command journal，超时重试复用同一命令。
- Publisher 加入 `workflow_command`、dispatcher 和 Redis Stream `run_flow`。
- Consumer 加入 inbox、DAG 状态、节点状态和 outbox。
- Publisher 加入 v2 reply queue 消费、Event Store 和按 cursor 回放。
- WebSocket 改成先 `auth` 后 `attach_flow`，不要把 token 和 cursor 混在一帧。
- `runAll()` 不能在 HTTP 返回后立刻结束运行态，要等 workflow event 驱动画布状态。

迁移时不要并行保留两套 run 协议。现有入口应就地升级到 OpenCreator 的命令、事件、恢复协议；DAG 细节、WebSocket 重连参数和 AI provider 分别在对应专题展开。
