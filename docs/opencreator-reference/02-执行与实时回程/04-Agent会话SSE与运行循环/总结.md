# Agent 会话、SSE 与运行循环全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“聊天能流式出字”，而是一次用户输入如何变成可幂等的 Agent run，后台 AgentLoop 如何循环调用 LLM 和工具，事件如何写入 Redis Stream，前端如何用 `Last-Event-ID` 续接，以及刷新后怎样区分“还有 active run”和“只能回 Mongo 历史”。

先把一句话背下来：

OpenCreator 的 Agent 聊天是 task-backed run 加 SSE 事件流。前端不是直接调用一个长连接聊天接口，而是先创建 run，后端在后台 task 中跑 AgentLoop，并把事件写入 Redis Stream；前端再用 SSE 订阅这个 run 的事件，用 `Last-Event-ID` 续接断线期间的输出。长期事实在 Mongo session，不在这次 SSE 里。

## 0. 先分清四个对象

`session` 是多轮聊天、HITL、pipeline state 和历史消息。事实源是 Mongo + Redis session cache。

`run` 是某一次用户输入的执行实例。事实源是 Redis run meta + Redis Stream。

`SSE` 是当前 run 的短期事件传输和断线续接。恢复字段是 Redis Stream ID / `Last-Event-ID`。

`chat projection` 是前端刷新后重建 UI 的长期消息视图。它来自 Mongo，不是 Redis run stream。

面试时一定要把这四个东西讲开。不要和画布的 `flow_task_id` + `attach_flow` 混成一套协议。

## 1. 前端：先准备身份，再创建 run

按用户发送一条消息后的顺序看。第 4 步才创建 run，第 5 步才开始 SSE。

关键文件：

- `use-agent-run-controller.ts`：把发送、恢复、取消转成 Agent run 动作。
- `agent-run-store.ts`：保存 active run、AbortController、取消标记和画布 refs。
- `agent-chat.api.ts`：封装非 SSE 的普通 HTTP API。
- `agent-chat-stream.ts`：先 `POST /v1/agent/runs`，再订阅 SSE。
- `agent-chat-event-replay.ts`：把 live / replay 事件投影成聊天 UI。
- `use-agent-chat.ts`：把 run、HITL、workflow 同步和反馈动作收口给组件。

用户发送时先准备：

- `session_id`
- `client_request_id`
- `workflow_snapshot`
- `metadata.files` / `rich_text_html`
- optimistic user / assistant message

然后调用 `runAgentChatStream()`。

## 2. 创建 Agent run

```text
POST {AGENT_BASE_URL}/v1/agent/runs
Authorization: Bearer <__opencreator_jwt>
```

body 里关键字段有 `message`、`session_id`、`flow_id`、`stream`、`agent_model`、`client_request_id`、`workflow_snapshot`。

成功后返回：

```json
{
  "run_id": "run_xxx",
  "status": "queued",
  "created": true
}
```

`queued` 不表示 Agent 已经完成回答。如果返回 `409 ACTIVE_RUN_EXISTS` 且带 `active_run_id`，前端转为订阅已有 active run，并通过 replay 补 UI。

旧 `POST /v1/agent/chat` 只返回 `410 USE_AGENT_RUNS`，不是现网入口。

## 3. 后端入口只创建 run 和打开读口

`creato/api/server.py` 的 `POST /v1/agent/runs`：

```text
验证 JWT
  → 规范化 flow_id / locale / model
  → 解析 client_request_id
  → 检查 request_key 是否已有 run
  → 获取 session run lock
  → 检查 active run
  → RedisRunStore.create_run()
  → _start_agent_run_task()
  → 返回 run_id
```

`GET /v1/agent/runs/{run_id}/events`：

```text
验证 JWT
  → 读取 run meta
  → 校验 meta.user_id == 当前用户
  → resume_cursor = Last-Event-ID or 0-0
  → ensure_resume_available()
  → StreamingResponse(text/event-stream)
```

它还提供 active-run、cancel、cancel-by-request、sessions 和 messages。

## 4. RedisRunStore 是 SSE 恢复窗口

`agent_redis_run_store.py` 负责：

```text
create_run()
  → request_key NX
  → run meta hash
  → active_run_key(session_id)
  → stream TTL

append_event()
  → XADD stream
  → 更新 last_event_id / status
  → terminal event 清 active run

read_events()
  → ensure_resume_available()
  → XREAD
```

关键参数：`RUN_TTL_SECONDS = 24h`，`RUN_STREAM_MAXLEN = 2000`。窗口外 cursor 返回 `410 RESUME_WINDOW_EXPIRED`。

## 5. AgentLoop 在后台跑

外层先过两道并发保护：session lock 和全局并发门。进入 `_process_message()` 后整理上下文，并提前持久化当前用户消息。

真正执行在 `_run_agent_loop()`：

```text
LLM
  → message.delta / thinking.delta
  → tool_calls
  → tool.started
  → 执行 tool
  → tool.completed / tool.failed / tool.event
  → tool result 回填
  → 下一次 LLM
```

直到完成、失败、取消、HITL 或迭代上限。基础 loop 默认 40 次，main profile 可以覆盖，不能把某个数字写成所有 Agent 的固定上限。

## 6. SessionManager 分层保存事实

长期事实写入顺序：

```text
append raw messages
  → upsert session metadata
  → rebuild chat projection
  → insert tool traces
  → write Redis session cache
```

前端实时 UI 来自 SSE；刷新后的历史 UI 来自：

```text
GET /v1/agent/sessions/{session_id}/messages
```

这条历史接口读取的是 chat projection，不是 Redis run stream。

## 7. Agent HITL 是 session metadata 恢复

工具触发 HITL 时，AgentLoop 把 pending tool call 写入 `session.metadata["pending_hitl"]`。

下一条用户输入进入同一个 session 后：

```text
pending_hitl
  → replace_last_tool_result()
  → session.messages append hitl.resolved tool_event
  → 清掉 pending_hitl
  → 继续 AgentLoop
```

前端看到的是 `tool.event` 里的 `hitl.request` 和 chat projection 中的 `hitl` part。真正恢复点在 session metadata。

它和工作流 node select 不是一张表，也不是同一个 resume 入口。

## 8. 前端按事件更新 UI

`agent-chat-stream.ts` 收到事件后按事件名分发：

- `agent.started`：绑定真实 `session_id`。
- `chat.message.created`：创建 assistant message。
- `chat.message.delta`：文本泵追加正文。
- `chat.part.upsert`：更新工具卡片、HITL、workflow 卡片。
- `chat.message.completed`：完成 assistant message。
- `run.completed` / `run.failed` / `run.cancelled`：结束 run 生命周期。

live 事件和恢复 replay 要走同一套投影逻辑，否则刷新后工具卡片、HITL 卡片和任务面板会变形。heartbeat comment 不能当状态事件。

## 9. 刷新恢复和取消

刷新或重新进入 session 时：

```text
GET /v1/agent/sessions/{session_id}/active-run
  → 如果有 active run_id
  → runAgentChatStream(existingRunId=run_id, hydrateMessagesFromReplay=true)
  → GET /v1/agent/runs/{run_id}/events
```

如果没有 active run，前端同步历史消息和画布状态。恢复 active run 时，前端不会再发新的用户输入。

已知 `run_id` 走 cancel；只知道 `client_request_id` 走 cancel-by-request。前端取消时还会 abort 当前 SSE，并记录用户主动取消，避免马上 resume 同一个 run。

## 10. 和画布运行链路的关系

Agent 可以通过 `run_workflow`、`get_workflow`、`edit_workflow` 等工具操作画布。这些工具产生的 workflow 事件可以被桥接成 Agent SSE 的 `workflow.*`，让聊天里显示节点进度。

但边界必须清楚：

```text
Agent SSE
  → 聊天 UI、工具卡、HITL、部分 workflow 状态投影

画布 workflow WebSocket
  → 某个 flow_task_id 的完整可恢复运行事件
```

Agent SSE 不替代画布可恢复 WebSocket。

## 11. 文件编写顺序

先有 session 长期事实，再有 run 运行时事实，再有 SSE 协议，最后接前端 UI：

1. `creato/schemas/session.py`
2. `creato/session/manager.py`
3. `creato/services/agent_redis_run_store.py`
4. `creato/core/events.py`
5. `creato/core/loop.py`
6. `creato/api/server.py`
7. 前端 types、API、run store、event replay、stream、controller

不要先写一个流式聊天组件，再回头补幂等、恢复和历史重建；也不要把创建 run 和订阅 SSE 合并成一个接口。

## 12. 面试 1 分钟口述

OpenCreator 的 Agent 聊天不是一个 POST 直接流式返回整段对话。前端发送消息时先准备 `session_id` 和 `client_request_id`，再 `POST /v1/agent/runs`。后端按 `user_id + session_id + client_request_id` 做幂等，再用 session lock 保证同一会话只有一个 active task-backed run，然后创建 Redis run 并在后台启动 AgentLoop。前端接着 `GET /v1/agent/runs/{run_id}/events`，用 `Last-Event-ID` 从 Redis Stream 续接。AgentLoop 会循环调用 LLM 和工具，把 `chat.message.delta`、`tool.*`、`workflow.*` 写成 SSE 事件。HITL 时 pending tool call 写入 session metadata，下一条用户输入变成 tool result 后继续。Redis Stream 只是 24 小时、最多约 2000 条的短期窗口；窗口过期返回 410，前端必须回 Mongo chat projection。刷新先查 active-run，有就只订阅旧 run，没有就拉历史消息。这套协议和画布 WebSocket 的 `attach_flow` 不是一回事。

## 13. 面试官追问怎么答

如果问为什么不直接一个接口流式返回：

因为创建 run 要幂等、互斥、可取消、可恢复。把执行和订阅拆开，前端超时重试、刷新恢复和取消未完成创建才有落点。

如果问 session 和 run 为什么要分开：

session 跨多轮，保存历史、HITL 和 pipeline；run 只服务一次输入。用一个 `isRunning` 会把互斥、续接和历史重建搅在一起。

如果问 HITL 为什么不把 run 改成长期 waiting：

工具 HITL 的恢复点在 session metadata。下一条用户输入属于同一 session，不一定属于同一个 task-backed run 的公开状态机。不要只靠 run status 判断。

如果问 `Last-Event-ID` 过期怎么办：

不能死循环重连。返回 410 后重新同步 Mongo 历史和必要 workflow 状态。

如果问 Agent SSE 能不能替代画布 WebSocket：

不能。Agent SSE 只投影聊天和部分 workflow 卡片。某个 `flow_task_id` 的完整可恢复事件仍走 Publisher Event Store。

如果问旧 `/v1/agent/chat` 还能不能用：

不能当主链。现网返回 `410 USE_AGENT_RUNS`。

## 14. NovelComic 当前实现自查

只看本章，NovelComic 当前还没有打通 Agent 会话主链：

- 前端 `AssistantProvider` 能消费首页 handoff，并调用画布 `runAll()`。
- `novelcomic-agent` 只有包结构和配置骨架。
- 还没有 `POST /v1/agent/runs`、SSE events、RedisRunStore、AgentLoop 和 session 分层存储。
- 还没有 `client_request_id` 幂等、active run 互斥、`Last-Event-ID` 续接和 cancel-by-request。

现有测试只覆盖了首页 handoff 被画布侧消费。这属于上一组首页 Composer 和画布运行入口，不是本章 Agent run。

本章验收口径：

如果只验收“首页输入能交到画布并触发一次 runAll”，这不叫 Agent 会话完成。  
如果按 OpenCreator 现网模型验收，必须拆成创建 run、订阅 SSE、Redis 短期事件、Mongo 长期事实、刷新找回 active run，以及窗口过期后的历史同步。不要把旧 `POST /v1/agent/chat` 复活成新的主链路。
