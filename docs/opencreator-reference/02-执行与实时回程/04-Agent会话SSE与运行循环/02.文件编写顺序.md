# Agent 会话、SSE 与运行循环：文件按什么顺序写

对照 [00-Agent会话SSE与运行循环技术点.md](./00-Agent会话SSE与运行循环技术点.md) 和 [01-Agent会话SSE与运行循环.md](./01-Agent会话SSE与运行循环.md)。01 讲运行时谁调谁，这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖，不按用户看到聊天气泡的顺序。

本文只写“Agent 会话、SSE 与运行循环”。画布登录、workflow run、DAG、可恢复 WebSocket 已经在前面几组解决；这里继续往下接：Agent session、run 幂等、Redis Stream SSE、AgentLoop、HITL、前端聊天 runtime 和刷新恢复。

先背这份链路。Agent 后端文件写 `opencreator-agent/` 仓库相对路径；前端文件从 `src/` 写起。

```text
creato/schemas/session.py
  → creato/session/manager.py
  → creato/services/agent_redis_run_store.py
  → creato/core/events.py
  → creato/agents/main/profile.py
  → creato/core/loop.py
  → creato/api/server.py
  → src/features/agent-chat/shared/agent-chat-types.ts
  → src/features/agent-chat/api/agent-chat.api.ts
  → src/features/agent-chat/runtime/agent-run-store.ts
  → src/features/agent-chat/runtime/stream/agent-chat-event-replay.ts
  → src/features/agent-chat/runtime/stream/agent-chat-stream.ts
  → src/features/agent-chat/hooks/use-agent-run-controller.ts
  → src/features/agent-chat/runtime/use-agent-chat.ts
```

这条顺序有一个原则：先有 session 长期事实，再有 run 运行时事实，再有 SSE 协议，最后接前端 UI。不要先写一个流式聊天组件，再回头补幂等、恢复和历史重建；也不要把创建 run 和订阅 SSE 合并成一个接口。

## 写之前先有的东西

缺这些不要开始本组：

1. 登录态和 `__opencreator_jwt` 已经能进入 Agent API。
2. 前端已有画布 `flowId`、nodes、edges，能生成 Agent 私有 `workflow_snapshot`。
3. Redis 可用于 run meta、request 幂等、active run、Stream 和取消标记。
4. Mongo 有 Agent session 相关集合。
5. Agent 能调用 LLM provider。
6. Agent 工具注册体系已经能加载 main profile。
7. 前端聊天面板已经能渲染文本、结构化 part、工具卡片和 HITL 卡片。

做完基线：用户能打开画布和 Agent 面板，但发送消息可以尚未跑通；这时还不应该写假流式 UI。

## 6. 写 AgentLoop

OpenCreator 对照：

[loop.py](../../../../../opencreate/opencreator-agent/creato/core/loop.py)

先写并发骨架：

```text
run()
  → session lock
  → CREATO_MAX_CONCURRENT_REQUESTS gate
  → _process_message()
```

再写 `_process_message()`：

```text
SessionManager.get_or_create()
  → 恢复 pending_hitl / task store
  → 注入 hook / pipeline constraints
  → collect_uploaded_files()
  → retrieve memory
  → microcompact_history()
  → trim / compress history
  → build_messages()
  → early persist user message
  → _run_agent_loop()
  → save durable session
```

再写 `_run_agent_loop()`：

```text
LLM
  → text / thinking delta
  → tool_calls
  → tool.started
  → execute tool
  → tool.completed / tool.failed / tool.event
  → tool result 回填
  → 下一轮
```

HITL：

```text
工具 interrupt
  → session.metadata["pending_hitl"]
  → 返回空 final_content

下一条用户输入
  → replace_last_tool_result()
  → append hitl.resolved tool_event
  → 清 pending_hitl
  → 继续 loop
```

做完：单轮文本对话能完成；工具调用能产生事件；HITL 能暂停并在下一条用户消息恢复。

## 完整验收顺序

按这个顺序验完整链路：

1. 未登录调用 Agent API 被拒绝。
2. `POST /v1/agent/runs` 缺少必要字段时返回可解释错误。
3. 同一个 `client_request_id` 重试返回同一个 `run_id`，不重复开 loop。
4. 同一个 session 已有 active run 时，新请求返回 `409` 或复用 `active_run_id`。
5. `GET /v1/agent/runs/{run_id}/events` 校验用户归属，不能订阅别人的 run。
6. SSE `Content-Type` 是 `text/event-stream`。
7. 没有事件时发送 heartbeat comment，不改变 UI。
8. `chat.message.delta` 能流式显示文本。
9. `tool.started` / `tool.completed` 能显示工具卡片。
10. `tool.event=hitl.request` 能显示 HITL 卡片。
11. HITL 回复后，下一条用户消息能注入 tool result 并继续 loop。
12. `workflow.node_status` 能更新聊天中的 workflow 卡片，必要时同步画布状态。
13. `run.completed` 后 SSE 正常结束，active run 被清理。
14. 刷新页面后，`active-run` 能找回正在跑的 run，并继续订阅 SSE。
15. `Last-Event-ID` 在恢复窗口内能补事件。
16. 恢复窗口过期返回 `410 RESUME_WINDOW_EXPIRED`，前端重新拉历史而不是无限重试。
17. 用户取消时 abort SSE，并调用 run cancel 或 cancel-by-request。
18. 旧 `POST /v1/agent/chat` 返回 `410 USE_AGENT_RUNS`，不会被新前端继续使用。

完整验收要覆盖 run 幂等、session 互斥、SSE 续接、AgentLoop、SessionManager 持久化、HITL、取消和刷新恢复；只看到文本能流式输出不算完成。验收顺序按事实层推进，不按组件截图推进。
