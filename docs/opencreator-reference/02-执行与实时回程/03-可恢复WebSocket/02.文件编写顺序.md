# 可恢复 WebSocket：文件按什么顺序写

对照 [00-可恢复WebSocket技术点.md](./00-可恢复WebSocket技术点.md) 和 [01-可恢复WebSocket.md](./01-可恢复WebSocket.md)。01 讲运行时谁调谁，这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖，不按浏览器 WebSocket 生命周期排序。

本文只写“可恢复 WebSocket”。前面几组已经解决登录、画布项目加载、run 创建、Consumer 执行、事件回程到 Publisher Event Store。这里继续往下接：事件存储、WebSocket 协议、cursor replay、前端 handler、心跳重连和刷新恢复。

先背这份链路。Publisher 文件写仓库根相对路径；前端文件从 `src/` 写起。

```text
services/workflow_event_store.py
  → database/mq.py
  → controller/v2/flow_runs.py
  → src/lib/workflow-reconnect-policy.ts
  → src/lib/workflow-resumable-websocket.ts
  → src/components/headBar/hooks/useWebSocketFlow.ts
  → src/components/headBar/hooks/useWorkflowRunner.ts
  → src/components/canvas/workflow-runtime-provider.tsx
  → src/lib/workflow-side-effect-claim.ts
```

这条顺序有一个原则：先有可 replay 的事件事实，再写 WebSocket 读口，再把事件接回画布状态。不要先写一个裸 socket，再回头补 Event Store。

---

## 写之前先有的东西

缺这些不要开始本组：

1. 登录态和 `__opencreator_jwt` 已经能进入业务请求。
2. `/canvas/{flowId}` 已经能读取自己的 nodes / edges。
3. `POST /api/v2/flow/runs` 已经能返回 `flow_task_id`、`flow_run_id`、`trace_id`。
4. Consumer 已经能把执行事件发到 RabbitMQ v2 reply queue。
5. Publisher 已经能消费 v2 reply queue。
6. Redis 可用于 Stream、Pub/Sub、TTL 和 connection generation。
7. 前端已经有节点状态 handler，能把 `running` / `success` / `select` 写回画布 store。

做完基线：点击 Run 后，后端能产生事件，但前端可以还没通过可恢复 WebSocket 收到。

## 1. 先写 Event Store

OpenCreator 对照：

[workflow_event_store.py](../../../../../opencreate/opencreator-publisher/services/workflow_event_store.py)

这份文件先写，因为 WebSocket 恢复能力完全依赖它。

要写的能力：

```text
append_event(flow_task_id, event)
  → ensure_event_identity()
  → 按 event_id 去重
  → XADD 到 Redis Stream
  → 返回 event_cursor
  → 记录 event_id → event_cursor
  → 设置 TTL
  → PUBLISH 新事件通知

replay(flow_task_id, cursor)
  → 校验 cursor
  → 读取 cursor 后面的事件
  → 按顺序返回

read_live(flow_task_id, cursor)
  → 从最新 cursor 后继续阻塞读
  → 给 live 阶段使用
```

必须守住：

- 同一个 `event_id` 重复 append，只返回原 cursor，不写第二份事件。
- `event_cursor` 用 Redis Stream ID。
- replay 的顺序必须和 Stream 顺序一致。
- Pub/Sub 只是通知，不能替代 Stream。

做完：手动 append 三个事件后，带第二个 cursor replay，只返回第三个事件；重复 append 第一个事件不会多一条。

## 2. 再把 RabbitMQ 回程写入 Event Store

OpenCreator 对照：

[database/mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py)

Publisher 消费 Consumer 回程时，要先落 Event Store，再 ACK RabbitMQ。

顺序：

```text
consume v2 reply
  → 校验 protocol_version=2
  → WorkflowEventStore.append_event()
  → 更新 flow_task.last_event_cursor / status
  → ACK RabbitMQ
```

不要反过来先 ACK。否则 Publisher 崩在 ACK 后、append 前，浏览器永远 replay 不到这条事件。

做完：Consumer 发来的事件能稳定进入 Redis Stream；Publisher 重启后不会因为重复消息写出重复事件。

## 3. 写 WebSocket endpoint 的协议骨架

OpenCreator 对照：

[flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)

先只写协议骨架，不急着接前端 UI。

路由：

```text
WS /api/v2/flow/runs/{flow_task_id}/events/{connection_id}
```

服务端顺序固定：

```text
accept()
  → 15 秒内等待 auth
  → 校验 auth.event_type == "auth"
  → JwtService 校验 token
  → WorkflowRunV2Service.get_run_summary(user_id, flow_task_id)
  → 发送 authenticated
  → 等 attach_flow
  → 校验 flow_task_id / connection_id / cursor
  → replay
  → resume_ready
  → event loop
```

关闭码先定下来：

| code | 场景 |
| --- | --- |
| `4401` | auth 缺失或 JWT 验证失败 |
| `4404` | run 不存在或不属于当前用户 |
| `4400` | attach、cursor 或协议字段无效 |
| `4409` | cursor 超出保留窗口且无法恢复 |
| `4001` | 同 connection 被新 generation 替换 |
| `1011` | 服务端内部错误 |

做完：用测试客户端连接后，不发 auth 会关闭；发合法 auth 后能收到 `authenticated`；attach 合法后能收到 `resume_ready`。

## 4. 接上 replay 和 live loop

仍在 [flow_runs.py](../../../../../opencreate/opencreator-publisher/controller/v2/flow_runs.py)。

认证和 attach 都通过后，先 replay：

```text
events = WorkflowEventStore.replay(flow_task_id, last_event_cursor)
  → send 每个 event
  → send resume_ready
```

再进入 live loop：

```text
while socket alive:
  → 从 Event Store 读取最新 cursor 后的事件
  → 发送给前端
  → 等 Pub/Sub 通知或短轮询
```

注意：

- `resume_ready` 必须在 replay 完之后发。
- Pub/Sub 丢了也不能丢事件，下一轮读取 Stream 要能追上。
- event loop 不重新判断 DAG，不改 Consumer 状态，只投递事件。

做完：先 append 旧事件再 attach，前端能先收到旧事件，再收到 `resume_ready`；attach 后 append 新事件，前端能继续收到。

## 5. 写 connection generation

generation 属于后端 WebSocket 连接管理，具体持久化能力放在 [workflow_event_store.py](../../../../../opencreate/opencreator-publisher/services/workflow_event_store.py)。

要实现的语义：

```text
WorkflowEventStore.claim_connection_generation(flow_task_id, connection_id)
  → generation + 1
  → 当前 socket 记录 generation

WorkflowEventStore.is_current_generation(flow_task_id, connection_id, generation)
  → 当前 generation 仍是最新
       → 可以发送
  → 已被新连接替代
       → close(4001)
```

做完：同一个 `flow_task_id + connection_id` 开第二条连接，旧连接会退出，不会两条连接同时推同一批事件。

## 7. 写前端底层 transport

OpenCreator 对照：

[workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts)

这份文件只负责协议和连接，不写节点业务。

要写的行为：

```text
connect(flowTaskId, options)
  → 生成 connectionId
  → new WebSocket({NEXT_PUBLIC_WEBSOCKET_URL}/api/v2/flow/runs/{flowTaskId}/events/{connectionId})
  → onopen 后 getToken("__opencreator_jwt")
  → send auth
  → 收 authenticated 后 send attach_flow
  → 收 resume_ready 后标记 connected
  → 收普通 event 后交给 onEvent
```

本地 cursor：

```text
getCursor(flowTaskId)
  → sessionStorage["workflow:v2:cursor:{flowTaskId}"]

setCursor(flowTaskId, cursor)
  → handler 成功后才写
```

前端主动关闭码：

| code | 场景 |
| --- | --- |
| `4000` | 心跳超时 |
| `4001` | 消息 JSON 解析失败 |
| `4002` | 业务 handler 抛错 |
| `4003` | 获取 token 失败 |
| `4004` | 连接超时 |
| `4005` | 重置 cursor 后换连接 |
| `4007` | 连接后 30 秒内没有收到 `resume_ready` |

做完：transport 能独立连接 mock endpoint，完整跑完 auth、attach、resume_ready，并且 handler 成功后才保存 cursor。

## 8. 补心跳和重连

仍在 [workflow-resumable-websocket.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-resumable-websocket.ts)。

心跳：

```text
每 30 秒 ping
  → 10 秒没有任何返回帧
  → close(4000)
  → reconnect
```

重连：

```text
1s → 2s → 4s → 8s → 15s → 30s
  → 乘 0.8-1.2 jitter
  → 最多尝试 10 次
```

页面和网络状态：

- `document.hidden` 时暂缓主动 ping。
- 浏览器 `offline` 时不空转重连。
- 收到 `online` 或页面重新可见时尝试恢复。

做完：断网后不会疯狂重连；恢复网络后会带上最后 cursor 重新 attach。

## 13. 最后补 cursor 过期和 reset

后端如果返回 cursor 过期：

```text
close 4409
或发送 resume_error(cursor_expired)
```

前端不要拿同一个 cursor 无限重连。

可选处理顺序：

```text
收到 cursor_expired
  → 停止当前 transport
  → 清理该 flow_task_id 的 cursor
  → 查询 run 当前状态
  → 如果有 snapshot，用 snapshot 恢复
  → 否则提示刷新或重新打开运行视图
```

做完：Event Store TTL 过期后，前端不会陷入无限重连；用户能看到明确恢复失败状态。

## 完整验收顺序

按这个顺序验完整链路：

1. 未发 auth 首帧，WebSocket 在超时后关闭。
2. JWT 无效，服务端关闭 `4401`。
3. JWT 有效但 run 不属于当前用户，服务端关闭 `4404`。
4. auth 成功后收到 `authenticated`。
5. attach cursor 无效，服务端关闭 `4400`。
6. attach 合法后，服务端先 replay cursor 后面的旧事件。
7. replay 完成后收到 `resume_ready`，前端才显示 connected。
8. live 阶段新事件能继续推到前端。
9. handler 成功后才保存 cursor；handler 抛错不推进 cursor。
10. 刷新页面后，前端查询 active run，并用 cursor 补回断线期间的事件。
11. 同一个 `flow_task_id + connection_id` 开新连接，旧连接退出。
12. 心跳超时会重连；离线时不疯狂重试；恢复在线后能继续 attach。
13. 同一 `event_id` replay 多次，节点状态不乱，副作用不会重复触发。
14. cursor 过期时不会无限重连，会进入明确恢复失败或 reset 流程。

完整验收要覆盖认证、归属、attach、replay、live、cursor、去重、重连和刷新恢复；只看到 `onopen` 不算完成。
