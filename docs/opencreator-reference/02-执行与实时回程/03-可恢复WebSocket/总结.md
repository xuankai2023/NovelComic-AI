# 可恢复 WebSocket 全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“socket 能 onopen”，而是前端拿到 `flow_task_id` 之后，怎么先认证再 attach，Publisher 怎么从 Event Store 按 cursor 回放，handler 成功后怎么推进 cursor，以及刷新或网络抖动后怎样回到同一批事件处理结果。

先把一句话背下来：

OpenCreator 的可恢复 WebSocket 是 workflow run 的事件读口。前端先用 REST 创建 run，拿到 `flow_task_id`；再连接 WebSocket，首帧认证，第二帧 attach；Publisher 从 Event Store 按 cursor 回放旧事件，再继续推实时事件。真正成功点是 `resume_ready`，不是 `onopen`。

## 0. 先分清四个状态

`onopen`：浏览器和服务端握手成功。

`authenticated`：JWT 已通过，并确认 run 属于当前用户。

`resume_ready`：cursor 后的事件已经 replay 完，可以接 live events。

`connected`：前端运行态认可这条连接可用。

`onopen` 不等于连接已恢复。面试时一定要把这四个状态讲开。

## 1. 前端：run 创建后才建连

运行入口在 `useWorkflowRunner.ts`。用户点击 Run 后，前端先走 REST：

```text
runAll()
  → command journal 生成 command_id
  → postCreateWorkflowRun()
  → POST /api/v2/flow/runs
  → 返回 flow_task_id / flow_run_id / trace_id
```

只有拿到 `flow_task_id` 后，才进入事件连接：

```text
startWebSocketForFlow(flow_task_id)
```

WebSocket 不负责创建 run，也不负责把 nodes / edges 提交给后端。它只负责读取这个 run 的事件。

## 2. useWebSocketFlow 管生命周期和分发

`useWebSocketFlow.ts` 负责：

- 启动某个 `flow_task_id` 的事件连接。
- 注册各类事件 handler。
- 处理 `resume_ready`、`resume_error`、`flow_snapshot`、`flow_killed`。
- 把节点事件转给 `useWorkflowRunner` 和节点状态管理逻辑。
- 刷新恢复时带上上次 cursor 重新 attach。

这层不直接实现底层 socket 协议。底层协议在 `workflow-resumable-websocket.ts`。

## 3. workflow-resumable-websocket 实现协议

连接地址：

```text
{NEXT_PUBLIC_WEBSOCKET_URL}/api/v2/flow/runs/{flowTaskId}/events/{connectionId}
```

物理连接打开后，前端第一步取 JWT，然后发送 auth：

```json
{
  "event_type": "auth",
  "protocol_version": 2,
  "token": "<__opencreator_jwt>"
}
```

收到 `authenticated` 后，再发送 attach：

```json
{
  "event_type": "attach_flow",
  "protocol_version": 2,
  "flow_task_id": "...",
  "connection_id": "...",
  "last_event_cursor": "..."
}
```

如果本地没有 cursor，就传 `null` 或等价空值，让服务端从头恢复。

## 4. Publisher：WebSocket 入口仍在 flow_runs.py

它和 run 的 REST 接口放在同一个 controller 下：

```text
POST /api/v2/flow/runs
POST /api/v2/flow/runs/{flow_task_id}/continue
POST /api/v2/flow/runs/{flow_task_id}/cancel
GET  /api/v2/flow/runs
GET  /api/v2/flow/runs/{flow_task_id}
WS   /api/v2/flow/runs/{flow_task_id}/events/{connection_id}
```

WebSocket endpoint 的核心顺序：

```text
accept()
  → 等 auth
  → JwtService 校验 token
  → get_run_summary(user_id, flow_task_id)
  → 发送 authenticated
  → 等 attach_flow
  → 校验 cursor
  → replay
  → 发送 resume_ready
  → 进入 event loop
```

JWT 合法不代表一定能订阅。服务端还要确认这个 run 属于当前用户。

## 5. Event Store 负责 replay 和 live 追赶

Consumer 的执行事件不是直接推给浏览器，而是先进入 Publisher：

```text
Consumer outbox
  → RabbitMQ v2 reply queue
  → Publisher database/mq.py
  → WorkflowEventStore.append_event()
  → ACK RabbitMQ
```

Event Store 写入 Redis Stream 后，生成 `event_cursor`，类似 `1710000000000-0`。

WebSocket attach 时，服务端按 `last_event_cursor` 读取后面的事件，replay 完成后发送 `resume_ready`。连接进入 live 阶段后，继续用 `read_live()` 从最新 cursor 往后追。Pub/Sub 只负责唤醒等待中的连接，真正的事件正文仍从 Redis Stream 读。

浏览器断线时，Consumer 和 Publisher 仍继续处理事件。浏览器回来后用 cursor 补读。

## 6. 前端 handler 成功后才推进 cursor

正确顺序：

```text
收到 event
  → 检查 event_id 是否已处理
  → 调业务 handler
  → handler 成功
  → 保存 event_cursor
```

保存位置按 `flow_task_id` 放进 sessionStorage。如果 handler 抛错，连接会关闭，cursor 不推进。下次重连还能 replay 这一帧。

这是可恢复语义最容易写错的地方。cursor 提前越过失败事件，画布会留下永久状态洞。

## 7. 前端 handler 才真正改变画布

WebSocket transport 不直接知道节点怎么变色。它只把事件交给上层。

`useWebSocketFlow.ts` 会分发：

- `start_flow`
- `node_status`，再按 `ready` / `running` / `success` / `select` / `pause` / `failed` 分支处理
- `llm_model_ready`
- `llm_model_status`
- `finish_flow`
- `flow_killed`
- `workflow_error`

所以可恢复 WebSocket 的目标不是“连接保持不断”，而是“断了也能恢复到同一批事件处理结果”。

## 8. 心跳、重连和 generation

连接进入 live 阶段后，前端大约每 30 秒 ping；10 秒内没收到任何帧就按心跳超时重连。页面 hidden 时主动心跳会收敛。

重连时复用同一个 `flow_task_id`，重新生成或沿用连接身份，并带上本地保存的 `last_event_cursor`。重连成功仍以 `resume_ready` 为准。

服务端为 `(flow_task_id, connection_id)` 维护 generation。同一个逻辑 connection 被新的物理 socket 占用时，旧连接关闭，避免两条 socket 同时向同一个前端运行态发事件。

## 9. cursor 过期是协议错误

如果前端带来的 cursor 已经超出保留窗口，并且服务端也不能提供 snapshot 恢复，服务端会返回恢复失败或关闭连接，常见是 `4409`。

这时不能无限重连同一个 cursor。前端要把它当成需要重置运行视图、重新查询 run 状态或提示用户刷新的场景。

常见关闭码：

- `4401`：缺少 auth 或 JWT 失败。
- `4404`：run 不存在或不属于当前用户。
- `4400`：attach / cursor 协议无效。
- `4409`：cursor 超出保留窗口。
- `4000`：前端心跳超时。
- `4002`：业务 handler 抛错。
- `4007`：30 秒内没有 `resume_ready`。

## 10. 服务端 event loop 只做投递

WebSocket 服务端循环不重新计算 DAG，也不决定节点是否 ready。

它只做：

```text
从 Event Store 读取事件
  → 发送给当前连接
  → 等 Pub/Sub 通知或周期性追赶
  → 连接关闭时退出
```

DAG 的执行事实在 Consumer，事件事实在 Event Store。WebSocket 只是事件事实的一个可恢复读口。

## 11. 刷新恢复靠 active run 和 cursor

页面刷新后，物理 socket 已经断开，但 run 可能还在继续。

```text
GET /api/v2/flow/runs?flow_id=...&status=active
  → 找到 active flow_task_id
  → 读取 sessionStorage cursor
  → 重新建立 WebSocket
  → attach_flow(last_event_cursor)
```

关闭 WebSocket 不等于停止任务。停止任务要走 `POST /api/v2/flow/runs/{flow_task_id}/cancel`。

## 12. v1 和 v2 不要混用

旧 v1 路径 `/api/v1/flow/flow_task/{ws_id}` 把命令和结果绑在普通 WebSocket 上，依赖实例内连接表，没有 v2 cursor 恢复语义。

当前主链是：

```text
REST 命令
  + Redis Stream 命令队列
  + RabbitMQ 结果回程
  + Publisher Redis Event Store
  + v2 可恢复 WebSocket
```

阅读代码时看到 v1 文件仍存在，不表示当前画布 Run 仍走 v1。写 NovelComic 时不要把 run 创建、事件恢复和节点状态全部塞回一条普通 socket。

## 13. 文件编写顺序

1. 先保证 Event Store 能 append / replay / 去重。
2. Publisher `flow_runs.py` 接 WebSocket：auth → 归属 → attach → replay → `resume_ready`。
3. 前端 `workflow-resumable-websocket.ts` 实现协议。
4. `useWebSocketFlow.ts` 分发事件。
5. handler 成功后才写 cursor。
6. 最后补心跳、重连策略、generation、关闭码和 cursor 过期。

不要先写一个裸 socket，再回头补 Event Store。

## 14. 面试 1 分钟口述

OpenCreator 的可恢复 WebSocket 不属于页面打开，而属于某一次 workflow run。前端先 `POST /api/v2/flow/runs` 拿到 `flow_task_id`，再连 `WS /api/v2/flow/runs/{flow_task_id}/events/{connection_id}`。浏览器原生 WebSocket 不能方便地带 Authorization，所以 token 放在第一帧 `auth` 里；服务端验 JWT 后还要按 `user_id + flow_task_id` 确认 run 归属。认证成功后发 `attach_flow(last_event_cursor)`，Publisher 从 Redis Stream Event Store replay 漏掉的事件，然后发 `resume_ready`。前端只有这时才把连接标成 available。事件 handler 成功后才把 cursor 写入 sessionStorage；handler 失败就断开，重连还能补回这一帧。刷新后查 active run，再用 cursor attach。关闭 socket 不等于 cancel。

## 15. 面试官追问怎么答

如果问为什么 token 不放 URL：

因为 query token 容易进日志、代理和历史记录。服务端先接受连接，再要求首帧 auth，既能绕过浏览器 WebSocket 不能自定义 header 的限制，也能在认证失败时立刻关连接。

如果问为什么 `onopen` 不够：

之后还有取 token、验 JWT、查 run 归属、校验 cursor、replay。任何一步失败都不能算连接可用。

如果问 cursor 和 event_id 区别：

cursor 是读位置，event_id 是逻辑事件身份。重复 append 同一 event_id 不能再写出第二条事件；前端还要用 event_id 避免同一连接里 replay 和 live 打两次 handler。

如果问 handler 失败为什么不能先存 cursor：

存了就等于告诉系统“这帧处理完了”。下次重连不会再给这帧，画布缺的状态补不回来。

如果问 Pub/Sub 能不能当事件仓：

不能。它只叫醒在线连接。可靠事实是 Redis Stream。通知丢了，下一轮 read 还能追上。

如果问别人能不能监听我的 run：

不能。即使 JWT 合法，也必须 `get_run_summary(user_id, flow_task_id)` 通过。否则关连接，通常是 `4404`。

## 16. NovelComic 当前实现自查

只看本章，NovelComic 当前已经具备协议骨架：

- 前端 `workflow-resumable-websocket.ts` 能按 `flow_task_id` 建连。
- 首帧发 JWT auth，随后发 `attach_flow`，并按 `flow_task_id` 保存 cursor。
- Publisher `flow_runs.py` 已有 WebSocket 入口，能等 auth、校验 run、replay。
- `useWebSocketFlow` 能处理 `resume_ready` 并分发节点事件。
- `useWorkflowRunner` 能在刷新后查询 active run。

仍需按本章继续补齐：

- 心跳、退避抖动、页面 hidden 策略和完整关闭码还需要对齐。
- generation 防止旧连接乱入还需要继续确认。
- cursor 过期后的 snapshot 恢复或重置运行视图还不完整。
- handler 失败不推进 cursor 的行为需要端到端验收。
- 刷新后“active run + cursor replay 让节点重新亮灯”还缺完整验收。

本章验收口径：

如果只验收“创建 run 后能连上 v2 WebSocket，并且首帧认证、第二帧 attach”，当前骨架已经具备。  
如果按 OpenCreator 完整可恢复连接验收，还必须做到 replay、`resume_ready`、handler 成功后推进 cursor、刷新补事件、归属隔离和 cursor 过期处理。
