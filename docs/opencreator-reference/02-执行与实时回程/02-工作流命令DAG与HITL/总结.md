# 工作流命令、DAG 与 HITL 全链路笔记

这份不是文件清单，是给面试和迁移用的链路笔记。要讲清楚的不是“有一个 /runs 接口”，而是点击 Run 之后，命令怎么获得稳定身份，Publisher 怎么只写命令事实，Consumer 怎么按 durable DAG 找 ready 节点，模型结果怎么聚合成 success / failed / select，以及用户选择后怎样通过 continue 继续跑后继。

先把一句话背下来：

OpenCreator 的工作流执行分两条通道：命令通道把 start / continue / cancel 从浏览器送到 Consumer；事件通道把节点状态从 Consumer 送回浏览器。HITL 夹在 DAG 中间：多候选时节点进入 `select`，用户选完再发 `continue`，Consumer 覆盖 `selected_outputs` 后重新 resume。

## 0. 先分清三层事实

`Publisher 命令事实` 是 `flow_task` 和 `workflow_command`。它负责幂等、公开状态和派发。它不是 DAG 执行真相。

`Consumer 执行事实` 是 durable run 和 durable node。它负责 ready 节点、模型计划和 HITL 选择写回。它不是浏览器连接表。

`Publisher 事件事实` 是 Event Store 里的 `event_id` 和 cursor。它负责 replay，不重新计算节点状态。

面试时一定要把这三层讲开。只写一个 `run_status`，入口重试、节点选择、断线恢复都会抢同一个字段。

## 1. 前端：发命令，不判 DAG

前端运行域主要在：

- `workflow-command-journal.ts`
- `api/modules/flow.ts`
- `useWorkflowRunner.ts`
- `useWebSocketFlow.ts`
- `workflow-resumable-websocket.ts`
- `workflow-runtime-provider.tsx`

用户点击 Run，`useWorkflowRunner` 不应该直接裸调接口。它先拿命令身份：

```text
getOrCreateWorkflowCommand(operationKey, request, "wf")
```

同一次点击在网络超时后仍然复用同一个 `command_id`。`continue` 和 `cancel` 也一样要走 command journal。

`flow.ts` 只封装传输：

```text
postCreateWorkflowRun()
postContinueWorkflowRun()
postCancelWorkflowRun()
getWorkflowRun()
getActiveWorkflowRuns()
```

这些函数只负责 URL、body、JWT 和返回体。不要在 API 层判断节点是否 ready，也不要把 `202` 当 success。

## 2. Publisher：收命令，写事实，派发

`CreateWorkflowRunRequest` 至少要固定：

| 字段 | 用途 |
| --- | --- |
| `client_request_id` | 前端操作身份 |
| `command_id` | 幂等命令身份 |
| `flow_id` | 所属画布项目 |
| `flow_task` | 本次执行的 nodes / edges |
| `start_ids` / `end_ids` | 子图范围 |

`create_run()` 的 start 顺序：

```text
command_id = req.command_id or req.client_request_id
  → _resolve_command_replay()
  → _validated_graph()
  → 生成 flow_task_id / flow_run_id / trace_id
  → insert flow_task
  → insert workflow_command
  → dispatch_command()
```

`flow_task` 给前端查询和公开状态用。`workflow_command` 给幂等、派发、恢复用。两行一起写，避免“前端有 task 但 dispatcher 找不到 command”。

入口会拒绝环，但不会决定每个节点何时执行。

## 3. continue 和 cancel 也是命令

`continue_run()` 不是直接改 Consumer 节点。它先在 Publisher 做 CAS：

```text
flow_task.status 必须是 waiting_for_selection
  → insert workflow_command
  → flow_task.status = running
  → dispatch
```

`cancel_run()`：

```text
insert workflow_command
  → flow_task.status = cancel_requested
  → dispatch
```

真正 SELECT → SUCCESS、真正 kill 节点，都在 Consumer。断开 WebSocket 不会触发这条链。

## 4. dispatch 发布到 Redis Stream

`dispatch_command()` claim 住 `workflow_command` 后调用：

```text
FlowService.enqueue_flow_task()
  → FlowTask.run_flow.publish()
```

Publisher 的 `tasks/flow.py` 是 producer。队列名是 `run_flow`，broker 是 Redis Stream。Consumer 仓同名 `tasks/flow.py` 才执行。

## 5. Consumer：claim inbox 后初始化 durable run

Consumer `FlowTask.run_flow()` 收到 Stream 消息：

```text
校验 protocol_version=2
  → command_id 必须存在
  → FlowCommandInboxService.claim_command()
```

claim 不到就返回。这样 Redis Stream 重投不会重复初始化 run，也不会重复 cancel。

start 命令执行：

```text
init_flow_run()
  → init_nodes()
  → seed_user_selection_outputs()
  → publish start_flow
  → FlowResumeTask.handle_resume(reason="start")
  → mark_start_initialized()
```

`start_initialized` 是恢复边界。命令 claim 到，不代表节点表已经铺完。

## 6. FlowResumeTask 找 ready 节点

`handle_resume()`：

```text
拿 run lock
  → run 必须是 running
  → ready_nodes()
  → 按批处理节点
  → finish_if_all_terminal()
```

ready 的含义不是“所有前驱都存在”，而是：

- 节点本身还没终态。
- 节点属于本次 active 子图。
- active 前驱已完成。
- 非 active 前驱的产物已经通过 `user_selection` 注入。

`start_ids / end_ids` 只限定本次子图，完整前后继仍要保存。

## 7. 模型节点先计划再提交

模型节点处理顺序：

```text
加载已有 execution_plans
  → 没有则 ModelInvocationPlanner.plan_node()
  → 写 expected_result_ids / execution_plans
  → mark node running
  → publish node_status=running
  → ModelInvocationService submit
```

计划先落库，是为了 callback、恢复、重试都能认同一批 `result_id`。

如果先调模型再补记录，超时重试会产生第二批结果身份，callback 回来时找不到应该聚合到哪个节点。

## 8. callback 后聚合节点

provider 回调更新 invocation 后，进入 `NodeAggregationService`：

```text
waiting：还有结果没回来
failed：没有成功结果
select：多候选 + 有后继 + 不是 end_node
success：可以继续后继
```

`select` 时，Consumer run 仍是 running。Publisher 公开 `flow_task` 会被回程事件推到 `waiting_for_selection`。

`select` 不是异常，也不是整图完成。

## 9. 一条 HITL 选择怎么走

```text
模型节点有多候选输出
  → NodeAggregationService 判定 select
  → FlowNodeStateService 把节点状态写 select
  → FlowEventPublishService 发 node_status=select
  → Publisher Event Store append
  → flow_task.status = waiting_for_selection
  → WebSocket 推给前端
  → 前端显示候选
  → 用户选择
  → postContinueWorkflowRun()
  → Publisher continue_run() CAS waiting_for_selection → running
  → Redis Stream continue command
  → Consumer apply_user_selection_for_continue()
  → SELECT → SUCCESS
  → FlowResumeTask 继续后继节点
```

验收时只看前端 UI 会误判。必须确认：

- Publisher 公开状态变过 `waiting_for_selection`。
- Consumer node state 有 `selected_outputs`。
- SELECT 节点被恢复为 SUCCESS。
- 后继节点不是前端硬触发，而是 resume 算出来的 ready node。

工作流 HITL 和 Agent HITL 不是一张表。搬工作流选择时，要走 `continue_run()` 和 `apply_user_selection_for_continue()`，不要套 Agent 卡片状态。

## 10. 事件回程先落事实，再推连接

```text
FlowEventPublishService.publish()
  → flow_event_outbox
  → RabbitMQ v2 reply queue
  → Publisher workflow_v2_mq_callback()
  → WorkflowEventStore.append_event()
  → ACK Rabbit
  → WebSocket event loop replay
```

典型事件：`start_flow`、`node_status`、`start_running_llm_models`、`llm_model_ready`、`llm_model_status`、`finish_running_llm_models`、`finish_flow`、`flow_killed`、`workflow_error`。

Pub/Sub 只负责叫醒在线 socket。断线重连读的是 Stream，不是 Pub/Sub。

## 11. 四把 ID 不要互换

| ID | 位置 | 用途 |
| --- | --- | --- |
| `command_id` | 前端 journal / Publisher `workflow_command` | 同一道 start / continue / cancel |
| `wire_command_id` | Publisher 派发给 Consumer | Consumer inbox 副作用身份 |
| `event_id` | Consumer outbox / Publisher Event Store | 同一条事件去重 |
| `event_cursor` | Publisher Redis Stream | replay 位置 |
| `connection_id` | WebSocket URL | 当前物理连接世代 |

常见错法：用 `event_id` 当 cursor、重连时换 cursor、超时重试时换 `command_id`、用 WebSocket 是否在线判断 run 是否还在跑。

## 12. 文件编写顺序

先有命令事实，再有执行事实，再有事件事实：

1. `workflow-command-journal.ts`
2. `api/modules/flow.ts`
3. `schemas/workflow_runs_v2.py` / `services/workflow_runs_v2.py`
4. `controller/v2/flow_runs.py`
5. Publisher `tasks/flow.py`
6. Consumer inbox、run state、node state
7. `flow_resume.py`
8. model invocation planner / service
9. `node_aggregation_service.py` / `flow_completion_service.py`
10. outbox、RabbitMQ、Event Store
11. 前端 WebSocket 和 runner

不要先写一个“能连上的 WebSocket”，再回头补状态机。

## 13. 和 NovelComic 对照

NovelComic 搬这组时，不要做成“一个 `/run` 接口 + 一个 socket”。最小可交付也要覆盖命令身份、同事务命令事实、Redis Stream、Consumer inbox、durable DAG、模型计划、HITL、事件回程和前端恢复。

只做到 202，用户会看到“点了没反应”。只做到 WebSocket，刷新会丢事件。只做到 select UI，continue 后后继不会真正跑。

## 14. 面试 1 分钟口述

OpenCreator 把工作流执行拆成命令通道和事件通道。前端点击 Run 先走 command journal，拿到稳定 `command_id`，再 `POST /api/v2/flow/runs`。Publisher 验 JWT、校验图是 DAG、按 `command_id` 做幂等，同事务写 `flow_task` 和 `workflow_command`，返回 `202`，再 dispatch 到 Redis Stream `run_flow`。Consumer claim 命令后初始化 durable run 和 node state，`FlowResumeTask` 按前后继算 ready 节点。输入节点本地完成，模型节点先持久化 `execution_plans` 再提交 AI。callback 回来后聚合：没齐就 waiting，全失败就 failed，多候选且有后继就 select，否则 success。select 时 Consumer run 仍是 running，公开状态变成 `waiting_for_selection`。用户选择后发 continue，Publisher CAS 后再 dispatch，Consumer 覆盖 `selected_outputs`，把 SELECT 切 SUCCESS，再 resume 后继。事件一律先入 Event Store 再推 WebSocket。Stop 必须发 cancel 命令，关 socket 不会停图。

## 15. 面试官追问怎么答

如果问为什么 Publisher 不跑 DAG：

因为入口要快速交差、做幂等和公开状态。节点何时 ready 依赖 durable 前后继、子图范围和用户选择，这些事实在 Consumer。

如果问 `202` 能不能让前端标完成：

不能。`202` 只说明命令收下了。节点完成要看事件通道里的 `node_status` 和 `finish_flow`。

如果问 ready 为什么不是“所有前驱都在”：

因为本次可能只跑子图。非 active 前驱的产物要靠 `user_selection` 注入，否则单节点重跑和 HITL 后续都会算错。

如果问 callback 为什么不等于节点完成：

一个节点可能对应多条 invocation。还要等齐、判断失败、判断是否该让用户选。这是聚合，不是单次回调。

如果问工作流 HITL 和 Agent HITL 能不能共用：

不能。工作流是 node select + `continue_run()`；Agent 是 `pending_hitl` + 下一条用户输入替换 tool result。

如果问 cancel 是不是断开连接：

不是。断开只影响收事件。真正停止要等 cancel command 被 Consumer claim 并执行 kill tail。

## 16. NovelComic 当前实现自查

只看本章，NovelComic 当前已经具备 start 主骨架：

- 前端 command journal 和 create / continue / cancel API 已经存在。
- Publisher `create_run()` 能写命令事实并 dispatch `run_flow`。
- Consumer 能 claim start、初始化 run / nodes，并用 `FlowResumeTask` 推进基础输入节点。
- 模型节点能先写 expected result，再提交 AI task。
- 事件能经 outbox / RabbitMQ 进入 Event Store。

仍需按本章继续补齐：

- Consumer 目前只实现 start，continue / cancel 会直接拒绝。
- Publisher continue / cancel 主要改本地 run 状态和写事件，没有完整 CAS + dispatch + Consumer 执行。
- 没有独立的 `NodeAggregationService`，也没有完整 `select` 判定。
- `selected_outputs` 覆盖写回和 resume 后继还没有按 OpenCreator 做完。
- 模型 callback 后如何收成 success / failed / select，还需要继续接。

本章验收口径：

如果只验收“点击 Run 后 start 命令能被 Consumer 认领，基础节点能推进”，当前主骨架已经具备。  
如果按 OpenCreator 完整 DAG / HITL 验收，必须看到 `Run → running → 模型结果 → success / select → continue → 后继继续 → finish_flow`，以及真正的 cancel 和刷新恢复。
