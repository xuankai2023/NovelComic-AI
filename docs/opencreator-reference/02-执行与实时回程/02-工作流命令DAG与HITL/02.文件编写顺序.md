# 工作流命令、DAG 与 HITL：文件按什么顺序写

对照 [00-工作流命令DAG与HITL技术点.md](./00-工作流命令DAG与HITL技术点.md) 和 [01-工作流命令DAG与HITL.md](./01-工作流命令DAG与HITL.md)。01 讲运行时谁调谁，这篇讲照 OpenCreator **先写哪份文件**。顺序按依赖，不按用户看到的按钮顺序。

本文只写“工作流命令、DAG 与 HITL”。上一组“从登录到画布亮灯”已经把打开画布、项目读取、历史结果和基础亮灯讲过；这里继续往下接：命令幂等、Publisher 入站、Consumer 跑图、选择续跑、事件回程、WebSocket replay。

先背这份链路。Publisher 文件写仓库根相对路径；前端文件从 `src/` 写起；Consumer 和 AI 文件带仓库前缀。

```text
src/lib/workflow-command-journal.ts
  → src/api/modules/flow.ts
  → schemas/workflow_runs_v2.py
  → services/workflow_runs_v2.py
  → controller/v2/flow_runs.py
  → services/flow.py
  → tasks/flow.py
  → opencreator-consumer/services/workflow/flow_command_inbox_service.py
  → opencreator-consumer/services/workflow/flow_run_state_service.py
  → opencreator-consumer/services/workflow/flow_node_state_service.py
  → opencreator-consumer/tasks/flow.py
  → opencreator-consumer/tasks/flow_resume.py
  → opencreator-consumer/services/invocation/model_invocation_planner.py
  → opencreator-consumer/services/invocation/model_invocation_service.py
  → opencreator-consumer/services/workflow/node_aggregation_service.py
  → opencreator-consumer/services/workflow/flow_completion_service.py
  → opencreator-consumer/services/workflow/flow_event_publish_service.py
  → opencreator-publisher/database/mq.py
  → services/workflow_event_store.py
  → src/lib/workflow-resumable-websocket.ts
  → src/components/headBar/hooks/useWebSocketFlow.ts
  → src/components/headBar/hooks/useWorkflowRunner.ts
  → src/components/canvas/workflow-runtime-provider.tsx
```

这条顺序有一个原则：先有命令事实，再有执行事实，再有事件事实。不要先写一个“能连上的 WebSocket”，再回头补状态机。

## 写之前先有的东西

缺这些不要开始本组：

1. 登录态和 `__opencreator_jwt` 已经能进业务请求。
2. `/canvas/{flowId}` 已经能读出自己的 nodes / edges。
3. 画布 store 里有当前 nodes / edges 和项目 id。
4. Mongo、Redis Stream、RabbitMQ、Redis Event Store 在本地可用。
5. opencreator-ai 的任务提交和 callback 通路已经有入口。

做完：打开一张自己的画布，能看到节点和边；但点击 Run 还没要求能跑。

## 1. 先写前端命令身份

第一步只解决“这是不是同一次用户操作”。没有这一步，后面所有幂等都是假的。

OpenCreator 对照：

[workflow-command-journal.ts](../../../../../opencreate/opencreator-frontend/src/lib/workflow-command-journal.ts)

要写的行为：

```text
getOrCreateWorkflowCommand(operationKey, request, prefix)
  → pending 里已有同一 operationKey
       → 返回原 commandId 和原 payload
  → 没有
       → 生成 wf_ / continue_ / cancel_ 前缀 id
       → 写入 sessionStorage

completeWorkflowCommand()
  → HTTP 202 或后续事件确认后清理

abandonWorkflowCommand()
  → 确定性 4xx 后清理
```

不要把超时和断网当失败清理。超时后重试必须复用同一把 `command_id`。

做完：同一 `operationKey` 连续两次拿到同一个 id；换 payload 但旧命令未结束时，仍返回第一次 payload。

## 4. 写 Publisher 命令服务

OpenCreator 对照：

[services/workflow_runs_v2.py](../../../../../opencreate/opencreator-publisher/services/workflow_runs_v2.py)

先写 start，再写 continue / cancel。

### 4.1 start

顺序固定：

```text
command_id = req.command_id or req.client_request_id
  → _resolve_command_replay()
  → _validated_graph()
  → 生成 flow_task_id / flow_run_id / trace_id
  → 同事务 insert flow_task + workflow_command
  → dispatch_command()
```

要守住两条：

- 相同 `command_id` + 相同 payload：返回原 run，`idempotent_replay=true`。
- 相同 `command_id` + 不同 payload：`409`。

### 4.2 continue

顺序固定：

```text
flow_task.status 必须是 waiting_for_selection
  → insert workflow_command
  → CAS waiting_for_selection → running
  → dispatch_command()
```

这里不能直接改 Consumer node。Publisher 只负责公开状态和命令事实。

### 4.3 cancel

顺序固定：

```text
insert workflow_command
  → flow_task.status = cancel_requested
  → dispatch_command()
```

做完：不接 Redis Stream 也能验证 replay、409、DAG 拒环和状态 CAS。

## 7. 写 Consumer inbox 和 start 初始化

OpenCreator 对照：

- [flow_command_inbox_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_command_inbox_service.py)

## 8. 写 DAG resume

OpenCreator 对照：

[flow_resume.py](../../../../../opencreate/opencreator-consumer/tasks/flow_resume.py)

先写主循环：

```text
handle_resume()
  → run lock
  → get flow_run_state
  → status 不是 running 就跳过
  → ready_nodes()
  → 处理一批 ready node
  → finish_if_all_terminal()
```

`ready_nodes()` 的判定在：

[flow_node_state_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/flow_node_state_service.py)

- 当前节点未终态。

- active 前驱都已成功。
- 非 active 前驱靠 `selected_outputs` 提供产物，不阻塞。

做完：不接模型时，输入节点和简单 DAG 能从 idle 推到 success。

## 10. 写 callback 聚合

OpenCreator 对照：

[node_aggregation_service.py](../../../../../opencreate/opencreator-consumer/services/workflow/node_aggregation_service.py)

聚合规则：

```text
缺 result 或仍 in flight
  → waiting

没有成功 result
  → failed

多候选 + 有后继 + 不是 end_node
  → select

否则

```

success / failed / select 都要发 `node_status` 事件。failed 还要 stop descendants。success 后要继续 resume，select 则停在等待用户选择。

做完：模型 callback 后，节点不会永远卡 running；多候选节点能进入 select。

- [database/mq.py](../../../../../opencreate/opencreator-publisher/database/mq.py)


## 完整验收顺序

按这个顺序验，不要跳：

1. 同一 `command_id` + 同一 payload，第二次返回原 `flow_task_id`。
2. 同一 `command_id` + 不同 payload，返回 409。
3. 带环图返回 422。
4. 合法图返回 `202`、`flow_task_id`、`flow_run_id`、`trace_id`。
5. Redis Stream `run_flow` 有 v2 command。
6. Consumer inbox 同一 command 只 claim 一次。
7. start 后有 `flow_run_state` 和完整 `flow_node_state`。
8. ready 节点能按 DAG 顺序推进。
9. 模型节点写入 `execution_plans / expected_result_ids`。
10. callback 后节点能 success / failed。
11. 多候选有后继的节点进入 `select`。
12. Publisher 公开状态变成 `waiting_for_selection`。
13. continue 后 `selected_outputs` 覆盖，SELECT 节点变 SUCCESS。
14. 后继节点由 resume 继续跑。
15. cancel 后发布 `flow_killed`。
16. Consumer 事件先落 outbox，再进 RabbitMQ。
17. Publisher 先 append Event Store，再 ACK RabbitMQ。
18. WebSocket auth 后 attach，能 replay cursor 后事件。
19. 刷新后能查 active run 并继续接事件。
20. 关闭 WebSocket 不会停止 run；只有 cancel 会停止。

这组做完的标准是：Run、select、continue、cancel、刷新恢复都走同一套命令和事件事实。只返回 202、只连上 WebSocket、或只在前端本地把节点改色，都不算完成。
