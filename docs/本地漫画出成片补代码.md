# 本地漫画出成片：待补代码

这份文档只列还没接到真实进程上的代码。领域契约、状态机、worker 和内存账本已经在 `novelcomic-agent` 里。按下面的顺序补，先让阶段 B 在本机从漫画走到 MP4，再补 L1/L2、ZIP 和其余出图供应商。

不要新开第二个服务，也不要重写 repository 里的业务规则。PostgreSQL、COS、RabbitMQ 都实现现有协议，替换 `MemoryLedger`、`MemoryObjectStore` 和内存队列。

## 0. 先守住的边界

- 产品入口仍是现有 FastAPI：`novelcomic-agent/src/novelcomic_agent/main.py`。comic 路由和 worker 挂在这个进程的 lifespan 里。
- 权威事实仍按 `comic/ARCHITECTURE_B.md`：production、draft、artifact、成本、outbox、lease 在 PostgreSQL；大文件在对象存储；任务投递走 RabbitMQ。Remotion 的 HTTP 200 不是草稿提交，只有 `DraftRepository.commit_command_cas` 成功才算新 revision。
- 阶段 B 的路径是 L0：分格、OCR、TTS、Compose、本机渲染、成片。拆层、眼嘴、审片、ZIP 不挡 `DELIVERED`。
- `MemoryLedger` 和 `MemoryObjectStore` 留给测试。线上进程改用 PostgreSQL 和 COS，repository 继续调用同一套 session 方法。
- ZIP 不放进 Next route。`export-package` 继续只回 manifest。ZIP 由已有的 `PackageWorker` + `PackageBuilder` 在阶段 E 写入对象存储。
- 金额继续用整数 fen。对象库只存稳定 key，不存签名 URL。外部图片 URL 必须是 HTTPS，并走现有 allowlist。

## 4. PostgreSQL

### 4.1 迁移 runner

新增 `comic/persistence/migrate.py`。启动时按文件名顺序执行：

```text
comic/drafts/migrations/0001_initial.sql
comic/drafts/migrations/0002_stage_b.sql
comic/drafts/migrations/0003_stage_e_ledger.sql
```

用表 `schema_migrations(version text primary key, applied_at timestamptz)` 记录已执行版本。每个文件一个事务。重复启动不得重放已记录版本。

`0001` 和 `0002` 不要改语义。它们还没有 delivery、tombstone、alert。新增 `0003_stage_e_ledger.sql`，表字段对齐 `persistence/rows.py` 里的 `DeliveryRow`、`TombstoneRow`、`AlertRow`：

- `deliveries`：主键 `delivery_id`；唯一键 `(production_id, package_input_hash)`。
- `object_tombstones`：主键 `tombstone_id`；唯一键 `(tenant_id, object_key)`。
- `alerts`：主键 `dedup_key`。

`claim_outbox` 和 `claim_job` 必须 `SELECT … FOR UPDATE SKIP LOCKED`，租约字段与 `MemorySession.claim_outbox` / `claim_job` 一致：过期租约可以再次领取，未过期租约不能被别人拿走。`save_production` 带 `expected_version`，更新 0 行就是并发冲突。唯一约束冲突映射成现有的 `UniqueViolation`。

### 4.2 PostgresLedger

新增 `comic/persistence/postgres.py`。一个 `transaction()` 对应一个 asyncpg 事务，异常时回滚。session 方法读写 `rows.py` 的 dataclass，jsonb 在边界上做一次转换。

不要把 SQL 写进 `ProductionRepository` 或其他 repository。那些类已经通过 session 表达受理、CAS 和 outbox。

### 4.3 完成标准

- 空库启动后三份迁移都在 `schema_migrations` 里，再启动一次不会重复执行。
- 两个并发事务抢同一条 outbox 或同一条 job，只有一个拿到租约。
- 状态更新和 outbox 插入在同一个事务里；事务回滚后两边都不留。
- Compose 命令重放不增加 revision。这条继续由现有 `ComposeCommandApplier` 保证，PostgreSQL 只提供 CAS 存储。

## 5. 腾讯云 COS

新增 `comic/storage/cos_store.py` 的 `CosObjectStore`，实现 `ObjectStore`。

环境变量与 Remotion 对齐，加到 `Settings`：

```text
COS_SECRET_ID
COS_SECRET_KEY
COS_REGION
COS_BUCKET
COS_CDN_DOMAIN
```

`stable_url(key)` 返回 `https://{COS_CDN_DOMAIN}/{key}`，这是写入数据库的地址。`signed_url` 单独签发，调用方不得持久化。

`put_verified` 保持现有顺序：

1. 写入 `_tmp/{sha256}/{uuid}`。
2. HEAD 或下载校验 sha256。
3. 拷贝到正式 key。正式 key 已存在且摘要不同则失败，相同则直接返回摘要。
4. 删除临时对象。未通过校验的对象不得登记为成功。

key 继续走 `storage/key_layout.py`。`_reject_unsafe_key` 的规则保持不变。

依赖使用腾讯云 Python COS SDK。上传、下载、删除都走异步封装，不要在事件循环里直接堵死同步 SDK；可以用线程池包住官方同步调用。

### 完成标准

- 同一 key 重复上传相同字节成功；不同字节失败。
- 校验失败后正式 key 不存在。
- `signed_url` 过期参数非法时拒绝，且数据库记录里没有签名 URL。

## 6. RabbitMQ outbox 消费

新增两个模块，都在 comic 进程内启动，不新开应用入口：

- `comic/queue/outbox_publisher.py`
- `comic/queue/worker_consumer.py`

发布端循环：

1. `LedgerOutboxRepository.claim`。
2. 把 `OutboxEvent` 发到持久队列 `comic.workers`。消息体是 payload，并带上 `eventId`、`type`。
3. broker confirm 之后 `mark_published`。
4. 发布失败则 `release`，按现有 attempt 后退 `available_at`。

消费端按 `payload.worker` 调用已经构造好的 worker：

| worker | 调用 |
| --- | --- |
| `analyze` | `AnalyzeWorker.run(production_id)` |
| `voice` | `VoiceWorker.run(production_id)` |
| `render` | `RenderWorker.run(production_id)` |
| `preview` | 阶段 E 才绑定 `PreviewWorker.run` |
| `package` | 阶段 E 才绑定 `PackageWorker.run` |
| `none` | 确认消息，不调用 worker |

阶段 B 进程只绑定 `analyze`、`voice`、`render`。收到 `preview` 或 `package` 时确认并记一条错误，不要在 B 进程里 import 阶段 E。

消费要幂等。worker 自己会读当前状态，重复消息不得重复付费。处理中的异常按现有 `ComicServiceError.retryable` 决定重新入队还是把错误写回 production。取消后的生产不得再发起付费调用，这条已在 worker 和预算里，消费端不要绕过。

RabbitMQ 使用 `DependencyManager` 已有连接。队列持久、消息持久。本地默认 URL 已是 `amqp://novelcomic:novelcomic@127.0.0.1:5672/`。

### 完成标准

- 受理事务提交后，分析 worker 会被调用；进程在提交后、发布前杀掉，重启后仍会投递。
- 同一条消息投递两次，TTS 和渲染不会第二次扣费。
- `worker=none` 不会把任务打回 `CREATED`。

## 7. 真实供应商

适配器放在 `comic/providers/`。不要改 `PanelAnalyzer`、`VoiceSynthesizer`、`L1LayerService`、`L2SpriteService` 的预算和状态逻辑。

### 7.1 PanelDetector 与像素裁切

新增 `comic/providers/opencv_panel.py`，类名 `OpenCvPanelDetector`，实现 `PanelDetector.detect`。

几何步骤按实施方案第 5.2 节，只在这个类里做一遍：

1. 灰度化和自适应阈值。
2. 检测长直线、留白沟槽和封闭轮廓。
3. 丢掉过小框，合并被气泡切碎的相邻区域。
4. 返回页面宽高、每个框的 `x/y/width/height/confidence`，以及不含供应商随机 ID 的 `raw`。

阅读顺序仍交给 `panel_analyzer.order_panels`。检测结果里的 `provider_id` 可以留空，分析器会丢掉它。

质量门禁失败时不要在检测器里发明分格。`PanelAnalyzer` 已会退回整页 L0。

新增 `comic/analyzer/pixel_cropper.py`，用 Pillow 或 OpenCV 按归一化或像素边界裁出 PNG。`build_stage_b` 把它传给 `PanelAnalyzer(cropper=...)`，替换 `BoundsTaggedCropper`。裁切结果交给现有 `CropPublisher` 上传。

OCR 新增 `comic/providers/ocr.py` 的协议 `OcrEngine`：输入页图字节，输出气泡文本、置信度、polygon。`OpenCvPanelDetector` 在每个 panel 内调用它，填 `DetectedBubble`。说话人和旁白语义不要改 OCR 原文。供应商没选定之前，类通过 `Settings` 读取 endpoint 和 key；没有配置时 `detect` 仍返回分格，气泡为空，让无对白路径能出片。低置信度继续交给 `panel_quality_gate`，不要在检测器里改字。

依赖：`opencv-python-headless`、`pillow`。算法版本写入 `provider_config_version`，默认仍由 wiring 的 `panel-v1` 传入；改算法时改这个版本，避免复用旧 artifact。

### 7.2 SpeechProvider

新增 `comic/providers/speech.py` 的 `HttpSpeechProvider`，实现 `SpeechProvider`。

- `synthesize` 使用调用方传入的 `request_id` 作为供应商幂等键，返回 `SpeechSynthesis`：音频字节、`duration_ms`、`provider_request_id`、`cost_fen`、可选 viseme、`content_type`。
- `reconcile` 用同一个 `request_id` 查询已受理任务。还在处理时返回 `None`。超时抛现有的 `audio.voice_synthesizer.ProviderTimeout`，不要在适配器里重新扣费。
- 没有 viseme 时返回空元组。口型三态由现有时间线逻辑处理。
- 声音 ID、endpoint、key、单价 fen 放进 `Settings`。未配置 key 时启动阶段 B 应失败，并写明缺哪个变量，避免受理后在 worker 里才发现不能出声。

单行失败继续由 `VoiceSynthesizer` 写成 `missingReason`。适配器不要把整页标成失败。

### 7.3 LayerProvider 与 SpriteProvider

这两项在 L0 成片之后再做。阶段 B 的 `RenderWorker._prepare` 不会调用它们。

新增：

- `comic/providers/gpt_image_layer.py` 的 `GptImageLayerProvider(LayerProvider)`
- `comic/providers/gpt_image_sprite.py` 的 `GptImageSpriteProvider(SpriteProvider)`

两者内部调用现有 `GptImage2Client.edit`。`request_id` 仍然是幂等键。`reconcile` 在这个同步客户端上没有独立查询接口时，只能返回已经保存在 artifact 上的结果；不要为了 reconcile 再付费生成一次。

`LayerProvider.separate` 要把返回的 PNG 填成 `ProviderLayer`，语义使用 `l1_layer_service` 已有目录：`background`、`body`、`foreground` 等。画布尺寸用调用方传入的 `canvas_width/canvas_height`。`recomposition_score`、`alpha_hole_ratio`、`edge_artifact_score` 由适配器按门禁需要的范围给出；算不出来就 `requires_fallback=True`，让 `L1LayerService` 降回 L0。

`SpriteProvider.generate` 只生成调用方传入的 `required_states`。缺的状态放进 `SpriteGeneration.missing`，不要补一张假图。状态名保持 `eye:open`、`eye:closed`、`mouth:closed`、`mouth:open`、`mouth:half`。

阶段 C/D 要真正跑起来，还得改消费派发。现在 `PREPARING_ASSETS` 固定派给 `render`。接 L1 时，让阶段 C 进程在这一状态调用 `AssetWorker`，完成后再进入现有 Compose；不要让 `RenderWorker` 和 `AssetWorker` 各写一遍 L0。

### 7.4 完成标准

- 一张有格线的测试图得到有序 `PanelSpec`，crop 是真实 PNG，对象存储里能打开。
- 分格失败的页仍能以整页 URL 继续，production 不进入 `PERMANENT_FAILED`。
- 同一 `stableLineKey` 第二次合成命中 artifact，供应商请求数为 0。
- 一行 TTS 失败时，其余行仍有音频，失败行有 `missingReason`。
- L1 失败时 shot 仍是 L0，且不会第二次调用 `GptImage2Client`。

### 8.2 `blurred-background-contain`

`ImageItem` 增加可选字段，缺省保持现在的单层居中 contain，避免旧工程变样：

```text
fit: 'contain' | 'cover'
blurRadiusPx?: number
dimOpacity?: number
role?: 'panel-foreground' | 'panel-background'
```

`append-image-sequence.ts` 在 `panelFitPolicy === 'blurred-background-contain'` 时，为每个 shot 写两层，共用同一个 asset：

```text
track:{shotId}:panel-background   cover，blurRadiusPx=28，dimOpacity=0.45
track:{shotId}:panel-foreground   contain，完整保留画面
```

稳定 ID：

```text
asset:{shotId}:panel
item:{shotId}:panel-background
item:{shotId}:panel-foreground
track:{shotId}:panel-background
track:{shotId}:panel-foreground
```

背景轨在前景轨下面。模糊和压暗做在 `src/editor/items/image/image-layer.tsx` 的样式上，数值来自 item 字段。不要只改编辑器 CSS。

`app/api/compose/image/sequence/route.ts` 增加必填策略时，阶段 B 只接受 `blurred-background-contain`。请求里带上这个字段，并把它放进命令输入，让 Agent 的 command `inputHash` 能覆盖算法版本。常量与 `comic/assets/l0_panel.py` 保持一致：半径 28、压暗 0.45、版本 `contain-blur-v1`。

`l0_sequence_payload` 要带上 `panelFitPolicy`。`RenderWorker._prepare` 和 `_compose` 里的 `panelFitApplied: False` 改为真实结果：两层都写进已提交工程才是 true。

横图在 1080×1920 上应看到完整 panel，空白区是同一张图的放大、模糊、压暗，不是纯黑边。

### 8.3 本机 renderMedia

新增 `src/editor/rendering/render-media-local.ts`，用 `@remotion/renderer` 的 `bundle`、`selectComposition`、`renderMedia`。bundle 缓存在进程内。输出写到本地临时文件，再上传到 Remotion 已有的 COS，`outputFile` 用 CDN HTTPS 地址。

`app/api/render/route.ts` 和 `render-batches/route.ts` 按环境变量分流：

```text
REMOTION_RENDER_BACKEND=local | lambda
```

本地出片用 `local`。`lambda` 保持现在的 `renderMediaOnLambda`。

本机渲染通常超过 Agent 的 HTTP 超时，所以提交接口不要等到渲染结束才返回。行为要和现在的 Lambda 提交一致：

1. 生成 `renderId`，`bucketName` 固定为 `local`。
2. 立即返回 `{ type: 'success', bucketName, renderId }`。
3. 后台跑 `renderMedia`。进度写入本进程或 Redis，键是 `renderId`。
4. `app/api/progress/route.ts` 见到 `bucketName=local` 时读这份进度，不调用 `getRenderProgress`。
5. 完成后响应仍是 Agent 已解析的形状：`type: 'done'`，`outputFile` 为 HTTPS。失败时 `type: 'error'`。

`frameRange` 继续传给 `renderMedia`。没有 `frameRange` 的整片导出保持整段渲染。

本地默认可以不配 AWS。`requireServerEnv()` 不要在 `local` 模式下强迫 Lambda 区域和函数名。COS 变量仍然要有，因为成片要放进对象存储。

### 8.4 export-package 与 ZIP

`app/api/compose/project/export-package/route.ts` 继续只返回 `{ manifest }`。不要在这个 route 里下载文件或写 ZIP。

ZIP 已经在 Agent：

- `comic/delivery/package_builder.py` 按 `source/`、`panels/`、`layers/`、`audio/`、`subtitles/`、`preview/`、`videos/`、`project/`、`diagnostics/` 以及根上的 `manifest.json`、`play-order.json` 打包。
- `PackageWorker` 在状态 `PACKAGING` 时调用它并上传。

阶段 E 进程启动并接上 COS 之后，这条才算接通。阶段 B 的 `DELIVERED` 不要求 ZIP。

### 8.5 完成标准

- 总时长不足 5 秒的工程调用 `project/pad` 后，末尾 shot 被拉长，revision 只加一。
- 横构图 panel 的前景层是 contain，背景层是 cover，模糊半径 28，压暗 0.45。
- `REMOTION_RENDER_BACKEND=local` 时，`render-batches` 立刻返回 `renderId`，进度接口最终给出可下载的 MP4 URL。
- `lambda` 模式的请求体和响应保持不变。

## 9. GPT Image 2 注册表

文件：`novelcomic-ai/packages/core/src/models/gpt-image-2.ts`。

现在两个模型的 `robin_calls` 都只有 `createCall`，而 `createCall` 只构造百度客户端。OpenCreator 的顺序是：

```text
opencreator/text-to-image/gpt-image-2
  百度 → 腾讯 → OpenAI → Fal → Kie

opencreator/image-to-image/gpt-image-2-edit
  百度 → 腾讯 → OpenAI → Fal → Kie
```

对照源码：

- `opencreate/opencreator-ai/packages/core/src/models/gpt-image-2.ts`
- `opencreate/opencreator-ai/packages/core/src/api/tencent/gpt-image-2.ts`
- `opencreate/opencreator-ai/packages/core/src/api/openai/gpt-image-2.ts`
- `opencreate/opencreator-ai/packages/core/src/api/fal/gpt-image.ts` 里的 `callFalGptImage2TextToImage` 和 `callFalGptImage2ImageToImage`
- `opencreate/opencreator-ai/packages/core/src/api/kie/gpt-image-2.ts`

移植到 `novelcomic-ai` 时，沿用这里已有的 `CoreProviderCall` 形状：`provider`、`model_id`、`options_schema`、`result_mode`、`submit`、`normalizeResult`。不要把 OpenCreator 的 `CoreRunContext` 原样搬过来。百度客户端 `packages/core/src/provider/baidu_gpt_image_client.ts` 是模板：同步拿到图片就返回 `status: 'succeeded'` 和 `outputs.images`。

建议落点：

```text
novelcomic-ai/packages/core/src/provider/tencent_gpt_image_client.ts
novelcomic-ai/packages/core/src/provider/openai_gpt_image_client.ts
novelcomic-ai/packages/core/src/provider/fal_gpt_image_client.ts
novelcomic-ai/packages/core/src/provider/kie_gpt_image_client.ts
```

供应商模型和路径与 OpenCreator 对齐：

| 供应商 | 文生图 | 图生图 |
| --- | --- | --- |
| 百度 | 已有 `gpt-image-2` | 已有 edits |
| 腾讯 | `custom-textmodel-gt`，`/v1/aiart/gttext` | `custom-imagemodel-gt`，`/v1/aiart/gtimage` |
| OpenAI | `gpt-image-2` | `gpt-image-2` edit |
| Fal | `openai/gpt-image-2` | `openai/gpt-image-2/edit` |
| Kie | Market GPT Image 2 文生图 | Market GPT Image 2 图生图 |

某个供应商的 key 未配置时，跳过该 call，而不是让整条 robin 在构造客户端时抛错。百度失败后应能落到腾讯。这与 Python `GptImage2Client` 已有行为一致。Python 客户端这次不用扩到 OpenAI、Fal、Kie，除非注册表移植时发现请求体不一致，再只改不一致的那一段。

`novelcomic-ai` 现有测试按百度客户端补腾讯及后面的失败切换：第一个 call 抛错时，runner 使用下一个 call。不要改模型 id：`opencreator/text-to-image/gpt-image-2` 和 `opencreator/image-to-image/gpt-image-2-edit`。
